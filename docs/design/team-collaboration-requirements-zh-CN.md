# 团队协作 — 需求分析

- **功能 ID：** team-collaboration
- **版本：** 1.0
- **状态：** 已提案（待架构评审）
- **作者：** ui-ux-agent
- **日期：** 2026-10-12

## 1. 竞品调研总结

| 平台 | 团队 / 分享方式 | 关键启示 |
|---|---|---|
| **AIPRM** | 专业版中的团队/角色分离（所有者/管理员/成员）；带使用遥测的共享提示词库 | 所有者/管理员/成员的角色分离是专业工具的预期模型；共享库是核心载体 |
| **Notion** | 工作区 → 页面；细粒度分享（查看/评论/编辑）；邮件邀请 | "与我共享"是一等入口；邮件邀请是默认心智模型 |
| **Google Drive** | 文件夹/文件上的所有者 + 编辑者 + 查看者；"与我共享"列表 | 按对象授权强大但笨重；团队实际使用的是文件夹级共享 |
| **GitHub（组织/仓库）** | 组织 → 仓库 → 协作者权限级别；转移所有权 | 所有权转移是每个团队工具最终都需要的安全出口 |
| **PromptBase / FlowGPT / Snack Prompt** | 无团队功能（仅个人账户） | 提示词平台目前全是个人产品 —— 差异化机会 |
| **Slack（频道）** | 带过期的邀请链接；无需既有账户关系即可加入 | 对小团队而言邀请链接优于邮件邀请（不依赖邮件基础设施） |

**综合分析：** 胜出的 v1 模式是**共享工作区**：团队是一个命名的分组，拥有共享的模板空间。任何用户都可以创建团队并成为所有者，然后通过**用户 ID**（产品的公开标识符，与 `users.id` 格式一致）邀请成员 —— 刻意不做邮件邀请，以避免邮件基础设施依赖。模板可以归团队所有（团队所有）而非用户所有；具有相应角色的团队成员可以编辑它们。角色恰好三种：**所有者**（一人，可转移；拥有全部权限 + 删除团队 + 管理成员）、**管理员**（管理成员，编辑所有团队模板）、**成员**（在团队空间创建/编辑自己的模板，查看所有团队模板）。团队模板默认对团队私有，可由管理员/所有者公开发布（发布保留团队所有权，署名显示团队）。个人模板不受影响；用户的既有内容保持个人属性，除非显式转移。这是让"我们团队的提示词库"落地的最轻模型。

## 2. 问题陈述

1. **团队靠导出文件分享提示词。** 目前一群人共享模板的唯一方式是导入/导出或将所有内容公开 —— 没有共享空间、没有访问控制、没有单一事实来源。
2. **团队内容没有归属。** 离职员工编写的模板归其个人账户所有；账户注销后团队就失去了访问权。
3. **没有角色。** 产品有 user/admin 平台角色，但没有组级权限；分享一个模板意味着分享整个账户或什么都不分享。
4. **竞品全是个人产品。** 每个提示词平台都只有个人功能；团队（代理商、开发团队、客服团队）是被忽视的细分市场，且具有最强的留存画像。

## 3. 目标用户

- **团队创建者（主要）：** 希望为群体（开发团队、代理商、客服团队）建立共享提示词库的用户。
- **团队所有者/管理员：** 管理成员资格和团队的公开形象。
- **团队成员：** 向共享空间贡献模板并复用同事的成果。
- **平台管理员：** 在管理控制台查看团队（成员数、模板数）以应对滥用；v1 不提供团队管理工具。

## 4. 用户故事

- **US-T1：** 作为用户，我想创建一个带名称和描述的团队，让我的群体拥有共享空间。
- **US-T2：** 作为团队所有者，我想通过用户 ID 邀请成员，让我们无需邮件基础设施即可开始协作。
- **US-T3：** 作为团队所有者，我想分配管理员和成员角色，让权限与责任匹配。
- **US-T4：** 作为团队成员，我想在团队空间内创建模板，让我的工作归属于团队而非个人账户。
- **US-T5：** 作为团队成员，我想查看并使用所有团队模板，从同事的工作中受益。
- **US-T6：** 作为团队管理员，我想编辑任何团队模板，让团队库保持准确。
- **US-T7：** 作为团队所有者， 我想将所有权转移给其他成员，让团队在我离开后依然存续。
- **US-T8：** 作为团队所有者，我想移除成员，让成员资格结束时访问权随之终止。
- **US-T9：** 作为用户，我想在一个地方看到我所属的所有团队，以便在个人空间和团队空间之间切换。
- **US-T10：** 作为平台管理员，我想在管理控制台看到团队及其规模，以便响应滥用举报。

## 5. 功能需求

### 5.1 数据模型

- **FR-1：** 新表 `teams`：`id UUID 主键`、`name VARCHAR(80) NOT NULL`、`description TEXT`（0–500 字）、`owner_id TEXT NOT NULL REFERENCES users(id)`、`created_at`、`updated_at`。索引 `(owner_id)`。
- **FR-2：** 新表 `team_members`：`team_id UUID NOT NULL REFERENCES teams(id) ON DELETE CASCADE`、`user_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE`、`role VARCHAR(10) NOT NULL CHECK (role IN ('owner','admin','member'))`、`joined_at TIMESTAMPTZ NOT NULL DEFAULT NOW()`，主键 `(team_id, user_id)`。索引 `(user_id)`。
- **FR-3：** `templates` 增加可空列 `team_id UUID REFERENCES teams(id) ON DELETE SET NULL`（通过既有 ALTER TABLE 模式迁移）。`team_id IS NULL` = 个人模板（既有行为完全不变）；`team_id` 有值 = 团队所有。团队模板保留 `owner_id` 作为*创建者*（审计用途），但访问控制由 `team_id` 决定。
- **FR-4：** 限制：一个用户最多加入 10 个团队；一个团队最多 50 名成员；一个团队最多拥有 200 个模板。服务端强制执行并返回友好错误。

### 5.2 团队管理（普通用户端）

- **FR-5：** 已认证用户在 `/teams/new` 创建团队：名称（必填）、描述。创建者成为所有者（team_members 中 role=owner 的行）。
- **FR-6：** 团队主页 `/teams/{id}` 展示：团队名称、描述、成员列表（头像、显示名、角色徽章）、团队模板网格（复用既有卡片模式），以及按角色显示的管理操作。
- **FR-7：** **邀请：** 所有者/管理员通过精确的用户 ID 添加成员（校验用户存在且未被封禁；已是成员则报错）。v1 不做邮件邀请、不做邀请链接。被邀请用户立即以成员角色出现。
- **FR-8：** **角色与权限：**
  - 所有者：全部权限；转移所有权（自己降级为管理员）；删除团队；移除任意成员；变更角色。
  - 管理员：添加/移除成员（不能移除其他管理员或所有者）；编辑/删除任意团队模板；发布/取消发布团队模板。
  - 成员：在团队空间创建模板；仅编辑/删除自己创建的模板；查看所有团队模板。
- **FR-9：** **退出：** 成员/管理员可随时自助退出团队。所有者必须先转移所有权或删除团队才能退出。
- **FR-10：** **删除：** 删除团队（仅所有者，需在确认弹窗中输入团队名称）软删除团队；其模板的 `team_id` 置为 NULL、`visibility` 置为 private，`owner_id`（创建者）保留个人所有权 —— 内容存续，访问权回归创建者。
- **FR-11：** **我的团队：** `/teams` 列出用户所属团队（卡片：名称、成员数、模板数、角色徽章），以及"创建团队"入口。顶部导航用户下拉菜单增加"我的团队"入口。

### 5.3 团队模板

- **FR-12：** "在团队中"创建模板通过团队页面的创建操作（创建弹窗预设团队上下文）或将既有个人模板转移给团队（团队所有者/管理员 + 模板所有者）完成。
- **FR-13：** 团队模板对所有成员可见（无论可见性如何）；`private` 团队模板对团队外不可见；`public` 团队模板出现在公共广场并带团队署名（"by {团队名}"）。
- **FR-14：** 编辑团队模板使用与个人模板相同的编辑器和版本机制；编辑权限检查改为基于角色（FR-8）而非 `owner_id == 当前用户`。
- **FR-15：** 团队模板上的点赞、收藏、评论、评分、复刻行为与个人模板完全一致（它们作用于模板而非所有者）；v1 中团队模板事件的通知发送给*创建者*（owner_id）。

### 5.4 API

- **FR-16：** `POST /api/v1/teams`、`GET /api/v1/teams?member=me&page=`、`GET /api/v1/teams/{id}`、`PUT /api/v1/teams/{id}`（名称/描述）、`DELETE /api/v1/teams/{id}`、`POST /api/v1/teams/{id}/members`（body：user_id）、`DELETE /api/v1/teams/{id}/members/{user_id}`、`PUT /api/v1/teams/{id}/members/{user_id}`（角色变更）、`POST /api/v1/teams/{id}/transfer`（body：user_id）、`POST /api/v1/teams/{id}/leave`、`POST /api/v1/teams/{id}/templates`（转移既有模板，body：template_id），以及通过既有端点扩展可选 `team_id` 在团队上下文中创建/更新模板。
- **FR-17：** 所有团队操作在服务端强制角色检查；除公开团队模板视图外，任何团队范围的读取都要求成员资格。

### 5.5 管理端

- **FR-18：** 管理控制台在 `/admin/teams` 下新增"团队"页面：列表（名称、所有者、成员数、模板数、创建时间）、按名称搜索、只读成员下钻。v1 不提供团队变更操作（滥用响应用既有的用户封禁：封禁团队所有者不会删除团队；团队变为无管理状态 —— 见开放问题）。
- **FR-19：** 管理 API：`GET /api/v1/admin/teams?query=&page=`、`GET /api/v1/admin/teams/{id}`（含成员）。只读。

### 5.6 通知集成

- **FR-20：** 若通知功能已上线：`team_invite`（发给被邀请用户：团队名、邀请人）、`team_role_change`（发给受影响成员）、`team_removed`（发给被移除的成员）。若通知未上线，这些事件延迟实现，不阻塞本功能。

## 6. 非功能需求

- **NFR-1（性能）：** 50 名成员、200 个模板的团队页加载 < 1 秒（模板网格分页、成员列表封顶展示）。
- **NFR-2（安全）：** 所有权限检查在服务端（FR-17）；团队范围查询按成员资格过滤；公开 API 不泄露团队数据（私有团队模板绝不出现在公开列表/搜索中）。
- **NFR-3（兼容性）：** 既有个人模板行为 100% 不变（team_id NULL 路径）；迁移是纯增量。
- **NFR-4（国际化）：** 所有文案通过 i18next 提供 EN/ZH（`teams.*` 命名空间）；角色名翻译（Owner/Admin/Member → 所有者/管理员/成员）。
- **NFR-5（无障碍）：** 角色徽章文本+颜色双编码；成员列表和操作可键盘操作；弹窗遵循既有焦点陷阱模式。
- **NFR-6（一致性）：** 团队模板复用所有既有模板界面（卡片、详情、编辑器、版本、审核）；仅所有权/权限语义不同。

## 7. 验收标准

- **AC-1：** 用户创建团队，通过用户 ID 添加成员，成员在 `/teams` 中看到该团队且角色徽章为"成员"。
- **AC-2：** 成员在团队空间创建模板；其他成员可查看并使用；该模板在私有状态下不出现在成员的个人模板或公共广场。
- **AC-3：** 管理员编辑成员创建的团队模板；非创建者的成员编辑他人模板被拒（403）。
- **AC-4：** 发布团队模板使其公开并带"by {团队名}"署名；取消发布后恢复为团队私有。
- **AC-5：** 所有者将所有权转移给管理员；原所有者变为管理员且不能再删除团队。
- **AC-6：** 成员退出团队；其创建的团队模板保留在团队中（保留创建者署名）。
- **AC-7：** 删除团队将其模板的 team_id 置空、可见性设为私有，模板留在各创建者名下。
- **AC-8：** 非成员无法访问私有团队页面或其私有模板（404/403）；私有团队模板绝不出现在公开搜索中。
- **AC-9：** 管理端 `/admin/teams` 列出团队及成员/模板数；普通用户无法访问管理团队 API（403）。
- **AC-10：** 限制生效：第 51 名成员被拒；第 11 个团队加入被拒；返回友好错误。
- **AC-11：** 所有文案 EN/ZH 翻译；无硬编码文案。
- **AC-12：** 功能中没有任何变现内容（无团队套餐、无席位定价、无付费计划）。

## 8. 范围之外

- 邮件邀请、邀请链接或凭码加入。
- 团队级合集/链（v1 仅模板；团队后续再支持其他内容类型）。
- 三种角色之外的按模板细粒度权限。
- 团队动态流、团队操作审计日志（平台审计日志不变）。
- 团队 API 密钥（密钥保持个人属性）。
- 任何形式的变现（支付、定价、购买、收益、席位费、团队套餐）—— 本产品永久排除。

## 9. 依赖与假设

- **D-1：** `users.id` 是公开、可分享的标识符（字母数字+下划线，展示在个人资料中）—— 按用户 ID 邀请依赖这一点。
- **D-2：** templates 表及所有模板界面（列表、详情、编辑器、版本、审核）是扩展而非替换；`team_id` 是增量列。
- **D-3：** 既有 ALTER TABLE IF NOT EXISTS 迁移模式（用于 users.role/status）适用于添加 templates.team_id。
- **D-4：** 管理控制台的列表页模式（搜索 + 表格 + 分页）被 `/admin/teams` 复用。
- **D-5：** 通知功能的事件机制（若已上线）承载团队事件（FR-20）。
- **D-6：** follow-creators 功能的所有者身份区块为公开团队模板增加团队变体（"by {团队名}"）。

## 10. 给架构师的开放问题

1. **团队名唯一性：** 团队名应全局唯一（如 users.id）还是仅每个所有者内唯一？建议：全局唯一、大小写不敏感 —— 署名和 URL 更简单。
2. **所有者被封禁：** 若团队所有者被封禁，团队没有活跃所有者。选项：(a) 自动晋升任职最长的管理员，(b) 保持无管理状态直到平台管理员介入，(c) 阻止封禁拥有活跃团队的所有者。建议：v1 采用 (b) + 管理控制台可见。
3. **模板转移语义：** 个人模板转移给团队时，点赞/收藏/评论/评分是否跟随模板（是 —— 它们作用于模板），创建者是否在团队署名之外保留个人署名？建议：显示"by {团队}，创建者 {用户}"。
4. **team_id ON DELETE SET NULL vs CASCADE：** FR-10 在删除团队时用 SET NULL + 可见性私有（内容存续）。请对照软删除方案（软删除的团队保留模板直到清理）确认。
5. **公开团队署名：** 公开模板载荷是否需要 `team: {id, name}` 对象（类似 follow-creators 的 owner 对象），审核界面如何展示团队所有模板（所有者列显示团队）？
6. **搜索范围：** 公共广场的搜索是否默认包含公开团队模板（建议包含）且 v1 不提供团队过滤器，还是增加"团队模板"过滤器？
