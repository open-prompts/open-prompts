# 内容举报 — 需求分析

- **功能 ID：** content-reporting
- **版本：** 1.0
- **状态：** 已提案（待架构评审）
- **作者：** ui-ux-agent
- **日期：** 2026-10-12

## 1. 竞品调研总结

| 平台 | 举报方式 | 关键启示 |
|---|---|---|
| **FlowGPT** | 提示词上的举报/标记流程；审核员审查被举报内容；封禁垃圾账号 | 举报驱动的审核比发布前审查更具扩展性 —— 我们采用的模型 |
| **Reddit** | 举报按钮 → 原因选择器（垃圾、骚扰…）→ 带举报计数的版务队列；达到阈值自动折叠 | 固定的小原因列表优于自由文本；版务队列按条目分组而非按举报分组 |
| **GitHub** | 仓库/issue 上的滥用举报 → 人工审查；举报者不会直接看到结果 | 对举报者静默是可接受的；但"已解决"状态让队列保持诚实 |
| **YouTube** | 举报者选择类别；系统在规模阈值下自动隐藏待审 | 高举报速度下的自动隐藏是有效的滥用刹车 —— 但误报风险高 |
| **PromptBase** | 员工预审每份提交（其规模下无需用户举报） | 预审对我们太重；事后举报适合开放平台 |
| **Wikipedia** | 标记 + 编辑 + 讨论页；破坏巡逻仪表盘 | 给可信用户巡逻工具能放大小型管理团队 |

**综合分析：** 管理控制台已有审核列表，但**没有入站信号**：没有任何东西告诉管理员哪些内容需要关注。v1 模式（Reddit/FlowGPT）：每个公开模板和公开评论上的**举报**操作，带**固定原因列表**（垃圾信息、冒犯/仇恨、误导、隐私侵犯、其他 + 可选备注），每用户每条目一次举报（重复举报替换），以及按条目分组的管理端**举报队列**，按未解决数量和新鲜度排序，提供一键处置（驳回或行动：取消发布模板 / 删除评论 / 封禁作者 —— 全部是既有管理操作，现在可从队列直达）。v1 不做自动下架（始终人工决策）；高速度信号只是让队列排序更靠前。举报者获得一次确认，没有持续的案件跟踪（对举报者静默，GitHub 风格）—— 该功能的职责是路由注意力，而非构建案件管理系统。

## 2. 问题陈述

1. **没有入站滥用信号。** 管理控制台可以查看和审核模板，但没有任何东西告诉管理员*该看什么*；审核完全依赖外部渠道（邮件、聊天）的被动响应。
2. **用户没有发言渠道。** 发现垃圾信息、仇恨内容或泄露隐私提示词的访客在产品内无计可施 —— 只能离开或在平台外抱怨。
3. **评论无人审核。** 评论功能上线时没有管理员删除路径，也没有用户举报路径。
4. **社区平台上线即需此功能。** 每个 UGC 平台（Reddit、FlowGPT）都把举报视为基本要求；缺失会阻碍健康的社区增长。

## 3. 目标用户

- **举报者（普通用户）：** 发现问题公开模板或评论，希望以低摩擦方式标记。
- **平台管理员：** 需要一个按优先级排序的被标记内容队列，上下文足够在一处完成决策。
- **内容作者：** 受益于误报被快速驳回（内容在人工审查期间保持在线 —— 无自动下架）。

## 4. 用户故事

- **US-R1：** 作为用户，我可以在模板详情页举报公开模板，选择原因并可选添加备注，让问题内容到达管理员。
- **US-R2：** 作为用户，我可以举报公开评论，让 abusive 讨论也被标记。
- **US-R3：** 作为用户，我看到举报已被记录的即时确认，知道操作生效了。
- **US-R4：** 作为用户，我不能刷举报系统 —— 每条目每用户一次 —— 让队列保持有意义。
- **US-R5：** 作为管理员，我看到按条目（模板/评论）分组的举报队列，按未解决数和新鲜度排序，最糟糕的内容最先浮现。
- **US-R6：** 作为管理员，我可以在不离开队列的情况下打开被举报条目的完整上下文（内容、作者、举报原因、举报者备注），快速决策。
- **US-R7：** 作为管理员，我可以通过驳回（误报）或行动（取消发布模板 / 删除评论 / 封禁作者）处置举报组，每个案件一个流程闭环。
- **US-R8：** 作为管理员，我的处置操作被记录在审计日志中，让审核保持可问责。
- **US-R9：** 作为管理员，我可以按状态（未解决/已解决）、条目类型和原因过滤队列，处理特定积压。

## 5. 功能需求

### 5.1 数据模型

- **FR-1：** 新表 `content_reports`：`id UUID 主键`、`item_type VARCHAR(10) NOT NULL CHECK (item_type IN ('template','comment'))`、`item_id UUID NOT NULL`、`reporter_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE`、`reason VARCHAR(20) NOT NULL CHECK (reason IN ('spam','offensive','misleading','privacy','other'))`、`note TEXT`（0–500 字，可选）、`status VARCHAR(10) NOT NULL DEFAULT 'open' CHECK (status IN ('open','resolved'))`、`resolution VARCHAR(10)`（解决前为 NULL：'dismissed' | 'actioned'）、`resolved_by TEXT REFERENCES users(id)`、`resolved_at TIMESTAMPTZ`、`created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()`，UNIQUE `(item_type, item_id, reporter_id)`。索引：`(status, item_type, item_id)`、`(reporter_id)`。
- **FR-2：** 用户重复举报同一条目时更新其既有行的 reason/note 和 `created_at`（提升新鲜度）而非创建重复行；若已解决则状态重置为 open。
- **FR-3：** 举报需要登录（匿名用户不能举报）；被封禁用户不能举报。

### 5.2 普通用户端

- **FR-4：** **举报**操作出现在每个公开模板详情页（点赞/收藏/复刻旁边的 ⋯ 菜单中）和每条公开评论上（评论 ⋯ 菜单）。用户自己的内容上隐藏。
- **FR-5：** 举报弹窗：五个单选原因及简短说明（垃圾信息或诈骗；冒犯或仇恨；误导或有害；隐私侵犯；其他），可选备注 textarea（≤ 500 字），取消/提交。选择原因前提交禁用。
- **FR-6：** 提交后：乐观关闭 + 成功 toast"举报已提交 —— 感谢。我们的审核员将进行审查。"若用户已举报过该条目，toast 显示"您的举报已更新。"
- **FR-7：** 举报者无案件跟踪：提交后没有状态页，解决时无通知（对举报者静默）。若用户对该条目有未解决举报，举报菜单项显示对勾状态（"您已举报此内容"），允许更新或撤回（撤回 = 删除其行）。

### 5.3 管理端 — 举报队列

- **FR-8：** 管理控制台在 `/admin/reports` 新增**举报**页：按条目分组的队列（每个被举报条目一行），列：条目类型徽章、条目标题/片段、作者、未解决举报数、原因摘要（标签）、最新举报时间、状态、操作（审查）。
- **FR-9：** 默认排序：未解决优先，按未解决数降序，再按最新举报时间降序。过滤器：状态（未解决/已解决/全部）、条目类型（模板/评论）、原因。
- **FR-10：** **审查抽屉：** 点击审查打开侧边抽屉，含完整上下文 —— 条目内容（模板预览或评论文本）、作者信息（链接到管理端用户详情）、每条举报（举报者、原因、备注、时间）—— 及处置操作：
  - **驳回举报**（误报）：将该条目所有未解决举报处置为 'dismissed'；内容不动。
  - **行动：** 取消发布模板（既有审核操作）或删除评论（既有评论审核），均需原因；随后举报自动处置为 'actioned'。"封禁作者"快捷方式链接到管理端用户详情（封禁流程留在原处）。
- **FR-11：** 处置在该条目所有未解决举报上记录 `resolved_by`、`resolved_at`、`resolution`，并写入审计日志条目（`report.dismiss` 或底层操作的既有条目，如 `template.unpublish`），附管理员的原因。
- **FR-12：** 已删除/未发布条目：若模板通过任何路径被取消发布或评论被删除，其未解决举报自动处置为 'actioned'（无悬空队列行）。
- **FR-13：** 管理仪表盘（既有 KPI 页）新增"未解决举报"KPI 卡片，链接到队列。

### 5.4 API

- **FR-14：** 用户 API：`POST /api/v1/reports`（body：item_type、item_id、reason、note）、`GET /api/v1/reports/mine?item_type=&item_id=`（返回用户对该条目的未解决举报，用于对勾状态）、`DELETE /api/v1/reports/mine`（body：item_type、item_id —— 撤回）。
- **FR-15：** 管理 API：`GET /api/v1/admin/reports?status=&item_type=&reason=&page=`（分组队列）、`GET /api/v1/admin/reports/{item_type}/{item_id}`（含全部举报的详情）、`POST /api/v1/admin/reports/{item_type}/{item_id}/resolve`（body：resolution 'dismissed'|'actioned'、reason）。取消发布/删除操作复用既有端点。
- **FR-16：** 速率限制：用户每小时最多提交 20 次举报（服务端强制，友好错误），防止举报刷屏。

### 5.5 通知集成

- **FR-17：** v1 无通知（对举报者静默；管理员看队列）。若通知功能后续上线管理端通知机制，可再增加"未解决举报阈值"提醒 —— 现在不在范围内。

## 6. 非功能需求

- **NFR-1（性能）：** 举报提交 < 300 毫秒；1,000 条未解决举报的管理队列分页（50/页）加载 < 1 秒。
- **NFR-2（隐私）：** 举报者仅对管理员可见（绝不对内容作者或其他用户暴露）；备注是保密的审核数据。
- **NFR-3（完整性）：** 每用户每条目一次举报由数据库约束强制（FR-1）；处置在条目所有未解决举报间原子完成。
- **NFR-4（无自动审查）：** v1 中不基于举报自动隐藏、降权或标注任何内容 —— 每个后果都需要显式管理员操作。
- **NFR-5（国际化）：** 所有原因标签、弹窗文案、队列列名、toast 通过 i18next（`reports.*`、`admin.reports.*` 命名空间）提供 EN/ZH；原因代码与语言无关。
- **NFR-6（无障碍）：** 举报弹窗是标准的焦点捕获对话框，带单选组语义；管理抽屉和队列表格遵循既有管理端无障碍模式。
- **NFR-7（一致性）：** 处置操作复用既有管理流程（取消发布、删除评论、封禁）—— 不发明新的审核权力。

## 7. 验收标准

- **AC-1：** 登录用户可以带原因和可选备注举报公开模板；成功 toast 确认；该行出现在管理队列。
- **AC-2：** 从评论 ⋯ 菜单举报评论的工作方式完全相同。
- **AC-3：** 同一用户再次举报同一条目会更新其举报（无重复行）；toast 显示"已更新"。
- **AC-4：** 有未解决举报的用户在条目上看到"您已举报此内容"；撤回后其举报从队列计数中移除。
- **AC-5：** 匿名用户看不到举报操作；被封禁用户调用举报 API 得到 403。
- **AC-6：** 管理队列按条目分组，显示未解决数和原因标签，未解决优先按数量再按新鲜度排序。
- **AC-7：** 审查抽屉显示条目内容、作者和每条举报（举报者和备注）。
- **AC-8：** 驳回将所有未解决举报处置为 'dismissed' 并写审计条目；条目不受影响。
- **AC-9：** 行动（取消发布/删除）将举报处置为 'actioned' 并以必填原因执行底层操作。
- **AC-10：** 通过常规审核列表（而非队列）取消发布模板也会自动处置其未解决举报。
- **AC-11：** 每小时 20 次举报限制在第 21 次返回友好错误。
- **AC-12：** 举报者身份绝不在管理端界面之外暴露；所有文案 EN/ZH 翻译。

## 8. 范围之外

- 举报阈值下的自动下架或自动隐藏（v1 始终人工决策）。
- 面向举报者的案件跟踪或处置通知。
- 举报用户/资料（仅内容：模板和评论；用户滥用走既有封禁流程）。
- 举报链、合集或团队（在这些界面上线审核时增加）。
- 审核工作区、认领分配、SLA 计时器。
- 任何形式的变现 —— 本产品永久排除。

## 9. 依赖与假设

- **D-1：** 评论功能（已设计）提供带 id 的评论实体和管理员删除路径；若评论未上线，评论举报部分（FR-2、FR-4 评论部分、FR-10 评论操作）延迟，模板举报单独上线。
- **D-2：** 复用管理控制台的列表页模式（搜索/过滤/分页/抽屉）和审计日志机制（`admin_audit_logs`，action + reason）。
- **D-3：** 既有的模板取消发布/审核操作（管理端模板页）是模板的"行动"路径。
- **D-4：** 模板详情和评论上的 ⋯ 菜单模式已存在或随评论功能到来。
- **D-5：** 存在速率限制基础设施（或简单的每用户窗口检查）。

## 10. 给架构师的开放问题

1. **条目标识：** 模板使用既有 id；评论需要稳定的公开 id —— 请确认评论设计的 id 方案在列表载荷中暴露（建议：是，响应中含评论 id）。
2. **分组查询：** 队列按 (item_type, item_id) 分组并 COUNT + MAX(created_at) —— 请确认索引 `(status, item_type, item_id)` 在预期规模下足够，还是偏好反规范化的 `report_groups` 汇总表。
3. **自动处置触发器：** FR-12 需要挂接取消发布/评论删除路径以自动处置 —— 事件驱动（服务层）还是在队列读取时清扫？建议：在取消发布/删除时服务层挂钩。
4. **撤回语义：** DELETE /reports/mine 完全删除该行（无痕迹）vs 标记为已撤回 —— 建议：硬删除（最简单；唯一约束随后干净地允许重新举报）。
5. **速率限制存储：** 内存窗口 vs redis（栈中有 redis）—— 建议：带 1 小时 TTL 的 redis 计数器。
6. **审计动作命名：** `report.dismiss` 作为新审计动作类型加入既有的 ban/unban/role_change/template 动作 —— 请确认审计动作枚举可扩展。
