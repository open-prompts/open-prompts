# 模板版本管理 UX — 需求分析

- **功能标识:** template-versioning
- **版本:** 1.0
- **状态:** 已提案（待架构评审）
- **作者:** ui-ux-agent
- **日期:** 2026-10-10

## 1. 竞品研究摘要

| 平台 | 版本管理方式 | 关键启示 |
|---|---|---|
| **GitHub/GitLab** | 完整历史带提交信息；统一/并排 diff；revert 创建*新的*前向提交；逐文件历史 | 变更说明是第一可用性要素；保存前 diff 防止事故；revert 是非破坏性的（仅前向） |
| **Notion** | 版本历史抽屉：带时间戳的快照、恢复任意快照、无说明 | 无说明的恢复可用，但用户只能靠日期区分版本 |
| **Google Docs** | 命名版本 + 自动版本；恢复；通过"比较"做 diff | 在自动编号之上叠加可选命名/说明是最优解 |
| **npm / Docker Hub** | 带发布说明的版本标签；"latest" 指针 | 发布说明让版本列表可扫读；清晰的"最新"标识很重要 |
| **PromptBase** | 无版本管理 —— 单一可编辑内容 | 这是缺口；创作者盲改，没有安全网 |
| **FlowGPT** | 简单的编辑历史（仅时间戳） | 仅时间戳是最小可用版本管理 —— 正是 Open Prompts 现在的位置 |
| **AIPRM / Snack Prompt** | 无有意义的版本管理 | 不是可借鉴的模式 |

**综合结论:** 内容平台的胜出模式是：自动编号版本（已有）+ **可选变更说明**（单项价值最高的补充）、**丰富的历史列表**（而不只是下拉框）、**任意两版本之间的 diff**、以及**非破坏性恢复**（恢复 v3 会创建内容为 v3 的 v7 —— 绝不删除中间版本）。Open Prompts 已具备最难的部分（内容变更时服务端创建版本、`UNIQUE(template_id, version)`、提示词固定到 `version_id`）；缺失的完全是 UX 层加上一个可空列。

## 2. 问题陈述

1. **版本无法区分。** 版本下拉只显示"v3 (2026/6/20)"。有 8 个版本的用户无法分辨哪个引入了语气调整、修复或退化 —— 仅日期不承载意图。
2. **看不到改了什么。** 要比较 v3 与 v4，用户必须切换版本并在脑中对两堵文字墙做 diff。没有 diff 视图。
3. **无法恢复。** 如果某次保存让模板变差，唯一的恢复方式是从旧版本复制粘贴到编辑器 —— 易错且难以发现。后端已支持（内容不同时 UpdateTemplate 会创建新版本），但没有任何 UI 暴露它。
4. **历史是下拉框而非界面。** 40px 的下拉框无法展示说明、使用量或操作。版本管理需要真正的面板。
5. **没有使用量可见性。** 提示词固定到特定 `version_id`，但没有任何地方显示"v2 被 14 条提示词使用" —— 这些信息存在于模式中，本可指导恢复决策。
6. **保存流程没有框架。** "保存新版本"什么都不问；每次保存都是匿名快照。

## 3. 目标用户

- **创作者（主要）:** 迭代模板、需要理解/比较/恢复版本历史的用户。
- **Fork 用户:** fork 了模板、想看源模板如何演进的只读历史 + diff 用户。
- **普通用户/浏览者:** 查看公开模板、想了解其演进并信任其维护的任何人。
- **管理员:** v1 不受影响 —— 版本历史是按模板的内容，不是审核关注点；无管理员控制台界面（若将来构建管理员模板审核，那是独立功能）。

## 4. 用户故事

### 4.1 变更说明

- **US-V1:** 作为创作者，保存新版本时我希望可选地添加简短变更说明（"修复语气漂移"），以便历史自解释。
- **US-V2:** 作为创作者，我希望说明是可选的，以便快速保存不被拖慢。
- **US-V3:** 作为浏览者，我希望在历史列表中看到每个版本的说明，以便无需 diff 即可理解模板演进。

### 4.2 版本历史面板

- **US-V4:** 作为用户，我希望模板页上有版本历史面板，列出所有版本（最新在前）及编号、说明、时间戳、内容长度和"最新"徽标，以便一目了然纵览历史。
- **US-V5:** 作为用户，我希望从面板选择版本后在既有预览中看到其内容，以便版本浏览与今天的下拉一致但更丰富。
- **US-V6:** 作为用户，我希望知道每个版本创建了多少提示词，以便判断哪些版本真正被用过。

### 4.3 Diff

- **US-V7:** 作为创作者，我希望对任意两个版本做 diff，高亮新增/删除/变更的行，以便精确看到一次保存改了什么。
- **US-V8:** 作为创作者，我希望有 diff 统计（+N −M 行），以便一眼判断变更规模。
- **US-V9:** 作为用户，我希望每个版本行上有快捷"与上一版比较"操作，以便最常见的比较一键完成。

### 4.4 恢复

- **US-V10:** 作为创作者，我希望有"恢复此版本"操作，用旧版本内容创建新版本，以便从糟糕的保存中恢复而不丢失历史。
- **US-V11:** 作为创作者，我希望恢复的版本带自动生成的说明（"Restored from v3"），以便历史保持自解释。
- **US-V12:** 作为创作者，我希望恢复绝不删除或重编号既有版本，以便历史是仅追加且安全的。

### 4.5 系统

- **US-V13:** 作为系统，我将恢复限制为仅所有者，以便只有模板所有者能修改内容。
- **US-V14:** 作为系统，我限制说明长度，以便说明保持可扫读且存储有界。
- **US-V15:** 作为系统，我保持既有 API 客户端（别名 → 版本映射、固定到 version_id 的提示词创建）完全可用，以便没有任何破坏。

## 5. 功能需求

### 5.1 数据模型

- **FR-1:** `template_versions` 应新增可空列 `change_note TEXT`（最长 200 字符，服务端强制；既有行与快速保存为 NULL）。
- **FR-2:** `UpdateTemplateRequest` 应接受可选 `change_note`；当内容变更并创建新版本时，说明随之存储。内容未变时忽略说明（不创建版本 —— 保持既有行为）。
- **FR-3:** `TemplateVersion` proto 消息应在 `GetTemplate.latest_version`、`ListTemplateVersions` 与 `UpdateTemplateResponse.new_version` 中暴露 `change_note`（NULL 时为空字符串）。
- **FR-4:** `ListTemplateVersionsResponse` 的版本应包含 `prompt_count`（`version_id` 引用该版本的提示词数量），通过对 `prompts` 的 LEFT JOIN + COUNT 计算。

### 5.2 版本历史面板（模板详情页）

- **FR-5:** 模板详情页应在版本选择器旁提供"历史"开关，打开版本历史面板（页内区块，非路由），最新在前列出：版本号、"最新"徽标（最新版）、变更说明（或"无说明"）、相对时间戳（`title` 中有绝对时间）、内容长度（字符/行数）、提示词数量，以及每行操作。
- **FR-6:** 点击行即选中该版本（与今天的下拉行为一致：预览切换，进入编辑模式时编辑器载入其内容）。
- **FR-7:** 面板应通过既有 `page_token` 模式分页（每页 20 条，"加载更多"），替换当前一次性 `page_size: 100` 的获取。
- **FR-8:** 既有 `VersionSelect` 下拉应保留（快速切换），并在有说明时于日期下方显示说明摘要。
- **FR-9:** 面板对任何能查看该模板的人可见（公开模板 → 含匿名）；操作按权限门控（恢复仅限所有者，见 FR-13）。

### 5.3 Diff 视图

- **FR-10:** "比较"操作应打开 diff 弹窗，含两个版本选择器（A = 较旧，B = 较新；默认：选中版本 vs 最新版），渲染统一行 diff：未变更上下文行、删除行（−，红）、新增行（+，绿），带行号与统计（+N −M）。
- **FR-11:** diff 应由客户端基于两个版本的内容计算（两者均已通过 ListTemplateVersions 获取）；无新后端端点。"交换 A/B"控件，变更后重新运行"比较"。
- **FR-12:** diff 对任何能查看该模板的人可用（只读；无需权限）。

### 5.4 恢复

- **FR-13:** 每个版本行（最新版除外）应向模板所有者提供"恢复"：调用既有 `UpdateTemplate`，传入旧版本内容与自动生成的说明 `Restored from v{n}`（不允许客户端本地化 —— 说明是存储数据；存储规范英文字符串 "Restored from v{n}" 并原样渲染）。
- **FR-14:** 恢复应需要确认（弹窗显示来源版本与"将创建新版本"的警告）。
- **FR-15:** 恢复绝不删除、重编号或修改既有版本；它总是追加（UpdateTemplate 的后端行为已保证这一点）。
- **FR-16:** 恢复成功后 UI 应选中新版本、刷新历史列表并显示成功 toast。

### 5.5 保存流程

- **FR-17:** 编辑模式应在保存按钮上方显示可选的"变更说明（可选）"输入框（maxlength 200）；说明随 `UpdateTemplate` 发送。
- **FR-18:** 内容未变时保存保持今天的行为（不创建新版本，仅元数据更新路径不受影响）；说明输入被忽略。

### 5.6 API 摘要

- **FR-19:** 无新 REST 端点。变更：`PUT /api/v1/templates/{id}` 请求体新增可选 `change_note`；`GET /api/v1/templates/{id}/versions` 响应中每个版本新增 `change_note` 与 `prompt_count`；`GET /api/v1/templates/{id}` 的 `latest_version` 新增 `change_note`。
- **FR-20:** 向后兼容：所有新字段可选/可空；忽略它们的旧客户端行为与今天完全一致。别名映射（`GetPromptByAlias` → 版本）与提示词创建（`version_id` 固定）不受影响。

### 5.7 普通用户与管理员划分

- **FR-21:** 版本管理 UX 是模板详情页上的普通用户界面。管理员用户作为浏览者/所有者的体验完全一致。
- **FR-22:** 本功能不包含任何管理员控制台页面（`/admin/*`）与管理员 API（`/api/v1/admin/*`）。

## 6. 非功能需求

- **NFR-1（性能）:** 历史面板首屏 p95 < 300ms（既有索引查询 + 一个 JOIN）；典型模板内容（≤ 32KB）客户端 diff 计算 < 100ms；恢复是单次既有 UpdateTemplate 调用。
- **NFR-2（兼容性）:** 仅增量的模式/proto 变更；无破坏性 API 变更；既有页面与别名/API-key 提示词流程不变（FR-20）。
- **NFR-3（隐私/安全）:** 历史/diff 可见性跟随模板可见性（公开 → 任何人，私有 → 所有者）；恢复仅限所有者，由既有 UpdateTemplate 授权在服务端强制；变更说明是纯文本（React 转义），最长 200 字符。
- **NFR-4（无障碍）:** 面板、diff 弹窗与恢复流程完全可键盘操作；diff 行带语义标记（新增/删除状态对屏幕阅读器可感知）；见 UI/UX 文档 §10。
- **NFR-5（国际化）:** 所有新 UI 字符串中英文同步；存储的变更说明与自动生成的恢复说明是用户/系统数据，原样渲染（渲染时绝不翻译）；相对时间戳用共享工具。
- **NFR-6（韧性）:** 若 `prompt_count` 无法计算（如旧后端），UI 隐藏使用量列而不是报错；若 diff 库不可用，比较操作回退为并排原始视图。
- **NFR-7（数据完整性）:** `change_note` 可空且服务端限长；恢复说明使用单一规范格式以保证历史可机器解析（"Restored from v{n}"）。

## 7. 验收标准

- **AC-1:** 带变更说明保存的版本在历史面板与版本下拉中存储并显示该说明；不带说明保存存储 NULL 并显示"无说明"。
- **AC-2:** 历史面板最新在前列出版本，含编号、最新徽标、说明、相对时间、内容长度与提示词数量，每页 20 条分页并带加载更多。
- **AC-3:** 点击历史行（或下拉选项）将预览切换到该版本，与当前下拉行为一致。
- **AC-4:** 比较打开任意两版本的 diff 弹窗，+/- 行高亮、行号与 +N −M 统计正确；交换 A/B 可用。
- **AC-5:** 恢复（仅所有者、非最新行）用旧内容与说明"Restored from v{n}"创建新版本，不触碰任何既有版本，选中新版本并刷新列表。
- **AC-6:** 非所有者看到面板与 diff 但没有恢复操作；匿名用户在公开模板上看到只读面板。
- **AC-7:** 超过 200 字符的说明被服务端拒绝（400）并被客户端阻止（maxlength + 计数器）。
- **AC-8:** 既有行为不变：仅元数据保存不创建版本；别名 → 版本映射返回相同结果；早前创建的提示词仍引用其原始 version_id。
- **AC-9:** 所有新 UI 字符串在 `en` 与 `zh` 翻译文件中存在且键集一致。
- **AC-10:** 模板详情页（查看/编辑/fork/点赞/收藏/提示词生成）除新面板、说明输入与操作外行为不变。
- **AC-11:** API 响应中缺失 `prompt_count` 时，使用量列无错隐藏（NFR-6）。

## 8. 范围之外（v1）

- 并排（双栏）diff —— v1 仅统一 diff。
- 版本删除（历史仅追加；删除会使固定到该版本的提示词成为孤儿）。
- 版本分支/标签（如"stable"与"beta" —— 超出现有别名机制）。
- 按版本署名（当前版本仅所有者可编辑；协作编辑不存在）。
- 元数据 diff（标题/标签/分类）—— 仅内容 diff。
- 服务端 diff 端点（仅客户端；若模板变得非常大再议）。
- 管理员控制台版本管理（`/admin/*`）。
- 版本变更的邮件/通知（通知功能仅覆盖参与事件）。
- 移动应用专属布局（仅响应式 Web）。

## 9. 依赖与假设

- **D-1:** `UpdateTemplate`（backend/internal/service/prompt.go）已在内容不同时创建新版本并作为 `new_version` 返回 —— 恢复无需新端点，只需 `change_note` 透传（FR-2）。
- **D-2:** `template_versions` 有 `UNIQUE (template_id, version)` 与 `template_id` 索引（deployment/init.sql）—— 历史查询与提示词计数 JOIN 均有索引支持。
- **D-3:** `prompts.version_id` 引用 `template_versions(id)`（deployment/init.sql）—— `prompt_count` 是 LEFT JOIN COUNT；零提示词的版本显示 0。
- **D-4:** `ListTemplateVersions` RPC 与 REST 路由已存在且支持分页；前端当前一次性获取 `page_size: 100`（TemplateDetails.js）—— FR-7 用真实分页替换。
- **D-5:** 客户端 diff 需要一个 diff 实现。建议：`diff` npm 包（Myers，约 10KB）—— 是否加依赖由开发者/架构师决定；手写最小 LCS 是回退方案（开放问题 #2）。
- **D-6:** 相对时间工具与 user-dashboard 和 notifications 功能共享（它们的 D-4/D-6）；若都未交付，则由本功能引入。
- **D-7:** 自动生成的恢复说明以规范英文存储（"Restored from v{n}"），因为它是数据而非界面文案（NFR-5）；围绕它的确认弹窗完全本地化。
- **D-8:** 内容长度显示（字符/行数）由客户端基于已获取的内容计算；无 API 变更。

## 10. 给架构师的开放问题

1. **`prompt_count` 计算:** 在 `ListTemplateVersions` 内联 LEFT JOIN + COUNT（简单，当前规模没问题）还是单独的批量计数查询。建议：内联 JOIN。
2. **Diff 库:** 引入 `diff`（npm，Myers）作为前端依赖，还是手写 LCS 工具（无依赖，约 60 行，对 ≤ 32KB 内容足够）。建议：为保证边界情况的正确性用 `diff` 包；若要最小化依赖，手写也可接受。
3. **`CreateTemplate` 上的 `change_note`:** v1 假定初始版本（v1）无需说明（隐含"初始版本"）。请确认，或为对称性也在 CreateTemplateRequest 上加该字段。
