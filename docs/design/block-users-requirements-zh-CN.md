# 屏蔽用户（Block Users）— 需求分析

- **功能 ID：** block-users
- **版本：** 1.0
- **状态：** 已提案（待架构评审）
- **作者：** ui-ux-agent
- **日期：** 2026-10-12

## 1. 竞品调研总结

| 平台 | 屏蔽方式 | 关键启示 |
|---|---|---|
| **Twitter/X** | 屏蔽对屏蔽者静默，对被屏蔽者近乎不可见（他们可以访问但无法关注/互动）；设置中有屏蔽列表 | 对屏蔽者静默是标准做法；被屏蔽方不会收到通知 |
| **Instagram** | 屏蔽使双方互相看不到对方资料；被屏蔽用户的评论/点赞被隐藏 | 互相不可见比选择性隐藏更容易推理 |
| **GitHub** | 没有用户级屏蔽（仅仓库级）；依赖审核 | 前车之鉴 —— 创作者骚扰没有用户级答案 |
| **Reddit** | "Block" 实为静音（向你隐藏其内容）；他们仍能看到你的 | 最弱的解释；用户期待更多 |
| **Mastodon** | 屏蔽 + 可选静音；被屏蔽用户无法关注或提及你 | 屏蔽切断关注图 —— 最重要的效果 |
| **FlowGPT / Snack Prompt / PromptBase** | 看不到屏蔽功能 | 提示词平台尚未解决此问题；复制社交网络模式即是答案 |

**综合分析：** Open Prompts 正在获得社交层（评论、关注、`/creators/:id` 创作者资料、通知）。每个社交层都需要一个不需要管理员介入的个人安全阀。制胜的 v1 模式是 Twitter/Mastodon 混合：`user_blocks` 表（屏蔽者 → 被屏蔽者）；屏蔽**双向切断关注图**（双向自动取关）、**向屏蔽者隐藏被屏蔽用户的内容**（其模板从屏蔽者的列表/搜索/信息流中消失，其评论折叠）、**阻止互动**（无法关注、点赞/收藏、评论屏蔽者的模板），并且**静默**（不通知被屏蔽用户；他们永远不会被告知）。被屏蔽用户仍可*查看*屏蔽者的公开模板（公开内容保持公开 —— v1 不做 Instagram 式互相不可见；记录为范围外），但无法与之互动。**"已屏蔽账号"**管理列表位于既有的个人资料页（设置区）。无管理界面：屏蔽是个人图数据，屏蔽滥用（如屏蔽所有人）只损害屏蔽者自己的体验。

## 2. 问题陈述

1. **没有个人安全阀。** 随着评论、关注和通知落地，被其他用户骚扰或困扰的用户没有自助救济 —— 他们必须（通过内容举报）向管理员举报并等待。
2. **关注图没有出口。** 后悔关注或想断开连接的用户可以取关，但对方可以简单地重新关注；没有"阻止此人关注我"。
3. **内容暴露不可避免。** 有意屏蔽的用户的模板仍然涌入屏蔽者的搜索结果、标签页和关注信息流；其评论仍出现在共享模板上。
4. **管理员是唯一的执行者。** 目前每个人际冲突都路由到管理员审核 —— 缓慢、沉重，对个人偏好屏蔽来说不必要。

## 3. 目标用户

- **普通用户（主要）：** 任何想要持久、个人化"不要这个人"控制的人 —— 骚扰受害者、厌恶垃圾信息的用户或单纯偏好。
- **创作者（次要）：** 想要阻止特定用户评论或点赞其作品的模板所有者。
- **管理员（减负）：** 更少的人际投诉路由到审核；屏蔽处理个人偏好，举报处理政策违规。

## 4. 用户故事

- **US-B1：** 作为用户，我可以从其资料页或其评论的 ⋯ 菜单屏蔽另一个用户，以便无需管理员帮助即可阻止不必要的关注。
- **US-B2：** 作为用户，屏蔽双向切断关注（他们停止关注我，我停止关注他们），以便连接被完全切断。
- **US-B3：** 作为用户，被屏蔽用户的模板从我的搜索结果、标签/分类页和关注信息流中消失，以便我的浏览干净。
- **US-B4：** 作为用户，被屏蔽用户的评论在我查看的模板上折叠为单行"已屏蔽账号"，以便话题保持可读而不向我显示其内容。
- **US-B5：** 作为创作者，被屏蔽用户无法评论、点赞、收藏或关注我及我的模板，以便屏蔽真正阻止互动。
- **US-B6：** 作为用户，屏蔽是静默的 —— 被屏蔽用户永远不会收到通知，也无法确切知道何时发生。
- **US-B7：** 作为用户，我可以在个人资料设置中查看和管理已屏蔽列表，并在改变主意时取消屏蔽。
- **US-B8：** 作为用户，我无法屏蔽管理员或自己；系统以清晰消息拒绝。
- **US-B9：** 作为被屏蔽用户，我仍可查看屏蔽者的公开模板（公开就是公开），但每个互动端点返回通用错误，以便我知道操作失败而不知道原因。

## 5. 功能需求

### 5.1 数据模型

- **FR-1：** 新表 `user_blocks`：`blocker_id`（FK → users，`ON DELETE CASCADE`）、`blocked_id`（FK → users，`ON DELETE CASCADE`）、`created_at` TIMESTAMPTZ、`PRIMARY KEY (blocker_id, blocked_id)`、`CHECK (blocker_id <> blocked_id)`。`blocked_id` 上建索引用于反向查询。
- **FR-2：** 屏蔽**不**在 `users` 上反规范化（无 block_count）；该表是唯一事实来源。除自动取关副作用（FR-4）外，屏蔽不影响任何一方的关注者/正在关注计数器。

### 5.2 屏蔽操作

- **FR-3：** `POST /api/v1/users/{userId}/block`（需认证）创建屏蔽（屏蔽者 = 令牌用户）。幂等：屏蔽已屏蔽的用户返回 200 和 `{blocked: true}`。自屏蔽返回 400；屏蔽管理员返回 403 和清晰消息；屏蔽不存在的用户返回 404。
- **FR-4：** 创建屏蔽时，系统事务性地移除**双向**的关注行（屏蔽者→被屏蔽者和被屏蔽者→屏蔽者），并相应调整关注者/正在关注计数器（复用关注功能的计数器维护）。
- **FR-5：** `DELETE /api/v1/users/{userId}/block`（需认证）移除屏蔽。幂等。取消屏蔽**不**恢复任何关注关系。
- **FR-6：** 速率限制：每账号每分钟最多 20 次屏蔽/取消屏蔽操作（HTTP 429 带 `Retry-After`），以遏制屏蔽滥用。

### 5.3 互动强制（服务端）

- **FR-7：** 当存在 A 到 B 的屏蔽时：B 无法关注 A（403）、B 无法点赞/收藏 A 的模板（403）、B 无法评论 A 的模板（403）、B 无法 fork A 的模板（403）。错误是通用的（"操作不可用"）—— 绝不透露存在屏蔽。
- **FR-8：** A 不受反向影响：A 仍可查看 B 的公开模板（公开内容就是公开的），也可评论 B 的模板（屏蔽是盾不是剑 —— A 屏蔽 B 不会让 A 在 B 的内容上噤声；记录为 §8 的 v2 问题）。
- **FR-9：** 屏蔽双向抑制通知：B 的操作不为 A 生成通知（反正按 FR-7 他们无法操作），A 的操作不为 B 生成通知（A 点赞 B 的模板不通知 B）。

### 5.4 内容可见性（屏蔽者视图）

- **FR-10：** 对屏蔽者（A），B 的模板被排除出：主页广场列表、搜索结果、标签/分类过滤页、关注信息流、相关模板横栏和"来自作者的更多"行。直接导航到 B 模板的 URL 仍有效（深链不断裂；页面渲染并带微妙的"你已屏蔽此创作者"提示）。
- **FR-11：** 对屏蔽者（A），B 在任何模板上的评论折叠为单行"来自已屏蔽账号的评论"（可点击展开显示，遵循渐进披露的无障碍模式）。
- **FR-12：** B 的资料页（`/creators/:id`）对 A 可见，但显示横幅"你已屏蔽此创作者"和取消屏蔽按钮；B 的关注者/正在关注列表保持可见（公开数据）。
- **FR-13：** 被屏蔽用户（B）在任何地方都看不到差异：A 的模板正常出现在 B 的列表/搜索中（公开内容），A 的资料正常渲染，B 的互动尝试按 FR-7 通用失败。B 永远不会收到屏蔽通知。

### 5.5 管理界面

- **FR-14：** 个人资料页增加**"已屏蔽账号"**设置区：可搜索的已屏蔽用户列表（头像、显示名、屏蔽日期），每项带取消屏蔽按钮。空状态解释屏蔽的作用。
- **FR-15：** 屏蔽入口：创作者资料页（`/creators/:id`）的 ⋯ 菜单和任何评论的 ⋯ 菜单（评论功能）。两者都打开确认弹窗（"屏蔽 {name}？他们将无法再关注你或与你的内容互动。他们不会收到通知。"）带屏蔽/取消。
- **FR-16：** 无管理界面：屏蔽是个人图数据。管理员用户详情页不显示屏蔽列表（屏蔽者的隐私）。管理员不可被屏蔽（FR-3）。

### 5.6 API 汇总

- **FR-17：** `GET /api/v1/users/me/blocks`（需认证）返回调用者的已屏蔽列表（分页、公开用户卡片 + blocked_at）。`POST/DELETE /api/v1/users/{userId}/block` 按 FR-3/5。模板列表/搜索/信息流端点增加服务端屏蔽过滤（FR-10）—— 无新参数；对已认证调用者自动过滤。

## 6. 非功能需求

- **NFR-1（性能）：** 屏蔽/取消屏蔽 p95 < 200 毫秒；列表/搜索上的屏蔽过滤每查询增加 < 10 毫秒（对 PK 索引的 `user_blocks` 做反连接）。
- **NFR-2（静默）：** 任何代码路径都不得通知用户他们被屏蔽或取消屏蔽；通知抑制（FR-9）在事件发射层强制执行。
- **NFR-3（原子性）：** 屏蔽创建 + 双向取关（FR-4）是一个事务；失败不留下部分状态。
- **NFR-4（隐私）：** 已屏蔽列表对屏蔽者私有（仅 `GET /users/me/blocks`）；没有公开端点揭示谁屏蔽谁。屏蔽存在绝不通过错误消息披露（FR-7）。
- **NFR-5（国际化）：** 所有屏蔽 UI 字符串翻译（EN/ZH）；通用互动错误是单一共享键。
- **NFR-6（无障碍）：** 屏蔽确认弹窗遵循无障碍 Modal 模式；折叠的被屏蔽评论可键盘展开；已屏蔽列表是标准的无障碍表格/列表。
- **NFR-7（兼容性）：** 仅增量 —— 一张新表、新端点、列表查询过滤和 UI 入口；无既有响应形态变化（屏蔽过滤仅是移除）。

## 7. 验收标准

- **AC-1：** 从资料或评论 ⋯ 菜单屏蔽打开确认弹窗；确认创建屏蔽并显示成功 toast。
- **AC-2：** A 屏蔽 B 后，B 对 A 的关注和 A 对 B 的关注都消失；计数器正确。
- **AC-3：** A 屏蔽 B 后，B 的模板从 A 的主页/搜索/标签/关注信息流/相关界面消失；直接 URL 访问仍渲染并带"已屏蔽创作者"提示。
- **AC-4：** B 的评论对 A 在每个模板上折叠渲染（"来自已屏蔽账号的评论"）；一键展开。
- **AC-5：** B 在 A 内容上关注/点赞/收藏/评论/fork 的尝试全部以通用错误失败；B 看不到屏蔽专属消息。
- **AC-6：** 被屏蔽或取消屏蔽时 B 不收到通知；A 后来在 B 内容上的操作不为 B 生成通知。
- **AC-7：** 个人资料"已屏蔽账号"区列出已屏蔽用户和取消屏蔽；取消屏蔽移除该行且不恢复关注。
- **AC-8：** 自屏蔽和管理员屏蔽尝试显示清晰错误；重复屏蔽同一用户是无操作返回 200。
- **AC-9：** A 查看 B 的资料显示"你已屏蔽此创作者"横幅和取消屏蔽；B 查看 A 的资料不变。
- **AC-10：** 所有屏蔽 UI 字符串以 EN 和 ZH 渲染。

## 8. 范围之外

- 互相不可见（Instagram 式：被屏蔽用户看不到屏蔽者的公开内容）—— v1 保持公开内容公开；如果骚扰报告需要则重新审视。
- 屏蔽作为剑（A 屏蔽 B 也让 A 在 B 的内容上噤声 —— FR-8 保留 A 的发言）—— v2 问题。
- 对管理员可见的屏蔽列表；管理员解除屏蔽的能力。
- 基于域名/邮箱的屏蔽、IP 屏蔽、影子封禁。
- 静音（隐藏内容而不切断关注）—— 更轻量的未来功能。
- 从模板卡片屏蔽（v1 仅资料 + 评论入口）。
- 任何形式的变现（付费、定价、购买、收益）—— 本产品永久排除。

## 9. 依赖与假设

- **D-1：** follow-creators 功能的 `user_follows` 表、计数器维护和关注/取关端点存在（或将存在）；FR-4 事务性地复用取关路径。
- **D-2：** 评论功能的评论渲染（带来自 content-reporting 的 ⋯ 菜单）提供评论级屏蔽入口；如果评论未上线，评论入口推迟，资料屏蔽先行。
- **D-3：** follow-creators 的创作者资料页（`/creators/:id`）提供资料屏蔽入口和横幅界面。
- **D-4：** 模板列表/搜索查询集中在仓库层（单一咽喉点），因此屏蔽过滤（FR-10）是一次反连接添加，而不是每个界面 N 个补丁。
- **D-5：** 通知功能的事件发射层可以按（操作者，接收者）对抑制事件 —— 其既有自操作抑制的小扩展。
- **D-6：** related-templates 和"来自作者的更多"端点（related-templates 功能）应用与其他列表相同的屏蔽过滤。

## 10. 给架构师的开放问题

1. **过滤范围：** FR-10 将被屏蔽用户的模板从屏蔽者的列表/搜索/信息流/相关中排除。*被屏蔽*用户（B）是否也应看到 A 的模板从其列表中移除（对称过滤），还是 v1 仅屏蔽者过滤正确？我推荐仅屏蔽者（公开内容保持公开；对称过滤泄露屏蔽存在）。
2. **反连接形态：** `NOT EXISTS (SELECT 1 FROM user_blocks WHERE blocker_id = $caller AND blocked_id = templates.owner_id)` 添加到每个列表查询 vs 每调用者的物化"隐藏用户"缓存。我推荐反连接（PK 索引，当前规模便宜）。
3. **评论折叠：** 服务端（评论 API 为调用者返回每条评论的 `is_blocked` 标志）vs 客户端（获取屏蔽列表，客户端过滤）。我推荐服务端标志（无额外往返，不通过 API 泄露屏蔽列表）。
4. **Fork 强制（FR-7）：** fork 是复制操作 —— 被屏蔽用户是否应无法 fork 屏蔽者的公开模板？我推荐是（互动完整性），但因为 fork 是先读后创建所以可争论。
5. **通知抑制（FR-9）：** 在发射时抑制（插入前检查屏蔽表）vs 在读取时（过滤通知列表）。我推荐发射时（更便宜，无过期行）。
6. **管理员豁免（FR-3）：** 屏蔽管理员返回 403 —— 确认，还是也允许屏蔽管理员（他们也是用户）？我推荐豁免以避免支持死胡同。
