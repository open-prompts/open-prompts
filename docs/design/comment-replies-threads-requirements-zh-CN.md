# 评论回复与话题 — 需求分析

- **功能标识:** comment-replies-threads
- **版本:** 1.0
- **状态:** 已提案（待架构评审）
- **作者:** ui-ux-agent
- **日期:** 2026-10-12

## 1. 竞品研究摘要

| 平台 | 话题方式 | 关键启示 |
|---|---|---|
| **Reddit** | 深度嵌套话题（默认很深）；"continue this thread" 折叠；回复是首要动词 | 深层嵌套在移动端不可读；折叠必不可少；回复是核心参与动词 |
| **GitHub（议题/讨论）** | 平铺列表 + 一级回复缩进；回复引用父级；时间线视图 | **一级缩进是问答的最佳平衡**：视觉成组、无深层嵌套、分页简单 |
| **Stack Overflow** | 评论 + 回复，@ 式称呼；"show N more comments" | 回复的回复很少见且通常应指向顶层父级；懒加载保持页面快速 |
| **YouTube** | 顶层评论下一级回复；"View replies (N)" 可折叠桶 | "回复桶"模式（默认折叠、计数可见）让长评论区保持可扫读 |
| **FlowGPT** | 平铺评论，创作者内联回复，无嵌套 | 证实纯平铺可用但多方问答难以跟随 |
| **Disqus** | 嵌套数级；回复通知父级作者 | 回复通知是留存钩子：它把父级作者带回 |

**综合结论:** 评论区的行业答案（区别于论坛）是**一级嵌套**：顶层评论 + 缩进的回复，回复的回复平铺到同一顶层话题（GitHub/YouTube 模式）。这让表结构简单（在既有 `template_comments` 表上加 `parent_comment_id`）、分页简单（顶层评论分页；回复按话题加载），并契合提示词问答的真实流向（"GPT-4 能用吗？" → 创作者回复 → 追问）。Open Prompts 已上线平铺评论（提交 793a48f），其设计文档明确将嵌套延后 —— 本功能即该功能。它直接构建于已上线的 `CommentsSection`/`CommentItem`/`CommentComposer` 组件、15 分钟编辑窗、所有者/管理员审核和速率限制之上。

## 2. 问题陈述

1. **多方对话无法跟随。** 平铺评论下，创作者对 Alice 提问的回答出现在其他评论之间的无关行里。读者无法判断一条回复在回答哪条评论。
2. **回复意图丢失。** 用户写"@创作者 JSON 还是坏的"时，没有结构化方式把消息挂到它所回答的评论上；唯一手段是手动打 @，而已上线的功能不支持。
3. **父级作者永远收不到通知。** 创作者回复用户评论时，该用户无从知晓 —— 已上线的通知只告知模板所有者有新评论。对话无声死亡。
4. **问答价值被埋没。** 评论区最有价值的内容是创作者的回答；没有嵌套它们就散落在列表各处，没有过滤器读者也找不到已答/未答的问题。

## 3. 目标用户

- **评论者（提问者）:** 希望追问挂在自己的原评论下，并希望有人回复时收到通知。
- **创作者（模板所有者）:** 希望在上下文中回答具体问题，并让已答问答被未来读者找到。
- **读者/潜在用户:** 希望扫读评论区并把"问题→回答"成对阅读。
- **管理员:** 用与今天相同的工具审核带话题的评论（话题结构不得让删除变复杂）。

## 4. 用户故事

### 4.1 回复

- **US-R1:** 作为已登录用户，我希望回复公开模板下的任何评论，以便我的回应挂在我所回答的评论上。
- **US-R2:** 作为评论者，有人回复我的评论时我希望收到通知，以便继续对话。
- **US-R3:** 作为用户，我回复一条回复时，希望我的回复挂到同一顶层话题（而非嵌套更深），以便话题保持可读。
- **US-R4:** 作为匿名访客，尝试回复时被引导登录，以便流程可理解。
- **US-R5:** 作为被封禁用户，我不能回复，与账号受限状态一致。

### 4.2 阅读话题

- **US-R6:** 作为读者，我希望回复直接缩进在其父评论下，以便跟随"问题→回答"对。
- **US-R7:** 作为读者，我希望回复桶默认折叠并显示计数（"查看 3 条回复"），以便长评论区保持可扫读。
- **US-R8:** 作为读者，我希望按需加载话题的回复，以便 200 条评论的模板保持快速。
- **US-R9:** 作为读者，我希望创作者的回复有视觉区分（既有 CREATOR 徽章），以便在话题中找到官方回答。

### 4.3 审核与生命周期

- **US-R10:** 作为评论者，我可以在与顶层评论相同的规则内编辑/删除自己的回复（15 分钟编辑窗），以便行为一致。
- **US-R11:** 作为模板所有者，我可以删除我模板下的任何回复，以便所有者审核统一运作。
- **US-R12:** 作为管理员，我可以从管理台带理由删除任何回复，以便审核不受话题影响。
- **US-R13:** 作为系统，删除顶层评论时删除其回复（级联），以便不留下孤儿回复。
- **US-R14:** 作为系统，删除一条回复时其父级和兄弟回复保持完好。

### 4.4 系统

- **US-R15:** 作为系统，`templates.comment_count` 只统计顶层评论，以便计数器保持其含义（"评论数"）且不重复计算对话。
- **US-R16:** 作为系统，我对回复施加与评论相同的速率限制，以便话题不是垃圾信息旁路。

## 5. 功能需求

### 5.1 数据模型

- **FR-1:** `template_comments` 新增 `parent_comment_id`（UUID，可空 —— 顶层评论为 null）和 `reply_count`（INT，非空，默认 0 —— 直接回复数，事务性维护）。在 `(parent_comment_id, created_at ASC)` 上建索引以支持按话题加载回复。`parent_comment_id` 不强制外键（删除级联由 FR-11 处理）；架构师也可选择加 `REFERENCES template_comments(id) ON DELETE CASCADE`。
- **FR-2:** `CreateComment` 应接受可选 `parent_comment_id`。设置时：父级必须存在、属于同一模板、且是**顶层评论**（其自身 `parent_comment_id` 为 null）—— 回复一条回复时挂到同一顶层父级（US-R3）。违规返回 400 并附具体信息。
- **FR-3:** 回复应完整继承既有评论规则：1–2000 字符、被封禁用户 403、速率限制（5/分钟、50/天）、编辑窗（15 分钟）、作者或所有者或管理员删除。
- **FR-4:** 发布回复应事务性递增父级的 `reply_count`。`templates.comment_count` **仅对顶层评论递增**；回复不影响它（US-R15）。

### 5.2 阅读

- **FR-5:** `ListComments` 应只返回**顶层评论**（分页、最新在前、结构不变），每项扩展 `reply_count` 和 `has_creator_reply`（布尔 —— 模板所有者是否在该话题中回复过；驱动"已解答"角标）。
- **FR-6:** 新增 `ListCommentReplies` RPC（`GET /api/v1/comments/{id}/replies`）应返回某顶层评论的全部回复，最旧在前（对话顺序），不分页（由 FR-8 的回复上限约束）。每条回复使用既有 `Comment` 结构加 `is_own`。
- **FR-7:** 两个端点遵循已上线的可见性规则：公开模板匿名可读；私有模板仅所有者（否则 404）。
- **FR-8:** 一个话题最多 **50 条回复**；第 51 条返回 400 并附友好信息（"此话题已满 —— 请发表新评论"）。这为不分页的回复响应设界。

### 5.3 通知

- **FR-9:** 发布回复应向父评论作者发送 `comment_reply` 通知（尽力而为、自我抑制），作为既有 `comment` 通知（发给模板所有者）之外的补充。若父评论作者同时是模板所有者，只发送 `comment` 通知（不重复）。
- **FR-10:** 通知载荷包含模板 id/标题、回复者显示名和回复摘要（前 100 字符），与既有通知载荷模式一致。

### 5.4 审核与生命周期

- **FR-11:** 删除顶层评论应在同一事务中删除其回复（级联）。`templates.comment_count` 仅递减 1（顶层评论本身）；父级的 `reply_count` 无关紧要（父级正被删除）。
- **FR-12:** 删除回复应事务性递减其父级的 `reply_count`；`templates.comment_count` 不变。
- **FR-13:** 管理员评论列表（`/admin/comments`）应显示 `parent` 列（顶层为 null，回复显示"回复 {作者}"），从管理台删除任何评论遵循 FR-11/FR-12 语义并保留既有强制理由 + 审计日志。
- **FR-14:** 编辑回复遵循既有编辑规则（15 分钟窗、仅更新 `updated_at`、不重排）；回复无论是否编辑都保持对话顺序（最旧在前）。

### 5.5 前端（普通用户界面）

- **FR-15:** 每个顶层 `CommentItem` 应渲染 `Reply` 操作（仅登录；匿名显示登录提示）。点击后在评论正下方打开内联回复编辑器（与主编辑器同组件的紧凑变体）。
- **FR-16:** `reply_count > 0` 时，条目渲染折叠的回复桶："View {N} replies ▾"（或"1 reply"）；点击展开并经 FR-6 懒加载回复；再点击折叠。展开状态为条目级组件状态（不持久化）。
- **FR-17:** 回复在父级下缩进渲染，使用既有 `CommentItem` 视觉（头像、名字、CREATOR 徽章、相对时间、已编辑标记、按既有权限规则的悬停编辑/删除操作）。
- **FR-18:** `has_creator_reply: true` 的话题在顶层评论时间戳旁显示"已解答"角标，以便读者找到已回答的问题（US-R9 的配套）。

## 6. 非功能需求

- **NFR-1（性能）:** 顶层列表成本不变（相同查询 + 两个新列）。回复按话题按需加载（≤ 50 行，单次索引查询）。无 N+1：`reply_count`/`has_creator_reply` 在顶层列表查询中计算（join 或子查询），而非逐条计算。
- **NFR-2（一致性）:** `reply_count` 使用与 `comment_count`/`like_count` 相同的事务性计数模式；并发回复下无漂移。
- **NFR-3（隐私）:** 回复可见性完全遵循已上线的评论可见性；无新数据暴露。通知摘要不超过回复的前 100 字符。
- **NFR-4（国际化）:** 所有新 UI 字符串在 `en` 和 `zh` 中存在且键集一致；回复编辑器、桶标签、"已解答"角标、话题已满错误均本地化。
- **NFR-5（无障碍）:** 话题是嵌套语义列表；展开/折叠是带 `aria-expanded` 的真实按钮；回复编辑器有标签；所有操作键盘可操作。
- **NFR-6（韧性）:** 回复列表请求失败仅在桶内显示内联错误 + 重试；评论区其余部分不受影响。回复发布失败保留草稿（既有模式）。
- **NFR-7（兼容性）:** 既有平铺评论（迁移后所有行的 `parent_comment_id` 为 null）渲染与今天完全一致。忽略 `reply_count`/`has_creator_reply` 的 API 消费者不受影响。`comment` 通知类型及其偏好条目仍然有效。

## 7. 验收标准

- **AC-1:** 已登录用户可回复顶层评论；回复（展开桶后）缩进显示在其下，最旧在前；父级 `reply_count` 递增；`templates.comment_count` 不变。
- **AC-2:** 回复一条回复时新回复挂到同一顶层话题（仅一级嵌套）；API 对指向回复的 `parent_comment_id` 返回 400。
- **AC-3:** 父评论作者收到带回复者名字和 ≤100 字符摘要的 `comment_reply` 通知；回复自己的评论不发通知；创作者在自己模板上回复只发送既有的 `comment` 通知给自己 —— 即无。
- **AC-4:** 有回复的话题显示"View N replies"；展开懒加载回复；折叠再展开不重新请求（组件状态缓存）。
- **AC-5:** 有创作者回复的话题在顶层评论上显示"已解答"角标。
- **AC-6:** 编辑/删除回复遵循与评论相同的 15 分钟窗和权限规则；删除回复递减 `reply_count` 且兄弟回复完好。
- **AC-7:** 删除顶层评论在同一事务中移除其回复；`comment_count` 恰好递减 1。
- **AC-8:** 话题的第 51 条回复返回 400 并附本地化的"话题已满"信息；UI 内联显示并保留草稿。
- **AC-9:** 速率限制对回复同样适用（5/分钟、50/天）；超限返回 429 附 `Retry-After` 和友好信息。
- **AC-10:** `/admin/comments` 显示 parent 列；删除回复或顶层评论（带理由）遵循级联规则并写入审计日志行。
- **AC-11:** 匿名访客可阅读公开模板的话题但回复时看到登录提示；私有模板的话题仅限所有者。
- **AC-12:** 既有平铺评论渲染不变（无桶、无角标、已上线评论 FVT 无回归）。
- **AC-13:** 所有新字符串在 `en` 和 `zh` 中存在；话题在两种语言和两种主题下正确渲染。

## 8. 范围之外（v1）

- 超过一级的多层嵌套（回复的回复平铺到顶层话题）。
- 回复文本中的 @提及（纯文本；独立的 mention-notifications 功能）。
- 回复表情/回应。
- 回复排序选项（仅最旧在前）。
- 50+ 回复话题的"continue this thread"分页（上限已处理）。
- 发布后修改回复目标。
- 折叠单条回复。
- 回复通知的邮件摘要。
- 创作者置顶回复。
- 向父级作者以外的人（如话题其他参与者）发送回复通知。
- 管理员话题视图 UI（v1 的管理列表 + parent 列已足够）。
- 任何货币化相关功能（按项目范围规则）。

## 9. 依赖与假设

- **D-1:** 模板评论已上线（提交 793a48f）：`template_comments` 表、Comment CRUD RPC、15 分钟编辑窗、作者或所有者删除、Redis 速率限制（5/分钟、50/天）、`comment_count` 维护、带理由 + 审计日志的管理员审核、`CommentsSection`/`CommentItem`/`CommentComposer`/`CommentEditForm` 前端组件。本功能扩展以上全部；无需返工。
- **D-2:** 通知系统支持类型化事件（`like`/`favorite`/`fork`/`comment`）；`comment_reply` 是新类型，需要：`notifications.type` CHECK 枚举扩展、notification-preferences 条目（该功能的类型列表是数据驱动的）、本地化通知文案。若偏好 UI 遵循其数据驱动设计，将自动渲染新类型。
- **D-3:** `Comment` proto 消息新增 `reply_count`、`has_creator_reply`，回复无需其他字段 —— `is_own` 已存在。`ListCommentsResponse` 除逐项新增外不变。
- **D-4:** REST 网关已路由 `/api/v1/comments/{id}`（更新/删除）；`/api/v1/comments/{id}/replies` 沿用相同模式。
- **D-5:** 已上线的评论 FVT（`test_template_comments`）覆盖平铺 CRUD/权限/审核；本功能为回复挂载规则、级联删除、计数器、通知和话题上限新增 FVT 用例。

## 10. 给架构师的开放问题

1. **`parent_comment_id` 约束:** 普通 UUID 列（推荐 —— 级联由服务层处理，与已上线的删除流程一致）还是外键 `REFERENCES template_comments(id) ON DELETE CASCADE`（数据库强制）。已上线表对 template/user 使用外键；自引用用哪种？
2. **回复上限:** 每话题 50 条（我的提议，为不分页响应设界）。替代：回复也分页（为罕见场景增加更多机制）。确认 50 或调整。
3. **`has_creator_reply` 计算:** 顶层列表查询中的子查询，还是回复插入时维护的反规范化标志（多一次写、读更便宜）。推荐：子查询（列表页 ≤ 50 行；索引化的父级查询很便宜）。
4. **通知类型命名:** `comment_reply`（推荐，与 `comment` 一致）还是 `reply`。另请确认 notification-preferences 需要迁移还是数据驱动渲染。
