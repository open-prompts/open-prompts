# 导出格式 — 需求分析

- **功能 ID：** export-formats
- **版本：** 1.0
- **状态：** Proposed（待架构评审）
- **作者：** ui-ux-agent
- **日期：** 2026-10-13
- **配套文档：** `export-formats-ui-ux-design-zh-CN.md`

## 1. 竞品调研

| 产品 | 导出能力 | 优势 | 不足 |
|---|---|---|---|
| PromptBase | 市场列表上的"复制提示词"按钮 | 一键消费 | 无结构化格式；无元数据 |
| FlowGPT | 提示词详情页复制到剪贴板 | 无摩擦 | 仅纯文本；变量无定界 |
| AIPRM | JSON 导出/导入用于团队迁移 | 结构化、元数据丰富 | 仅机器格式；人类不可读 |
| LangFlow | JSON 流程导出；Python/API 代码片段 | 面向开发者的多样性 | 对非技术用户过于复杂 |
| GitHub Gists | 任意格式的原始文件 | 通用 | 无提示词专属结构 |
| ChatGPT（自定义提示词） | 纯文本复制 | 简单 | 无结构、无变量 |

**结论：** 竞品分为两派：无摩擦但无结构的复制（PromptBase/FlowGPT），或结构化但仅限机器的导出（AIPRM/LangFlow）。没有人两者兼备：人类可读格式（文档用 Markdown、配置驱动工具用 YAML、聊天用纯文本）与既有 JSON 可移植格式并存。open-prompts 已拥有 JSON 往返（import-export）；增加消费格式补全了版图。

## 2. 问题陈述

用户在三种真实场景分享提示词：粘贴进聊天（需要带变量定界的干净文本）、嵌入文档/README（需要带元数据的 Markdown）、接入 n8n/LangChain 等配置驱动工具（需要 YAML）。今天他们必须手工转换 JSON 导出或手动清理渲染页面。模板详情页现有的复制操作只复制原始内容，没有变量定界、元数据或格式结构。

## 3. 目标用户

- **聊天用户** —— 把即填即用的提示词粘贴进任意 AI 聊天，变量清晰定界。
- **文档作者** —— 把提示词连同元数据放进 README、wiki 或团队文档。
- **自动化搭建者** —— 通过 YAML 把提示词接入 n8n、LangChain 或 CI 配置。
- **模板创作者** —— 以消费者想要的格式分享作品。

## 4. 用户故事

- **US-1**：作为聊天用户，我想把模板复制为带 `{{变量}}` 定界的纯文本，以便在任何聊天中粘贴并填写。
- **US-2**：作为文档作者，我想下载带标题、描述、标签和内容的 Markdown 文件，以便放进 README。
- **US-3**：作为自动化搭建者，我想下载 YAML 格式的模板，以便挂载到配置驱动工具。
- **US-4**：作为用户，我想在模板详情页有格式选择器，以便就地选择合适格式。
- **US-5**：作为用户，我想在复制/下载前看到格式化输出的实时预览，以便确切知道会得到什么。
- **US-6**：作为用户，我想选择导出版本（最新或特定历史版本），以便分享稳定快照。
- **US-7**：作为创作者，我希望导出遵守模板可见性，私有模板不被非所有者导出。
- **US-8**：作为键盘用户，我想通过既有快捷键触达格式选择器，不打断操作流。
- **US-9**：作为移动端用户，我希望有复制到剪贴板的格式，下载不是唯一选项。

## 5. 功能需求

- **FR-1**：模板详情页必须提供"导出"菜单，含四种格式：**Markdown (.md)**、**YAML (.yaml)**、**纯文本 (.txt)**、**JSON (.json)**（既有 import-export 格式，不变）。
- **FR-2**：所有格式必须在客户端由既有 `getTemplate`（选择特定版本时加 `getTemplateVersion`）响应生成；无新后端端点。
- **FR-3**：**纯文本**必须包含以 `{{变量}}` 形式呈现变量的模板内容，后接空行与 `Variables: a, b, c` 行（存在变量时）；无元数据头。
- **FR-4**：**Markdown** 必须包含：H1 标题、斜体描述段、项目符号标签列表、`**Type:**`/`**Category:**`/`**Language:**` 元数据行、`---` 分隔线、以围栏代码块呈现的内容（`{{变量}}` 形式）、以及结尾 `> Exported from open-prompts · <日期>` 行。
- **FR-5**：**YAML** 必须包含顶层键 `title`、`description`、`type`、`category`、`language`、`tags`（列表）、`variables`（名称列表）、`version`（所选版本号）、`exported_at`（ISO-8601）、以及保留换行的块标量（`|`）形式的 `content`。
- **FR-6**：**JSON** 必须与 import-export FR-2 格式在 schema 上字节一致（格式标识 `open-prompts-template`、格式版本 `1`），导出最新版本时含完整版本历史。
- **FR-7**：每种格式必须打开预览弹窗，在带行号的只读代码视图中展示确切输出，并提供**复制**与**下载**按钮。
- **FR-8**：下载文件名必须遵循 import-export FR-4 的 slug 规则：`<slug>-<id8>.<扩展名>`（如 `cold-email-template-a1b2c3d4.md`）。
- **FR-9**：预览弹窗必须包含默认为最新版本的版本选择器；选择旧版本时重新生成所有格式的预览。
- **FR-10**：复制必须使用 Clipboard API 并为旧浏览器回退到 `document.execCommand('copy')`，且必须显示"已复制"确认。
- **FR-11**：公开模板任何已认证用户均可导出；私有模板仅所有者可导出（与查看权限规则相同）。
- **FR-12**：任何格式的导出都不得包含所有者身份（用户 id、邮箱、显示名），与 import-export FR-6 一致。
- **FR-13**：Markdown/YAML/纯文本格式必须只包含所选版本的内容（不含版本历史）；仅 JSON 携带历史。
- **FR-14**：导出菜单必须可键盘操作（Tab 顺序、Enter/Space 打开、方向键选格式），并在模板详情页聚焦时作为 `E` 快捷键接入 keyboard-shortcuts 帮助面板。
- **FR-15**：生成失败（如剪贴板权限被拒）必须在弹窗内显示带重试的行内错误；下载失败回退为在新标签页打开数据。
- **FR-16**：四种格式必须在管理员模板详情页（`/admin/templates/:id`）同样提供，用于支持工作流。

## 6. 非功能需求

- **NFR-1（性能）**：100 KB 模板的格式生成在客户端 < 50 ms 完成；预览渲染无可感知延迟。
- **NFR-2（保真）**：内容绝不被改动 —— 只做包裹/定界。往返（导出纯文本 → 粘贴进聊天）保留内容主体的每个字符。
- **NFR-3（确定性）**：相同模板 + 版本 + 格式始终产生字节一致的输出（YAML/JSON 键序稳定、日期格式稳定）。
- **NFR-4（兼容性）**：YAML 输出是合法 YAML 1.2；Markdown 在 GitHub 风格 Markdown 下正确渲染；纯文本为 UTF-8、LF 换行。
- **NFR-5（安全）**：内容按格式正确转义（YAML 块标量、内容含 ``` 时 Markdown 代码围栏用四反引号），防止格式注入。

## 7. 验收标准

- **AC-1**：在公开模板上打开导出 → Markdown，显示含 H1 标题、元数据行、围栏内容与结尾导出来源行的预览；复制将完全相同的文本放入剪贴板。
- **AC-2**：导出 → YAML 产生可解析的 YAML，`content: |` 块标量保留所有换行；`variables` 列出内容中发现的每个 `{{名称}}`。
- **AC-3**：导出 → 纯文本仅产出内容 + `Variables: a, b, c` 行；无标题或元数据。
- **AC-4**：导出 → JSON 与 import-export 格式完全一致；导回 open-prompts 成功。
- **AC-5**：在预览中选择 6 个版本中的第 3 个，四种格式重新生成为版本 3 的内容，YAML 中 `version: 3`。
- **AC-6**：非所有者打开私有模板时无导出菜单（404 页面，与现状一致）。
- **AC-7**：下载 Markdown 产生 `cold-email-template-a1b2c3d4.md`（slug + id8 + 扩展名）。
- **AC-8**：剪贴板权限被拒时显示带重试的行内错误；预览文本保持可选中以便手动复制。
- **AC-9**：在模板详情页按 `E` 打开导出菜单；方向键 + Enter 无需鼠标即可选择格式。
- **AC-10**：含三反引号的内容导出为 Markdown 时使用四反引号外层围栏，在 GitHub 上正确渲染。

## 8. 不在范围内

- 从 Markdown/YAML/纯文本导入（导入仍仅限 JSON，见 import-export）。
- 多模板批量导出（已推迟；import-export 第 104 行已推迟批量）。
- PDF/DOCX/图片导出；用户自定义输出形状模板。
- 服务端导出端点；渲染某种格式的分享链接（template-qr-share 负责链接格式）。
- 任何形式的变现 —— 本产品永久不做。

## 9. 依赖与假设

- **D-1**：import-export 的 FR-2 JSON schema 是权威可移植格式；本功能原样复用（FR-6）。
- **D-2**：`getTemplate` 与 `getTemplateVersion` 响应包含所需全部字段（标题、描述、类型、分类、语言、标签、内容、从内容提取的变量）。
- **D-3**：变量提取遵循产品既有的 `{{变量}}` 约定（variable-presets、template-health-hints）。
- **D-4**：模板详情页已有复制操作；本功能以导出菜单替换/扩展它（UI 决策见配套文档）。
- **D-5**：预计无后端变更；若架构师倾向 YAML/Markdown 走服务端端点，此处格式定义不变。

## 10. 给架构师的开放问题

- **OQ-1**：本菜单的 JSON 导出应原样复用 import-export 的客户端组装（共享代码模块），还是建立共享"格式注册表"更可取？
- **OQ-2**：客户端变量提取（正则 `{{...}}`）是否可接受，还是后端应提供解析后的变量列表以避免与 variable-presets 漂移？
- **OQ-3**：YAML 的 `tags` 应为流式列表 `[a, b]` 还是块列表？（提案：块列表，可读性更好。）
- **OQ-4**：管理员控制台导出是否应包含额外管理员专属元数据（举报数、审核状态），还是与用户导出完全一致？
- **OQ-5**：`E` 快捷键是否与模板详情页既有绑定冲突？
