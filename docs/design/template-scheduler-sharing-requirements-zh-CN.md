# 模板定时分享 — 需求分析

- **Feature ID:** template-scheduler-sharing
- **Version:** 1.0
- **Status:** Proposed（待架构评审）
- **Author:** ui-ux-agent
- **Date:** 2026-10-12
- **Related docs:** [UI/UX 设计](./template-scheduler-sharing-ui-ux-design-zh-CN.md) · [English requirements](./template-scheduler-sharing-requirements.md)

## 1. 竞品调研总结

| 平台 | 定时方案 | 关键启示 |
|---|---|---|
| **Buffer / Hootsuite** | 先撰写内容，再选择未来时间点（提供"明天 9:00"等快捷预设），内容进入队列并在到期时自动上线 | 对常见场景而言，预设优于自由输入日期时间；带状态的队列/列表才是管理界面 |
| **WordPress** | 未来日期的文章获得 `scheduled` 状态，由 cron 任务在到期时发布；错过的执行会在下一轮补上 | 补执行语义很重要：停机绝不能让定时被静默丢弃 |
| **YouTube Studio** | "首映"定时：视频在指定时刻前保持私有；创作者列表显示 **Scheduled** 徽标和确切时间 | 内容列表中可见的徽标是创作者信任"定时确实生效"的方式 |
| **DocSend** | 临时分享：链接在 N 天后失效，过期时间对发送方可见 | 限时分享（"公开一周后自动转私有"）是一种独立且有价值的模式 —— 不只是延迟发布 |
| **Substack** | 定时在未来时间发送通讯；触发前横幅一直显示"scheduled for …" | 编辑界面中明确的"待执行"状态可防止意外重复定时 |
| **GitHub（gists/pages）** | 完全没有定时功能 | 模式必须来自内容发布平台 |
| **PromptBase / FlowGPT / Snack Prompt** | 无定时、无临时链接 | 差异化机会：没有任何竞品允许创作者安排发布时机或限时分享 |

**综合结论：** Open Prompts 目前唯一的可见性控制是即时的分享/取消分享开关（`TemplateDetails.js` 中的 `handleShare`/`handleUnshare`，通过完整的 `updateTemplate` 调用切换 `VISIBILITY_PUBLIC`/`VISIBILITY_PRIVATE`）。创作者无法安排发布时机（"明天上午受众在线时再公开我的 prompt"），也无法限时分享（"会议期间公开一周，之后自动转私有"）。template-qr-share 设计已明确预留"定时/临时分享链接（由 template-scheduler-sharing 负责）"。本特性新增面向所有者的、一次性的**可见性定时任务**：定时未来的 `publish` 或 `unpublish`（同一模板可同时挂起两者，构成分享窗口），由 webhooks 设计确立的 DB 轮询 ticker 模式执行（30 秒一轮、停机后补执行），配合 TemplateDetails 中的定时弹窗、带取消操作的待执行时间线、模板页与仪表盘卡片上的 Scheduled 徽标，并提供完整的 EN/ZH 双语支持。

## 2. 问题陈述

1. **发布是全有或全无且即时的。** 凌晨 1 点完成 prompt 的创作者要么立即分享（错过受众），要么记得稍后回来点击分享 —— 而往往忘记。
2. **无法限时分享。** "仅在活动期间分享" prompt 需要手动取消分享；没有任何机制自动将内容转回私有，导致过度分享的内容无限期地保持公开。
3. **待执行的自动化不可见。** 即使创作者打算稍后切换可见性，模板页和仪表盘都不会显示任何"将于 T 时刻公开"的状态 —— 没有什么可以信任或验证。
4. **平台没有调度器。** 后端没有任何 cron、ticker 或任务基础设施（已验证：`main.go` 中只有 gRPC 服务器 goroutine）；webhooks 设计引入的进程内 DB 轮询 ticker 是已接受的模式，本特性复用它。
5. **手动切换与自动化可能静默冲突。** 今天的分享按钮是一次完整的 `updateTemplate` 载荷；任何未来的自动化都必须明确说明如何与手动切换共存，否则创作者会被无法解释的可见性翻转吓到。

## 3. 目标用户

- **注重发布时机的创作者：** 在特定时刻（产品发布、通讯推送、活动开幕）公开 prompt。
- **限时分享者：** 让模板在有界窗口内公开（演示日、课程周），并确信它会自动转回私有。
- **批量发布者：** 起草多个 prompt 并希望各自在计划时间出现的创作者，无需守着分享按钮。
- **管理员：** v1 没有专门的管理界面（定时任务面向所有者；管理员删除模板会级联清除它们 —— 见 §8）。

## 4. 用户故事

- **US-1:** 作为创作者，我希望为模板安排在未来某时刻自动公开，以便在受众真正在线时发布。
- **US-2:** 作为创作者，我希望为模板安排在未来某时刻自动转私有，以便限时分享自动结束，无需我记得取消分享。
- **US-3:** 作为创作者，我希望组合两者（T1 发布、T2 取消发布），以便一次操作打开一个有界的分享窗口。
- **US-4:** 作为创作者，我希望在模板页上看到待执行定时任务及其确切时间，以便确信自动化已就绪。
- **US-5:** 作为创作者，我希望随时取消待执行的定时任务，以便计划变更时不必等待或撤销自动翻转。
- **US-6:** 作为创作者，我希望仪表盘卡片上有 Scheduled 徽标，以便一眼看出哪些模板有待执行的自动化。
- **US-7:** 作为创作者，我希望选择器中有快捷预设（明天上午、+1 天、+7 天），以便常见场景无需输入日期时间。
- **US-8:** 作为创作者，我希望时间以我自己的时区显示并带有明确标签，以便绝不会因 UTC 偏移而误读定时。
- **US-9:** 作为创作者，我希望看到最近执行和已取消的定时任务，以便确认自动化实际做了什么。
- **US-10:** 作为创作者，我希望手动分享/取消分享与待执行定时任务独立运作且待执行状态清晰可见，以便不会被遗忘的翻转吓到。
- **US-11:** 作为创作者，我希望定时任务在服务器重启后依然存在并在停机期间过期后补执行，以便部署绝不会静默丢弃我的发布计划。
- **US-12:** 作为用户，我希望定时界面提供完整的 EN/ZH 双语，以便语言从不是安排发布的障碍。

## 5. 功能需求

### 5.1 数据模型与 API

- **FR-1:** 新增 `template_schedules` 表：`id UUID PK`、`template_id UUID FK templates(id) ON DELETE CASCADE`、`user_id TEXT FK users(id) ON DELETE CASCADE`、`action TEXT NOT NULL CHECK (action IN ('publish','unpublish'))`、`run_at TIMESTAMPTZ NOT NULL`、`status TEXT NOT NULL CHECK (status IN ('pending','executed','cancelled'))`、`executed_at TIMESTAMPTZ`、`created_at/updated_at TIMESTAMPTZ`。约束：每个 `(template_id, action)` 最多**一个待执行定时**（已有待执行 publish 时再次创建 publish 会被拒绝并返回友好错误）；每用户最多 **20 个待执行定时**；创建时 `run_at` 必须在 `now + 1 分钟` 到 `now + 90 天` 之间。
- **FR-2:** REST API（会话鉴权、所有者限定；他人或非本人模板的 ID 返回 `not_found`，不泄露信息）：
  - `GET /api/v1/templates/{id}/schedules` — 待执行在前（按 `run_at` 升序），随后是最近 10 条已执行/已取消；响应项包含 `id, action, run_at, status, executed_at, created_at`。
  - `POST /api/v1/templates/{id}/schedules` — 请求体 `{action, run_at}`（带偏移的 RFC3339）；校验 FR-1 约束；返回 `201` 和创建的定时任务。
  - `DELETE /api/v1/schedules/{id}` — 取消调用者的**待执行**定时（`status → cancelled`）；取消已执行的定时返回 `409`。
  - 创建操作限流为**每用户每小时 30 个**（Redis 计数器，与现有 API 限流相同模式），防止刷量。

### 5.2 执行引擎

- **FR-3:** 调度器轮询（进程内 ticker，每 30 秒 —— 与 webhooks 重试调度器相同的模式和运维简洁性）选取到期行：`status = 'pending' AND run_at <= now()`，最旧优先，每轮最多 50 行。**补执行：** 服务器停机期间过期的定时任务会在重启后的第一轮执行（绝不静默丢弃）；执行按行幂等（以 `status` 作为守卫的先认领后执行）。
- **FR-4:** 执行语义：使用与手动切换相同的仓储路径将模板 `visibility` 翻转为 `public`（publish）或 `private`（unpublish），**不创建新模板版本、不触碰内容**（内容未变时版本分支本就跳过）；更新 `updated_at`；将定时标记为 `executed` 且 `executed_at = now()`。若模板已处于目标状态，定时仍标记为 `executed`（幂等空操作）。若模板已不存在，FK 级联已删除该行。执行不发送互动通知（notifications 表是互动形状的；见 §8）。
- **FR-5:** **与手动切换共存：** `handleShare`/`handleUnshare` 与待执行定时相互独立 —— 手动翻转不取消待执行定时，定时界面显著展示待执行定时（徽标 + 时间线），因此手动翻转绝不会让创作者意外。只要存在待执行定时，TemplateDetails 分享区域就显示持久提示（"已定时于 10 月 15 日 09:00 变为公开"）。

### 5.3 用户界面

- **FR-6:** TemplateDetails 中的**定时分享弹窗**（仅所有者；分享按钮旁的时钟图标"定时"按钮）：操作选择器（发布/取消发布，分段控件）、日期时间字段（原生 `datetime-local`，分钟粒度）配快捷预设（明天 09:00、+1 天同一时刻、+7 天同一时刻）、由浏览器推导的明确时区标签，以及实时预览语句（"该模板将于 2026 年 10 月 15 日 09:00（UTC+08:00）变为公开"）。行内校验：过去时间、超过 90 天、重复的待执行操作、达到上限。
- **FR-7:** 弹窗内的**待执行时间线**：该模板的待执行定时按序列出（操作图标、绝对本地时间 + 相对提示、带确认的取消按钮）；下方是折叠的"历史记录"区块，显示最近 10 条已执行/已取消的定时（状态徽标、执行或取消时间）。
- **FR-8:** **Scheduled 徽标：** TemplateDetails 所有者栏（仅所有者可见）和用户仪表盘模板卡片（时钟图标 + 简短相对时间，悬停显示确切时间）上显示带下一个待执行操作和时间的时钟徽标。点击徽标打开定时弹窗。
- **FR-9:** **时区处理：** `run_at` 以 UTC 存储；客户端发送带浏览器偏移的 RFC3339；所有显示时间以浏览器本地时区渲染并带明确的 `(UTC±HH:MM)` 标签；预览语句和时间线始终同时显示绝对时间和相对提示（"2 天后"）。
- **FR-10:** **仪表盘集成：** 用户仪表盘"我的模板"卡片在存在待执行定时时显示 Scheduled 徽标（数据通过现有列表查询扩展 `pending_schedule` 摘要字段获得）；v1 不新增仪表盘标签页。
- **FR-11:** **Toast 反馈：** 创建定时显示成功 toast（"已定时 —— 该模板将于 10 月 15 日 09:00 变为公开"）；取消显示确认对话框后跟成功 toast；徽标和时间线乐观更新，出错时回滚。
- **FR-12:** 所有定时界面文案以 EN/ZH 通过 react-i18next 提供（新增 `scheduling` 命名空间）；API 错误体保持机器可读的英文（API 契约，非 UI）。

## 6. 非功能需求

- **NFR-1（性能）:** 调度器轮询通过 `(status, run_at)` 上的 b-tree 索引实现 O(到期行数)；每轮最多处理 50 行。可见性翻转复用现有的单行模板更新 —— 无表扫描、无行级以外的锁。弹窗随模板加载一并发起一次 `GET` 获取定时列表。
- **NFR-2（可靠性）:** 定时任务由 DB 支撑（重启后持久）；补执行在停机后的第一轮执行过期行。先认领后执行（条件 `UPDATE … WHERE status='pending'`）使重叠轮询下也不可能重复执行。执行循环中的 panic 会被恢复并记录日志；单条坏行绝不阻塞整批。
- **NFR-3（安全）:** 所有端点会话鉴权且所有者限定；定时 ID 为不可猜测的 UUID；他人 ID 返回 `not_found`。`run_at` 在服务端校验（窗口、RFC3339 解析）—— 客户端校验仅为体验。无新数据暴露：定时任务只包含可见性意图，绝不含内容。
- **NFR-4（一致性）:** 定时翻转使用与手动分享/取消分享开关相同的仓储可见性更新，因此两条路径的行为绝不分叉（封禁所有者隐藏、公开列表过滤、embed 检查都读取同一个 `visibility` 列）。
- **NFR-5（可观测性）:** 每次执行记录一条结构化日志（定时 ID、模板 ID、操作、计划时间 vs 实际时间、结果），级别 info；跳过的空操作和补执行在日志中可区分。历史列表是面向用户的镜像。
- **NFR-6（国际化）:** 弹窗、徽标、时间线、历史、toast 和校验错误全部双语（EN/ZH）；API 载荷中的操作名保持英文（`publish`/`unpublish`，机器契约）。

## 7. 验收标准

- **AC-1:** 所有者定时"明天本地 09:00 发布"；模板在此之前保持私有；09:00 后 60 秒内模板出现在公开列表且详情页可匿名访问；定时在历史中显示为 `executed` 及执行时间。
- **AC-2:** 所有者定时"T1 发布"和"T2 取消发布"（T2 > T1）；模板在 T1 与 T2 之间公开、之后私有，两个定时按序执行并列在历史中。
- **AC-3:** 通过时间线取消的待执行定时绝不触发；它在历史中显示为 `cancelled`；取消已执行的定时返回 `409` 且 UI 阻止该操作（取消按钮仅在待执行行上）。
- **AC-4:** 已有待执行 `publish` 时为同一模板创建第二个待执行 `publish` 失败并显示友好的重复错误；用户的第 21 个待执行定时失败并显示上限错误；过去或超过 90 天的 `run_at` 在前端和服务端都被拒绝。
- **AC-5:** 服务器在定时 `run_at` 过去后重启；启动后第一轮执行它（补执行），日志标记为补执行，模板可见性反映翻转结果。
- **AC-6:** 定时翻转不创建新模板版本（版本数不变）、不修改内容、不向任何人发送互动通知。
- **AC-7:** 所有者手动取消分享一个有待执行 publish 的模板；模板立即私有，待执行定时仍然可见（徽标 + 时间线），并在 `run_at` 时再次变为公开 —— 弹窗的提示事先已明确此行为。
- **AC-8:** 为已公开的模板定时 `publish` 成功创建并作为幂等空操作执行（`executed`、可见性不变、日志标记空操作）。
- **AC-9:** TemplateDetails 所有者栏显示带下一个待执行操作和时间的时钟徽标；有待执行定时的模板的仪表盘卡片显示徽标；点击任一徽标打开定时弹窗并聚焦时间线。
- **AC-10:** 预览语句和时间线显示带明确 `(UTC±HH:MM)` 标签的绝对本地时间加相对提示；不同时区的用户看到正确转换的时间（UTC 存储、本地渲染）。
- **AC-11:** 非所有者看不到定时按钮，直接调用他人模板定时 API 返回 `not_found`；匿名 API 调用返回 `401`。
- **AC-12:** 整个定时界面（弹窗、徽标、时间线、历史、toast、错误）以 EN 和 ZH 完整渲染，无未翻译文案。

## 8. 不在范围内（v1）

- 循环定时（如"每个工作日 9–17 点公开"）—— v1 仅一次性操作。
- 非可见性操作的定时（定时删除、定时版本固定）。
- 定时执行时的邮件或应用内通知（notifications 表是互动形状的；系统通知渠道是独立特性）。
- 面向定时任务的管理控制台（平台级待执行自动化视图）。
- 仪表盘批量定时（批量操作由 bulk-operations 负责）。
- 秒级粒度或显式时区定时（v1 使用浏览器本地输入、分钟粒度）。
- *链接*的过期分享（qr-share 负责链接层面；本特性只定时模板可见性）。

## 9. 依赖与假设

- **D-1:** template-qr-share（设计）已明确预留"定时/临时分享链接（由 template-scheduler-sharing 负责）"（其 §8 第 99 行）—— 无冲突；本特性定时模板可见性，而非链接过期。
- **D-2:** 可见性模型是现有的 `templates.visibility`（`CHECK(public, private)`）；手动开关是 `handleShare`/`handleUnshare`（`TemplateDetails.js:549–610`）调用带完整载荷的 `updateTemplate` —— 定时路径复用仓储层可见性更新，而非客户端载荷。
- **D-3:** 进程内 DB 轮询 ticker（30 秒一轮、到期扫描、无外部队列）是 webhooks 设计 D-3 确立的已接受调度模式；本特性新增第二个 ticker（或共享一个 —— 见 §10 问题 1）。
- **D-4:** `UpdateTemplate` 的版本分支在内容未变时跳过版本创建（`prompt.go:~284–310`），因此仅可见性翻转不会增加版本号 —— 本特性依赖的已验证行为。
- **D-5:** TemplateDetails 所有者操作栏（分享/Fork/编辑/删除）是定时按钮的插入点；user-dashboard 设计的模板卡片是徽标的插入点（其卡片组件支持元信息徽标）。
- **D-6:** notifications 表是互动形状的（`template_id`/`actor_id` NOT NULL）—— 这是 v1 不提供执行通知的原因（与 webhooks 设计结论相同）。

## 10. 给架构师的开放问题

1. **一个 ticker 还是两个：** 共享 webhooks 的 30 秒 ticker 循环（单个 goroutine、两个到期扫描）还是每特性独立 goroutine —— 部署方案是否倾向于从一开始就引入统一的调度器抽象？
2. **表还是列：** `template_schedules`（可审计、可扩展到循环）还是 `templates` 上两个可空列 `publish_at`/`unpublish_at`（更简单、无 join）—— 哪个更符合 schema 规范？
3. **认领机制：** 条件 `UPDATE … WHERE status='pending'` 作为认领（假设，单实例安全）还是 `SELECT … FOR UPDATE SKIP LOCKED`（仅在多实例部署时需要）—— 多实例是否在路线图上？
