# 模板链接与引用（Template Linking & References）— 需求分析

- **Feature ID:** template-linking-references
- **Version:** 1.0
- **Status:** Proposed（待架构评审）
- **Author:** ui-ux-agent
- **Date:** 2026-10-12
- **相关文档：** [UI/UX 设计](./template-linking-references-ui-ux-design-zh-CN.md) · [Requirements (EN)](./template-linking-references-requirements.md)

## 1. 竞品调研总结

| 平台 | 引用/链接方案 | 关键启示 |
|---|---|---|
| **GitHub（README + "Used by"）** | 作者在 README 中链接相关仓库；GitHub 自动计算 "Used by" 反向链接（依赖图） | 作者声明的链接承载意图（"为什么相关"）；自动计算的反向链接在另一个方向创造发现闭环 |
| **Stack Overflow（"Linked" / "Related"）** | "Linked" = 作者/社区声明的重复与配套问题（左侧栏）；"Related" = 算法推荐（右侧栏） | 两者在视觉和语义上分离 —— 声明的链接是精选且少量的；算法的是大量且排序的。两者共存不混淆 |
| **Wikipedia（"See also" + "What links here"）** | "See also" 由编辑者精选，偶带一行说明；"What links here" 是工具页的反向链接视图 | 每条链接一个简短可选注释（"流式处理变体见此"）是价值最高的标注；反向链接放在次级界面而非内联 |
| **PromptBase / FlowGPT / Snack Prompt** | 无作者声明的交叉链接；只有算法"相似 prompt"推荐栏 | Prompt 平台尚未构建此功能 —— Wikipedia/Stack Overflow 模式是应引入的范本 |
| **npm（依赖）** | 包作者声明依赖；使用者遍历依赖图 | 声明的边成为用户真正会遍历的导航图 —— 每条边都是一次发现旅程 |

**综合分析：** Open Prompts 目前有两种连接类型 —— 算法相似（related-templates 设计：基于标签/模型的推荐栏）和 fork 谱系（template-remix-forks-tree 设计：系统记录的祖先关系）。缺失的是**作者声明的边**："既然你在这里，也看看我挑选的这些模板。"这就是 Wikipedia 的 "See also" 模式：作者最清楚哪些模板与自己的互补（"系统提示词"链接配套的"用户提示词"、v2 链接它取代的 v1、适合链式调用的模板链接其兄弟篇）。设计：`template_references` 表（源、目标、可选 200 字符注释、位置），通过详情页的选择器弹窗由所有者管理，渲染为精选的"引用"小节 —— 与算法推荐栏视觉区分 —— 加上"被引用"反向链接小节（仅公开来源，隐私安全）。轻量 `GET /templates/lookup?q=` 端点为选择器提供搜索，不依赖未上线的 search-filtering 功能。尽力而为的 `reference` 通知在模板被引用时告知创作者，遵循既有的互动通知模式。

## 2. 问题陈述

1. **作者无法指向任何地方。** 模板页是死胡同：作者无法说"这与 X 配对"或"这取代了我的旧 Y"。唯一的交叉导航是算法推荐栏，作者无法控制。
2. **互补模板是分散的。** 配对的 system/user 提示词、多部分系列、替代变体作为无关的行存在于列表中；用户必须搜索（搜索上线后）或翻分类页才能凑齐一套。
3. **算法推荐栏无法表达意图。** related-templates 按共享标签/模型排序；它无法知道模板 B 是 A 的*前身*还是*配套*件。只有作者能声明这一点，而一条简短注释解释了原因。
4. **被引用的创作者永远不知情。** 当有人基于或引用某模板构建时，其所有者得不到任何信号 —— 不像点赞/收藏/fork 都有通知。
5. **没有反向链接发现。** 即使链接单向存在，目标模板的受众也无法发现"谁指向这里" —— 反向边正是偶然发现发生的地方（GitHub "Used by"、Wikipedia "What links here"）。

## 3. 目标用户

- **模板作者：** 精选引用以引导用户找到互补作品和系列；需要带搜索的快速选择器。
- **浏览者/集成者：** 遍历作者精选的链接以凑齐完整 prompt 集合；比算法更信任声明的链接。
- **被引用的创作者：** 得知作品被引用；通过反向链接获得发现渠道。
- **管理员：** 无需专门界面（引用是用户内容；若 content-reporting 扩展到引用则适用审核流程 —— 不在此范围）。

## 4. 用户故事

- **US-1:** 作为作者，我希望在模板页链接相关模板并附可选的一行注释，这样用户能找到我指定的配套件。
- **US-2:** 作为作者，我希望有一个可搜索（按标题）的选择器，列出公开模板和我自己的私有模板，这样添加引用只需几秒。
- **US-3:** 作为作者，我希望能重排和删除引用，这样随着集合演进小节保持精选。
- **US-4:** 作为作者，我希望强制上限（10 条）并有清晰提示，这样小节永远不会变成链接堆场。
- **US-5:** 作为浏览者，我希望引用显示为带标题、作者、注释和统计数据的卡片，这样能判断是否跟随每条链接。
- **US-6:** 作为浏览者，我希望作者精选小节与算法"相关"推荐栏视觉区分，这样能理解链接是谁选的、为什么。
- **US-7:** 作为创作者，我希望模板上有"被引用"小节，这样能看到谁引用了我的作品并从中获得流量。
- **US-8:** 作为创作者，我希望有人引用我的公开模板时收到通知，这样无需手动检查反向链接就能发现引用。
- **US-9:** 作为用户，我希望私有模板绝不通过引用泄露（既不作为他人可见的目标，也不作为反向链接来源），这样可见性保证成立。
- **US-10:** 作为移动端用户，我希望引用小节和选择器在单列下工作，这样在任何设备上都能精选。
- **US-11:** 作为用户，我希望引用链接永不 404（被删目标干净消失），这样小节永远可信。
- **US-12:** 作为非英语用户，我希望整个引用体验是我的语言（EN/ZH），这样精选和浏览在两种语言下都是一等公民。

## 5. 功能需求

### 5.1 数据模型

- **FR-1:** 新表 `template_references`：`id UUID PK DEFAULT uuid_generate_v4()`、`source_template_id UUID NOT NULL REFERENCES templates(id) ON DELETE CASCADE`、`target_template_id UUID NOT NULL REFERENCES templates(id) ON DELETE CASCADE`、`note VARCHAR(200)`（可空）、`position INT NOT NULL DEFAULT 0`、`created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()`。约束：`UNIQUE(source_template_id, target_template_id)`、`CHECK (source_template_id <> target_template_id)`、`CHECK (char_length(note) <= 200)`。索引：`(source_template_id, position)` 用于出站列表，`(target_template_id)` 用于反向链接。

### 5.2 管理 API（源所有者）

- **FR-2:** `POST /api/v1/templates/{id}/references` — 仅所有者（他人 403，匿名 401）。体 `{target_id: UUID, note?: string}`。校验：目标存在（404 `template_not_found`）；目标公开**或**属于同一用户（他人的私有 → 404，绝不 403，避免存在性泄露）；无自引用（400 `self_reference`）；无重复对（409 `duplicate_reference`）；源已有 < 10 条引用（400 `reference_limit_reached`）；注释 ≤ 200 字符（400）。返回带目标摘要的已创建引用。
- **FR-3:** `DELETE /api/v1/templates/{id}/references/{referenceId}` — 仅所有者；引用不属于此源时 404。幂等式（缺失 404）。
- **FR-4:** `PATCH /api/v1/templates/{id}/references/order` — 仅所有者。体 `{order: [referenceId, …]}` 必须恰好包含该源当前全部引用 ID 的期望顺序；服务端在一个事务中原子地重排 `position` 为 0..n。ID 集合不匹配 → 400。

### 5.3 读取 API

- **FR-5:** `GET /api/v1/templates/{id}/references` — 模板公开（任何人含匿名）或调用者是其所有者时可见。返回有序引用，每条含 `id`、`note`、`position`、`created_at` 和目标摘要（`target_id`、`title`、`owner_id`、`owner_display_name`、`like_count`、`favorite_count`、`fork_count`、`visibility` —— 包含 visibility 以便所有者看到自己的私有目标标记）。私有模板 + 非所有者 → 404（与模板详情行为一致）。
- **FR-6:** `GET /api/v1/templates/{id}/references/inbound` — 反向链接：目标为该模板的引用，**仅来自公开来源**（私有来源的出站引用是其所有者的事务；它们绝不作为反向链接出现在任何人面前，包括目标所有者）。每条：来源摘要（id、标题、作者显示名、like_count）+ 注释。可见性规则与 FR-5 相同。
- **FR-7:** `GET /api/v1/templates/lookup?q=&limit=` — 选择器搜索。认证可选。`q`（最少 1 字符）对 `title` 做大小写不敏感的子串匹配；返回最多 `limit`（默认 10，最大 20）个公开**或**属于调用者的模板，按 `like_count DESC, title ASC` 排序；排除正在编辑的模板（`exclude_id` 参数）以及所有者屏蔽了调用者/被调用者屏蔽的模板（block-users 规则）。响应项：`id`、`title`、`owner_display_name`、`visibility`、`like_count`、`fork_count`。

### 5.4 UI

- **FR-8:** 模板详情页新增**引用**小节（提示词生成器之下、别名之上）：有序卡片（标题、作者、可选的弱化注释、点赞/fork 数、链接到 `/templates/{target_id}`）；最多 10 条。非所有者仅在 ≥ 1 条引用时看到小节；所有者始终看到，带"添加引用"按钮、每卡片删除（×）和上下移动箭头，以及空状态（"暂无引用 —— 链接相关模板"）。
- **FR-9:** 模板详情页新增**被引用**小节（引用之下，默认折叠带计数）：反向链接卡片（来源标题、作者、注释）链接到来源。为空时完全隐藏。此界面不可编辑。
- **FR-10:** **引用选择器弹窗**（所有者，从"添加引用"进入）：搜索输入（防抖 300ms，最少 1 字符）请求 `/templates/lookup`；结果行（标题、作者、所有者自己私有命中的可见性徽章、点赞/fork 数）带"添加"操作；添加时提示可选注释（内联字段，200 字符计数器）并立即 POST（按操作持久化，与别名管理器模式一致）；当前列表显示在顶部，可删除/重排；"完成"关闭。错误（达到上限、重复）在弹窗内联显示。
- **FR-11:** **引用通知：** 当创建的引用目标是其他用户拥有的公开模板时，向目标所有者发出新类型 `reference` 的通知（尽力而为；no_self；任一方屏蔽另一方时抑制；接收者通知偏好关闭 `reference` 时抑制）。通知深链到*源*模板。
- **FR-12:** **删除语义：** 删除目标模板通过 CASCADE 移除其入站引用行（源的小节直接缩短 —— 无死卡片）；删除源移除其出站行；fork 模板**不**复制其引用（fork 从干净状态开始，与当前 `ForkTemplate` 行为一致）。

## 6. 非功能需求

- **NFR-1（性能）：** 引用和反向链接与详情页既有加载特性一致：两条索引查询（FR-1 索引），各 ≤ 10 行，联表 templates/users 取摘要。Lookup 是单条索引 `ILIKE` 加 LIMIT —— v1 规模下 p99 < 50 ms。
- **NFR-2（隐私/安全）：** 无存在性泄露：FR-2 中他人的私有模板与不存在的模板不可区分（404 而非 403）；反向链接只暴露公开来源（FR-6）；lookup 只返回公开 + 自己的（FR-7）；私有模板的引用列表仅所有者可见（FR-5）。所有管理路由服务端重新校验所有权。
- **NFR-3（一致性）：** 引用卡片复用既有模板卡片视觉语言（PromptCard 衍生的紧凑行）；选择器复用别名管理器交互模式（搜索 → 添加 → 立即持久化）；通知复用互动通知管道。
- **NFR-4（限制）：** 服务端强制硬上限：每源 10 条引用、200 字符注释、lookup limit ≤ 20。UI 镜像上限（10 条时禁用添加、实时注释计数器）让用户不会意外撞上服务端错误。
- **NFR-5（无障碍）：** 引用列表是语义化的链接列表；重排箭头和删除按钮可键盘操作且有可辨识名称；选择器是带标签的搜索组合框（结果播报）；折叠的"被引用"是带 `aria-expanded` 的标准展开按钮。
- **NFR-6（国际化）：** 所有字符串（小节标题、空状态、选择器、错误、通知文案）通过 react-i18next 提供 EN/ZH；用户撰写的注释原样存储，绝不机器翻译。

## 7. 验收标准

- **AC-1:** 所有者添加指向公开模板的引用并附注释"配套用户提示词" → 201；引用小节显示带注释的卡片；刷新后顺序保留。
- **AC-2:** 非所有者对模板引用的 POST/DELETE/PATCH → 403；匿名 → 401；无状态变化。
- **AC-3:** 引用其他用户的私有模板 → 404 `template_not_found`（与不存在的 ID 响应一致）；引用未创建；私有模板的任何信息未泄露。
- **AC-4:** 自引用 → 400 `self_reference`；重复对 → 409 `duplicate_reference`；两者都在选择器中内联提示。
- **AC-5:** 添加第 11 条引用 → 400 `reference_limit_reached`；选择器的添加按钮在 10 条时禁用并显示上限提示。
- **AC-6:** 匿名 GET 公开模板的引用 → 带目标摘要的完整有序列表；私有模板（非所有者）→ 404。
- **AC-7:** 公开 A 引用 B → B 的"被引用"显示 A。私有 C 引用 B → B 的反向链接对任何人（包括 B 的所有者和管理员通过此界面）不显示来自 C 的任何内容。
- **AC-8:** `q=sql` 的 lookup 返回标题包含 "sql"（大小写不敏感）的公开模板（及调用者的私有模板），排除 `exclude_id`，遵守 limit，并隐藏被屏蔽/屏蔽中所有者的模板。
- **AC-9:** 箭头重排持久化（PATCH order）；任何删除后 position 为 0..n-1 无间隙。
- **AC-10:** 创建指向其他用户公开模板的引用时向该所有者发出 `reference` 通知，深链到源；自引用不发出；被屏蔽对和偏好关闭的接收者不发出。
- **AC-11:** 删除被引用的目标会从所有引用小节移除其卡片（无 404 链接）；删除源移除其出站引用及反向链接贡献。
- **AC-12:** 所有 UI 字符串以 EN 和 ZH 渲染；选择器、空状态、错误消息和通知文案完全翻译；注释逐字显示。

## 8. 不做范围（v1）

- 引用*类型*（如"取代"、"依赖"、"变体"）—— 仅自由文本注释。
- 指向非模板实体（合集、链、用户、外部 URL）的引用。
- 创建后编辑注释（删除 + 重新添加等效；如有需求再议）。
- fork 时复制引用或 fork 感知的"继承引用"徽章。
- 引用分析（点击计数）。
- 选择器内的算法建议（"你可能还想链接……"）。
- 引用注释的审核/举报（content-reporting 扩展 —— 独立功能）。
- 批量引用管理（bulk-operations 扩展）。

## 9. 依赖与假设

- **D-1:** `templates` 表和详情页保持现状；小节嵌入既有详情布局（提示词生成器之下、所有者专属别名小节之上）。
- **D-2:** notifications 的 `type` CHECK 增量扩展（如为 `comment` 所做及为 `comment_reply`/`mention` 计划的）加入 `reference`；notification-preferences 增加 `reference` 列（其设计指定了数据驱动的类型列表正是为此扩展）。
- **D-3:** block-users FR-7/FR-9 语义（不与被屏蔽用户内容互动、双向通知抑制）适用于 lookup 结果和引用通知。
- **D-4:** 选择器的 lookup 端点自包含（标题 ILIKE），刻意**不**依赖未上线的 search-filtering 功能（其面向主列表并含内容匹配）；若 search-filtering 先上线，lookup 可委托给它。
- **D-5:** 别名管理器（TemplateAliasManager）确立了选择器遵循的所有者专属、按操作持久化管理模式；PromptCard 确立卡片视觉语言。
- **D-6:** related-templates（算法栏）和 template-remix-forks-tree（谱系）保持独立小节；本功能的小节标注并样式化为作者精选以避免混淆（见 §10）。

## 10. 给架构师的开放问题

1. **小节共存：** 详情页将有引用（精选）、被引用（反向链接）、相关（算法）、Forks（谱系）—— 四个小节是否太多？选项：合并到一个"关联"标题下的标签页，或将算法栏与作者精选合并（精选在前、算法在后、视觉标记）？
2. **通知类型扩展：** `reference` 加入 CHECK 是与 `comment_reply`/`mention` 同一迁移（一次扩展）还是每功能单独？
3. **反向链接隐私：** 私有来源的引用是否应作为弱化的"私有来源"行对*目标*所有者可见（GitHub 向父仓库所有者显示私有 fork），还是按设计完全隐藏（Wikipedia 模式）？当前设计：完全隐藏。
4. **Lookup 排序：** like_count DESC 偏向热门模板；是否应改为新近度或精确前缀匹配优先？
5. **注释可编辑性：** v1 接受删除重加，还是现在就包含对引用的 PATCH（注释文本）（加上很便宜）？
6. **Position 语义：** 每次删除都密集重排 0..n-1（如设计）还是只追加带间隙的 position（写更少）？
7. **引用通知是否在载荷中包含注释文本**（作者撰写且 ≤ 200 字符）还是只通知引用事实？
