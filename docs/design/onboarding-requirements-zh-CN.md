# 新手引导体验 — 需求分析

- **Feature ID:** onboarding
- **Version:** 1.0
- **Status:** Proposed（待架构评审）
- **Author:** ui-ux-agent
- **Date:** 2026-10-10

## 1. 竞品研究总结

| 平台 | 新手引导做法 | 关键启示 |
|---|---|---|
| **GitHub** | 注册后清单（"验证邮箱、添加头像、创建仓库"）带进度条；任务链接直达操作位置；可关闭 | 清单模式比导览更能驱动激活；每个条目必须直接链接到操作发生的地方 |
| **Notion** | 欢迎模态框 + 模板库入口；渐进式"入门"页面；带 CTA 的友好空状态 | 空状态就是引导界面 —— 每一个"这里还没有内容"的屏幕都应该教用户下一步 |
| **ChatGPT** | 极低摩擦：注册 → 直达产品；首次使用时上下文提示 | 不要用向导挡住产品；让用户立即开始、内联引导 |
| **PromptBase** | 商店优先：立即浏览市场；只有点击"出售"时才进入卖家引导 | 对提示词平台，先展示价值（浏览模板）再要求设置工作，顺序是对的 |
| **FlowGPT** | 直达信息流；创建入口靠显眼按钮；无引导式 onboarding | 没有引导就把激活交给运气 —— 我们目前的缺口 |
| **AIPRM** | 扩展安装流程兼作引导；安装时选择模板分类 | 早期问一个轻量的偏好问题即可个性化首屏 |
| **Reddit** | 注册后兴趣选择器 → 个性化信息流 | 单步个性化（选分类）能显著提升首次会话参与度 |

**综合结论：** Open Prompts 目前在注册后把新用户直接丢到首页网格，零引导。v1 的制胜模式组合：(1) 注册后一次性欢迎模态框（价值主张 + "开始使用"）；(2) 首页侧栏区域可关闭的进度清单，4 个激活任务直达各自操作位置并通过现有 API 自动勾选；(3) 所有"空空如也"的地方提供带 CTA 的上下文空状态。不做强制向导、不做阻断式导览 —— 产品保持立即可用，引导是环境式的。所有任务检测都使用现有端点（profile、templates、API keys、prompts），v1 零后端改动。

## 2. 问题陈述

1. **无激活引导。** 注册后用户落在首页网格，完全不知道产品的关键动作是什么（创建模板、生成 API key、通过 SDK 使用提示词）。发现全靠运气。
2. **无欢迎时刻。** 注册以静默跳转到 `/` 结束。没有"你已加入，这能给你带来什么"的时刻，而竞品正是在这里建立价值认知。
3. **空状态是死胡同。** `home.no_results`（"No templates found."）是一句裸文案，没有任何指引：新用户在筛选无结果时看到一堵空墙，没有 CTA。"我的模板"空视图同样没有"创建你的第一个模板"的提示。
4. **关键工作流不可见。** API key → SDK 集成路径（产品的核心开发者闭环）只能通过个人资料下拉菜单找到 API Keys 页面。新开发者常常永远发现不了它。
5. **无进度反馈。** 确实去探索的用户得不到任何确认；没有"我已全部设置好"的感觉。
6. **首次会话流失风险。** 以上问题叠加：最可能流失的用户（首次会话）得到的支持反而最少。

## 3. 目标用户

- **新注册用户（主要）：** 刚完成邮箱+验证码注册；需要了解 4 个激活动作并获得方向感。
- **新开发者用户：** 为 SDK/API 而来；需要找到 API key 生成和模板页上的 SDK 代码片段。
- **从未激活的回访用户：** 早已注册但从未创建模板或 key；清单（若未关闭）继续引导他们。
- **管理控制台用户：** v1 不在范围内（管理控制台是内部使用；见 §8）。

## 4. 用户故事

- **US-O1:** 作为新用户，注册成功后立即看到欢迎模态框，说明我能在这里做什么，从而获得方向感而不是被丢进网格。
- **US-O2:** 作为新用户，我可以一键关闭欢迎模态框并立即开始浏览，引导绝不阻断我。
- **US-O3:** 作为新用户，我看到 4 个设置任务（完善资料、创建第一个模板、生成 API key、使用提示词）的清单和进度，从而知道下一步做什么。
- **US-O4:** 作为用户，每个清单条目直接链接到操作发生的位置，从而无需自己寻找。
- **US-O5:** 作为用户，当我在应用任何地方完成动作时，清单条目自动勾选，从而无需手动管理清单。
- **US-O6:** 作为用户，我可以关闭清单，它绝不会变成干扰。
- **US-O7:** 作为用户，完成全部 4 个任务后看到庆祝完成态，从而有"设置完毕"的感觉。
- **US-O8:** 作为用户，当列表或视图为空时，我看到带明确下一步动作的空状态（如"创建你的第一个模板"），空屏幕教会我而不是让我碰壁。
- **US-O9:** 作为用户，当筛选无结果时，空状态帮我恢复（清除筛选 / 浏览全部），从而不会卡住。
- **US-O10:** 作为用户，首次访问 API Keys 页面时，空状态解释 key 的用途，从而在创建前理解这个功能。
- **US-O11:** 作为中文用户，所有引导界面完全翻译，从而首次体验就是我的语言。
- **US-O12:** 作为键盘/读屏用户，欢迎模态框和清单完全无障碍（焦点圈定、标签、进度播报），引导对我同样有效。
- **US-O13:** 作为已完成设置动作的回访用户，清单出现时就是已完成状态（或全部完成时根本不出现），从而不会被要求重做。

## 5. 功能需求

### 5.1 欢迎模态框（注册后）

- **FR-1:** 注册成功后跳转到 `/` 时，显示一次性欢迎模态框（localStorage 标记 `onboarding.welcome_dismissed`）。
- **FR-2:** 模态框包含：带用户显示名称的问候、3 行价值主张（浏览并使用社区模板 / 创建并版本化你自己的模板 / 通过 API key + SDK 集成）、主按钮"开始使用"和次要动作"浏览模板"。
- **FR-3:** "开始使用"关闭模态框并展示/滚动到清单；"浏览模板"关闭模态框并聚焦模板网格。
- **FR-4:** 模态框可通过 Escape、遮罩点击和关闭按钮关闭；任何关闭方式都设置标记，使其不再出现（按浏览器）。
- **FR-5:** 模态框不得在已有账号登录时出现 —— 只在注册后的首次导航出现。

### 5.2 激活清单

- **FR-6:** 已认证用户在首页看到"Onboarding"卡片（桌面端在侧栏列，移动端在网格上方），条件是：未关闭 且 未全部完成。
- **FR-7:** 清单恰好 4 个条目，各有完成状态、标签和深链：
  1. 完善你的资料 → `/profile`
  2. 创建你的第一个模板 → 打开创建模板模态框
  3. 生成 API key → `/api-keys`
  4. 使用一个提示词 → 第一个公开模板的详情页（无则首页网格）
- **FR-8:** 完成检测（首页挂载时，仅在卡片可见期间）：
  - 资料完善：`getProfile()` 返回 display_name 且 avatar（email 恒存在）。
  - 拥有模板：`getTemplates({ owner_id: user.id })` 返回 ≥1（任意可见性）。
  - 拥有 API key：`listAPIKeys()` 返回 ≥1 个活跃 key。
  - 拥有提示词：`listPrompts({ owner_id: user.id })` 返回 ≥1。
- **FR-9:** 检测不得阻塞渲染：各检查完成前条目显示为待定状态；失败静默降级为"未完成"（不弹错误 toast）。
- **FR-10:** 完成状态也实时更新：用户在别处完成动作（创建模板、生成 key）后回到首页，挂载时重新检测即可覆盖；无需后台轮询。
- **FR-11:** 进度指示："2 of 4" 文本 + 进度条（百分比宽度），通过 `aria-live` 礼貌地播报给读屏器。
- **FR-12:** 未完成条目是链接/按钮；已完成条目显示勾选图标且不再是链接（无障碍：看起来禁用但不可聚焦）。
- **FR-13:** "关闭"入口（×）永久隐藏卡片（localStorage `onboarding.checklist_dismissed`）。
- **FR-14:** 4 项全部完成时：卡片显示完成态（"You're all set!"），使用 Aurora 强调色和成功图标（无撒花动效），附"浏览模板"链接，并在下次导航后自动隐藏（设置标记 `onboarding.checklist_completed`）。
- **FR-15:** 若首次渲染时 4 项已全部完成（回访用户），卡片完全不出现（直接进入完成标记）。

### 5.3 上下文空状态

- **FR-16:** 首页"无结果"（筛选无匹配）：插图/图标 + 上下文文案 + 动作："清除筛选"（恢复默认视图）和（若已认证）"创建模板"。
- **FR-17:** "我的模板"为空（owner 筛选、无模板）："你还没有创建任何模板" + 主 CTA"创建你的第一个模板"（打开创建模板模态框）。
- **FR-18:** API Keys 页为空（无 key）：一句话解释 API key 的用途（在你的代码中调用 API）+ "生成新 Key" CTA（复用现有按钮行为）。
- **FR-19:** 点赞/收藏空视图："你点赞/收藏的模板会出现在这里" + "浏览模板"动作。
- **FR-20:** 所有空状态必须 i18n（中英）且无障碍（CTA 是真正的按钮；状态作为区域播报）。

### 5.4 普通用户与管理员划分

- **普通用户界面：** 以上全部适用于主应用（`/`、`/profile`、`/api-keys`、`/templates/:id`）。
- **管理控制台（`/admin`）：** v1 无引导 —— 控制台由少数已受训的内部管理员使用，加清单价值低（见 §8）。共享 `EmptyState` 组件的改进（若被复用）会自动惠及 admin 页面。

## 6. 非功能需求

- **NFR-1（零后端改动）：** 所有检测使用现有端点（`getProfile`、`getTemplates`、`listAPIKeys`、`listPrompts`）；无新 API、无 schema 变更。
- **NFR-2（性能）：** 检测调用仅在清单卡片可见时发起（最多 4 个请求，每次首页挂载一次）；无轮询；结果不跨会话缓存（每次挂载重新检测成本低且正确）。
- **NFR-3（持久化）：** 关闭/完成标记存 localStorage（按浏览器）；已记录的局限 —— 标记不跨设备同步（开放问题 Q2 提出服务端替代方案）。
- **NFR-4（无障碍）：** 欢迎模态框复用无障碍 `Modal`（焦点圈定、Escape）；清单是带 `aria-checked` 语义的列表；进度经 `aria-live="polite"` 播报；全部遵循无障碍特性的基线。
- **NFR-5（i18n）：** 所有文案在 `onboarding.*` 命名空间，中英同次变更加入；无硬编码文本。
- **NFR-6（视觉）：** 严格使用 Aurora token；清单卡片与侧栏 section 样式一致；不新增颜色或插图系统（复用现有简单图标）。
- **NFR-7（不阻断）：** 引绝不阻断导航或任何核心流程；一切可关闭；所有引导关闭后产品完全可用。

## 7. 验收标准

- **AC-1:** 新注册用户恰好看到一次欢迎模态框；任何方式关闭（按钮、Escape、遮罩）后，后续登录不再出现（同一浏览器）。
- **AC-2:** 模态框无障碍：焦点圈定、Escape 关闭、焦点归还触发上下文。
- **AC-3:** 清单卡片对新用户以 0/4 出现，显示"0 of 4"，每个条目深链到正确目标。
- **AC-4:** 完成每个动作（保存带名称+头像的资料、创建模板、生成 key、使用提示词）后回到首页，对应条目显示已勾选。
- **AC-5:** 检测失败（任一检查网络错误）绝不向用户显示错误；条目保持未勾选。
- **AC-6:** 关闭清单后永久隐藏；全部完成的用户再也看不到卡片。
- **AC-7:** 四个空状态场景（§5.3 FR-16..19）在中英文下都渲染正确文案和可用 CTA。
- **AC-8:** 无结果空状态上的"清除筛选"恢复默认首页视图。
- **AC-9:** 所有引导 UI 完全翻译（中文下无英文泄漏）并使用 `onboarding.*` 命名空间。
- **AC-10:** 纯键盘用户可完成整个引导流程（关闭模态框、导航清单、激活条目）。
- **AC-11:** 清单关闭或完成时不发起任何新网络请求（网络面板验证）。
- **AC-12:** 欢迎模态框绝不在登录时出现（仅注册后首次导航）。

## 8. 不在范围内（v1）

- 服务端引导状态（清单/关闭的跨设备同步）—— 作为开放问题提出，不在 v1。
- 交互式产品导览 / 聚光灯覆盖层（coach marks）。
- 分类兴趣个性化选择器（Reddit 式）—— 侧栏已展示分类。
- 邮件引导序列（验证邮件已有；营销邮件不在范围）。
- 管理控制台引导。
- 游戏化（徽章、连续签到、积分）。
- 召回提示（长期未登录后的"完成设置"横幅）。

## 9. 依赖与假设

- **D-1:** 现有端点足以检测：`getProfile`、`getTemplates`（带 `owner_id`）、`listAPIKeys`、`listPrompts`（带 `owner_id`）—— 均已存在于 `services/api.js`。
- **D-2:** 无障碍 `Modal` 组件（无障碍特性落地后带焦点圈定）被欢迎模态框复用。
- **D-3:** 创建模板模态框可以从首页以编程方式打开（它已在 `Layout` 中，有浮动创建按钮；清单 CTA 触发同一打开路径）。
- **D-4:** localStorage 可用（已用于 auth token 和可见性偏好）；key 以 `onboarding.*` 命名空间。
- **D-5:** 无障碍特性的基线（焦点管理、aria 模式）适用于此处所有新组件；若该特性先落地，直接消费其基础组件。
- **D-6:** i18n key 在同一次变更中加入 `en` 与 `zh` 两个翻译文件。

## 10. 给架构师的问题

1. **检测调用预算：** 卡片可见期间首页挂载发起 4 个近似串行的 GET —— 可接受吗？还是加一个轻量聚合端点 `GET /api/v1/users/me/onboarding-status`（后端返回 4 个布尔值）以减少请求？v1 没有它也能工作；聚合适合 v2。
2. **服务端状态：** 关闭/完成标记是否应存在用户记录上（如 `users.onboarding_state JSONB` 列或 user_preferences 表），从而跨设备同步、清缓存后不丢？若是，这是个小后端增量 —— v2 值得做。
3. **"使用提示词"的定义：** 任何提示词创建都算（通过 UI"使用"按钮），还是 SDK 服务的提示词（通过 API key）也算？SDK 使用目前只记 `api_keys.last_used_at`，不按提示词记录 —— v1 建议只算 UI 提示词创建。
4. **欢迎模态框触发：** 注册后客户端标记 vs. 注册处理函数附加 `?welcome=1` 查询参数（更明确、刷新后仍在）？建议查询参数 + 标记组合。
5. **清单位置：** 侧栏列（桌面）还是内容区顶部（横幅式）？我按侧栏 section 样式设计以保持一致；请确认。
