# 无障碍（WCAG 2.1 AA）— 需求分析

- **Feature ID:** accessibility
- **Version:** 1.0
- **Status:** Proposed（待架构评审）
- **Author:** ui-ux-agent
- **Date:** 2026-10-10

## 1. 竞品研究总结

| 平台 | 无障碍做法 | 关键启示 |
|---|---|---|
| **GitHub** | 完整键盘支持；可见焦点环；跳转到内容；菜单/对话框 ARIA；`lang` 同步；状态用 live region 播报；专门的无障碍审计流程 | 高密度 Web 应用的标杆：跳转链接、对话框焦点管理、一致的 landmark 是基本要求 |
| **ChatGPT** | 强键盘/读屏支持；路由切换时焦点管理；流式响应用 aria-live 播报 | 路由切换重置焦点 + live region 播报是 SPA 中杠杆最大的两个模式 |
| **PromptBase** | 基础语义 HTML；部分键盘支持；无跳转链接 | 提示词平台普遍无障碍薄弱 —— 这是差异化机会，而非可照抄的模式 |
| **FlowGPT** | div 实现的可点击卡片；焦点可见性弱 | 仅可点击的卡片（如我们当前的 `PromptCard`）是提示词平台最常见的无障碍失败 |
| **AIPRM** | 浏览器扩展 UI；部分 ARIA | 扩展场景不同；唯一启示是纯图标按钮必须有可访问名称 |
| **Notion** | 出色的键盘快捷键体系；cmdk 面板；reduced-motion 支持 | 公开键盘快捷键说明能建立高级用户信任 |
| **Figma** | 激进的焦点管理、播报、forced-colors 支持 | forced-colors（Windows 高对比度）支持是成熟度标志；用媒体查询即可低成本实现 |

**综合结论：** Open Prompts 基础不错（语义化 `header`/`nav`/`aside`/`main` landmark、`Field` 标签关联、`Modal` 支持 Escape + 打开时聚焦、全局 `prefers-reduced-motion` 守卫、`VersionSelect` 列表框 ARIA），但存在明显缺口：无跳转链接、切换语言时 `lang` 不同步、`PromptCard` 与侧栏项仅可点击、纯图标按钮（点赞/收藏/复制）无 `aria-label`、`Modal` 无焦点圈定与焦点归还、路由切换无焦点管理、toast 无 `aria-live`、按钮仅靠 `title` 命名、未定义 WCAG 目标等级。正确做法是对现有界面进行系统性的 WCAG 2.1 AA 整改，按用户影响排序，并用 CI（axe-core）守住验收基线 —— 而不是重新设计。

## 2. 问题陈述

1. **键盘用户无法使用核心浏览流程。** `PromptCard` 是可点击的 `div` —— 不可聚焦、无法用 Enter/Space 激活。侧栏分类/标签项同样如此。纯键盘用户无法从首页网格打开任何模板。
2. **读屏用户获得不完整或错误的信息。** 纯图标按钮（点赞、收藏、复制代码）仅依赖 `title` 提示；中文界面下 `document.lang` 仍是 `en`；toast 无 `aria-live`，操作结果从不播报；点赞/收藏状态（是否已按下）未暴露。
3. **焦点丢失或不可见地被困。** `Modal` 打开时聚焦自身，但不把 Tab 圈定在对话框内，关闭时也不归还焦点给触发器；路由切换（卡片 → 详情）后焦点落在已移除的元素上，重置到 `body`。
4. **无跳转导航。** 侧栏 + 头部在 DOM 顺序上位于 `main` 之前；键盘用户每次加载页面都要先 Tab 穿越约 30 个链接才能到达内容。
5. **对比度与目标尺寸风险。** 暗色主题下 `--text-3` 在 `--surface` 上约 4.0:1（低于正文 4.5:1 要求）；点赞/收藏点击区是 17px 图标；无 `forced-colors` 支持。
6. **无无障碍基线或回归防护。** 没有任何机制阻止新代码重新引入违规；没有文档化的目标等级、没有 axe-core 检查、设计文档的完成定义中也没有无障碍章节（本特性为后续特性补上这一章）。

## 3. 目标用户

- **键盘优先用户**（高级用户、使用 API-key 工作流的开发者、单纯不碰鼠标的人）—— 目前被核心的"浏览 → 打开"流程阻断。
- **读屏用户**（NVDA/JAWS/VoiceOver，中英文）—— 目前收到无名称控件、错误语言播报、无声的操作反馈。
- **低视力用户** —— 需要 ≥4.5:1 文本对比度、可见焦点指示、200% 缩放不损失功能。
- **运动障碍用户** —— 需要 ≥24px 有效目标尺寸，以及精确悬停的替代方式。
- **所有用户** —— 可见焦点、尊重 reduced-motion、缩放容忍让所有人受益；无障碍修复通常能提升整体 UX 指标。
- **管理控制台用户**（未来的 `/admin` 界面）—— 无障碍基线必须从第一天就覆盖 admin 页面，而不是事后补。

## 4. 用户故事

- **US-A1:** 作为键盘用户，我可以 Tab 到任何模板卡片并按 Enter 打开，从而无需鼠标即可浏览。
- **US-A2:** 作为键盘用户，页面加载后按一次 Tab 即可到达"跳转到内容"链接，从而不必每次穿越整个侧栏。
- **US-A3:** 作为键盘用户，模态框打开时焦点保持在框内，关闭时焦点回到打开它的按钮，从而不会丢失位置。
- **US-A4:** 作为读屏用户，当我把界面切换为中文时，读屏器用中文语音朗读内容，从而标签可听懂。
- **US-A5:** 作为读屏用户，每个纯图标按钮（点赞、收藏、复制、关闭、主题、语言）都播报其名称，从而在激活前知道其作用。
- **US-A6:** 作为读屏用户，点赞/收藏按钮播报当前状态（已按下/未按下），从而知道是否已点赞过某模板。
- **US-A7:** 作为读屏用户，当操作完成或失败（保存、复制、点赞）时 toast 被播报，从而获得与明眼用户相同的反馈。
- **US-A8:** 作为读屏用户，导航到新页面时页面标题与主标题被播报，从而知道自己在哪。
- **US-A9:** 作为低视力用户，所有正文文本在两个主题下都满足 4.5:1、大字 3:1 对比度，从而阅读不费力。
- **US-A10:** 作为低视力用户，我可以缩放到 200% 并完整使用应用，从而小字不构成障碍。
- **US-A11:** 作为运动障碍用户，交互目标至少 24×24px（布局允许时 44px），从而能准确点击。
- **US-A12:** 作为对动效敏感的用户，动画尊重系统的 reduced-motion 设置，从而不会不适（已部分实现；必须保持）。
- **US-A13:** 作为任意用户，当前聚焦元素始终清晰可见，从而不会跟丢位置。
- **US-A14:** 作为读屏用户，表单校验失败时错误被播报，从而可以修正（现有 `Field` 已展示错误；需补焦点/播报接线）。
- **US-A15:** 作为管理控制台用户，以上所有在 `/admin` 页面同样成立，从而无障碍在那里不是二等公民。

## 5. 功能需求

### 5.1 键盘可操作性

- **FR-1:** 所有交互元素必须可用 Tab/Shift+Tab 到达，并可用 Enter（链接/按钮）或 Space（按钮）激活 —— 不允许仅鼠标交互。
- **FR-2:** `PromptCard` 必须可键盘操作：整卡通过单一 Tab 停靠点导航（锚点或按钮包裹/覆盖卡片内容），保留现有点击行为。
- **FR-3:** 侧栏分类、标签、特殊筛选项必须是可操作的链接或按钮（保留 `ul`/`li` 列表语义）。
- **FR-4:** 每个页面上"跳转到主内容"链接必须是第一个可聚焦元素；聚焦时可见，并把焦点移到 `main` landmark。
- **FR-5:** 焦点顺序必须遵循视觉阅读顺序（头部 → 侧栏 → 内容）；任何地方不得使用 `tabIndex` > 0。
- **FR-6:** 移动端侧栏抽屉打开时必须圈定焦点，Escape 关闭，关闭后焦点归还给菜单开关。
- **FR-7:** 下拉菜单（头部头像、语言、未来的通知铃铛）必须实现标准菜单/列表框键盘模式：方向键移动、Enter/Space 选择、Escape 关闭并归还焦点。

### 5.2 读屏语义

- **FR-8:** `document.documentElement.lang` 必须与激活的 i18n 语言（`en`/`zh`）保持同步 —— 初始化时和每次切换语言时。
- **FR-9:** 每个纯图标按钮必须有通过 `aria-label`（或视觉隐藏文本）提供的可访问名称：点赞、收藏、复制代码、复制提示词、关闭、主题切换、语言切换、菜单开关、头像菜单、编辑元数据、移除/添加标签（已有）、通知铃铛（未来）。
- **FR-10:** 点赞/收藏切换按钮必须通过 `aria-pressed` 暴露状态。
- **FR-11:** toast 容器必须是 `aria-live="polite"` 区域（错误：`role="alert"` 语义），使操作反馈被播报。
- **FR-12:** 路由切换必须 (a) 按页面设置 `document.title`（i18n）并 (b) 把焦点移到页面 `h1`/主标题（`tabIndex=-1`），使新上下文被播报。
- **FR-13:** 页面结构必须每页一个 `h1`，标题层级不跳级（详情页当前从 `h2` 开始 —— 必须修正）。
- **FR-14:** 表单校验失败必须把焦点移到（或播报）第一个无效字段；`Field` 已渲染 `aria-invalid` —— 需接上播报。
- **FR-15:** Landmark 必须完整且唯一：`header`、`nav`（主导航；侧栏加 `aria-label`）、`aside`、`main`，toast 作为带标签的区域。
- **FR-16:** 装饰性图标与图片必须 `aria-hidden`；有意义图片保留现有 `alt`（logo、头像已合规）。

### 5.3 焦点可见性与管理

- **FR-17:** 所有交互元素在两个主题下必须显示可见焦点指示（2px `--accent` 轮廓、2px 偏移）；当前 `.input:focus { outline: none }` 模式必须替换为绝不移除指示的 `:focus-visible` 样式。
- **FR-18:** `Modal` 打开期间必须把 Tab（与 Shift+Tab）圈定在对话框内，关闭时把焦点归还给打开它的触发器。
- **FR-19:** 元素移除（toast、列表项、删除后的卡片）时焦点绝不能丢失：有意地移动焦点或移到容器。

### 5.4 对比度、目标尺寸、动效、缩放

- **FR-20:** 文本对比度必须满足 WCAG 2.1 AA：正文 4.5:1、大字（≥18.66px 粗体 / 24px）3:1，明暗两主题均需满足；不达标的 token 值必须调整（尤其是暗色主题的 `--text-3`）。
- **FR-21:** 交互目标至少 24×24px（WCAG 2.2 目标尺寸最低要求），布局允许时优先 44×44px；点赞/收藏按钮必须扩大点击区（用 padding，而非加大图标）。
- **FR-22:** 所有动画必须尊重 `prefers-reduced-motion`（全局守卫已存在；新组件不得绕过）；不得仅靠动画传达关键信息。
- **FR-23:** 应用在 200% 浏览器缩放和 320px 视口宽度（reflow）下必须完全可用，内容不出现横向滚动（代码块除外，可原地滚动）。
- **FR-24:** 必须支持 `forced-colors`（Windows 高对比度）：尊重系统颜色、焦点指示可见、不仅靠颜色传达信息（点赞/收藏激活态除颜色外还需图标填充/形状提示）。

### 5.5 流程与回归防护

- **FR-25:** axe-core 无障碍检查必须进入 CI（或作为 npm script），覆盖关键页面（首页、登录、模板详情、个人资料），以 0 个 critical/serious 违规作为门禁。
- **FR-26:** 仓库中必须文档化一个纯键盘冒烟测试脚本（Tab 穿越首页 → 打开卡片 → 交互），供 QA/test-agent 执行。
- **FR-27:** 未来特性的设计文档模板必须包含无障碍章节（本特性及此前的 UI/UX 文档已有；今后作为明确要求）。
- **FR-28:** 管理控制台页面（`/admin`）从首次发布起必须满足同一基线；admin 特有模式（数据表格）还必须有正确的 `th` scope、caption 和可排序表头按钮语义。

### 5.6 普通用户与管理员划分

- **普通用户界面（现有全部页面）：** FR-1..24 全量适用。
- **管理控制台（`/admin`，全新构建）：** FR-1..24 同样适用；FR-28 追加表格专项要求；admin 页面可路由后必须纳入 FR-25 的 CI 检查。
- **共享组件（`Modal`、`Field`、`VersionSelect`、toast、未来的铃铛下拉）：** 修复在此一次落地、两个界面同时受益；这是实现的优先顺序。

## 6. 非功能需求

- **NFR-1（兼容性）：** 不做视觉重设计 —— 修复必须保留 Aurora 外观；token 对比度调整是唯一有意的视觉变化，必须在两个主题下评审。
- **NFR-2（性能）：** 不引入运行时无障碍库；修复全部是原生 ARIA/HTML + 一个小型焦点管理工具。axe-core 只在 CI 运行，绝不进入生产包。
- **NFR-3（零后端改动）：** 纯前端；无 API、schema、proto 变更。
- **NFR-4（可测试性）：** 每条 FR 映射到一条 axe 规则或一个手动键盘测试步骤；CI 门禁必须在新违规时大声失败。
- **NFR-5（增量交付）：** 各修复相互独立、可任意顺序合入；先共享组件（Modal、toast、PromptCard），再页面，再 admin。
- **NFR-6（双主题）：** 每个对比度/焦点修复必须在明暗两个主题下验证。
- **NFR-7（双语言）：** 每个可访问名称必须 i18n（中英）；`aria-label` 中不得硬编码英文。

## 7. 验收标准

- **AC-1:** 纯键盘用户可完成核心流程：加载首页 → 跳转链接 → Tab 到卡片 → Enter → 详情页 → 点赞 → 复制提示词 → 返回 —— 全程焦点可见、无需鼠标。
- **AC-2:** axe-core（CI）在首页、登录、注册、模板详情、个人资料、API keys 页面报告 0 个 critical、0 个 serious 违规，两个主题均需通过。
- **AC-3:** UI 语言设为中文时 `document.documentElement.lang === 'zh'`；切换语言立即更新。
- **AC-4:** 打开任何模态框（创建模板、删除确认）焦点被圈定在框内；关闭后焦点归还触发器；Escape 可关闭。
- **AC-5:** 每个纯图标按钮在两种语言下都暴露可访问名称（通过 axe "button-name" 规则验证）。
- **AC-6:** 点赞/收藏按钮暴露 `aria-pressed`；切换时状态播报更新。
- **AC-7:** toast 被读屏器播报（存在 aria-live 区域；错误 toast 使用 assertive 语义）。
- **AC-8:** 文本对比度在两个主题下通过 4.5:1（正文）/ 3:1（大字），通过对所有文本 token 组合的对比度审计验证。
- **AC-9:** 200% 缩放和 320px 宽度下，所有页面 reflow 无横向滚动（代码块除外）。
- **AC-10:** `prefers-reduced-motion: reduce` 在两个主题下禁用所有非必要动画（现有全局守卫 + 无新增绕过）。
- **AC-11:** 路由切换播报新页面（设置标题 + 焦点移到标题）；返回导航行为一致。
- **AC-12:** 键盘冒烟测试脚本存在于仓库中，并在六个核心页面上手动通过。

## 8. 不在范围内（v1）

- WCAG 2.1 AAA 级符合（v1 目标 AA）。
- 使用 NVDA/JAWS/VoiceOver 的完整读屏人工认证审计（v1 仅 axe + 键盘测试；人工读屏通过是后续工作）。
- 字幕/说明文字功能（无音视频内容）。
- 第三方嵌入内容的无障碍（不存在）。
- 除最小 token 对比度调整之外的任何视觉语言重设计。
- 语音输入/语音控制优化。

## 9. 依赖与假设

- **D-1:** 假设现有 `Modal`、`Field`、`VersionSelect` 与 toast（`NotificationContext`）组件仍是共享基础组件；修复集中在这些地方。
- **D-2:** 假设使用 react-router（或等价的客户端路由），路由切换 effect 可以设置标题/焦点；页面组件渲染在现有 `Layout` 内。
- **D-3:** 假设 axe-core 可作为 devDependency 加入，并通过现有测试运行器（Jest/RTL）或 Playwright 运行；CI 已对 push 设门禁。
- **D-4:** 假设 Aurora token 集（`--text-1/2/3`、`--surface*`）是文本颜色的唯一来源；调整 token 即可一次性修复所有使用点。
- **D-5:** 假设所有新增可访问名称的 i18n key 在同一次变更中加入 `en` 与 `zh` 两个翻译文件（不做半语言发布）。
- **D-6:** 假设未来特性（通知铃铛、版本面板、管理控制台）将消费修复后的共享组件 —— 本特性尽早排序可避免违规成倍扩散。

## 10. 给架构师的问题

1. **CI 集成：** axe-core 应在现有 Jest/RTL 套件内运行（jsdom，快但受限），还是通过 Playwright/nightwatch 对运行中的环境跑一遍（慢但更准）？仓库两套测试都有。
2. **对比度 token 调整：** 暗色主题 `--text-3`（#6e768c 在 #171b26 上 ≈ 4.0:1）正文不达 AA。建议修复：提亮到 ~#8b92a8（即亮色主题的值，暗色表面上 ≈ 5.4:1）。请确认接受这一有意的 token 变更，以及 `--text-3` 是否应仅保留给大字/禁用文本。
3. **PromptCard 模式：** 用 `<a>` 包裹卡片（语义最佳，但内部嵌套交互元素需处理）还是覆盖按钮模式（绝对定位按钮铺满卡片、现有内部按钮叠在其上）？推荐覆盖按钮，DOM 改动最小。
4. **路由切换焦点：** 每次导航都把焦点移到 `h1`（`tabIndex={-1}`），还是只在"主"导航（卡片 → 详情）时做，以免干扰同页筛选变化？
5. **v1 页面范围：** 六个核心页面（首页、登录、注册、详情、个人资料、API keys）作为 CI 门禁集合是否合适，还是门禁先更小（首页 + 详情）？
