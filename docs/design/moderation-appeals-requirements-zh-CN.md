# 审核申诉 — 需求分析

- **功能 ID：** moderation-appeals
- **版本：** 1.0
- **状态：** Proposed（待架构评审）
- **作者：** ui-ux-agent
- **日期：** 2026-10-13
- **配套文档：** `moderation-appeals-ui-ux-design-zh-CN.md`

## 1. 竞品调研

| 产品 | 申诉能力 | 优势 | 不足 |
|---|---|---|---|
| YouTube Studio | 创作者可对每次移除申诉；每操作一次；数日内出结果 | 结构化、按操作、可追踪 | 标准不透明；无对话 |
| GitHub（仓库下架） | 所有者开支持工单；反转即恢复 | 人工审查、有记录 | 带外；无状态界面 |
| Reddit | 每操作一个 Modmail 会话 | 双向对话 | 线程无界；无 SLA |
| Discord | 服务器所有者通过支持表单申诉 | 入口简单 | 无状态追踪 |
| PromptBase/FlowGPT | 无 | — | 尚无可申诉的审核系统 |

**结论：** YouTube 模式最合适：**每次审核操作一次申诉**、结构化表单（理由纯文本）、带显式状态的案件追踪（open → under review → upheld/reversed）、管理员队列裁决。对话为一轮（创作者陈述；管理员带裁决说明决定）—— 而非无界线程（Reddit 的弱点）。这补上了 admin-template-moderation 留在带外的一环。

## 2. 问题陈述

admin-template-moderation 给了创作者原因和"联系支持"提示，但没有产品内抗辩路径。误判没有结构化的反转请求：创作者必须找带外渠道，管理员也没有分流争议的队列。审计日志为申诉提供事实依据（US-M9），但没有东西消费它。

## 3. 目标用户

- **创作者** —— 通过结构化、可追踪的申诉，对模板上的审核操作提出异议。
- **管理员** —— 分流申诉队列、查看操作的审计上下文、以裁决说明反转或维持。

## 4. 用户故事

- **US-1**：作为创作者，我想从通知本身对模板上的审核操作（取消发布/锁定/删除）发起申诉，使抗辩一步可达。
- **US-2**：作为创作者，我想用结构化表单陈述理由（操作为何错误），使管理员获得清晰可审的论据。
- **US-3**：作为创作者，我想看到申诉状态（open/审核中/已裁决）与结果，不再悬而未决。
- **US-4**：作为创作者，我希望每次审核操作恰好一次申诉，使流程不被刷屏。
- **US-5**：作为创作者，我想在申诉裁决时收到通知，含结果与管理员说明。
- **US-6**：作为管理员，我想要按时间排序、带模板与操作上下文的申诉队列，以快速分流争议。
- **US-7**：作为管理员，我想在申诉旁内联看到原操作的审计条目（操作者、原因、时间戳），使裁决基于事实。
- **US-8**：作为管理员，我想以反转或维持裁决申诉并附必填说明，使创作者总能获得解释。
- **US-9**：作为管理员，我希望反转的取消发布/删除自动恢复模板，使救济与裁决一致。
- **US-10**：作为管理员，我希望申诉人与裁决人不同，使自我审查不可能。

## 5. 功能需求

- **FR-1**：创作者可对自有模板上的任何审核操作（取消发布、锁定、软删除）发起申诉，入口：所有者横幅/移除通告（admin-template-moderation FR-12）、审核通知、或 `/appeals`（新页面）。
- **FR-2**：申诉表单包含：所引用操作（只读上下文：操作类型、原因、操作者显示名、时间戳）与案情陈述（必填，50–2000 字符）。v1 无附件。
- **FR-3**：**每次审核操作恰好一次申诉** —— 第二次尝试返回 409"该操作已被申诉"；UI 禁用申诉入口并显示既有申诉状态。
- **FR-4**：申诉状态：`open` → `under_review` → `resolved_upheld` | `resolved_reversed`。除初始创建外，状态迁移仅限管理员。
- **FR-5**：用户 API：`POST /api/v1/appeals`（body：`{moderation_action_id, statement}`）、`GET /api/v1/appeals`（自己的申诉，分页 20/页，最新在前）、`GET /api/v1/appeals/{id}`。
- **FR-6**：管理员 API：`GET /api/v1/admin/appeals?state=open|under_review|resolved&page...`（队列，状态内最旧在前）、`GET /api/v1/admin/appeals/{id}`、`POST /api/v1/admin/appeals/{id}/review`（open → under_review）、`POST /api/v1/admin/appeals/{id}/resolve`（body：`{outcome: upheld|reversed, note}`；说明必填 20–1000 字符）。
- **FR-7**：裁决为 `reversed` 时，若操作为取消发布或软删除，自动恢复模板（等价于 admin-template-moderation restore）；锁定则解锁。恢复与裁决在同一事务中原子完成。
- **FR-8**：裁决为 `upheld` 不改变模板；审核状态维持。
- **FR-9**：裁决人不得是原审核操作的操作者（自我审查防护；403 并解释）。
- **FR-10**：裁决时创作者收到通知（新 `appeal_resolved` 类型，数据驱动注册），含结果与说明摘录，深链到申诉详情。
- **FR-11**：`/appeals`（用户页）列出创作者的申诉，含状态 chip、操作上下文、时间戳；详情视图显示完整案情陈述、原操作上下文、裁决说明（已裁决时）。
- **FR-12**：管理控制台：`/admin/appeals` 队列，含状态过滤标签（open/审核中/已裁决）、时间排序、计数；`/admin/appeals/:id` 详情含申诉、原操作审计条目、Review/Resolve 操作。
- **FR-13**：所有申诉操作（创建、审查、裁决）写入审计日志，含操作者、申诉 id、适用时的结果。
- **FR-14**：仅当底层审核操作仍存在时可申诉（未被后续恢复撤销 —— 已恢复模板的操作显示"已取代"且不可申诉；申诉入口隐藏）。
- **FR-15**：某操作存在 open 或审核中申诉时，创作者在所有者横幅上内联看到其状态（取代申诉 CTA）。
- **FR-16**：每用户同时最多 5 个 open 申诉；超出返回 429 并附明确信息。

## 6. 非功能需求

- **NFR-1（性能）**：1000 条申诉下管理队列 p95 < 200 ms（按 state + created_at 索引）。
- **NFR-2（公平）**：状态内申诉 FIFO；v1 无优先级机制。
- **NFR-3（国际化）**：所有 UI 字符串中英同步；案情陈述与说明为用户/管理员内容，原样展示。
- **NFR-4（透明）**：创作者总能看到结果与说明；没有静默裁决。
- **NFR-5（安全）**：陈述与说明为纯文本（无 HTML/Markdown）；长度受限；以文本渲染（构造上防 XSS）。

## 7. 验收标准

- **AC-1**：从移除通告页，"申诉此决定"打开预填操作上下文的表单；提交创建 `open` 申诉。
- **AC-2**：对同一操作提交第二次申诉返回 409；UI 显示既有申诉状态而非表单。
- **AC-3**：管理员点击"Review"将申诉移至 `under_review`；创作者在 `/appeals` 看到状态变化。
- **AC-4**：软删除申诉裁决为 `reversed` 时，同一事务中恢复模板并将审核状态翻转为 `normal`；创作者收到 `appeal_resolved` 通知。
- **AC-5**：裁决为 `upheld` 时模板不动；通知陈述结果并附管理员说明。
- **AC-6**：原操作操作者尝试裁决该申诉收到 403"原操作操作者不能裁决此申诉"。
- **AC-7**：`/admin/appeals` 显示带计数的状态标签；open 申诉最旧在前。
- **AC-8**：被（管理员而非申诉反转）恢复的模板，其历史操作显示"已取代"且无申诉入口。
- **AC-9**：已有 5 个 open 申诉的用户提交第 6 个收到 429 与限额信息。
- **AC-10**：含 `<script>` 的陈述在所有出现位置按字面文本渲染。

## 8. 不在范围内

- 多轮对话/线程式往返（一次陈述 + 一次裁决说明）。
- 附件/证据上传；第三方仲裁；SLA 计时器或自动升级。
- 账号级操作的申诉（封禁 —— admin-user-management 领域）。
- 评论删除的申诉（admin-template-moderation 仅覆盖模板操作）。
- 任何形式的变现 —— 本产品永久不做。

## 9. 依赖与假设

- **D-1**：admin-template-moderation 的审核操作是带稳定 id 的审计日志条目；申诉引用 `moderation_action_id`（OQ-1：审计条目 id vs 专门 moderation_actions 表）。
- **D-2**：恢复路径（admin-template-moderation FR-5）可作为反转救济复用（FR-7）。
- **D-3**：`appeal_resolved` 通知类型通过数据驱动模式注册（mention-notifications）。
- **D-4**：admin-user-management 的管理控制台外壳与审计日志读取器承载队列页面。
- **D-5**：admin-template-moderation FR-12 的所有者横幅增加申诉 CTA/状态槽位（FR-1、FR-15）。

## 10. 给架构师的开放问题

- **OQ-1**：申诉应引用审计日志条目 id，还是 admin-template-moderation 应引入申诉（及历史 UI）读取的专门 `moderation_actions` 表？（提案：专门表 —— 为 FR-14 已取代状态提供更清晰的生命周期。）
- **OQ-2**：`under_review` 是否必须在裁决前经过，还是管理员可直接从 `open` 裁决？（提案：允许直接裁决 —— 对小团队两状态是仪式。）
- **OQ-3**：反转恢复是否需要独立审计代码（`template.restored_by_appeal`），还是复用 `template.restore` 加申诉引用？
- **OQ-4**：5 个 open 申诉限额（FR-16）是否应服务端可配置？
- **OQ-5**：通知中说明摘录长度（如 140 字符）是否可接受，还是仅深链？
