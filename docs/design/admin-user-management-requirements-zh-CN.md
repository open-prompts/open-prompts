# 管理员用户管理系统 — 需求分析

- **功能编号：** `admin-user-management`
- **版本：** 1.0
- **状态：** 已批准进入架构设计
- **作者：** UI/UX Agent（产品分析）
- **读者：** Architect、Developer、Test 各 Agent

---

## 1. 竞品调研总结

Open Prompts 目前**完全不具备管理能力**：没有管理员角色、没有管理控制台、没有审核工具、无法监督用户行为。为使本功能设计有业界依据，我们调研了同类提示词市场与 UGC 平台的管理/审核方案：

| 平台 | 管理方式 | 核心能力 | 对 Open Prompts 的启示 |
|---|---|---|---|
| **PromptBase** | 策展型市场，带卖家/发布者审核流水线 | 员工在提示词公开前逐一审核；可封禁卖家账号；以发布前审核保证内容质量 | 审核队列是管理端核心界面；但"发布前审核"较重，v1 不采用 |
| **FlowGPT** | 社区 UGC 平台，带举报/标记流程 | 用户举报提示词；审核员处理被举报内容、封禁垃圾账号、精选/推荐优质提示词 | 举报驱动的审核比预审更可扩展；"精选"策展驱动发现 |
| **Snack Prompt** | 策展型提示词信息流 | 编辑策展（每日精选）、用户屏蔽、垃圾信息过滤 | 规模增长后，策展 + 反垃圾是基本要求 |
| **AIPRM** | 基于插件的提示词库 | 集中式库管理、团队/角色分离（owner/admin/member）、使用遥测 | 专业工具普遍要求角色分离（admin 与 member） |
| **PromptHero** | 发现/排行榜平台 | 内容下架、账号封禁、排行榜策展 | 下架 + 封禁是最低可行的审核动作 |
| **通用 SaaS 管理控制台**（Stripe、Vercel、Supabase） | 独立 `/admin` 路由空间、独立认证域或严格权限校验、审计日志 | KPI 仪表盘、可搜索的分页用户列表、下钻详情、管理员操作审计 | "仪表盘 + 列表 + 详情 + 审计日志"是业界标准管理端信息架构 |

**综合结论。** 业界一致的模式是：

1. **独立的管理端路由空间**（`/admin/*`），在视觉与导航上与终端用户产品分离。
2. **仪表盘优先的信息架构**：管理员先看到总览（用户、模板、增长），再下钻到列表。
3. **用户列表 + 搜索 + 筛选 + 批量操作**是最核心的工作界面。
4. **封禁 / 解禁 / 角色管理**是核心账号操作，且必须附带**原因 + 审计记录**。
5. **模板审核总览**（被举报/违规内容）是第二支柱，因为内容监督正是管理员存在的意义。
6. **独立的管理员认证** —— 或独立登录域，或严格的服务端权限校验，绝不能只靠客户端隐藏入口。

v1 我们采用"仪表盘 + 用户管理 + 模板审核总览"模式，并刻意将"发布前审核队列"与"精选策展"留待后续功能。

## 2. 问题陈述

Open Prompts 是一个持续增长的 UGC 平台，任何注册用户都可以发布公开提示词模板。而今天平台**没有任何手段**：

- 了解用户/模板总量与增长情况（完全没有指标）。
- 查找特定用户或用户群体（没有管理端用户列表）。
- 制止恶意或刷屏用户（没有封禁能力）。
- 授予或撤销管理权限（没有角色模型）。
- 审查公开模板是否违规（没有审核视图）。

随着公开内容增长，平台在审核与安全方面的风险无限累积，却没有工具进行管理。本功能补齐最大的能力缺口：**一个安全、独立的管理控制台，用于用户与模板监督**。

## 3. 目标用户

| 角色 | 描述 | 主要诉求 |
|---|---|---|
| **平台运营者（管理员）** | 运营 Open Prompts 实例的人或团队。技术背景，每天使用产品。 | 一眼掌握平台健康度；快速找到用户；带原因封禁/解禁；管理角色；审查公开模板 |
| **次要：普通用户** | 间接受益者。 | 更干净、更安全的公开模板广场（他们永远看不到管理控制台） |

## 4. 用户故事

### 4.1 管理员视角

- **US-A1** — 作为管理员，我希望登录一个独立的管理控制台（与普通用户应用分离），使管理权限与日常产品使用隔离。
- **US-A2** — 作为管理员，我希望看到关键指标仪表盘（总用户、新用户、总模板、公开模板、创建的 Prompt、最近注册），以便一眼掌握平台健康度。
- **US-A3** — 作为管理员，我希望按用户 ID、邮箱或显示名搜索用户，以便快速定位任何账号。
- **US-A4** — 作为管理员，我希望按状态（正常/封禁）和角色（管理员/用户）筛选用户，以便分批处理（例如所有被封禁用户）。
- **US-A5** — 作为管理员，我希望用户列表支持分页，以便可预测地浏览大数据集。
- **US-A6** — 作为管理员，我希望查看用户完整档案（注册时间、头像、模板数、OAuth 身份、API Key 数量），以便在采取行动前评估账号。
- **US-A7** — 作为管理员，我希望封禁用户时必须填写原因，使滥用账号被制止且操作可审计。
- **US-A8** — 作为管理员，我希望解禁用户时填写原因，使误操作可以纠正，同样可审计。
- **US-A9** — 作为管理员，我希望将可信用户提升为管理员、将管理员降级为普通用户，使运营权限与团队匹配。
- **US-A10** — 作为管理员，我希望看到模板审核总览（所有公开模板及其所有者、点赞、收藏、日期，可排序），以便发现违规或垃圾内容。
- **US-A11** — 作为管理员，我希望查看任意模板的详情（包括私有模板），以便完整调查被举报的模板。
- **US-A12** — 作为管理员，我希望每个管理操作（封禁/解禁/角色变更）都记录操作者、对象、动作、原因、时间，使运营可问责。
- **US-A13** — 作为管理员，我希望管理控制台像主应用一样支持中英文和明暗主题，使团队可以在偏好的语言环境工作。

### 4.2 普通用户影响故事

- **US-U1** — 作为普通用户，我希望被封禁用户的公开模板从公开广场隐藏，使垃圾内容从发现页消失。
- **US-U2** — 作为普通用户，我希望被封禁的账号登录时收到清晰的错误提示，明白为何被拒绝。
- **US-U3** — 作为普通用户，我永远看不到任何管理端 UI、链接或路由，使产品界面保持干净。

## 5. 功能需求

### 5.1 管理员认证与访问控制

- **FR-1** 系统应支持用户账号的 `admin` 角色，存储在服务端（users 表 `role` 列，默认 `user`）。
- **FR-2** 管理端 Web 控制台路由应位于 `/admin` 之下（如 `/admin/login`、`/admin`、`/admin/users`、`/admin/users/:id`、`/admin/templates`、`/admin/templates/:id`、`/admin/audit-log`）。
- **FR-3** 管理端 API 应位于 `/api/v1/admin` 之下（如 `POST /api/v1/admin/login`、`GET /api/v1/admin/stats`、`GET /api/v1/admin/users`、`GET /api/v1/admin/users/{id}`、`POST /api/v1/admin/users/{id}/ban`、`POST /api/v1/admin/users/{id}/unban`、`POST /api/v1/admin/users/{id}/role`、`GET /api/v1/admin/templates`、`GET /api/v1/admin/audit-log`）。
- **FR-4** 所有 `/api/v1/admin/*` 端点应要求有效 JWT 且主体具有 `admin` 角色；非管理员令牌返回 `403 Forbidden`；未认证请求返回 `401 Unauthorized`。
- **FR-5** 管理员登录应为**独立页面**（`/admin/login`），使用与普通登录相同的凭据（邮箱 + 密码），但签发携带 admin 角色声明的令牌；非管理员尝试管理员登录时看到"该账号没有管理员权限"。
- **FR-6** 普通用户访问任何 `/admin/*` 路由时，应被重定向到 `/admin/login`（未认证）或看到 403 页面（已认证但非管理员）。
- **FR-7** 第一个管理员账号应通过服务端环境变量（如 `ADMIN_BOOTSTRAP_EMAIL`）或幂等 SQL 迁移提升指定邮箱来引导创建；不开放管理员注册。
- **FR-8** 管理会话应在可配置的空闲窗口（默认 30 分钟不活动）后过期并要求重新登录，比普通用户会话更短。

### 5.2 管理端仪表盘

- **FR-9** 仪表盘应展示 KPI 卡片：总用户数、活跃用户数、封禁用户数、总模板数、公开模板数、创建的 Prompt 数（数据支持时提供 7 天/30 天切换）。
- **FR-10** 仪表盘应展示"最近注册"列表（最新 10 个用户：ID、显示名、邮箱、注册时间），可跳转用户详情。
- **FR-11** 仪表盘应展示"最近更新的公开模板"列表（最新 10 个），可跳转模板详情。
- **FR-12** 所有仪表盘数字应由服务端从数据库计算（不允许客户端在列表端点上聚合）。

### 5.3 用户管理

- **FR-13** 用户列表应支持服务端分页（默认每页 20 条，可选 10/20/50/100）并返回总数。
- **FR-14** 用户列表应支持关键字搜索，匹配用户 ID、邮箱或显示名（不区分大小写的部分匹配）。
- **FR-15** 用户列表应支持筛选：状态（全部/正常/封禁）、角色（全部/管理员/用户）。
- **FR-16** 用户列表应支持按 created_at（默认最新优先）和 updated_at 排序。
- **FR-17** 每行应显示：头像（或首字母）、显示名、用户 ID、邮箱、角色徽章、状态徽章、模板数、创建日期，以及行操作菜单（查看 / 封禁或解禁 / 变更角色）。
- **FR-18** 点击行（或"查看"）打开**用户详情页**，展示：档案摘要、统计（模板数、获赞数、被收藏数、创建的 Prompt 数）、OAuth 身份、API Key（名称、前缀、状态、最近使用时间 —— 绝不显示密钥本身）、该用户的管理操作历史。
- **FR-19** **封禁**必须填写原因（自由文本，3–500 字符）。封禁将 `status` 置为 `banned`，记录审计条目，并立即失效该用户的活动会话/API Key 使用。
- **FR-20** **解禁**必须填写原因。解禁将 `status` 置为 `active` 并记录审计条目。
- **FR-21** **角色变更**（提升为管理员 / 降级为用户）必须填写原因，记录审计条目，并禁止自我降级（管理员不能降级自己）以避免锁死。
- **FR-22** 被封禁用户登录（密码与 OAuth）应被拒绝并返回明确的"账号已封禁"错误；其 API Key 应返回 `403`。
- **FR-23** 被封禁用户的公开模板应从公开列表端点（ListTemplates 公开可见性）及分类/标签计数中排除。
- **FR-24** 管理员可以查看任意模板（包括私有模板，只读监督；编辑/删除模板不在 v1 范围内）。
- **FR-24a** 管理端用户列表应包含"模板数"列，用户详情页应列出该用户的模板（ID、标题、可见性、点赞数、创建时间），并链接到管理端模板详情。

### 5.4 模板审核总览

- **FR-25** 模板审核列表应支持服务端分页、按标题/所有者搜索、按可见性（全部/公开/私有）筛选，以及按创建/更新/点赞排序。
- **FR-26** 每行应显示：标题、所有者（名称 + ID）、可见性徽章、类型、语言、标签、点赞数、收藏数、创建/更新日期，以及"查看"操作。
- **FR-27** 管理端模板详情应展示完整模板元数据及所有版本（ID、版本号、创建时间，只读），并提供返回所有者用户详情的链接。
- **FR-28** 审核列表默认按"最近更新"排序，使管理员优先看到新内容。

### 5.5 审计日志

- **FR-29** 每个管理端变更操作（封禁、解禁、角色变更）都应记录到 `admin_audit_logs` 表：id、actor_id、actor_email、action、target_type、target_id、reason、created_at。
- **FR-30** 审计日志页面应按最新优先分页列出条目，并支持按动作类型和操作者筛选。
- **FR-31** 审计条目应不可变（不提供更新/删除端点）。

### 5.6 普通用户侧变更

- **FR-32** 普通应用不应显示任何管理端入口。（未来功能可为管理员在头部下拉菜单加"管理控制台"链接；v1 保持两端完全分离。）
- **FR-33** 登录错误应区分"凭据无效"与"账号已封禁"，使被封禁用户得到可行动的提示。

## 6. 非功能需求

- **NFR-1 安全性。** 管理端端点必须在 API 层对普通用户不可达（每个请求服务端角色校验，而非仅 UI 隐藏）。管理员登录限流（如每 IP 15 分钟 5 次）。封禁必须立即失效会话。
- **NFR-2 性能。** 在 1 万用户 / 10 万模板规模下，用户列表与模板列表端点 p95 < 500ms（role、status、created_at 建索引；优化计数查询）。
- **NFR-3 可审计性。** 无原因不得执行管理端变更；审计日志只追加；操作者始终取自已验证的 JWT（绝不来自客户端提交）。
- **NFR-4 国际化。** 所有管理端 UI 文案通过 i18next 提供中英文，遵循现有 `locales/{en,zh}/translation.json` 模式（管理端命名空间 `admin.*`）。
- **NFR-5 主题。** 管理控制台使用与主应用相同的 Aurora 设计令牌及明暗主题支持。
- **NFR-6 可访问性。** 支持键盘导航（模态框焦点圈定、Escape 关闭）、图标按钮有 ARIA 标签、两种主题下色彩对比度 ≥ 4.5:1。
- **NFR-7 兼容性。** 不破坏现有面向用户的 API；`role`/`status` 列通过幂等迁移添加（init.sql 的 `DO $$ ... IF NOT EXISTS ...` 模式）。
- **NFR-8 数据隐私。** 管理端视图只暴露运营所需数据（绝不显示密码哈希、绝不显示完整 API Key）。为平台运营目的向管理员展示邮箱是可接受的。
- **NFR-9 响应式。** 管理控制台在 ≥ 1024px 下可用；表格在更窄宽度下优雅降级（横向滚动）；移动端（< 768px）尽力而为，非目标。
- **NFR-10 可部署性。** 兼容现有 docker-compose 与 helm chart；不引入新的基础设施依赖。

## 7. 验收标准

**AC-1 管理员登录分离。** 给定一个非管理员账号，当我在 `/admin/login` 提交凭据，则看到"该账号没有管理员权限"，且不签发管理令牌。

**AC-2 管理端路由守卫。** 给定未认证访客访问 `/admin/users`，则被重定向到 `/admin/login?redirect=...`；给定已登录的普通用户，则看到 403 页面。

**AC-3 仪表盘 KPI。** 给定管理员在 `/admin`，则看到总用户/活跃/封禁/总模板/公开模板/创建 Prompt 卡片，数值由服务端正确计算，并有最近注册与最近公开模板列表。

**AC-4 用户搜索与筛选。** 给定 25+ 用户，当我搜索 "gmail" 并筛选 status=banned，则只显示匹配的封禁用户，分页元数据正确。

**AC-5 封禁流程。** 给定一个正常用户，当我以原因 "spam" 封禁，则：状态变为 `banned`；创建审计条目（操作者=我、动作=ban、对象=user、原因）；其下次登录失败并提示"账号已封禁"；其公开模板从公开广场消失；其 API Key 返回 403。

**AC-6 解禁流程。** 给定一个封禁用户，当我以原因"申诉通过"解禁，则状态恢复 `active`，创建审计条目，可重新登录，公开模板重新出现。

**AC-7 角色管理。** 给定一名管理员，当我以原因将某用户提升为管理员，则该用户可登录 `/admin/login` 且列表行显示管理员徽章；当我尝试降级自己，操作被拒绝并给出明确错误。

**AC-8 用户详情。** 给定一个有 3 个模板和 2 个 API Key 的用户，其详情页显示模板数 3、列出模板、列出 API Key 名称/前缀/状态（无密钥明文）。

**AC-9 模板审核列表。** 给定混合公开/私有模板，当我筛选 visibility=private，则只显示私有模板及所有者信息；按点赞排序有效。

**AC-10 审计日志。** 给定此前的封禁/解禁/角色操作，审计日志按最新优先列出操作者、动作、对象、原因、时间；条目不可编辑或删除。

**AC-11 国际化与主题。** 切换语言到中文可翻译所有管理控制台文案；切换主题对所有管理页面生效。

**AC-12 普通端不变。** 给定普通用户，主应用不显示管理链接；公开广场排除被封禁用户的模板。

## 8. 范围之外（v1）

- 发布前模板审核队列（提交 → 批准流程）—— 未来功能。
- 普通用户举报/标记 —— 未来功能（与审核队列配套）。
- 管理员编辑或删除模板 —— v1 为只读监督；下架/删除是后续功能。
- 批量操作（批量封禁、批量角色变更）—— 未来。
- 向被封禁用户发送管理员通知/邮件 —— 未来。
- 管理员管理分类/标签体系 —— 未来功能。
- 超出仪表盘 KPI 的管理端分析（图表、趋势、留存）—— 未来功能。
- 通过 SSO/OAuth 登录管理控制台 —— v1 仅邮箱 + 密码。
- 移动端优化的管理布局（< 768px）—— 尽力而为。
- 管理员邀请流程 / 多租户管理团队 —— 未来。

## 9. 依赖与假设
