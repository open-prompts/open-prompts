# 账号注销 — 需求分析

- **功能 ID：** account-deletion
- **版本：** 1.0
- **状态：** Proposed（待架构评审）
- **作者：** ui-ux-agent
- **日期：** 2026-10-13
- **配套文档：** `account-deletion-ui-ux-design-zh-CN.md`

## 1. 竞品调研摘要

| 产品 | 账号注销模式 | 启示 |
|---|---|---|
| **GitHub** | 设置 → Danger Zone → "Delete your account"；需输入用户名 + 2FA；说明哪些会转移/停止；组织所有权阻断注销 | 显式摩擦（输入确认）防误操作；阻断项需提前呈现 |
| **OpenAI** | 设置 → 数据控制 → 删除账号；邮件确认链接；说明保留期 | 邮件确认回路是账号操作的标准第二因子 |
| **Notion** | 设置 → 成员 → 删除账号；含内容的 workspace 会被阻断并给出指引 | "你拥有他人依赖的东西"必须在注销前解决 |
| **Reddit** | 无自助内容删除；账号停用后帖子保留（用户名脱钩） | 内容与账号分离：社区保留内容，身份被移除 |
| **Vercel/Supabase** | 先删项目再删账号；最终确认弹窗逐项列出后果 | 逐项后果清单（"将删除 X 个模板、Y 个合集……"）管理预期 |
| **PromptBase / FlowGPT** | 注销流程极简或隐藏 | 信任差异化：干净坦诚的退出建立长期信任 |

**综合结论：** v1 的制胜模式是 **GitHub/Vercel 的 "Danger Zone" 模型**：现有 Profile/设置页中的 **Danger Zone 区块**，其"删除账号"操作打开**后果摘要弹窗**（逐项列出将被删除 vs. 匿名化的内容计数），要求**输入单词 `DELETE`**（或用户名）加**密码二次验证**，随后执行 **14 天软删除宽限期** —— 期间禁止登录，但用户可通过恢复流程取消；期满后**硬删除并匿名化**。社区依赖的公开内容（评论、评分）**匿名化而非删除**（Reddit 模式）—— 作者变为"已注销用户"；私有内容（模板、提示词、合集、预设、API key）**删除**。团队所有权阻断注销直至转移（GitHub 模式）。无需邮件基础设施：确认在应用内完成（密码 + 输入确认），宽限期即安全网。

## 2. 问题陈述

1. **没有退出路径。** 后端没有 `DeleteAccount` RPC；想离开的用户没有自助途径，只能找管理员 —— 不可扩展，且违背用户数据控制预期（GDPR 式的被遗忘权）。
2. **信任不对称。** 用户几秒就能注册，却无法注销。对一个处理个人 API key 和内容的平台，干净的退出本身就是信任功能。
3. **级联复杂性无人定义。** 用户注销牵涉：拥有的模板（含他人的 fork、点赞、评论）、他在别人模板下写的评论、评分、关注、屏蔽、合集、预设、API key、通知、团队成员/所有者身份、审计引用。目前没有任何设计定义这些语义。
4. **社区内容两难。** 直接删除用户评论会毁掉他人的对话（楼层变得支离破碎）；删除其公开模板会破坏 fork 谱系和他人的收藏。匿名化 vs. 删除的区分必须明确。

## 3. 目标用户

- **离开的用户：** 想退出并抹除个人数据的任何人。
- **注重隐私的用户：** 通过"能否离开"评估产品的数据实践。
- **管理员（次要）：** 获得清晰的生命周期管理（软删除用户在管理控制台可见，可恢复/强制删除）。
- **社区（隐含）：** 对话与 fork 谱系在用户离开后依然完整。

## 4. 用户故事

- **US-1:** 作为用户，我可以在 Profile 设置的 Danger Zone 中找到"删除账号"，以便无需客服即可发现退出路径。
- **US-2:** 作为用户，确认前我看到逐项摘要（我的模板数、评论数等，区分删除 vs. 匿名化），以便知情决策。
- **US-3:** 作为用户，我必须重新输入密码并输入 `DELETE` 才能确认，以防误删或被盗号删除。
- **US-4:** 作为用户，确认后有 14 天宽限期，期间登录即可取消，以便一时冲动或失误可以挽回。
- **US-5:** 作为用户，宽限期后我的账号与私有数据被永久删除，公开评论/评分被匿名化（"已注销用户"），以便身份被抹除而对话保持完整。
- **US-6:** 作为团队所有者，在转移所有权或解散团队前无法注销，以免队友被遗弃。
- **US-7:** 作为纯 OAuth 用户（无密码），我可以通过提供商重新认证确认注销，以便该流程适用于所有账号类型。
- **US-8:** 作为管理员，我可以在管理控制台看到软删除（待注销）用户，在宽限期内恢复或强制完成删除，以便处理客服请求。
- **US-9:** 作为用户，我的 API key 在软删除时立即吊销，以便离开中的账号在宽限期内无法继续调用 API。
- **US-10:** 作为用户，我可以在注销前导出模板（链接到现有 import-export 功能），以便离开不等于失去作品。

## 5. 功能需求

### 5.1 发现与确认

- **FR-1:** Profile 页（`/profile`）新增 **Danger Zone** 区块（视觉区分，危险色边框），内含"删除账号"操作。所有已认证用户可见。
- **FR-2:** 点击"删除账号"打开弹窗，展示从新端点获取的逐项后果摘要：拥有的模板数（公开/私有）、提示词数、合集数、评论数、评分数、拥有的团队数、API key 数、预设数。弹窗区分**删除**项（模板、提示词、合集、预设、API key、个人数据）与**匿名化**项（评论、评分 —— 内容保留，作者变为"已注销用户"）。
- **FR-3:** 确认需要：(a) 密码账号的密码二次验证 —— 密码错误显示错误并阻断；(b) 纯 OAuth 账号重定向到提供商重新认证（复用现有 OAuth 登录流程）；且 (c) 精确输入单词 `DELETE`。两者都通过后按钮才可用。
- **FR-4:** 弹窗包含指向 import-export 功能的链接（"先导出你的模板"），以及当用户拥有团队时指向 team-collaboration 所有权转移流程的链接。

### 5.2 软删除（宽限期）

- **FR-5:** 确认调用 `POST /api/v1/users/me/delete`（需认证）。后端设置 `users.status = 'pending_deletion'` 与 `users.deletion_scheduled_at = now() + 14 天`，并立即：吊销所有 API key（复用现有 key 删除语义）、失效所有会话、将用户从所有公开界面隐藏（主页返回 404、关注解除、屏蔽保留以策安全）。
- **FR-6:** 宽限期内：凭据登录返回 403 及特定"账号已计划注销"错误，并提供**取消注销**路径（重新认证 + 确认取消后恢复 `status = 'active'`）；用户的公开模板保持可见（社区连续性）但标记为只读（不接受新评论/点赞/fork —— 复用现有封禁用户语义）；其评论保持可见，匿名化推迟到硬删除。
- **FR-7:** 定时任务（webhooks 设计的 DB 驱动到期扫描 ticker 模式，30 秒一轮）查找 `deletion_scheduled_at <= now()` 且 `status = 'pending_deletion'` 的用户并执行硬删除。

### 5.3 硬删除语义

- **FR-8:** **直接删除（级联）：** 拥有的模板（含其版本、别名）、提示词、合集、预设（variable-presets）、API key、通知、关注行、团队成员身份。团队**所有权**是阻断项（FR-11），因此不会有团队被遗弃。
- **FR-9:** **他人对被删用户模板的 fork 保留**（fork 谱系保留）：`forked_from_template_id` 引用保留但源模板行被删除 —— 谱系展示（template-remix-forks-tree）优雅显示"源已删除"。他人对这些模板的收藏/点赞随目标消失而移除；计数随模板一起消失。
- **FR-10:** **匿名化（内容保留、身份移除）：** 用户在他人模板下写的评论（作者变为墓碑"已注销用户"、头像为空 —— comment-replies-threads 结构保持完整）、用户给出的评分（评分行匿名化：`user_id` 置 NULL，聚合平均分不变）、他人在评论中对用户的提及（文本保留 —— 历史记录；提及不再可链接）。
- **FR-11:** **阻断项：** 用户拥有任何团队（team-collaboration 的 owner 角色）时，注销被拒绝并返回 409 及团队名列表；须先转移所有权或解散团队。管理员账号不可自我注销（403，提示联系其他管理员）。
- **FR-12:** `users` 行被匿名化而非删除（保持审计日志与匿名评论的引用完整性）：`email`/`mobile` 覆写为 `deleted+{id}@invalid`、`display_name` = "已注销用户"、`avatar` = NULL、`bio` = NULL、`password_hash` = NULL、`status = 'deleted'`。该行从所有列表与查询中排除。

### 5.4 管理界面

- **FR-13:** 管理员用户列表（`/admin/users`）新增含 `pending_deletion` 的状态筛选；行显示"注销计划于：<日期>"，并提供**恢复**（取消，置为 `active`，写审计日志）与**立即删除**（强制完成硬删除，需填原因，写审计日志）操作。
- **FR-14:** `POST /api/v1/admin/users/{id}/restore` 与 `POST /api/v1/admin/users/{id}/force-delete`（原因必填，3–500 字符）—— 二者以新动作码 `restore_user` / `force_delete_user` 写入现有 `admin_audit_logs`。

### 5.5 取消流程

- **FR-15:** 待注销用户尝试登录时看到专属过渡页："你的账号将于 {日期} 注销"，含**取消注销**（重新认证 → 确认 → 恢复）与**继续等待**（登出）。宽限期内无其他应用访问权限。

## 6. 非功能需求

- **NFR-1（安全）：** 密码二次验证在服务端进行（哈希比对），不信任客户端。输入确认仅为客户端摩擦。所有注销端点要求新鲜认证（现有会话或重新认证）。
- **NFR-2（性能）：** 拥有数千模板的用户的硬删除作为后台任务执行（不在请求路径中）；API 返回 202 语义（由 ticker 接手）。宽限期取消即时生效。
- **NFR-3（隐私）：** 硬删除后，任何 API 响应都不再包含该用户的邮箱、手机号、显示名或头像。匿名化评论仅显示"已注销用户"。审计日志保留管理员操作记录（动作、目标 id、原因）—— 除不可变 id 外无 PII。
- **NFR-4（国际化）：** 所有 UI 文案、错误信息与过渡页 EN/ZH 双语。
- **NFR-5（数据完整性）：** 硬删除按聚合事务执行（可行时用户行 + 级联在同一事务；大账号按模板分块并幂等续跑 —— ticker 重新扫描未完成的删除）。

## 7. 验收标准

- **AC-1:** 用户打开 Profile → Danger Zone 可见 → "删除账号" → 弹窗显示逐项计数（如"3 个模板、12 条评论、1 个团队"），按删除 vs. 匿名化分组。
- **AC-2:** 密码正确且输入 `DELETE` 前，确认按钮保持禁用；密码错误显示行内错误。
- **AC-3:** 确认 → 会话失效、API key 吊销、状态 `pending_deletion`；重新登录显示带计划日期与取消选项的过渡页；取消后恢复完整访问。
- **AC-4:** 宽限期内，用户的公开模板可见但只读（评论/fork 被阻断）；其主页返回 404。
- **AC-5:** 14 天后（或管理员强制删除）：用户行匿名化（邮箱墓碑化、名称"已注销用户"）；拥有的模板/提示词/合集/预设消失；他在他人模板下的评论仍渲染为"已注销用户"；评分聚合不变。
- **AC-6:** 团队所有者尝试注销得到 409 及团队名；转移所有权后注销成功。
- **AC-7:** 他人的、fork 自被删用户模板的模板仍存在；其谱系显示"源已删除"而非链接。
- **AC-8:** 管理员按 `pending_deletion` 筛选用户，恢复一个（审计日志 `restore_user`），带原因强制删除另一个（审计日志 `force_delete_user`）。
- **AC-9:** 纯 OAuth 用户（未设密码）通过提供商重新认证完成注销，无需输入密码。
- **AC-10:** 硬删除后，`GET /api/v1/users/{id}/profile` 返回 404，且任何端点都不返回该用户的原始邮箱/名称。

## 8. 不在范围内（v1）

- 注销待执行的邮件通知（除验证码外无邮件基础设施）。
- 选择性删除（"删我的模板但保留我的评论"）。
- 将数据导出打包进注销流程（仅链接 —— 导出归 import-export 所有）。
- GDPR 正式请求工单 / DSR 流程（自助路径已覆盖删除需求）。
- 被删用户给出的点赞/收藏的匿名化（目标级联删除时计数自然减少或行删除）。
- 任何形式的变现 —— 本产品永久不做。

## 9. 依赖与假设

- **D-1:** `users.status` 已有 `active`/`banned` 值（admin-user-management）；`pending_deletion` 与 `deleted` 扩展该枚举。宽限期只读行为复用封禁用户的内容隐藏语义。
- **D-2:** team-collaboration 定义团队所有权与（按其设计）所有权转移；本功能以拥有团队为阻断条件。
- **D-3:** webhooks 设计的 DB 驱动到期扫描 ticker（30 秒一轮、补跑）是宽限期到期的调度器；account-deletion 新增一个扫描目标。
- **D-4:** comment-replies-threads 与 template-ratings 提供待匿名化的评论/评分结构；template-remix-forks-tree 提供谱系渲染（需"源已删除"状态）。
- **D-5:** admin-user-management 提供用户列表、审计日志与"操作+原因"模式；本功能新增两个动作。
- **D-6:** variable-presets 提供待级联的预设表。
- **D-7:** 假设：OAuth 账号可能没有密码哈希 —— 必须为其提供重新认证路径（US-7）。
- **D-8:** 假设：引用完整性倾向于匿名化 `users` 行而非删除（审计日志、评论引用它）。

## 10. 给架构师的开放问题

1. **users 行匿名化 vs. 删除：** FR-12 为引用完整性选择匿名化。备选：硬删该行并将引用表的外键改为可空（comments.user_id → NULL）。哪种更契合现有 schema 约束？推荐匿名化（schema 改动更少）。
2. **宽限期模板可见性：** FR-6 让公开模板在宽限期内可见但只读。备选：立即隐藏（隐私更干净，社区连续性更差 —— 链接断 14 天后内容照样消失）。推荐可见只读；请确认。
3. **删除任务机制：** 每用户一个事务 vs. 按模板分块幂等续跑（NFR-5）。现有大级联的模式是什么？推荐分块并在用户行上加 `deletion_progress` 标记。
4. **评分匿名化：** 将 `ratings.user_id` 置 NULL 要求该列可空，且"每用户一条评分"的唯一约束将 NULL 视为互异（Postgres 默认）。请确认评分 schema 是否支持，或评分行是否应删除（聚合会变化）。
5. **会话失效：** 现有认证栈是否支持服务端会话吊销（Redis 会话存储或 JWT 黑名单），还是仅客户端登出？宽限期登录阻断必须由服务端强制执行。
