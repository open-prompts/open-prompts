# API 使用历史 — 需求分析

- **Feature ID:** api-usage-history
- **Version:** 1.0
- **Status:** Proposed（待架构评审）
- **Author:** ui-ux-agent
- **Date:** 2026-10-12

## 1. 竞品调研总结

| 平台 | 用量追踪做法 | 关键启示 |
|---|---|---|
| **OpenAI Platform（Usage）** | 按天的用量图表（请求数、token），可按 API key 和项目筛选；默认 30 天窗口；CSV 导出 | 天粒度图表 + key 筛选是两个最常用的控件；用户想知道"哪个 key 在做什么" |
| **Anthropic Console（Usage）** | 最近 API 请求的活动日志（时间、模型、token、延迟、状态）+ 每日聚合图表 | 原始最近请求表与聚合图表回答不同问题（"发生了什么" vs "用了多少"）—— 两者都要 |
| **Stripe Dashboard** | 事件化请求日志（可按状态、方法、路径搜索）+ 聚合图表；日志保留 30 天 | 可搜索、可按状态筛选的请求日志是调试入口；有界保留让表保持小 |
| **GitHub（API usage insights）** | 按集成拆分的限流用量，滚动窗口 | 按凭证（而非仅按账号）呈现用量符合用户实际的集成方式 |
| **PromptBase / FlowGPT / Snack Prompt** | 无 API 用量界面（纯 Web 产品） | 提示词平台没有可借鉴的用量追踪 —— 模式必须来自开发者平台 |
| **Vercel Dashboard** | 带软/硬上限的用量表、按项目拆分、每日图表 | 简单的"本月请求数"表让用户无需图表即可感知规模 |

**综合结论：** v1 的制胜模式是开发者平台的用量页面，范围限定在 Open Prompts 实际拥有的东西：以个人 API key 鉴权的 API，核心调用是模板解析。我们引入轻量的 `api_usage_logs` 表（每个经过 API key 鉴权的请求一行：用户、key id、端点、方法、状态、延迟、时间戳），异步写入以不影响请求路径。用户界面是 "Usage" 页面：(1) 汇总条（总请求数、成功率、平均延迟、使用的 key 数，24h/7d/30d 切换）；(2) 窗口内每日请求柱状图；(3) 可筛选、分页的最近请求表（时间、key 名称、端点、状态、延迟），支持按 key 与状态筛选。保留期有界（90 天），预聚合留待 v2。这是*普通用户*功能（每人只看自己的用量）；管理员在管理控制台获得聚合视图（消费排行、错误率）以发现滥用。

## 2. 问题陈述

1. **API 活动不可见。** 用户创建 API key 并完成集成，但产品对这些 key 发起的调用毫无展示。`api_keys.last_used_at` 是唯一信号 —— 一个时间戳，且 UI 中不可见。
2. **集成调试是盲的。** 当用户的脚本间歇性失败（429？404？key 过期？）时，没有请求日志可查。他们必须自己加日志才能知道 API 返回了什么。
3. **Key 卫生无法进行。** 用户看不到哪些 key 在活跃使用、频率如何、旧 key 是否仍在发请求 —— API Keys 页面只显示名称/前缀/日期。
4. **管理员没有滥用信号。** 管理控制台展示用户数与模板审核，但对 API 消耗毫无感知。失控脚本或滥用集成在伤害基础设施之前是不可见的。

## 3. 目标用户

- **集成者（主要）：** 用 key 调用 API 的用户 —— 需要按请求的可见性来调试、按 key 的拆分来做卫生管理。
- **对 API 好奇的用户：** 想看到"我的 API 被使用了"以感知规模，再决定投入程度。
- **管理员：** 需要聚合消费与错误率信号来发现滥用与容量问题（管理控制台界面）。
- **普通 Web 用户：** 不受影响（Web 会话流量不是 API key 流量，v1 不记录）。

## 4. 用户故事

- **US-U1:** 作为集成者，我希望看到最近的 API 请求（时间、key、端点、状态、延迟），以便无需自己加日志就能调试集成。
- **US-U2:** 作为集成者，我希望按 API key 和状态（成功/错误）筛选请求，以便隔离行为异常的脚本。
- **US-U3:** 作为集成者，我希望看到最近 7/30 天的每日请求图表，以便观察趋势并发现异常。
- **US-U4:** 作为集成者，我希望得到所选窗口内总请求数、成功率、平均延迟的汇总，以便一眼评估集成健康度。
- **US-U5:** 作为集成者，我希望看到每个 key 在窗口内的请求数，以便决定保留或吊销哪些 key。
- **US-U6:** 作为集成者，我希望用量数据严格限定在我的账号内，以便绝不会看到他人的流量。
- **US-U7:** 作为管理员，我希望看到 API 消耗的聚合视图（消费排行、错误率、每日请求数），以便发现滥用并规划容量。
- **US-U8:** 作为用户，我希望旧用量记录自动过期（90 天），以便该功能不会变成隐私负担。

## 5. 功能需求

### 5.1 数据模型

- **FR-1:** 新表 `api_usage_logs`：`id UUID PK`、`user_id TEXT NOT NULL`、`api_key_id UUID NOT NULL REFERENCES api_keys(id) ON DELETE CASCADE`、`endpoint TEXT NOT NULL`（归一化路径模板，如 `/api/v1/templates/{id}/aliases/{alias}`）、`method TEXT NOT NULL`、`status INT NOT NULL`、`latency_ms INT NOT NULL`、`created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()`。索引：`(user_id, created_at DESC)`、`(api_key_id, created_at DESC)`、`(created_at)` 供保留期清理。
- **FR-2:** 日志写入是异步的（响应后即发即忘写入，或网关中的带缓冲 channel）；日志失败绝不导致 API 响应失败或延迟。极端负载下有界内存缓冲丢弃最旧条目（用量日志是尽力而为）。
- **FR-3:** 仅记录经 API key 鉴权的请求（v1 排除 Web 会话流量）。未鉴权请求（401）不记录（无从归属用户）。
- **FR-4:** 保留期：超过 90 天的行由周期清理任务（每日）删除。v1 不做聚合汇总表。
- **FR-5:** 端点路径以归一化形式存储（路径参数替换为 `{id}`/`{alias}` 占位符），使分组可行且资源 id 不泄漏进分析。

### 5.2 普通用户界面（`/usage` 页面）

- **FR-6:** 新路由 `/usage`（需登录；匿名 → 登录重定向），入口在用户下拉菜单与 API Keys 页面（每 key "查看用量" 与页面级链接）。
- **FR-7:** **汇总条**（所选窗口 24h / 7d / 30d，默认 7d）：总请求数、成功率（2xx 占比）、平均延迟、使用的 key 数。
- **FR-8:** **每日图表：** 窗口内每日请求数柱状图（成功与错误堆叠）；零请求日渲染为零高度柱。
- **FR-9:** **按 key 拆分：** 窗口内使用过的 key 表（key 名称、前缀、请求数、错误数、最近使用），按请求数降序；点击 key 筛选请求表。
- **FR-10:** **最近请求表：** 分页（25/页），最新在前；列：时间、key（名称）、端点、方法、状态（颜色编码）、延迟。筛选：key（来自 FR-9）、状态（全部/成功/错误）。每行仅数据（v1 无按请求详情页）。
- **FR-11:** 窗口内无用量时的空态："此期间没有 API 请求" + 链接到 API Playground 发起第一个请求。
- **FR-12:** 所有数据严格限定所有者（`user_id = me`）；无跨用户可见性。

### 5.3 API

- **FR-13:** `GET /api/v1/usage/summary?window=24h|7d|30d` → `{total_requests, success_rate, avg_latency_ms, distinct_keys, daily: [{date, success, error}]}`。需鉴权。
- **FR-14:** `GET /api/v1/usage/requests?key_id=&status=&page=&page_size=` → `{requests: [{id, created_at, key_name, key_prefix, endpoint, method, status, latency_ms}], total, page, page_size}`。需鉴权；限定所有者。
- **FR-15:** `GET /api/v1/usage/keys?window=` → `{keys: [{key_id, key_name, prefix, request_count, error_count, last_used_at}]}`。需鉴权；限定所有者。

### 5.4 管理端界面

- **FR-16:** 管理控制台新增 "API Usage" 页面 `/admin/usage`：平台级汇总（7 天总请求数、错误率、平均延迟）、每日图表、消费 Top-10 用户（用户 id、邮箱、请求数、错误数）、按请求数排序的端点 Top 榜。只读；v1 无按用户下钻（管理员用户详情页的未来用量标签不在本特性范围）。
- **FR-17:** 管理 API：`GET /api/v1/admin/usage/summary?window=`、`GET /api/v1/admin/usage/top-users?window=`、`GET /api/v1/admin/usage/endpoints?window=`。管理会话鉴权；只读。

### 5.5 隐私与删除

- **FR-18:** 用户删除 API key 时，关联用量行级联删除（外键）—— 用量归属于 key，被删 key 的历史随之而去。账号删除（若未来引入）经 user_id 移除所有行。
- **FR-19:** 用量行不含请求体、变量值、以及归属 id 之外的任何个人数据 —— 只有端点、方法、状态、延迟、时间戳。

## 6. 非功能需求

- **NFR-1（性能）：** 异步日志写入对 API 请求路径的额外开销 < 1 ms（带缓冲、非阻塞）。用量查询有索引；30 天窗口汇总 p95 < 500 ms。
- **NFR-2（存储）：** 受保留期（90 天）与限流约束；v1 用户规模下估计 < 100 MB。清理任务每日运行。
- **NFR-3（隐私）：** 处处限定所有者；管理员只见聚合（消费排行展示邮箱以便滥用联系，与现有管理员用户列表一致）。
- **NFR-4（国际化）：** 所有文案通过 i18next 提供 EN/ZH（`usage.*` 命名空间）。
- **NFR-5（无障碍）：** 图表提供可访问的数据表替代（可切换）；状态色配文字；全键盘导航。
- **NFR-6（可靠性）：** 用量日志是尽力而为；其失败绝不影响 API 可用性（熔断：连续写错误时停用日志）。

## 7. 验收标准

- **AC-1:** 发起 3 次经 API key 鉴权的请求后打开 `/usage`（7d 窗口），总请求数 = 3、成功率正确、请求表中出现 3 行。
- **AC-2:** 按 key 筛选只显示该 key 的请求；按状态=错误筛选只显示 4xx/5xx 行。
- **AC-3:** 每日图表与请求表在窗口内按天的计数一致。
- **AC-4:** 按 key 拆分列出每个使用过的 key 及正确计数；点击 key 应用 key 筛选。
- **AC-5:** Web 会话（非 API key）请求不出现在用量中。
- **AC-6:** 删除 API key 移除其用量行；该 key 从拆分中消失。
- **AC-7:** 管理员 `/admin/usage` 显示平台总量与消费排行；普通用户无法访问管理用量 API（403）。
- **AC-8:** 清理任务清除超过 90 天的行。
- **AC-9:** 所有文案 EN/ZH 已翻译；无硬编码文案。
- **AC-10:** 功能中没有任何变现相关内容（无配额、无按层级限额、无计费概念）。

## 8. 不做范围

- 基于用量的配额、限流分层或任何限额执行（仅可观测）。
- 任何形式的变现（支付、定价、购买、收益）—— 本产品永久不做。
- Web 会话流量记录；按请求详情页；请求/响应体捕获。
- 聚合汇总表（规模需要时 v2）；CSV 导出；用量告警/webhook。
- 按用户的管理端下钻（管理员用户详情用量标签 —— 未来）。

## 9. 依赖与假设

- **D-1:** 网关（`backend/cmd/server/main.go`）是识别经 API key 鉴权请求（经 `AuthInterceptor.VerifyAPIKey` / `VerifyHTTPRequest`）并可记录端点、方法、状态、延迟的唯一咽喉点。
- **D-2:** 现有 `api_keys` 表与仓库提供 key 归属（`api_key_id`）；`UpdateLastUsed` 已异步运行 —— 同一模式可扩展到用量日志。
- **D-3:** user-dashboard 功能的 `/dashboard` 已存在（或将存在），是未来用量小部件的家；v1 从 API Keys 页面与用户下拉菜单进入即可。
- **D-4:** 管理控制台现有的列表页模式（筛选 + 表格 + 分页）被 `/admin/usage` 复用。
- **D-5:** 图表渲染使用轻量无依赖方案或已有的图表库（若存在）；设计不假定特定库。

## 10. 给架构师的开放问题

1. **写入路径：** 用量日志应放在网关（net/http 中间件包裹 handler，路由级已知归一化路径）还是 gRPC 服务（经拦截器）？网关知道 REST 路径与状态；服务知道 RPC —— 哪个是更干净的唯一咽喉点？鉴权后网关能否拿到 `api_key_id`（目前只解析出 user id）？
2. **异步机制：** 进程内带缓冲 channel + 后台刷写，还是每请求直接异步 INSERT（类似 `UpdateLastUsed`）？你建议的缓冲大小/丢弃策略是什么？
3. **归一化路径：** 确认归一化映射（如 `/api/v1/templates/{id}/aliases/{alias}`）应是网关中的静态路由表查找，而非正则后处理。
4. **保留任务：** 复用已有的 cron/调度器（若存在，如管理统计？清理？），还是在服务中引入简单的 time.Ticker？它应放在哪里？
5. **管理端消费排行邮箱可见性：** 管理员用户列表已展示邮箱；确认消费排行中同样的可见性可接受（推荐，便于滥用联系）。
