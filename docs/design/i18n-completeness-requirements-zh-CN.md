# 国际化完整性与质量 — 需求分析

| | |
|---|---|
| **Feature ID** | FE-011 |
| **Version** | 1.0 |
| **Status** | Proposed（待架构评审） |
| **Author** | ui-ux-agent |

## 1. 竞品研究

| 产品 | 国际化方式 | 优点 | 缺点 |
|---|---|---|---|
| PromptBase | 仅英文 | — | 不服务国际用户 |
| FlowGPT | 英文 + 机翻子集 | 覆盖面广 | 质量参差，UI 混杂语言 |
| AIPRM | 英、德、法、西、葡 + 社区翻译；日期本地化 | 社区规模化翻译 | 无可见的键位一致性 CI；缺失键泄漏英文 |
| ChatGPT | 数十种语言；页面级本地化标题；复数感知文案 | 业界标杆级打磨 | — |
| Vercel/Linear（SaaS 基准） | 一切本地化：标题、日期、数字、复数；CI 校验键位一致性 | 专业感；无混杂语言泄漏 | — |

**结论：** 产品已有扎实的 EN/ZH 基础（各 378 个键，当前完全一致，日期本地化）。缺少的是*保障*：新增键时没有任何机制防止漂移，复数未处理，页面标题是静态英文，54 个死键在累积。感觉"原生"的竞品赢在保障机制，而非原始覆盖率。

## 2. 问题陈述

对 `frontend/src/locales/{en,zh}/translation.json` 及全部 `t()` 调用点的审计发现：

1. **无漂移防护。** EN 与 ZH *当前*一致（各 378 键），但没有任何强制。开发者只加 EN 键就会上线一个 ZH UI 静默回退英文的版本——无报错、无警告，只有用户能发现。
2. **死键累积。** 存在 54 个已定义未使用的键（如 `admin.reasonModal.consequence_*`、`admin.common.per_page`），每次功能迭代都增加翻译成本和漂移面。
3. **英文复数错误。** 三个键插入 `{{count}}` 但未使用 i18next 复数形式：`"{{count}} items"` 会渲染为 "1 items"。中文无复数屈折，该缺陷只藏在 EN 语言包中。
4. **静态页面标题。** `<title>Open Prompts</title>` 从不变化——无路由级标题、无本地化。浏览器标签页、历史记录和书签无论语言和页面都显示英文。
5. **静态 `<html lang="en">`。** 屏幕阅读器为 ZH 用户播报错误语言（无障碍设计已标记；归属该功能，此处仅引用）。
6. **后端错误原文透出。** API 错误消息（网关返回英文）在 ZH 用户的 toast 中原样展示，破坏原生 UI 的体验。
7. **用户侧数字未格式化。** 点赞/收藏数渲染为原始整数；管理端有 `formatNumber` 但用户页面未使用区域分组。

## 3. 目标用户

- **中文用户**：目前在边缘场景（复数、标题、后端错误）看到英文泄漏。
- **所有用户**：受益于专业的页面级标题和格式化数字。
- **开发者**：需要 CI 在 i18n 回归上线前拦截。
- **译者/未来贡献者**：需要干净、无死键的词条目录。

## 4. 用户故事

- **US-1**：作为 ZH 用户，我希望所有 UI 文案都是中文，体验中不泄漏英文。
- **US-2**：作为 EN 用户，我希望复数正确（"1 item"、"2 items"），UI 读起来自然。
- **US-3**：作为用户，我希望浏览器标签标题反映当前页面和语言，以便找到并返回正确的标签页。
- **US-4**：作为 ZH 用户，我希望后端错误消息以中文呈现，以便理解失败原因。
- **US-5**：作为用户，我希望计数（点赞、收藏、结果数）按我的区域格式化，数字读起来自然（1,234 vs 1234）。
- **US-6**：作为开发者，我希望 EN/ZH 键位分叉或代码引用缺失键时 CI 失败，回归永不上线。
- **US-7**：作为开发者，我希望未使用键被报告，词条目录保持干净，翻译工作不浪费。
- **US-8**：作为屏幕阅读器用户，我希望 `<html lang>` 与 UI 语言一致，发音正确（由无障碍功能交付；此处跟踪覆盖）。

## 5. 功能需求

### 5.1 一致性与漂移防护（CI）

- **FR-1**：CI 检查必须对比 `en/translation.json` 与 `zh/translation.json` 的扁平化键集合，任一方向不一致即失败，并列出问题键。
- **FR-2**：CI 检查必须从 `frontend/src/**/*.{js,jsx}` 提取所有 `t('...')` 字面量，引用键在 EN 目录缺失即失败（缺失键检查）。
- **FR-3**：CI 检查必须报告目录中已定义但代码未引用的键（未使用键检查），作为**警告**而非失败，列出待清理。
- **FR-4**：CI 检查必须对比每个键 EN 与 ZH 的插值占位符（`{{var}}`），不匹配即失败（如 EN 用 `{{name}}`，ZH 缺失）。
- **FR-5**：所有检查合并为单一脚本（`npm run i18n:check`），本地与 CI 均可运行；任一失败退出码非零。

### 5.2 复数正确性

- **FR-6**：所有 `{{count}}` 键必须迁移为 i18next 复数形式键（EN 用 `key_one`/`key_other`；ZH 用 `key_other`），使英文正确渲染 "1 item" / "2 items"。
- **FR-7**：迁移现有三个计数键（`admin.common.total_count`、`admin.common.per_page`、`admin.reasonModal.char_count`）；`char_count`（"12 / 500" 计数器）豁免复数化并注明。

### 5.3 本地化页面标题

- **FR-8**：每个路由必须将 `document.title` 设置为本地化的页面专属文案，模式为 `"{Page} · Open Prompts"`（EN）/“{页面} · Open Prompts”（ZH）。
- **FR-9**：覆盖路由：首页、登录、注册、个人资料、API 密钥、模板详情（`{title} · Open Prompts`）及全部 `/admin/*` 页面。
- **FR-10**：标题更新必须在单一可复用 hook（`usePageTitle`）中实现，读取当前语言并在切换语言时无需刷新即更新标题。

### 5.4 后端错误本地化

- **FR-11**：API 错误拦截器必须将已知后端错误签名（HTTP 状态 + 错误码/消息模式）映射为本地化的用户可读消息后再展示。
- **FR-12**：无法映射的错误回退到通用本地化消息（"出错了"），原始后端消息放在 `title` 工具提示/可展开详情中，绝不替代本地化标题。
- **FR-13**：映射表必须存放在语言包（`errors.*` 命名空间）中，新增翻译无需改代码。

### 5.5 数字格式化

- **FR-14**：用户侧计数（点赞数、收藏数、模板列表总数）必须使用 `Intl.NumberFormat` 按当前语言区域格式化。
- **FR-15**：`utils/adminFormat.js` 中现有的 `formatNumber` 必须提升为共享的 `utils/format.js`，管理端与用户侧共用（管理端行为不变）。

### 5.6 词条目录治理

- **FR-16**：必须审计现有 54 个未使用键：属于即将上线功能（按设计管线）的键保留并加注释白名单；其余在本功能落地时一并删除。
- **FR-17**：顶层裸字符串 `welcome` 必须规范化为命名空间（`welcome.title`），同步更新其唯一使用点。

### 5.7 普通用户与管理员划分

- **普通用户**：在所有用户界面受益于 FR-6..15（复数、标题、错误、数字）。
- **管理控制台**：`/admin/*` 路由同样受益（FR-9 标题、FR-11 错误）；管理端计数键在 FR-7 迁移复数。不引入管理端专属设置——语言仍由现有顶栏切换。

## 6. 非功能需求

- **NFR-1（性能）**：`i18n:check` 5 秒内完成；标题更新同步且廉价（无数据拉取）。
- **NFR-2（健壮性）**：错误映射拦截器绝不掩盖网络层故障（超时、离线）——这些保持现有处理。
- **NFR-3（兼容性）**：除列出的改进外无用户可见行为变化；已上线代码使用的键路径不变，仅复数迁移与 `welcome` 规范化除外（均在同一变更中更新代码）。
- **NFR-4（可维护性）**：一致性脚本零依赖（Node 内置模块），避免供应链负担。
- **NFR-5（无障碍）**：`document.title` 变化会被屏幕阅读器作为页面变化播报；`<html lang>` 同步由无障碍功能交付，是完整效果的前提。
- **NFR-6（国际化）**：所有新文案（标题、错误映射）同时提供 EN 与 ZH，由 FR-1 强制。

## 7. 验收标准

- **AC-1**：仅从 ZH 删除一个键后运行 `npm run i18n:check`，CI 失败并列出该键名。
- **AC-2**：在任意组件加入 `t('typo.key')` 后运行检查，失败并列出缺失键。
- **AC-3**：某键 EN 含 `{{name}}` 而 ZH 缺失时，占位符检查失败。
- **AC-4**：EN UI 渲染 "1 item" 和 "2 items"；ZH 从同一调用点渲染“1 项”和“2 项”（或自然的中文表述）。
- **AC-5**：导航到模板详情后标签标题为模板名；切换语言无需刷新即更新。
- **AC-6**：后端 409 冲突在 ZH 下呈现本地化消息；未知 500 显示通用本地化标题并可查看原始详情。
- **AC-7**：1,234 个点赞的模板在 EN 显示 "1,234"，ZH 显示 "1,234"（均按 `zh-CN` 惯例分组）。
- **AC-8**：清理后 `npm run i18n:check` 在 main 上通过；未使用键报告为空或已显式白名单。
- **AC-9**：`welcome` 字符串在规范化前后渲染一致。
- **AC-10**：所有检查在 CI 中随现有门禁在每个 PR 上运行。

## 8. 范围外

- 新增 EN/ZH 之外的语言（结构已就绪；新语言是未来决策）。
- 服务端内容本地化（模板内容、用户生成文本保持原样）。
- 本地化邮件/验证码消息（后端领域）。
- 从右到左（RTL）语言支持。
- 应用内语言偏好页面（现有顶栏切换仍是唯一入口）。
- 翻译记忆库 / 外部翻译工具集成。

## 9. 依赖与假设

- **D-1**：i18next 配置了 `fallbackLng: 'en'` 与 LanguageDetector；复数后缀（`_one`/`_other`）在捆绑的 i18next 版本下无需额外配置即可工作。
- **D-2**：所有 `t()` 调用点使用单引号字面量键（审计确认；无动态键构造），静态提取可靠。
- **D-3**：后端错误以稳定形态（消息字符串和/或错误码）到达，拦截器可模式匹配；映射表优雅降级到通用消息。
- **D-4**：无障碍功能交付 `<html lang>` 同步；本功能仅在其屏幕阅读器标题播报效果上依赖，功能行为不依赖。
- **D-5**：CI 可运行 Node 脚本（现有门禁已具备）。

## 10. 给架构师的开放问题

1. **错误映射粒度**：拦截器应仅按 HTTP 状态映射（粗粒度、稳定），还是按后端错误字符串/错误码（精确、脆弱）？设计假设状态 + 少量已知消息模式，以语言包为唯一事实来源。
2. **未使用键策略**：仅警告（FR-3）还是宽限期后失败？设计假设仅警告，避免阻塞先加键后加代码的功能分支。
3. **复数迁移时机**：三个计数键都在管理端界面；确认没有进行中的管理端改动与重命名为 `_one`/`_other` 变体冲突。
4. **`usePageTitle` 位置**：各页面组件内 hook，还是 `App.js` 中集中式路由变化 effect？设计假设逐页 hook（显式、可测试）——请确认偏好。
