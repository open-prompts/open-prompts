# 提示词分析 — 需求分析

- **功能标识:** prompt-analytics
- **版本:** 1.0
- **状态:** 已提案（待架构评审）
- **作者:** ui-ux-agent
- **日期:** 2025-06-25

## 1. 竞品研究摘要

| 平台 | 分析方式 | 关键启示 |
|---|---|---|
| **PromptBase** | 卖家仪表盘：销量、浏览、收入时间序列；单个商品统计；转化（浏览→购买） | 创作者被专属仪表盘激励；时间序列图是核心；转化漏斗是差异化点 |
| **FlowGPT** | 每个提示词公开展示浏览/点赞/收藏计数；创作者主页聚合；趋势按互动排名 | 公开计数形成社会认同并驱动排名；单条计数是基本要求 |
| **Snack Prompt** | 浏览计数、点赞、"remix"（使用）按提示词展示；创作者页聚合 | "使用"计数是提示词市场版的转化指标 |
| **AIPRM** | 每个提示词的浏览、投票、使用计数；库按这些指标排序 | 使用计数是提示词市场首要的质量信号 |
| **PromptHero** | 单条浏览与点赞计数；Hot 排名来自近期互动 | 时间窗互动（而非终身总数）驱动发现 |
| **通用创作者平台（YouTube/Medium/GitHub）** | 创作者分析：浏览/阅读时间序列、热门内容、流量来源、受众地域 | 时间范围选择器（7/30/90 天）、热门内容表、单一总览页是标准形态 |

**综合结论:** 持续出现两个界面：(1) **公开的单模板计数**（浏览、使用、点赞、收藏）形成社会认同并供给排名；(2) **私有创作者分析仪表盘**，含时间序列图、时间范围选择器和热门模板表。转化式指标（浏览→使用）是 PromptBase 值得低成本借鉴的差异化点（一个比率，而非漏斗）。

## 2. 问题陈述

Open Prompts 记录点赞、收藏和提示词实例化（`prompts` 表），但没有将其作为分析能力暴露：

1. **没有浏览追踪。** 无论是创作者还是平台都不知道模板被浏览多少次。最强的互动信号完全缺失。
2. **没有使用追踪界面。** `prompts` 表记录实例化（Web），`template_aliases` + `GetPromptByAlias` 服务 API key 使用，但产品中没有任何聚合的"使用"指标。
3. **没有创作者仪表盘。** 拥有 20 个模板的创作者无法看到哪些表现好、互动如何趋势化、编辑后发生了什么。仅有信号是每张卡片上的点赞/收藏计数。
4. **没有时间维度。** 所有计数都是终身总数；无法看到"最近 30 天"活动，而这才是创作者真正据此行动的。
5. **公开页面信息不足。** 模板详情展示点赞/收藏计数但不展示浏览/使用，相对所有竞品削弱了社会认同。

## 3. 目标用户

- **创作者（主要）:** 发布模板并想了解表现的用户 —— 哪些模板获得浏览、哪些把浏览转化为使用、编辑后趋势如何。
- **浏览者（次要）:** 从公开模板页更丰富的社会认同（浏览/使用计数）中受益。
- **管理员（间接）:** 平台级分析不在 v1 范围（见 §8），但此处引入的事件表是基础。

## 4. 用户故事

### 4.1 创作者

- **US-A1:** 作为创作者，我希望有一个私有分析页，展示所选时间范围内我所有模板的浏览、使用、点赞、收藏总量，以便了解整体表现。
- **US-A2:** 作为创作者，我希望每个指标有每日时间序列图，以便发现趋势并对变化做出反应。
- **US-A3:** 作为创作者，我希望有按范围内使用量（或浏览量）排名的热门模板表，以便知道该投资哪些模板。
- **US-A4:** 作为创作者，我希望在模板页（作为所有者时）看到单模板详细统计（浏览、使用、点赞、收藏、浏览→使用率），以便评估单个模板。
- **US-A5:** 作为创作者，我希望将时间范围与上一个等价范围比较（如本 30 天 vs. 上 30 天），以便知道是否在增长。
- **US-A6:** 作为创作者，我希望看到按来源（Web UI vs. API key）的使用拆分，以便了解模板如何被消费。

### 4.2 浏览者

- **US-A7:** 作为访客，我希望在模板详情页看到浏览和使用计数，以便在使用前判断模板的受欢迎程度。

### 4.3 系统

- **US-A8:** 作为系统，我在模板详情页渲染时记录浏览事件（按会话去重），以便浏览计数有意义且不被灌水。
- **US-A9:** 作为系统，我在从模板实例化提示词时（Web `CreatePrompt` 或 API `GetPromptByAlias`）记录使用事件，以便使用指标覆盖两个界面。
- **US-A10:** 作为系统，我保持事件数据最小化（无提示词内容、无变量、除可选 user id 外无 PII），以便分析存储隐私安全。

## 5. 功能需求

### 5.1 事件采集

- **FR-1:** 系统应在用户（认证或匿名）每次加载模板详情页时记录该模板的 `view` 事件。
- **FR-2:** 浏览去重：每个（模板, 会话）每 30 分钟最多一个浏览事件；会话由存储在 localStorage 的客户端生成 id（匿名）或用户 id（认证）标识。
- **FR-3:** 系统应在通过 Web UI 从模板创建提示词（`CreatePrompt`）时记录来源为 `web` 的 `use` 事件。
- **FR-4:** 系统应在通过 API key 以别名获取模板版本（`GetPromptByAlias`）时记录来源为 `api` 的 `use` 事件。
- **FR-5:** 事件应存储：`id`、`template_id`、`event_type`（`view`|`use`）、`source`（`web`|`api`）、`user_id`（可空）、`session_id`（可空，仅浏览）、`created_at`。无提示词内容、变量或其他 PII。
- **FR-6:** 点赞与收藏事件已存在（`template_likes`、`template_favorites` 带时间戳）；分析应从这些表聚合而非重复记录事件。
- **FR-7:** 事件写入绝不阻塞或导致触发它的用户操作失败（即发即弃的缓冲异步写；高负载下丢失分析数据可接受）。

### 5.2 公开计数

- **FR-8:** 模板详情页应向所有访客展示浏览计数与使用计数，与既有点赞/收藏计数并列。
- **FR-9:** 系统应在 `templates` 表维护反规范化的 `view_count` 与 `use_count` 列（事件写入时递增）以低成本公开展示；事件表仍是时间序列的事实来源。
- **FR-10:** v1 中 PromptCard 仅在布局无需重设计即可容纳时展示紧凑浏览计数（如 "1.2k"）；否则计数仅出现在详情页。*（决策：v1 仅详情页 —— 见 §8。）*

### 5.3 创作者分析页

- **FR-11:** 私有分析页应位于 `/analytics`（需登录；匿名时重定向到登录页）。
- **FR-12:** 页面应提供时间范围选择器：最近 7 天 / 30 天 / 90 天（默认 30）。
- **FR-13:** 页面应展示四个 KPI 卡片 —— 浏览、使用、新增点赞、新增收藏 —— 每个含范围总量与相对上一等价范围的百分比变化。
- **FR-14:** 页面应展示每日时间序列图，带指标切换（浏览 / 使用 / 点赞 / 收藏；默认 浏览+使用），对应所选范围。
- **FR-15:** 页面应展示范围内按来源（Web vs. API）的使用拆分，形式为两段条形或占比展示。
- **FR-16:** 页面应展示热门模板表（范围内按使用量前 10，其次浏览量）：列 —— 模板标题、浏览、使用、新增点赞、新增收藏、浏览→使用率 —— 每行链接到模板详情页。
- **FR-17:** 所选时间范围应反映在 URL（`?range=7|30|90`）并可通过深链恢复。

### 5.4 单模板所有者统计

- **FR-18:** 当登录用户是模板所有者时，模板详情页应展示仅所有者可见的统计区：四个计数、浏览→使用率、以及最近 30 天浏览+使用的每日迷你图（sparkline）。
- **FR-19:** 所有者统计应对非所有者隐藏（他们只看到 FR-8 的公开计数）。

### 5.5 API

- **FR-20:** 新 RPC `GetTemplateStats(template_id, days)` → 四个指标的每日序列、范围总量、来源拆分与浏览→使用率。REST：`GET /api/v1/templates/{id}/stats?days=30`。仅所有者（非所有者 403）。
- **FR-21:** 新 RPC `GetCreatorStats(days)` → 认证用户模板的聚合 KPI（含上一范围差值）、每日序列、来源拆分与热门模板列表。REST：`GET /api/v1/analytics/overview?days=30`。
- **FR-22:** 新 RPC `RecordTemplateEvent(template_id, event_type, session_id)` → 记录浏览事件（使用事件由服务端在 CreatePrompt/GetPromptByAlias 内记录，而非客户端）。REST：`POST /api/v1/templates/{id}/events`，body `{type: "view", session_id: "..."}`。允许匿名；限流。
- **FR-23:** `days` 仅接受 7、30、90；其他值 → 400 或回退到 30（服务端决策；为架构师记录）。
- **FR-24:** 聚合查询应按天（UTC）在数据库分桶，返回长度与范围一致的 `[{date, views, uses, likes, favorites}]` 数组。

### 5.6 普通用户与管理员划分

- **FR-25:** v1 所有分析均为普通用户界面（创作者 = 拥有模板的普通用户）。无管理员分析页；管理员仪表盘（admin-user-management 功能）仅展示平台 KPI，不消费本功能的端点。
- **FR-26:** 管理员作为创作者时与任何用户一样看到自己的创作者分析；管理员角色不授予访问他人分析的权限。

## 6. 非功能需求

- **NFR-1（性能）:** 事件写入路径对触发请求增加 <5ms p99（异步缓冲）；分析读端点对拥有 ≤1,000 模板、≤100 万事件的创作者 p95 < 800ms（按日聚合 + 索引）。
- **NFR-2（规模）:** 大规模时可能需要事件表分区或保留策略（如原始事件保留 180 天，每日汇总永久保留）；v1 以无分区 + 索引上线并记录汇总路径（架构师决策，见 D-4）。
- **NFR-3（隐私）:** 事件中无提示词内容或变量；user_id 可选；session_id 是随机客户端 id 而非追踪 cookie；分析数据绝不向第三方暴露。
- **NFR-4（兼容性）:** 无破坏性变更；新列（`view_count`、`use_count`）默认 0；既有客户端不受影响。
- **NFR-5（准确性）:** 计数是最终一致的（异步写入可能延迟数秒）；UI 不需要实时精度。
- **NFR-6（无障碍）:** 图表必须有可访问替代（表格切换或 `aria` 摘要）；KPI 卡片与表格可键盘导航（见 UI/UX 文档 §10）。
- **NFR-7（国际化）:** 所有新增字符串 EN/ZH 同步；数字按 locale 格式化（通过 i18next 的 1.2k / 1,200 惯例）。
- **NFR-8（安全）:** 统计端点强制所有权（FR-20/21）；事件端点限流（如 60 请求/分钟/IP）并校验模板存在；无注入面（参数化聚合 SQL）。
- **NFR-9（可观测性）:** 事件记录器每分钟记录事件数与缓冲丢弃数；读端点记录查询时长与行数。

## 7. 验收标准

- **AC-1:** 匿名访客加载模板详情页会递增其浏览计数（刷新可见）并记录浏览事件；30 分钟内刷新不会重复计数。
- **AC-2:** 在 Web UI 从模板创建提示词记录来源 `web` 的 `use` 事件；通过 API key 以别名获取模板版本记录来源 `api` 的 `use` 事件。
- **AC-3:** 模板详情页向所有访客展示浏览与使用计数。
- **AC-4:** 所有者查看其模板详情页看到所有者统计区（计数、浏览→使用率、30 天迷你图）；非所有者看不到。
- **AC-5:** `/analytics` 将匿名用户重定向到登录页；登录用户看到默认 30 天范围的 KPI 卡片、图表、来源拆分与热门模板表。
- **AC-6:** 切换范围到 7 或 90 天会更新 KPI、图表与表格，以及 URL（`?range=7`）。
- **AC-7:** KPI 卡片展示相对上一等价范围的百分比变化（如 30 天范围与前 30 天比较）。
- **AC-8:** 热门模板表按范围内使用量排名，链接到模板详情页，并展示浏览→使用率。
- **AC-9:** `GET /api/v1/templates/{id}/stats` 对非所有者返回 403，对所有者返回完整统计。
- **AC-10:** 零模板的用户在 `/analytics` 看到有意义的空状态（说明 + 创建模板链接）。
- **AC-11:** 所有新增 UI 字符串在 `en` 与 `zh` 翻译文件中存在且键集一致。
- **AC-12:** 既有点赞/收藏计数与行为不变（无回归）。

## 8. 范围外（v1）

- 平台级/管理员分析（admin-user-management 的管理员仪表盘覆盖平台 KPI；更深入的分析后续再做）。
- 受众地域、流量来源/引荐、设备分布。
- 超出浏览→使用比率的转化漏斗。
- 按版本分析（v1 在模板级聚合）。
- 实时流式分析。
- 邮件/每周摘要报告。
- 分析数据 CSV 导出。
- PromptCard 浏览计数展示（v1 仅详情页）。
- 事件保留汇总任务（作为未来工作记录，D-4）。
- 模板内容 A/B 测试。
- 带聚合统计的公开创作者主页。

## 9. 依赖与假设

- **D-1:** `template_likes` 与 `template_favorites` 行带有可用于时间序列聚合的 `created_at` 时间戳（schema 已确认）；若没有，点赞/收藏序列降级为终身总数（架构师验证）。
- **D-2:** `prompts` 表的 `created_at` 提供历史使用事件用于回填；v1 可以从中回填 `use` 事件或简单地并行聚合它 —— 由架构师选择（建议回填，这样第一天的图表不是空的）。
- **D-3:** `GetPromptByAlias`（API 路径）可以在不改变其响应契约的情况下在服务端插桩。
- **D-4:** 新表 `template_usage_events` + (`template_id`, `created_at`) 与 (`user_id`, `created_at`) 索引；`templates` 增加 `view_count`/`use_count` 整数列默认 0。汇总/保留策略是记录在案的未来优化（NFR-2）。
- **D-5:** 前端没有图表库；v1 图表是自定义轻量 SVG 组件（无新依赖）。添加 recharts 是开发者可以提出的替代方案；设计兼容两者（见 UI/UX 文档 §11）。
- **D-6:** 浏览去重的会话 id 是 localStorage 中的随机 UUID（`op_analytics_sid`），首次访问时创建；不与任何第三方共享。
- **D-7:** `/analytics` 路由需要既有认证守卫模式（类似 `/profile`）；无新认证机制。
- **D-8:** 时区：所有聚合使用 UTC；UI 展示日期不做时区转换（日期标签为 YYYY-MM-DD），v1 可接受。
- **D-9:** 公开事件端点（FR-22）的限流假设网关可以应用按 IP 限制（既有中间件或简单内存限流器；架构师确认机制）。
