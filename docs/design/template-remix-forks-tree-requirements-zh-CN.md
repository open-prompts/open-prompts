# 模板 Remix 与 Fork 树 — 需求分析

- **功能标识:** template-remix-forks-tree
- **版本:** 1.0
- **状态:** 已提案（待架构评审）
- **作者:** ui-ux-agent
- **日期:** 2026-10-12

## 1. 竞品研究摘要

| 平台 | Fork/Remix 方式 | 关键启示 |
|---|---|---|
| **GitHub** | 仓库头部显示 fork 数；fork 列表页；fork 页面显示"forked from 父仓库"标签；fork 网络图 | 归属标签 + fork 数是最小可行的谱系 UX；完整网络图属于高级用户功能，很少被访问 |
| **Scratch** | 著名的"remix 树"：每个项目显示其 remix 及 remix 谱系；remix 来源在项目页永久署名 | Remix 树是所有 UGC 平台中最强的社区回路：它把复制变成一种*有署名的创作行为*而非剽窃 |
| **Hugging Face** | 模型页显示"副本"/衍生（如 DreamBooth 社区 fork）；"模型树"列出微调衍生 | 衍生列表把热门基础模型变成枢纽：浏览 fork 本身就是一个发现面，而不只是记录 |
| **FlowGPT** | 用户随意复制提示词，无署名、无 fork 追踪 | 反面教材：没有谱系就没有 remix 署名、没有通过衍生发现的路径、创作者也得不到参与信号 |
| **CodePen** | 每个 pen 上有 Fork 按钮；fork 出的 pen 显示"A fork of {pen} by {user}"；卡片显示 fork 数 | 标题正下方一行"forked from"署名是用户秒懂的模式 |
| **Glitch** | "Remix"创建副本；remix 的应用显示"Remixed from {app}" | "Remix"的措辞让复制显得协作；署名行始终可见 |
| **PromptBase** | 无 fork 概念；提示词付费，禁止复制 | 证实 fork 是社区平台功能而非市场功能 —— 与本项目无货币化范围一致 |

**综合结论:** GitHub/Scratch/CodePen 的胜出模式是三个界面：(1) 卡片与详情页上的 **fork 计数**作为社会证明；(2) fork 模板上的 **"forked from" 署名行**；(3) 源模板上的 **fork 列表**用于发现。完整的交互式网络图（GitHub 式）对 v1 过重；**缩进谱系树**（上游链 + 有限深度的下游）以极小的复杂度交付核心价值。Open Prompts 已有 fork *动作*（`ForkTemplate` 将标题/描述/标签/分类/语言/内容复制为新的私有模板并通知所有者），但**完全没有记录谱系**：副本与原创无法区分，fork 计数在整个产品中不存在，创作者也看不到自己的作品如何传播。

## 2. 问题陈述

1. **没有谱系记录。** `ForkTemplate` 创建新模板时不引用其来源。fork 一旦完成，连接就永久丢失 —— 平台无法回答"它从哪来？"或"它衍生出了什么？"。
2. **没有 fork 社会证明。** 模板有 `like_count` 和 `favorite_count`，但 fork 数 —— 模板*好用到值得在其上构建*的最强信号 —— 既不追踪也不展示。
3. **没有 remix 署名。** fork 出的模板把别人的标题、描述、内容当作从零创作来呈现。原作者只收到一条通知，没有持久的公开署名，fork 者的受众也找不到原作。
4. **没有衍生发现。** 找到好模板的用户无法浏览其 fork 来发现改进版或特化版 —— 这是 Scratch 和 Hugging Face 上被验证过的发现面。
5. **fork 后没有引导。** fork 成功后用户只看到一条 toast，没有指向新模板的链接；必须自己去库里找。

## 3. 目标用户

- **浏览者/潜在用户:** 通过 fork 数和 fork 列表判断模板的实用性并发现变体。
- **Fork 者:** 希望署名流向原作者、希望快速到达自己的新 fork、希望看到自己的 fork 在谱系中的位置。
- **创作者（源所有者）:** 希望看到模板传播多远（fork 数、fork 列表、树）—— 这是可用的最深参与信号。
- **管理员:** 审核时需要只读的谱系上下文（例如从热门原创批量 fork 的垃圾模板）。

## 4. 用户故事

### 4.1 社会证明与署名（阅读）

- **US-FK1:** 作为浏览者，我希望在模板卡片和详情页看到 fork 数，以便判断有多少人在此模板上构建。
- **US-FK2:** 作为浏览者，我希望在 fork 的模板上看到"fork 自 {作者} 的 {标题}"署名行，以便访问原作并让署名流向创作者。
- **US-FK3:** 作为浏览者，我希望知道 fork 取自源模板的哪个版本，以便判断 fork 的新旧程度。
- **US-FK4:** 作为浏览者，我希望署名行在源模板被删除时优雅降级，以便页面永不出现死链。

### 4.2 Fork 探索（发现）

- **US-FK5:** 作为浏览者，我希望在模板详情页看到"Forks"区列出其公开 fork，以便发现变体。
- **US-FK6:** 作为浏览者，我希望看到模板的谱系树（上游 + 下游），以便一眼理解 remix 链。
- **US-FK7:** 作为浏览者，我希望在树中看到自己的私有 fork，以便在它们保持私有的同时也能找到自己的衍生作品。

### 4.3 Fork（写入）

- **US-FK8:** 作为 fork 者，我希望 fork 确认框告知新模板将与源模板关联，以便在确认前理解署名机制。
- **US-FK9:** 作为 fork 者，我希望 fork 成功后有"查看 Fork"入口，以便立即开始编辑。
- **US-FK10:** 作为 fork 者，我希望可以 fork 一个 fork，以便自然形成 remix 链。

### 4.4 创作者与管理员

- **US-FK11:** 作为创作者，我希望模板上的 fork 数准确，以便衡量超越点赞的真实影响力。
- **US-FK12:** 作为创作者，我希望 fork 列表尊重 fork 者的隐私（私有 fork 保持私有），以便该功能不泄露他人的私有作品。
- **US-FK13:** 作为管理员，我希望在管理台模板详情页看到只读谱系信息（fork 自、fork 数），以便带上下文审核 remix 滥用。

### 4.5 系统

- **US-FK14:** 作为系统，我在 fork 时记录谱系并事务性地维护 `fork_count`，以便计数始终一致。
- **US-FK15:** 作为系统，我绝不在 fork 列表或树中暴露其他用户的私有模板。
- **US-FK16:** 作为系统，删除 fork 时递减源的 `fork_count`；删除源模板绝不删除其 fork。

## 5. 功能需求

### 5.1 数据模型

- **FR-1:** `templates` 表新增：`forked_from_template_id`（UUID，可空 —— fork 时记录的源模板 id）、`forked_from_version`（INT，可空 —— fork 时源模板的版本号）、`fork_count`（INT，非空，默认 0 —— 此模板被 fork 的累计次数）。在 `forked_from_template_id` 上建索引以支持下游查询。
- **FR-2:** `forked_from_template_id` 应为**不带外键约束的普通 UUID 列**（推荐）：源模板被删除时，fork 保留该 id，UI 渲染"已删除"墓碑节点，保持链结构。*（替代方案 —— 外键 `ON DELETE SET NULL` —— 会切断孙辈的链；见开放问题 1。）*
- **FR-3:** `ForkTemplate` 应在新模板上设置 `forked_from_template_id` 和 `forked_from_version`，并在与模板创建相同的事务中递增源的 `fork_count`。其余 fork 行为（私有可见性、内容复制、所有者通知）不变。
- **FR-4:** 删除一个设置了 `forked_from_template_id` 的模板时，应事务性递减其源的 `fork_count`。删除源模板不影响其 fork（它们带着墓碑引用存续）。
- **FR-5:** 本功能之前 fork 的既有模板谱系为 NULL，按原创处理。无法回填（来源链接从未被记录）；此情况被接受并记录在案。

### 5.2 阅读 —— 模板详情与卡片

- **FR-6:** 模板详情响应（`GET /api/v1/templates/{id}`）应包含 `fork_count`，且当谱系存在时包含 `forked_from` 对象：`{template_id, title, version, owner: {id, display_name, avatar}, deleted: bool}`。源模板已删除时，`forked_from` 返回 `{template_id, deleted: true}`，不含标题/所有者。原创模板的 `forked_from` 为 null。
- **FR-7:** 模板列表响应（首页、搜索、收藏集）应包含 `fork_count`，以便卡片无需额外请求即可展示。
- **FR-8:** 署名行应在任何 fork 模板（公开或自己的）的详情页可见，源模板仍存在时链接到它。

### 5.3 阅读 —— fork 列表与树

- **FR-9:** `GET /api/v1/templates/{id}/forks` 应返回该模板**公开** fork 的分页列表（默认 20，最大 50），最新在前，使用既有模板列表项结构（以便 `PromptCard` 无改动渲染）。每项包含 `fork_count`（fork 本身也可被 fork）。其他用户的私有 fork 永不包含；查看者自己的私有 fork 包含在内（他们能看到自己的作品）。
- **FR-10:** `GET /api/v1/templates/{id}/fork-tree` 应返回模板的有界谱系：(a) **上游** —— 从该模板到根的完整链，最多 10 跳（更深的链被截断并带 `truncated: true` 标志）；(b) **下游** —— 直接与间接 fork，广度优先，最大深度 3、最多 50 个节点（超出部分标记 `truncated: true` 并给出隐藏节点数）。每个节点：`{template_id, title, owner: {id, display_name, avatar}, fork_count, is_current, deleted}`。可见性规则同 FR-9：公开模板、查看者自己的模板、以及已删除模板的墓碑。
- **FR-11:** 两个端点对公开模板公开可读（匿名可读）；私有模板仅所有者获得数据（否则 404），与既有模板可见性语义一致。
- **FR-12:** 墓碑节点（`deleted: true`）不携带标题或所有者数据 —— 只有"该位置曾存在一个模板"这一事实。

### 5.4 Fork 流程（普通用户界面）

- **FR-13:** fork 确认框应说明新模板将被公开署名为源的 fork（"此 Fork 的页面将显示 'fork 自 {标题}'"）。
- **FR-14:** fork 成功后，UI 应提供"查看 Fork"入口（成功 toast 或模态框中），导航到新创建的模板，作为既有成功反馈的补充。
- **FR-15:** 允许 fork 一个 fork；新模板的 `forked_from_template_id` 指向其直接来源（该 fork），形成链。fork 通知仅发给直接来源的所有者（既有行为，不变）。

### 5.5 管理控制台

- **FR-16:** 管理台模板详情页（`/admin/templates/:id`）应显示只读谱系面板："Fork 自"（标题、版本、所有者、源存在时链接到其管理详情）和"Fork 数"及公开 fork 列表链接。v1 不提供管理员专属的 fork 管理操作。

## 6. 非功能需求

- **NFR-1（隐私）:** 其他用户的私有 fork 在所有界面不可见（列表、树；计数仅为聚合值）。`fork_count` 数字是唯一的聚合信号；它绝不能被分解以揭示私有 fork 的身份。
- **NFR-2（性能）:** fork 树端点按设计有界（≤ 10 上游跳、≤ 50 下游节点、深度 ≤ 3），响应预算与模板详情相同（服务端 p95 < 300 ms）。fork 列表复用既有分页列表查询模式并使用新索引。
- **NFR-3（一致性）:** `fork_count` 使用与 `like_count`/`favorite_count` 相同的事务性反规范化计数模式；并发 fork 下无漂移（行级锁或原子 `UPDATE ... SET fork_count = fork_count + 1`）。
- **NFR-4（国际化）:** 所有新 UI 字符串在 `en` 和 `zh` 翻译文件中存在且键集一致；署名行、墓碑文案、树标签完全本地化。
- **NFR-5（无障碍）:** 谱系树作为嵌套语义结构可操作可阅读（标题/列表、键盘可导航链接）；fork 数是文本，不是仅颜色或仅图标的信号。
- **NFR-6（韧性）:** fork 列表或树的失败绝不影响模板详情页（区块级错误 + 重试，与评论相同的模式）。谱系数据缺失时降级为隐藏署名行。
- **NFR-7（兼容性）:** 既有 fork 流程、通知和模板 CRUD 除新增谱系字段外不变；忽略新字段的 API 消费者不受影响。

## 7. 验收标准

- **AC-1:** fork 一个公开模板会创建新的私有模板，其详情页显示"⑂ Fork 自 {源所有者} 的 {源标题} · v{N}"并带指向源的有效链接；源的 `fork_count` 递增 1。
- **AC-2:** 源模板详情页显示"Forks (N)"区，以卡片列出公开 fork；查看者自己的私有 fork 在自己的视图中出现；其他用户的私有 fork 永不出现。
- **AC-3:** 谱系树显示到根的上游链和深度 3 / 50 节点以内的下游；更深或更宽的结构显示"仅显示部分树"提示及隐藏数量。
- **AC-4:** fork 一个 fork 产生三节点链（A → B → C）；C 的树显示两个上游；B 的树显示 C 为下游。
- **AC-5:** 删除源模板后 fork 完好；fork 的署名行和树渲染"已删除"墓碑而非链接；无 404 或破损 UI。
- **AC-6:** 删除 fork 递减源的 `fork_count`；删除源不删除也不改动其 fork。
- **AC-7:** 模板卡片在 N > 0 时显示 fork 数角标（⑂ N）；0 fork 的卡片不显示（无视觉噪音）。
- **AC-8:** fork 模态框在确认前解释署名机制；fork 成功后"查看 Fork"导航到新模板。
- **AC-9:** 匿名访客可读取公开模板的 fork 数、fork 列表和树；私有模板的 fork 数据仅限所有者（其他人 404，与既有可见性一致）。
- **AC-10:** `/admin/templates/:id` 显示只读谱系面板（fork 自 + fork 数），数据正确。
- **AC-11:** 本功能之前 fork 的模板（NULL 谱系）按原创渲染 —— 无署名行、无错误；其 `fork_count` 从 0 开始。
- **AC-12:** fork/树 API 失败时，模板详情页完整渲染，fork 区显示内联错误 + 重试；署名行数据缺失时直接不显示。
- **AC-13:** 所有新字符串在 `en` 和 `zh` 中存在且键一致；树、署名、墓碑在两种语言和两种主题下正确渲染。

## 8. 范围之外（v1）

- 交互式网络图可视化（D3/图画布）—— 仅缩进树。
- 上游同步 / "从源拉取变更"（GitHub 式合并）—— fork 是独立副本。
- 面向 fork 者的"源已更新"通知。
- 向原始根所有者发送 fork-of-fork 通知（仅通知直接来源所有者，与既有行为一致）。
- Fork 原因/备注（"我为什么 fork"）。
- 事后重新挂载或编辑谱系。
- 向所有者以外的任何人（包括管理员在公开树中）展示私有 fork；管理员使用管理台自己的视图。
- fork 列表内的搜索/过滤（仅标准分页）。
- JSON 导出格式中的 fork 数据（import-export 功能的格式 v1 已冻结；未来格式版本可加入）。
- 通过 API key 访问 fork/树端点（v1 仅常规 Web UI）。
- 任何货币化相关功能（按项目范围规则）。

## 9. 依赖与假设

- **D-1:** `templates` 已有由仓库层事务性维护的反规范化 `like_count`/`favorite_count`；`fork_count` 沿用完全相同的模式（已在 `deployment/init.sql` 和 `template_repository.go` 中确认）。
- **D-2:** `backend/internal/service/prompt.go` 中的 `ForkTemplate` 是唯一的 fork 入口（复制元数据 + 最新版本内容、始终私有、通知所有者）—— 谱系记录加在此处；没有其他代码路径创建 fork。
- **D-3:** REST 网关通过 `cmd/server/main.go` 中的后缀匹配路由 `/templates/{id}/fork`；新的子资源路由（`/forks`、`/fork-tree`）沿用 `/templates/{id}/likes` 的模式。
- **D-4:** `PromptCard` 已从列表响应渲染 `like_count`/`favorite_count`；添加 `fork_count` 走相同的 prop 路径。`TemplateDetails.js` 已有 fork 模态框和操作按钮。
- **D-5:** 谱系数据中的所有者显示名/头像：follow-creators 功能引入公开资料数据（`GET /api/v1/users/{userId}/profile`）。若尚未上线，fork 端点必须通过 join 内嵌最小公开所有者对象（`id`、`display_name`、`avatar`）—— 请架构师确认统一方案，使模板详情、fork 列表和树使用一致的所有者结构。
- **D-6:** template-comments 功能确立了 TemplateDetails 上"内容下方区块"的模式（独立请求、骨架屏、错误 + 重试）；fork 区复用该模式。
- **D-7:** fork 通知已存在（`notifications` 中 `type='fork'`）；无需通知改动。

## 10. 给架构师的开放问题

1. **谱系引用完整性:** 推荐普通 UUID 列（无外键）+ 墓碑，在源被删除时保持链。替代：外键 `ON DELETE SET NULL`（完整性更简单，但丢失祖父链）。您倾向哪种？
2. **`fork_count` 语义:** 推荐：统计所有 fork（含私有）—— 它是所有者的参与度指标，且与既有 fork 通知一致（每次 fork 都通知所有者，无论私有与否）。列表/树随后只展示公开 fork，UI 文案说明"展示公开 fork"。替代：仅统计公开 fork（数字始终等于列表总数，但指标低估参与度）。请确认。
3. **树的边界:** 深度 3 / 50 节点 / 10 上游跳是我对 v1 的提议。若模板很少深层 fork，这些边界没有成本；请确认或调整。
4. **所有者对象结构（D-5）:** 现在就在 fork 端点内嵌最小所有者对象，还是等待 follow-creators 的资料端点、v1 仅按用户 id 链接？
