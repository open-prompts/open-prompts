# 通知来源偏好 — 需求分析

- **功能 ID：** notification-source-preferences
- **版本：** 1.0
- **状态：** Proposed（待架构评审）
- **作者：** ui-ux-agent
- **日期：** 2026-10-13
- **配套文档：** `notification-source-preferences-ui-ux-design-zh-CN.md`

## 1. 竞品调研

| 产品 | 按来源控制 | 优势 | 不足 |
|---|---|---|---|
| YouTube | 按频道铃铛：全部 / 个性化 / 无 | 全局之后最常用的控制；三档匹配真实意图 | 档位不透明（"个性化"？） |
| Reddit | 按社区覆盖 + 按类型开关 | 全局优先、覆盖其次 —— 分层正确 | 两个设置界面令人困惑 |
| GitHub | 按仓库 Watch 下拉：全部 / 参与 / 忽略 | 精确；"参与"被广泛理解 | 仅按仓库，无按行为人 |
| Twitter/X | 按账号：关 / 我关注的账号 / 所有人 | 简单三分 | 藏在通知条目溢出菜单里 |
| Instagram | 按账号：关 / 分别静音 story/reels/帖子 | 按来源细粒度 | 子开关过多 |

**结论：** notification-preferences 已交付按类型开关（like/favorite/fork/comment/follow + 全局暂停）并明确将按来源粒度推迟为 v2（第 102 行）。YouTube/GitHub 模式是正确的 v2：**按来源（按创作者）级别** —— `all`（默认，现行为）/ `mentions_only`（仅直接提及我的事件）/ `none` —— 从通知条目或创作者主页设置，*叠加在*按类型开关之上（最严者胜）。不做按模板粒度（GitHub 的仓库级最接近，但模板量级使其成为噪音；推迟）。

## 2. 问题陈述

按类型开关是全有或全无：想要大多数创作者的点赞、却被一个高产创作者淹没的用户，只能关掉全部点赞通知。缺失的控制是按来源："静音这个人"或"仅在被提及时"。YouTube 的数据（按频道铃铛是全局之后最常用的控制）表明这是价值最高的 v2 偏好。

## 3. 目标用户

- **通知接收者** —— 静音一个嘈杂的创作者而不失去信息流；保留所有人的提及。
- **创作者（作为行为人）** —— 不受影响；偏好仅在接收方。

## 4. 用户故事

- **US-1**：作为接收者，我想从通知的溢出菜单设置按创作者级别（全部 / 仅提及 / 无），使静音在噪音所在处一步完成。
- **US-2**：作为接收者，我想在创作者主页也有同样控制，以便预先管理来源。
- **US-3**：作为接收者，我希望"仅提及"保留 @提及与回复、丢弃该创作者的互动事件，使对话在静音中幸存。
- **US-4**：作为接收者，我想在一个列表中查看并编辑所有按来源级别，以便回顾过去的决定。
- **US-5**：作为接收者，我希望按来源级别与按类型开关组合（最严者胜），使行为可预测。
- **US-6**：作为接收者，我希望被静音创作者的既有通知保留在历史中（不追溯删除），使静音不是数据丢失。
- **US-7**：作为接收者，我希望级别仅作用于未来事件，使语义清晰。

## 5. 功能需求

- **FR-1**：新表 `notification_source_preferences`：`user_id`（接收者）、`source_user_id`（行为人/创作者）、`level`（`all` | `mentions_only` | `none`）、`updated_at`；主键 `(user_id, source_user_id)`。无行 = `all`（默认；无需回填）。
- **FR-2**：级别在**事件发射时**生效（与按类型开关同模型）：被抑制的事件不创建通知行，保持历史干净、未读徽标准确。
- **FR-3**：按事件类型的级别语义：`none` 抑制该来源的全部事件（like、favorite、fork、comment、reply、follow、mention）；`mentions_only` 抑制互动事件（like/favorite/fork/follow）但保留 mention 与 reply 事件；`all` 不抑制任何事件。
- **FR-4**：组合规则：仅当按类型开关开启**且**按来源级别允许时才发射事件（最严者胜）。按来源绝不*启用*被按类型关闭的事件。
- **FR-5**：入口：(a) 行为人为创作者的任何通知条目的溢出菜单 → "来自该用户的通知"子菜单含三档；(b) 创作者主页 → 铃铛下拉（YouTube 模式）含三档；(c) 通知设置面板 → "按来源偏好"列表。
- **FR-6**：API：`GET /api/v1/notification-preferences/sources?page_size=50&page_token=...`（列出非默认行，按更新时间新到旧）、`PUT /api/v1/notification-preferences/sources/{user_id}`（body：`{level}`；设为 `all` 删除该行）、`GET /api/v1/notification-preferences/sources/{user_id}`（当前级别，供主页渲染）。
- **FR-7**：设置中的按来源列表显示：创作者头像 + 显示名、当前级别（下拉）、更新时间、主页链接；分页 50/页；空态解释该功能。
- **FR-8**：静音仅接收方可见：被静音创作者不会被告知，其互动能力（评论、点赞）不受影响 —— 仅通知发射改变。
- **FR-9**：新静音创作者的既有通知保留在历史中；静音仅作用于未来事件（FR-2 发射时模型天然如此）。
- **FR-10**：不可对自己设置：API 拒绝 `source_user_id == user_id`（400）；UI 绝不在自己主页提供该控制。
- **FR-11**：与 block-users 交互：既有屏蔽已双向抑制通知（block-users FR-9）；对已屏蔽用户的按来源级别冗余但无害 —— 无论级别如何屏蔽都胜出。
- **FR-12**：主页铃铛下拉以勾选显示当前级别；更改即时生效（自动保存、无确认）并短暂 toast。
- **FR-13**：限额：每用户最多 500 行按来源偏好（服务端强制；友好错误）—— 防止无界行数。
- **FR-14**：所有级别按接收者；创作者的全局触达不发生任何变化。

## 6. 非功能需求

- **NFR-1（性能）**：发射时检查是对 `(user_id, source_user_id)` 的单次索引查询；为通知创建增加 < 2 ms。
- **NFR-2（可预测）**：组合规则（最严者胜）在 UI 中说明，用户可推理行为。
- **NFR-3（国际化）**：所有 UI 字符串中英同步；级别名称可翻译。
- **NFR-4（隐私）**：级别对接收者私有；任何界面都不向来源透露。
- **NFR-5（一致性）**：与 notification-preferences 相同的发射时抑制模型 —— 无第二条抑制路径。

## 7. 验收标准

- **AC-1**：从通知溢出菜单将创作者设为 `none` 后，其未来的 like/comment/follow 事件停止；既有行保留。
- **AC-2**：`mentions_only` 保留该创作者的回复作为通知到达，但丢弃其对同一模板的点赞。
- **AC-3**：按类型 `like` 开关关闭且来源为 `all` 时，不发射点赞通知（按类型胜出）。
- **AC-4**：主页铃铛下拉以勾选显示当前级别；改为 `none` 立即持久化并 toast。
- **AC-5**：设置列表显示所有非默认行及级别下拉；将级别改为 `all` 后该行移除（列表缩短）。
- **AC-6**：`source_user_id == user_id` 的 `PUT` 返回 400。
- **AC-7**：被屏蔽用户的事件无论其按来源级别如何都被抑制。
- **AC-8**：创建第 501 行按来源偏好失败并给出友好限额错误。
- **AC-9**：被静音创作者的互动（点赞、评论）仍出现在模板上 —— 仅通知被抑制。
- **AC-10**：设置列表 50/页分页正常。

## 8. 不在范围内

- 按模板粒度（GitHub 仓库 watch 的类比）—— 模板量级使其成为噪音；若创作者提出再议。
- 自定义级别（如"仅 fork"）、限时静音（"静音 7 天"）、关键词过滤。
- 邮件/推送渠道（仅应用内，见 notification-preferences）。
- 向来源透露静音状态（绝不 —— 隐私）。
- 批量静音（设置列表多选）。
- 任何形式的变现 —— 本产品永久不做。

## 9. 依赖与假设

- **D-1**：notification-preferences 的按类型开关、设置面板与发射时抑制模型按设计存在。
- **D-2**：通知事件类型（like、favorite、fork、comment、reply、follow、mention）已在数据驱动类型注册表中注册。
- **D-3**：block-users FR-9 双向抑制已就位（FR-11 交互）。
- **D-4**：创作者主页存在（follow-creators）并承载铃铛下拉。
- **D-5**：通知条目溢出菜单存在（标记已读/删除）并增加子菜单。

## 10. 给架构师的开放问题

- **OQ-1**：发射时检查应与既有按类型检查合并为一次查询，还是保持独立查询？（提案：一次查询 —— 按类型行与按来源行可一起获取。）
- **OQ-2**：`mentions_only` 是否是正确的中间档，还是应为 `comments_only`（评论 + 提及 + 回复）？（提案：mentions_only —— 回复与提及是"直接找我"的集合。）
- **OQ-3**：500 行限额（FR-13）应自动逐出最久未更新行还是硬失败？（提案：硬失败并引导清理。）
- **OQ-4**：主页铃铛下拉需要"all → 删除行"优化，还是显式 `all` 行可接受？（提案：删除行 —— 保持表稀疏。）
- **OQ-5**：500 行时设置列表是否需要按创作者名搜索/过滤，还是 v2 分页足够？
