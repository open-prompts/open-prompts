# 分类与标签管理（Taxonomy Management）— 需求分析

- **功能 ID：** taxonomy-management
- **版本：** 1.0
- **状态：** 已提案（待架构评审）
- **作者：** ui-ux-agent
- **日期：** 2026-10-12

## 1. 竞品调研总结

| 平台 | 分类体系方式 | 关键启示 |
|---|---|---|
| **AIPRM** | 管理员策划的分类树（60+ 分类）与管理员定义的子分类；自由标签由管理员清理 | 策划的分类列表保持浏览连贯；无人管理的标签会漂移成同义词 |
| **FlowGPT** | 固定分类列表 + 自由标签；标签显示为可点击的芯片 | 分类是主要浏览轴；标签芯片驱动次要发现 |
| **Snack Prompt** | 策划分类 + 输入时来自既有标签池的标签建议 | 来自既有标签池的自动补全防止新的近似重复标签 |
| **PromptHero** | 固定分类 + 自由标签；看不到管理员清理 | 无人策划时公开标签云会积累噪音（"ai"、"AI"、"a.i."） |
| **WordPress（后台）** | 术语表带合并/重命名；使用计数；批量操作 | 合并是最有价值的分类体系操作 —— 它保留内容 |
| **Stack Overflow** | 标签 wiki 页、同义词映射、burninate（重打标签+移除）工作流 | 同义词映射在写入时把旧标签重定向到规范标签 |

**综合分析：** Open Prompts 今天*完全没有*分类体系管理：分类和标签都是从 `templates` 表动态派生的（`SELECT category, COUNT(*) …` / `SELECT unnest(tags) …`），任何用户在创建模板弹窗中输入新分类或标签都会立即在共享公开列表中创建它。没有规范列表、没有去重、无法修复拼错的分类（"Writting"）、无法把 "ai" 合并进 "ai-assistant"、也无法退役一个分类。制胜的 v1 模式组合：(1) 由管理员在管理控制台管理的**规范 `categories` 表**（名称、slug、描述、排序、状态）；(2) **标签保持自由输入**，但有带管理员**合并/重命名**操作的**规范 `tags` 表**（名称、状态），就地重写 `templates.tags` 数组；(3) 创建模板弹窗的分类下拉由规范列表供给（普通用户的自定义分类入口移除），标签输入增加来自既有标签池的**自动补全建议**以防止新的近似重复；(4) 所有管理员分类体系变更写入既有 `admin_audit_logs`。这是一个**管理控制台功能**（新的 `/admin/taxonomy` 页面），带一个小的普通用户界面变化（分类下拉 + 标签建议）。

## 2. 问题陈述

1. **没有规范分类体系。** 分类和标签只作为模板行的派生聚合存在。没有任何东西定义有效集合，公开侧栏和搜索过滤器反映的只是用户碰巧输入的内容。
2. **用户无限制地创建分类。** 创建模板弹窗允许任何用户通过"创建新分类"铸造新的公开分类 —— 导致拼写错误、同义词和碎片化（"Writing"、"writting"、"Write"），破坏分类浏览。
3. **标签漂移。** 自由标签积累大小写变体和同义词（"ai"/"AI"/"a.i."、"chatgpt"/"chat-gpt"）；没有合并、重命名或清理路径，标签云过滤器越来越嘈杂。
4. **无法退役。** 失去用途（或被滥用创建）的分类无法隐藏或移除，除非删除模板。
5. **没有监督界面。** 管理控制台有用户、模板和审计日志页面，但没有分类体系 —— 管理员甚至看不到哪些分类/标签存在及其使用计数（公开端点只暴露公开模板的聚合）。

## 3. 目标用户

- **管理员（主要）：** 需要策划分类列表、清理标签漂移、保持浏览/过滤界面连贯。
- **模板创作者（次要）：** 获得干净的分类下拉和标签自动补全，减少意外重复。
- **浏览用户（受益者）：** 看到没有同义词噪音的连贯侧栏、分类页面和标签过滤器。

## 4. 用户故事

- **US-T1：** 作为管理员，我可以查看所有分类和标签及其使用计数（包括私有/未发布模板），以了解真实的分类体系状态。
- **US-T2：** 作为管理员，我可以创建带名称、slug 和描述的分类，以便在模板使用之前策划好规范列表。
- **US-T3：** 作为管理员，我可以重命名分类，以便一次性修复拼写错误和同义词。
- **US-T4：** 作为管理员，我可以把一个标签合并到另一个，以便 "ai" 和 "AI" 收敛为一个规范标签而不丢失模板。
- **US-T5：** 作为管理员，我可以隐藏（退役）分类或标签，以便无用或滥用的分类体系条目从浏览界面消失，同时模板保留数据。
- **US-T6：** 作为管理员，我做的每个分类体系变更都带原因记录在审计日志中，以便存在监督。
- **US-T7：** 作为创作者，分类下拉只显示规范策划列表，以便我不会意外碎片化分类体系。
- **US-T8：** 作为创作者，输入标签时建议既有标签，以便我复用规范标签而不是铸造近似重复。
- **US-T9：** 作为浏览用户，隐藏的分类/标签绝不出现在侧栏、分类过滤器和标签云中，以便浏览界面保持干净。

## 4a. 普通用户 vs 管理员划分

| 能力 | 普通用户 | 管理员 |
|---|---|---|
| 查看规范分类/标签（公开、active） | 是（侧栏、过滤器、创建弹窗） | 是 |
| 查看完整分类体系（含 hidden + 私有模板使用） | 否 | 是（`/admin/taxonomy`） |
| 创建分类 | 否（仅从列表选择） | 是 |
| 重命名分类 / 合并标签 | 否 | 是 |
| 隐藏/恢复分类或标签 | 否 | 是 |
| 标签自动补全建议 | 是（创建/编辑弹窗） | 是 |
| 分类体系操作的审计日志 | 否 | 是（既有审计页面） |

## 5. 功能需求

### 5.1 数据模型

- **FR-1：** 新表 `categories`：`id UUID PK`、`name TEXT UNIQUE NOT NULL`、`slug TEXT UNIQUE NOT NULL`、`description TEXT`、`sort_order INT NOT NULL DEFAULT 0`、`status TEXT NOT NULL DEFAULT 'active' CHECK (status IN ('active','hidden'))`、`created_at/updated_at TIMESTAMPTZ`。`templates.category` 继续存储分类**名称**（无外键；重命名保持同步 —— FR-6）。
- **FR-2：** 新表 `tags`：`name TEXT PK`（小写规范形式）、`status TEXT NOT NULL DEFAULT 'active' CHECK (status IN ('active','hidden'))`、`created_at/updated_at TIMESTAMPTZ`。`templates.tags` 继续存储标签名数组；合并/重命名重写数组（FR-8/9）。
- **FR-3：** 一次性回填迁移把既有的不同 `templates.category` 值插入 `categories`（slug 从名称派生），把不同的 `unnest(tags)` 值插入 `tags`（小写、去重）。幂等（`ON CONFLICT DO NOTHING`）。

### 5.2 管理控制台界面（`/admin/taxonomy`）

- **FR-4：** 管理控制台中的**分类体系**页面，含两个标签页：**分类**和**标签**。每个标签页是可搜索、可分页的表格：名称、使用计数（所有模板，不论可见性）、状态、更新时间、行操作。
- **FR-5（创建分类）：** 管理员可以创建分类（名称、slug 自动派生且可编辑、可选描述）。名称/slug 必须唯一；校验错误内联显示。
- **FR-6（重命名分类）：** 管理员可以重命名分类（名称和 slug）。重命名在一个事务中更新所有匹配模板的 `templates.category` 并记录审计日志。
- **FR-7（隐藏/恢复分类）：** 管理员可以在 `active` 和 `hidden` 之间切换分类。隐藏的分类从侧栏、分类过滤器、创建弹窗下拉和公开分类端点消失；模板保留其分类值（无数据丢失）。恢复可逆转。
- **FR-8（合并标签）：** 管理员可以把标签 B 合并进标签 A：每个 `tags` 数组包含 B 的模板将 B 替换为 A（不存在则添加、去重、数组重新排序），标签 B 行被删除，合并被审计。使用计数立即更新。
- **FR-9（重命名标签）：** 管理员可以重命名标签（规范小写）。与合并相同的重写语义（目标名称必须不存在；如果存在，操作变成合并 —— UI 提示这一点）。
- **FR-10（隐藏/恢复标签）：** 管理员可以切换标签状态。隐藏的标签从标签云、标签过滤器和标签建议消失；模板保留其标签值。
- **FR-11（审计）：** 每个分类体系变更（创建/重命名/合并/隐藏/恢复）写入一条 `admin_audit_logs` 行。`action` CHECK 约束扩展分类体系操作（`category_create`、`category_rename`、`category_hide`、`category_restore`、`tag_merge`、`tag_rename`、`tag_hide`、`tag_restore`）；`target_type` 增加 `category`/`tag`。原因为必填（3–500 字符，既有规则）。

### 5.3 普通用户界面变化

- **FR-12：** 创建/编辑模板弹窗的分类下拉只列出**active 的规范分类**（按 `sort_order` 排序，再按名称）。普通用户的"创建新分类"自由文本选项**移除**。如果模板当前分类被隐藏，它仍显示（只读上下文），但更改后无法重新选择。
- **FR-13：** 创建/编辑弹窗中的标签输入增加**自动补全建议**（最多 8 个），来自 active 规范标签，按前缀/子串不区分大小写匹配。用户仍可输入新标签（自由输入保留；模板保存时作为新的 active 行加入 `tags` —— FR-15）。
- **FR-14：** 公开侧栏和分类/标签端点只返回 **active** 的分类/标签（既有聚合查询增加对规范表的 join/semi-join）。计数仍从模板派生。
- **FR-15：** 模板创建/更新时，任何不在 `tags` 中的标签作为新的 active 行插入（upsert，小写规范化）。不在 `categories` 中的分类值（遗留行）被只读容忍，并通过"缺失于规范列表"指示器向管理员呈现（FR-16）。
- **FR-16：** 管理员分类标签页为被模板引用但不在规范表中的分类显示 **"Legacy"** 徽章和过滤器（回填后竞争产生的新散落项）；一键将其采纳进规范列表（以派生 slug 创建）。

### 5.4 API

- **FR-17：** `/api/v1/admin/taxonomy` 下的管理员分类体系 API：`GET /categories`（带计数、状态过滤、搜索、分页的列表）、`POST /categories`、`PATCH /categories/{id}`（重命名/slug/描述/sort_order）、`POST /categories/{id}/hide`、`POST /categories/{id}/restore`；`GET /tags`（相同形态）、`POST /tags/{name}/merge`（body：`into`）、`PATCH /tags/{name}`（重命名）、`POST /tags/{name}/hide`、`POST /tags/{name}/restore`。全部要求管理员角色（既有管理员认证中间件）。
- **FR-18：** 公开端点 `GET /api/v1/categories` 和 `GET /api/v1/tags` 只返回 active 条目，规范排序（分类按 `sort_order` 再名称；标签按使用计数降序，与今天相同），模板计数与今天相同。

### 5.5 通知集成

- **FR-19：** 无通知。分类体系变更是管理员专属且对用户静默（重命名分类或合并标签不通知模板所有者）。

## 6. 非功能需求

- **NFR-1（性能）：** 管理员分类体系列表端点在 1 万模板时 p95 < 300 毫秒；最多 5000 个受影响模板的标签合并在一个事务内 < 10 秒完成。
- **NFR-2（原子性）：** 重命名/合并操作是单事务（规范行 + 所有受影响的 `templates` 行）；失败不留下部分状态。
- **NFR-3（幂等回填）：** FR-3 迁移可重复运行而不产生重复行。
- **NFR-4（国际化）：** 所有管理员分类体系 UI 字符串和面向用户的下拉/建议字符串翻译（EN/ZH）；分类/标签**名称是用户数据，绝不翻译**。
- **NFR-5（可审计）：** 每个变更恰好产生一条审计行；既有审计日志页面以相同的表格/分页模式渲染分类体系操作。
- **NFR-6（无数据丢失）：** 隐藏绝不删除模板数据；合并保留所有模板（只有标签名变化）；重命名保留计数（使用数从模板重新计算）。
- **NFR-7（向后兼容）：** 分类/标签不在规范表中的模板（遗留）在今天的行为下继续渲染和过滤，直到管理员处理。

## 7. 验收标准

- **AC-1：** `/admin/taxonomy` 显示分类和标签标签页，带搜索、状态过滤、使用计数（包括私有模板）和分页。
- **AC-2：** 用已存在的名称或 slug 创建分类显示内联校验错误且不创建任何内容。
- **AC-3：** 重命名分类 "Writting" → "Writing" 立即更新每个模板的分类、侧栏和分类过滤器；使用计数保留。
- **AC-4：** 合并标签 "ai" 到 "ai-assistant" 从标签表和每个模板的 tags 数组中移除 "ai"；同时有两个的模板只保留一个 "ai-assistant"。
- **AC-5：** 隐藏分类将其从侧栏、公开分类端点、创建弹窗下拉和搜索过滤器中移除；其模板不变，仍可通过搜索/直链到达。
- **AC-6：** 每个变更写入一条审计行（操作、目标、原因），在审计日志页面可见。
- **AC-7：** 创建弹窗分类下拉只显示 active 规范分类；自由文本"创建新分类"选项消失。
- **AC-8：** 在标签输入中输入 "ai" 建议既有的 active 标签（不区分大小写）；选择一个即复用它。
- **AC-9：** 用全新标签保存的模板使该标签出现在规范标签表（active）和公开标签云中。
- **AC-10：** 遗留分类（被引用但不规范）在管理表格中显示 "Legacy" 徽章，可一键采纳。
- **AC-11：** 公开分类/标签端点只返回 active 条目；隐藏条目只是不列出（无 404）。
- **AC-12：** 所有分类体系 UI 字符串以 EN 和 ZH 渲染；分类/标签名称按原样渲染。

## 8. 范围之外

- 写入时的标签同义词/重定向映射（Stack Overflow 式同义词表）—— v1 用合并覆盖清理。
- 分类层级/子分类（仅平铺列表）。
- 标签描述/wiki 页面。
- 批量多选分类体系操作（一次合并多个）。
- 分类体系使用分析（随时间趋势）。
- 任何普通用户的标签/分类管理。
- 任何形式的变现（付费、定价、购买、收益）—— 本产品永久排除。

## 9. 依赖与假设

- **D-1：** `templates.category`（TEXT）和 `templates.tags`（TEXT[]）是记录的存储；规范表是元数据覆盖层，不是外键强制的引用（避免对热表进行有风险的迁移）。
- **D-2：** 既有的 ALTER TABLE IF NOT EXISTS 迁移模式（用于 `users.role/status`）扩展到 `admin_audit_logs` 的 CHECK 约束和新表。
- **D-3：** 管理控制台的列表页模式（搜索 + 表格 + 分页 + 抽屉/弹窗）来自用户/模板页面，复用于 `/admin/taxonomy`。
- **D-4：** 公开的 `ListCategories`/`ListTags` 仓库查询（从模板聚合）可以增加对规范表的 semi-join 而不改变响应形态。
- **D-5：** CreateTemplateModal 的分类下拉和标签输入是仅有的创作者侧入口（编辑弹窗共享它们）。
- **D-6：** 标签规范化是小写去空格（遗留混合大小写标签保留既有行为；合并/重命名规范化）。

## 10. 给架构师的开放问题

1. **规范表 vs 仅派生：** 我提议真实的 `categories`/`tags` 表作为元数据覆盖层（FR-1/2），`templates.category`/`tags` 不变。替代：保持仅派生，把重命名/合并实现为纯 `UPDATE templates` 脚本而无规范状态 —— 更便宜但无法支持隐藏/恢复或策划排序。确认覆盖层方案？
2. **分类存储：** 保持 `templates.category` 为名称字符串（重命名重写所有行，FR-6）vs 迁移到 `category_id` 外键（更干净但对最热的表是重迁移）。我推荐名称字符串 + 事务性重写。
3. **审计 CHECK 扩展：** 通过 ALTER TABLE 扩展 `action`/`target_type` CHECK 约束（D-2）vs 删除 CHECK 以求灵活。我推荐扩展（保持追加式保证显式）。
4. **标签合并规模：** 一个事务重写最多 N 个模板（NFR-1 上限 5000）vs 分批后台任务。我推荐带文档上限的单事务；如果预期更大量则分批。
5. **公开端点排序：** 分类按 `sort_order` 再名称排序（FR-18）—— 确认，还是分类保持今天的纯使用计数排序？
6. **新标签自动采纳（FR-15）：** 自由标签仍在保存时铸造新的规范行。替代：新标签排队等待管理员批准后才公开出现。我推荐自动采纳（无摩擦）+ 管理员通过合并/隐藏清理。
