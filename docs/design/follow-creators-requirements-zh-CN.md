# 关注创作者 — 需求分析

- **功能标识:** follow-creators
- **版本:** 1.0
- **状态:** 已提案（待架构评审）
- **作者:** ui-ux-agent
- **日期:** 2026-10-12

## 1. 竞品研究摘要

| 平台 | 关注方式 | 关键启示 |
|---|---|---|
| **FlowGPT** | 从创作者主页/提示词页关注；"Following" 信息流展示其新提示词 | 关注是留存的支柱：它把一次性发现变成可重复的"回来看看有什么新内容"回路 |
| **Snack Prompt** | 关注作者；被关注作者的活动出现在主页/个人页活动区 | 关注事件同时是主页的社会证明（"1.2k 粉丝"）；关注按钮必须出现在内容页而非仅主页 |
| **PromptBase** | 无关注；发现以搜索/浏览为中心 | 纯搜索式发现会流失回访用户；关注在不含任何商业机制的前提下填补该缺口 |
| **AIPRM** | 无创作者关注（提示词目录而非人） | 以提示词为中心的平台低估创作者；人的层面能提升创作者投入 |
| **GitHub** | 关注用户（动态流）；Watch 仓库 | 两个不同动词（关注人 vs 订阅物）—— v1 一个"关注创作者"动词已足够；订阅单个模板是未来的独立功能 |
| **Twitter/X** | 关注/取关切换、主页粉丝/关注计数、"关注了你"徽章 | 切换 + 计数 + 互相关注徽章是用户早已熟悉的通用语法 |
| **YouTube** | 订阅 + 铃铛；订阅信息流 | 订阅流按最新在前排序是最简单可行的聚合；算法流是 v2+ |

**综合结论:** v1 的胜出模式是 Twitter/GitHub 式：`user_follows` 表（关注者 → 被关注者）、创作者界面（模板详情页 + 本功能新增的创作者主页）上的 关注/已关注 切换按钮、主页上的粉丝/关注计数、"Following" 信息流（被关注创作者的公开模板，最新在前）、以及让创作者知道自己有受众的 `follow` 通知事件。Open Prompts 目前完全没有人的层面：模板详情页把所有者渲染为裸 ID 字符串（"by {owner_id}"）—— 用户甚至看不到模板是谁创建的，更谈不上持续追踪。

## 2. 问题陈述

1. **没有人的层面。** 产品仅以模板为中心。模板详情页显示裸用户 ID 作为所有者；没有创作者主页、没有创作者身份、也无法探索某创作者的其他作品。
2. **消费者没有留存回路。** 找到优秀创作者的用户无法看到该创作者的下一个模板，每次访问都从零开始发现。
3. **创作者没有受众。** 创作者没有粉丝数、没有受众感、也没有"有人想要更多我的作品"的信号 —— 这是持续贡献的最强动力。
4. **没有关注通知。** 通知功能（开发中）覆盖点赞/收藏/fork；获得新粉丝可以说是最强的参与事件，目前缺失。

## 3. 目标用户

- **消费者（主要）:** 找到优质创作者、希望以持久且低成本的方式跟进其新公开模板的用户。
- **创作者:** 希望拥有受众、以粉丝数作为社会证明、并在被关注时收到通知的用户。
- **所有用户:** 每个用户都是潜在创作者（人人可发布），因此每个主页都可被关注；零粉丝的用户看到友好空状态。
- **管理员:** v1 无管理控制台界面 —— 关注是个人社交图谱数据，不是需要审核的内容。（管理员用户详情页可展示粉丝/关注计数作为只读上下文；见 FR-17。）

## 4. 用户故事

### 4.1 关注

- **US-F1:** 作为消费者，我希望在模板详情页关注创作者，以便跟进其后续模板。
- **US-F2:** 作为消费者，我希望同样轻松地取关，以便关注保持低承诺。
- **US-F3:** 作为用户，我希望看到自己是否已关注某人（按钮状态），以便状态始终清晰。
- **US-F4:** 作为用户，我不能关注自己，以便计数保持诚实。
- **US-F5:** 作为匿名访客，尝试关注时被引导登录，以便流程可理解。
- **US-F6:** 作为被封禁用户，我不能关注他人也不能被新关注（新关注被拒绝），与账号受限状态一致。

### 4.2 创作者主页

- **US-F7:** 作为访客，我希望有一个公开的创作者主页，展示头像、显示名、简介、粉丝/关注计数和公开模板，以便评估并探索创作者的作品。
- **US-F8:** 作为创作者，我希望在主页写一段简短简介，以便粉丝了解我是谁。
- **US-F9:** 作为创作者，我希望主页只展示公开模板（不含私有），以便主页尊重模板可见性。
- **US-F10:** 作为用户，我希望在关注了我的主页上看到"关注了你"，以便识别相互关注。

### 4.3 Following 信息流

- **US-F11:** 作为消费者，我希望有一个"Following"信息流，按最新在前展示我关注的创作者的公开模板，以便不错过新作品。
- **US-F12:** 作为消费者，我希望信息流自动排除私有模板，以便只看到创作者选择发布的内容。
- **US-F13:** 作为消费者，我希望空状态推荐可关注的创作者，以便新账号不是死胡同。

### 4.4 管理我的图谱

- **US-F14:** 作为用户，我希望在自己主页上有"正在关注"列表，以便审阅并取关创作者。
- **US-F15:** 作为用户，我希望在自己主页上有"粉丝"列表，以便看到我的受众。

### 4.5 通知

- **US-F16:** 作为创作者，我希望被关注时收到通知，以便知道作品正在积累受众。*（依赖通知功能，见 §9）*

### 4.6 系统

- **US-F17:** 作为系统，我强制每对（关注者, 被关注者）恰好一行关注关系，以便计数准确。
- **US-F18:** 作为系统，我绝不暴露粉丝/被关注者的 email 或私有数据，以便社交图谱保持隐私安全。
- **US-F19:** 作为管理员，我能在管理员用户详情页看到某用户的粉丝/关注计数，以便获得审核上下文。

## 5. 功能需求

### 5.1 数据模型

- **FR-1:** 新增 `user_follows` 表：`follower_id`（外键 → users，`ON DELETE CASCADE`）、`followee_id`（外键 → users，`ON DELETE CASCADE`）、`created_at`（TIMESTAMPTZ）、`PRIMARY KEY (follower_id, followee_id)`，并加 `CHECK (follower_id <> followee_id)`。为粉丝列表查询在 `followee_id` 上建索引（主键已覆盖关注列表）。
- **FR-2:** `users.follower_count` 与 `users.following_count`（INT，默认 0）在关注/取关时事务性维护（与 `templates.like_count` 相同的反范式计数模式），以便主页与列表无需逐行 COUNT(*) 即可渲染计数。
- **FR-3:** 新增 `users.bio`（TEXT，可空，最长 280 字符）用于主页；经既有资料更新流程设置/更新。

### 5.2 关注/取关（普通用户面）

- **FR-4:** `POST /api/v1/users/{userId}/follow`（需登录）创建关注（关注者 = token 用户）。幂等：重复关注已关注用户返回 200 及当前状态（不产生重复行、不重复计数）。返回 `{following: true, follower_count}`。
- **FR-5:** `DELETE /api/v1/users/{userId}/follow`（需登录）移除关注。幂等：取关未关注用户返回 200 及 `{following: false, follower_count}`。用户不存在返回 404。
- **FR-6:** 系统拒绝自我关注，返回 400 及明确文案。被封禁的被关注者或被封禁的关注者，新关注一律 403 拒绝（既有关系保留；被封禁用户的模板按 FR-12 与 FR-18 从信息流排除）。
- **FR-7:** 速率限制：每账号每分钟最多 30 次关注/取关操作（HTTP 429 带 `Retry-After`），以遏制关注垃圾行为。服务端可配置。

### 5.3 创作者主页（普通用户面）

- **FR-8:** `GET /api/v1/users/{userId}/profile` 公开（匿名可读），返回：`id`、`display_name`、`avatar`、`bio`、`follower_count`、`following_count`、`created_at`（加入日期），以及调用者视角的 `is_following`（布尔，匿名为 false）+ `follows_you`（布尔，匿名为 false）。绝不含 email、mobile 或角色。
- **FR-9:** `GET /api/v1/users/{userId}/templates` 公开，仅返回该用户的公开模板（分页、最新在前），复用既有模板列表结构（以便 PromptCard 无改动渲染）。非所有者永远看不到私有模板。
- **FR-10:** `GET /api/v1/users/{userId}/followers` 与 `GET /api/v1/users/{userId}/following` 公开、分页（默认 20），返回公开用户卡片（`id`、`display_name`、`avatar`、`follower_count`、调用者的 `is_following`）—— 绝不含 email。
- **FR-11:** 资料更新流程（`PUT /api/v1/users/me` 或既有资料端点）接受 `bio`（去首尾空白后 0–280 字符；空则清除），校验错误形态与其他资料字段一致。

### 5.4 Following 信息流（普通用户面）

- **FR-12:** `GET /api/v1/users/me/following-feed`（需登录）返回所有被关注创作者的公开模板，最新在前，分页（默认 20、最大 50）。无论关注关系是否过期，私有模板一律在服务端排除。被封禁创作者的模板排除。已删除模板自然消失。
- **FR-13:** 信息流响应使用既有模板列表项结构并附加所有者的 `display_name`/`avatar`（以便卡片显示"by Alice"而非裸 ID），并含 `total_count` 供分页 UI 使用。

### 5.5 模板详情集成

- **FR-14:** 模板详情响应（`GET /api/v1/templates/{id}`）包含 `owner` 对象（`id`、`display_name`、`avatar`、`follower_count`、调用者的 `is_following`），以便页面无需额外请求即可渲染真实创作者身份与关注按钮。
- **FR-15:** 首页广场使用的模板列表响应每项包含所有者 `display_name`（可选 avatar），以便卡片显示"by Alice"；这是纯展示性增强，无行为变化。

### 5.6 通知集成

- **FR-16:** 当用户关注另一用户时，系统通过通知功能的事件机制向被关注者发出 `follow` 通知（接收者 = 被关注者，操作者 = 关注者，类型 = `follow`），遵循该功能的自操作抑制规则（自我关注本就不可能）。取关不发出通知。若通知功能尚未上线，本需求顺延至其上线。

### 5.7 管理面（只读）

- **FR-17:** 管理员用户详情响应（`GET /api/v1/admin/users/{id}`）包含 `follower_count` 与 `following_count` 作为只读上下文字段。v1 不提供管理员关注管理端点（关注是个人图谱数据；没有内容、没有文本，无需审核）。
- **FR-18:** 封禁用户不删除其关注图谱（解封后可能回归）；涉及被封禁用户的新关注按 FR-6 拒绝，其模板按 FR-12 从信息流排除。

### 5.8 删除行为

- **FR-19:** 删除用户级联删除其关注关系（双向），受影响用户的计数由同一事务性维护（FR-2）修正或重算。

## 6. 非功能需求

- **NFR-1（性能）:** 10 万行关注关系时，主页、粉丝/关注列表与信息流端点 p95 < 150 ms（主键/索引支撑）；关注/取关 p95 < 200 ms。反范式计数避免逐行 COUNT(*)。
- **NFR-2（可扩展性）:** 速率限制（FR-7）保护写路径。Following 信息流查询是 `user_follows` × `templates` 在索引键上的连接；若成为热点，物化信息流是 v2 优化（开放问题 §10.3）。
- **NFR-3（兼容性）:** 纯增量 —— 一张新表、三个新列、新端点、一个新页面（`/creators/:id`）、一个新信息流面，以及对既有响应的纯展示性增强。既有"by {owner_id}"渲染被 owner 对象取代；其他页面无行为变化。
- **NFR-4（隐私）:** 公开面仅暴露 `id`、`display_name`、`avatar`、`bio`、计数、加入日期及调用者相对的关注标志；绝不含 email、mobile、角色或私有模板。关注列表公开（与所有竞品一致），但仅含公开用户卡片。
- **NFR-5（无障碍）:** 关注按钮状态（关注/已关注/悬停取关）以文字标注而非仅颜色；主页与信息流页面完全可键盘操作；满足 WCAG 2.1 AA（与无障碍功能设计一致）。
- **NFR-6（国际化）:** 所有面向用户的文案中英同步；简介与显示名是用户内容绝不翻译；计数使用本地化复数与数字格式（两种语言下 1.2k 式缩写）。
- **NFR-7（安全）:** 所有写操作需登录；每个动作服务端校验；不渲染用户控制的标记（React 转义）；关注/取关路径限速。
- **NFR-8（韧性）:** 关注按钮失败显示 toast 并回退视觉状态；信息流/主页加载失败显示区块级错误 + 重试，绝不破坏导航。
- **NFR-9（数据完整性）:** 并发关注/取关下计数与行保持一致（事务性计数维护）；幂等端点使客户端重试安全。

## 7. 验收标准

- **AC-1:** 已登录用户可在模板详情页与创作者主页关注/取关创作者；按钮状态与粉丝数即时更新且刷新后保持。
- **AC-2:** 匿名访客可查看创作者主页、公开模板与粉丝/关注列表，但尝试关注时看到登录提示。
- **AC-3:** 自我关注返回 400；被封禁用户不能关注他人也不能获得新粉丝（403）。
- **AC-4:** 重复关注/取关调用幂等 —— 无重复行、无计数漂移。
- **AC-5:** `/creators/:id` 展示头像、显示名、简介、加入日期、粉丝/关注计数、关注/已关注按钮（适用时含"关注了你"徽章）及该创作者的公开模板；私有模板绝不出现。
- **AC-6:** "Following" 信息流按最新在前列出被关注创作者的公开模板，排除私有与被封禁创作者的模板，分页正确。
- **AC-7:** 用户自己的主页展示其 正在关注/粉丝 列表，且可从列表中取关。
- **AC-8:** 模板详情页展示创作者身份（头像 + 显示名，链接到 `/creators/:id`）而非裸所有者 ID，并带可用的关注按钮。
- **AC-9:** 关注某人向其发出一条 `follow` 通知（通知功能上线后）；取关不发出任何通知。
- **AC-10:** 超过每分钟 30 次关注操作返回 429 及 `Retry-After`；UI 显示友好提示。
- **AC-11:** 管理员用户详情页展示粉丝/关注计数；不存在管理员关注管理端点（任何尝试的管理关注路由返回 404）。
- **AC-12:** 删除用户双向移除其关注关系并修正受影响计数。
- **AC-13:** 所有新 UI 文案在 `en` 与 `zh` 翻译文件中键集一致；主页、信息流与列表在两种语言与两套主题下均正确渲染。
- **AC-14:** 关注 API 故障时模板详情页与首页仍完整渲染；关注按钮回退并弹错误 toast；信息流/主页显示错误 + 重试。
- **AC-15:** 任何公开主页、粉丝、关注或信息流响应中都不出现 email、mobile 或角色（经响应检查验证）。

## 8. 不做范围（v1）

- 关注推荐算法（"为你推荐"超出空状态中简单的近期创作者兜底）。
- 拉黑用户 / 黑名单（需独立设计的安全功能）。
- 屏蔽创作者（信息流中排除某人）—— v1 的答案是取关。
- 关注申请/审批（私密账号）—— v1 所有主页公开。
- "订阅模板"（关注单个模板的版本更新）—— 不同动词，未来的独立功能。
- 信息流排序/相关性算法（严格最新在前）。
- 信息流聚合或摘要邮件。
- 关于粉丝的创作者分析（谁在何时关注）—— prompt-analytics 功能覆盖模板指标。
- 管理员关注管理或审核端点。
- 关注图谱导入/导出。
- 任何与变现相关的功能（遵循项目范围规则）。

## 9. 依赖与假设

- **D-1:** `users` 表已存在，`display_name` NOT NULL、`avatar` 可空（已在 `deployment/init.sql` 确认）；新增 `bio`、`follower_count`、`following_count` 沿用 `avatar`、`role`、`status` 已使用的 `ALTER TABLE ... IF NOT EXISTS` 迁移模式。
- **D-2:** 反范式计数模式（templates 上的 `like_count`/`favorite_count`，由仓库层维护）是既有模式；`follower_count`/`following_count` 沿用。
- **D-3:** 模板详情页当前渲染 `t('template_details.by', { owner: template.owner_id })` —— 裸 ID。`owner` 对象（FR-14）取而代之；该 i18n 键增加显示名参数。首页广场卡片获得同样增强（FR-15）。
- **D-4:** 通知功能（已设计、开发中）定义了事件机制；FR-16 作为第四/第五种事件类型挂接（`follow` 与 like/favorite/fork 及评论功能的 `comment` 并列）。其需求文档将"关注通知"列为范围外是*因为当时关注功能不存在* —— 本功能补上它。
- **D-5:** 路由：`/creators/:id` 是 `App.js` 中与 `/templates/:id` 并列的新公开路由；首页广场增加"Following"入口（标签或区块 —— UI/UX 文档 §4.2），与既有导航模式一致。
- **D-6:** REST 网关现有 `/api/v1/users/*` 前缀用于资料操作；关注端点扩展该前缀。Following 信息流是与 `GET /api/v1/users/me` 风格一致的 `me` 作用域端点。
- **D-7:** 限速复用 auth 服务登录节流的 Redis 计数器方案（与评论功能的 D-7 假设相同）。
- **D-8:** `PromptCard` 渲染模板列表项；增加所有者行是纯展示性变更，不得破坏卡片既有用法（广场、收藏夹、搜索结果）。

## 10. 给架构师的开放问题

1. **服务放置:** 扩展 `UserService`（关注是用户关系；推荐）还是新建 `FollowService`，或放 `PromptService`（信息流查询模板）。建议：图谱与关注动作放 `UserService`；信息流查询可放那里（经既有仓库读模板）或放 `PromptService` —— 由架构师定。
2. **信息流形态:** 专用 `following-feed` 端点（推荐 —— 契约清晰、`me` 作用域）还是既有模板列表端点的 `following=true` 筛选。
