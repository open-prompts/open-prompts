# 模板锁与草稿(并发编辑保护)— 需求分析

- **功能 ID:** template-locks-drafts
- **版本:** 1.0
- **状态:** 已提议(待架构评审)
- **作者:** ui-ux-agent
- **日期:** 2026-10-12

## 1. 竞品调研摘要

| 平台 | 并发模式 | 关键启示 |
|---|---|---|
| **GitHub** | 乐观并发:基于过期基线保存文件时显示完整冲突屏(你的 vs 他们的)并强制显式解决 | "你的更改基于过期的基线" + diff 解决是文本冲突的金标准;静默覆盖绝不可接受 |
| **Google Docs** | 实时 presence(光标、"X 正在编辑")+ 字符级 OT/CRDT | 完全实时对提示词文本而言过重;但仅 *presence 感知* 就能预防大多数冲突 |
| **Notion** | presence 指示 + 最后写入胜出 + 页面历史(可恢复) | 当实时合并不可行时,presence + 可恢复历史是务实的中间地带 |
| **MediaWiki(维基百科)** | 带超时的硬编辑锁("有人正在编辑此页,等待或仍然编辑")+ 保存时编辑冲突屏 | 带超时的租约经过实战检验;"仍然编辑" 避免了有人离开后的锁劫持 |
| **Confluence** | 页面协作编辑;传统模式用 "你正在编辑,他人看到锁" 通知 | 向*查看者*展示锁(只读横幅)可减少意外的重复工作 |
| **Stack Overflow** | 帖子编辑的乐观修订检查(5 分钟宽限、修订号) | 最简可行模式:发送预期修订号,过期保存被拒绝并给出明确信息 |

**综合结论:** 在没有实时基础设施的条件下(平台今天没有 WebSocket/SSE),两个互补机制即可覆盖:(1) **presence 感知** —— 基于 Redis 的咨询式编辑租约配心跳,使第二个编辑者在*开始前*看到 "X 正在编辑"(MediaWiki/Confluence 模式,带 "仍然编辑" 逃生口);(2) **乐观并发** —— `UpdateTemplate` 接受编辑者加载时的 `expected_version`;不匹配则返回冲突并由 UI 显式解决(Stack Overflow/GitHub 模式)。Open Prompts 目前**两者皆无**:`UpdateTemplate` 是最后写入胜出,而版本历史(可让受害者找回文本)只能事后查看。advanced-editor 设计已加入 localStorage 草稿(客户端安全);本功能加入*服务端*正确性层与 presence UX,并与该草稿机制组合。

## 2. 问题陈述

1. **静默丢失更新。** 两个会话编辑同一模板(两个标签页、两名团队成员、所有者 + 管理员)都加载 v7;第一次保存创建 v8;第二次保存*基于 v7 文本*创建 v9 —— 第一位编辑者的更改被静默抹除。任何环节都没有警告。
2. **没有 presence 感知。** 第二个编辑者完全不知道他人正在编辑;重复/冲突的工作在无知中开始。
3. **草稿安全仅限客户端。** advanced-editor 设计按浏览器自动保存到 localStorage;用户换设备或清存储即丢失工作,且草稿对冲突处理不可见。
4. **冲突恢复是手动考古。** 丢失更新后,受害者必须察觉、找到版本历史、并从旧版本手工合并文本 —— 没有任何帮助。

## 3. 目标用户

- **编辑模板的创作者:** 需要工作不被覆盖,尤其是多标签页工作流。
- **团队成员(team-collaboration 功能):** 协作编辑同一团队模板是常态;没有保护冲突必然发生。
- **管理员:** 偶尔编辑模板;绝不能静默碾压所有者的进行中编辑。
- **查看者:** 受益于微妙的 "正在编辑" 信号,解释内容为何可能即将变化。

## 4. 用户故事

### 4.1 Presence 感知(咨询式租约)

- **US-L1:** 作为创作者,进入编辑模式时,我希望他人看到带心跳的 "我正在编辑",以便冲突在发生前被预防。
- **US-L2:** 作为创作者,在他人正在编辑的模板上打开编辑模式时,我希望看到是谁、编辑了多久,以便决定等待还是继续。
- **US-L3:** 作为创作者,我希望关闭标签页后租约自动过期(如 60 秒无心跳),以便离开的编辑者永不阻塞他人。
- **US-L4:** 作为查看者,我希望模板页有微妙的 "正由 X 编辑" 指示,以便理解内容可能即将变化。

### 4.2 冲突检测(乐观并发)

- **US-L5:** 作为创作者,保存时模板已在我加载后变化,我希望看到清晰的冲突信息 —— 而非静默覆盖 —— 以便双方的工作都得到保留。
- **US-L6:** 作为冲突中的创作者,我希望并排看到两个版本(我的 vs 当前),以便手工合并后保存结果。
- **US-L7:** 作为冲突中的创作者,我希望有一键 "加载当前版本" 操作,以便在主动选择时丢弃我的过期文本。
- **US-L8:** 作为创作者,我希望我的进行中文本在冲突流程中被保留(服务端草稿),以便解决冲突绝不丢失任何一方。

### 4.3 草稿(服务端)

- **US-L9:** 作为创作者,我希望编辑时草稿自动保存到服务端,以便换设备或浏览器崩溃不丢失草稿。
- **US-L10:** 作为创作者,在另一设备继续编辑时,我希望被提供最新草稿,以便从上次中断处继续。

### 4.4 安全

- **US-L11:** 作为系统,我绝不让过期保存创建静默丢弃他人更改的版本 —— 冲突总是被呈现。
- **US-L12:** 作为系统,我保持租约为咨询式(绝非硬阻塞),以便卡住的租约总能被 "仍然编辑" 覆盖。

## 5. 功能需求

### 5.1 咨询式编辑租约(presence)

- **FR-1:** 进入编辑模式应获取**编辑租约**:Redis 键 `edit-lease:{template_id}`,内容为 `{user_id, user_name, acquired_at, last_heartbeat}`,TTL 60 秒,编辑模式激活期间客户端每 20 秒心跳续期。
- **FR-2:** `GET /api/v1/templates/{id}/edit-lease`(仅所有者/管理员/团队编辑者)应返回当前租约(持有者名称、已用时间)或空。模板详情页在查看(非编辑)时每 30 秒轮询一次,渲染 "正在编辑" 指示(US-L4)。
- **FR-3:** 当存在活跃租约时第二个编辑者打开编辑模式,UI 应显示非阻塞通知:"{{name}} 已编辑 {{minutes}} 分钟 —— 仍然编辑 / 取消"。"仍然编辑" 继续(租约是咨询式的;第二个编辑者自己的租约获取覆盖该键,此后两个编辑者都受 FR-6 冲突保护)。"取消" 返回查看模式。
- **FR-4:** 租约应在保存、取消或离开编辑模式时显式释放(尽力 `DEL`),并由 TTL 过期隐式释放(60 秒无心跳)。租约操作绝不阻塞或使编辑流程失败 —— Redis 错误时系统降级为仅冲突检测(FR-6 仍保证正确性)。

### 5.2 乐观并发(正确性)

- **FR-5:** `UpdateTemplateRequest` 应接受可选 `expected_version`(整数)。提供且不等于模板当前最新版本号时,RPC 应返回 `Aborted`(HTTP 409)并附带当前最新版本信息 —— **不发生任何变更**。省略时行为不变(向后兼容;本功能上线后前端总是发送)。
- **FR-6:** 409 冲突时,客户端应进入**冲突解决流程**:获取当前最新版本,显示并排对比(我的编辑 vs 当前 —— 复用版本化功能的版本 diff 渲染),并提供:**"合并后保存"**(将当前版本文本载入编辑器,用户自己的文本保留在草稿面板供手工复制合并;保存时使用新的 expected_version)、**"覆盖"**(以当前 expected_version 原样保存我的文本 —— 明确的主动行为)、**"取消"**(返回编辑;草稿保留)。
- **FR-7:** 仅元数据编辑(通过元数据编辑器的标题/描述/标签/分类/可见性)应使用相同的 `expected_version` 检查;冲突时提供限定于元数据字段的相同解决流程。

### 5.3 服务端草稿

- **FR-8:** 编辑时,客户端应在脏状态时每 15 秒(防抖)自动保存**服务端草稿**,通过 `PUT /api/v1/templates/{id}/draft` 携带 `{content, metadata?, updated_at}` —— 存入 Redis(`draft:{template_id}:{user_id}`,TTL 7 天),每用户每模板一份草稿。响应返回草稿时间戳用于 "已保存" 指示。
- **FR-9:** 进入编辑模式时,若该用户存在服务端草稿、比加载的版本新且与之不同,UI 应提供:"恢复 {{time}} 的草稿?" —— **恢复**(载入草稿)/ **重新开始**(丢弃草稿)。这与 advanced-editor 的 localStorage 草稿组合:两者都存在且服务端草稿更新时服务端草稿优先;否则应用 localStorage 提示。
- **FR-10:** 草稿应在成功保存、显式 "重新开始"、以及 TTL(7 天)时删除。用户取消编辑且内容与草稿相比未变化时也调用 `DELETE /api/v1/templates/{id}/draft`(尽力)。
- **FR-11:** 草稿端点应仅限所有者/管理员/团队编辑者(与编辑相同的 authZ);草稿对其作者私有(团队成员绝看不到其他成员的草稿)。草稿内容不进入搜索、列表和版本历史。

### 5.4 指示与集成

- **FR-12:** 模板详情页(查看模式)在存在活跃租约时应向公开模板的所有查看者显示微妙的 "✏️ {name} 正在编辑(刚刚 / {n} 分钟前)" 指示(仅名称,无显示名之外的 PII)。
- **FR-13:** 编辑器应显示 "草稿已保存 · {time}" 状态行(来自 FR-8 响应),与现有 localStorage 自动保存指示并列并取代之(本功能上线后服务端草稿取代 localStorage;localStorage 保留为离线回退)。
- **FR-14:** 所有新端点应限流(心跳:30/分钟;草稿保存:12/分钟;租约读取:60/分钟),使用现有 Redis 限流器基础设施。

## 6. 非功能需求

- **NFR-1(正确性优先):** 冲突检查(FR-5)是事实来源;租约(FR-1)仅为咨询式 UX。即使 Redis 完全宕机,前端发送 `expected_version` 后就不会发生静默丢失更新。
- **NFR-2(性能):** 心跳、租约读取、草稿保存都是单键 Redis 操作 —— p99 < 50ms。30 秒查看模式轮询负载可忽略(每 30 秒每个打开的标签页一次 GET)。
- **NFR-3(向后兼容):** 省略 `expected_version` → 旧行为(不检查)。现有 API 消费者(API 密钥、playground)在选择加入前不受影响。
- **NFR-4(隐私):** 草稿按用户私有,绝不暴露给他人;租约仅暴露显示名(模板上本已公开)。
- **NFR-5(优雅降级):** 所有 Redis 支撑的部分(租约、草稿)失败开放:Redis 错误时编辑仍可用、冲突仍被检测,UI 隐藏 presence 指示而非报错。
- **NFR-6(国际化):** 所有新文案在 `en`/`zh` 且键一致;冲突/草稿时间本地化。
- **NFR-7(无障碍):** 冲突对话框和草稿提示遵循现有弹窗无障碍模式;"正在编辑" 指示出现时 `aria-live="polite"`;所有冲突操作可键盘到达。

## 7. 验收标准

- **AC-1:** 同一所有者的两个标签页编辑同一模板:标签页 A 保存(v7→v8);标签页 B(加载于 v7)保存 → 得到 409 冲突,看到并排对比(我的文本 vs v8),且过期保存未创建任何版本。
- **AC-2:** 冲突流程中,"覆盖" 将用户文本保存为 v9(使用 v8 的 expected_version);"合并后保存" 将 v8 载入编辑器且用户文本保留在草稿面板;"取消" 返回编辑且草稿完好。
- **AC-3:** 活跃租约存在时第二个编辑者打开编辑模式,看到 "{{name}} 已编辑 2 分钟" 及 仍然编辑 / 取消;"仍然编辑" 继续且两个编辑者都受 AC-1 冲突保护。
- **AC-4:** 不保存关闭标签页后,租约在 60 秒内过期;后续编辑者看不到 presence 通知。
- **AC-5:** 租约活跃期间模板查看者看到 "✏️ {name} 正在编辑(刚刚)";编辑者离开后约 60 秒内消失。
- **AC-6:** 编辑时脏状态每 ≤ 15 秒自动保存服务端草稿;在另一设备重新打开编辑模式时被提供 "恢复 {time} 的草稿" 并恢复确切文本。
- **AC-7:** 成功保存删除服务端草稿;"重新开始" 删除草稿;草稿 7 天后过期。
- **AC-8:** 团队成员的草稿对其他成员和所有者不可见(authZ 服务端强制;访问他人草稿返回 403)。
- **AC-9:** Redis 停止时:编辑和保存仍可用;冲突仍被检测(过期保存 409);不提供 presence 指示或草稿恢复;用户看不到任何错误。
- **AC-10:** 省略 `expected_version` 的 API 消费者行为零变化(无 409)。
- **AC-11:** 元数据编辑以相同方式冲突检查(过期元数据保存 → 409 → 解决流程)。
- **AC-12:** 所有新文案存在于 `en` 和 `zh`;心跳/草稿/租约端点强制限流(429 带友好信息)。

## 8. 不在范围内(v1)

- 实时协作编辑(OT/CRDT、共享光标)—— 需要 WebSocket 基础设施;平台加入后再议。
- 自动文本合并(用户文本对基线和当前版本的三方合并)—— v1 展示双方;用户手工合并。
- *新*(未保存)模板的服务端草稿 —— localStorage 覆盖创建场景(advanced-editor FR-6);服务端草稿仅限已存在模板。
- 租约通知("X 开始编辑你的模板")—— presence 仅为拉取式。
- fork 操作加锁(fork 是复制;不会丢失更新)。
- 管理员强制解除租约(租约是咨询式的;"仍然编辑" 总是可用)。
- 草稿 diff UI(恢复提示比较时间戳,不比较内容)。

## 9. 依赖与假设

- **D-1:** Redis 已部署,客户端封装(`data.NewRedisClient`)及限流器基础设施(评论功能在用)可用于租约/草稿/限流键。
- **D-2:** 版本化功能(已上线)提供带版本号的 `template_versions`、版本列表、以及冲突并排复用的统一 diff 渲染。
- **D-3:** advanced-editor 设计的 localStorage 草稿(`draft:template:{id}`)已存在或将上线;FR-9 定义组合方式(更新者优先服务端草稿)。
- **D-4:** `UpdateTemplate`(service)是内容和元数据的唯一变更路径;在那里加 `expected_version` 即覆盖详情页的两个编辑器(内容 + 元数据)。
- **D-5:** team-collaboration(已设计未上线)定义团队编辑者 authZ;在其上线前,租约/草稿 authZ 为所有者 + 管理员。
- **D-6:** 前端编辑模式位于 TemplateDetails(内容 + 元数据编辑器);冲突流程是该页上的新弹窗。

## 10. 给架构师的开放问题

1. **冲突错误形态:** `Aborted` gRPC 码 + 错误详情中的 `ConflictInfo`(current_version、current_content?)vs. 专用 `UpdateTemplateResponse.conflict` 字段?我推荐错误详情(保持主路径干净);请确认网关的错误详情透传。
2. **草稿存储:** Redis + 7 天 TTL(提案 —— 简单、临时、无 schema 变更)vs. `template_drafts` 表(持久、可查询、需迁移 + 清理任务)?临时草稿用 Redis 似乎合适;请确认 Redis 内存预算(每活跃草稿约 1 KB)。
3. **租约键粒度:** 按模板(提案)vs. 按模板按区域(内容 vs 元数据)?详情页有两个编辑器;每模板一个租约更简单且符合心智模型("有人正在编辑这个模板")。
4. **仅元数据保存的 `expected_version` 语义:** 相同检查(提案 —— 任何先前变更都使任何变更冲突)vs. 内容未变时跳过检查?相同检查更简单更安全;请确认。
