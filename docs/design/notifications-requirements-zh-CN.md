# 通知 — 需求分析

- **功能标识:** notifications
- **版本:** 1.0
- **状态:** 已提案（待架构评审）
- **作者:** ui-ux-agent
- **日期:** 2026-10-10

## 1. 竞品研究摘要

| 平台 | 通知方式 | 关键启示 |
|---|---|---|
| **GitHub** | 头部铃铛图标 + 未读徽标；下拉显示最近条目；独立收件箱页面带筛选（未读/全部）；单条与批量已读 | 铃铛 + 徽标 + 下拉 + 收件箱是经典形态；单条与批量已读都被用户预期 |
| **YouTube** | 铃铛 + 徽标；最近事件下拉；聚合文案（"A 和另外 3 人赞了你的视频"）；独立历史页 | 聚合能降低高流量内容的噪音；轮询保持徽标新鲜 |
| **FlowGPT** | 主页活动流（我的提示词收到的点赞/评论）；早期版本无头部徽标 | 参与反馈驱动创作者回访；入口可见性很重要（徽标 > 埋在深处的信息流） |
| **Snack Prompt** | 主页展示点赞/关注事件；自己操作用轻量 toast | 要区分"我的操作成功"的 toast 与"有人对我的内容做了操作"的通知 |
| **PromptBase** | 无应用内通知中心；以邮件为主 | 纯邮件带来延迟与再参与缺口；v1 先做应用内更优 |
| **AIPRM** | 极少/无应用内通知 | 这是缺口，不是可借鉴的模式 |
| **Reddit** | 收件箱页带全部/未读标签、单条与批量已读、删除 | 收件箱 + 两个筛选 + 条目管理是最小完整的管理界面 |

**综合结论:** v1 的胜出模式是 GitHub/Reddit 式：头部铃铛带未读徽标（轮询驱动，无需新基础设施）、轻量下拉显示最近条目、完整历史页带全部/未读筛选、单条已读、批量已读与删除。聚合文案（"A 和另外 3 人"）与实时推送有价值但 v1 非必需。Open Prompts 目前对创作者零反馈：模板可以积累点赞、收藏、fork，而所有者除了重新访问详情页之外无从得知。

## 2. 问题陈述

1. **创作者没有反馈回路。** 当有人点赞、收藏或 fork 用户的模板时，所有者无从得知。唯一信号是模板详情页上的计数器，需要所有者主动回访才能看到。
2. **没有再参与渠道。** 产品有参与动作（点赞/收藏/fork），却没有渠道告诉动作的对象"有人欣赏你的作品" —— 这是内容平台最强的自然再参与驱动。
3. **没有通知基础设施。** 没有通知表、API 或 UI。既有 `NotificationContext` 是用于*当前用户自己操作结果*的瞬态 toast 系统 —— 是另一个关注点，绝不能混淆（命名必须区分）。
4. **没有收件箱。** 用户无法回顾过去的参与（"上周谁收藏了我的模板？"），因为不存在历史。

## 3. 目标用户

- **创作者（主要）:** 发布模板、希望知道作品收到点赞/收藏/fork 的用户。
- **普通用户:** 任何拥有至少一个模板的登录用户（每个用户都能创建模板，因此每个用户都是潜在接收者）；从未拥有模板的用户只会看到空收件箱。
- **管理员:** 与普通用户一样，为自己模板收到的通知使用同一界面；v1 不需要管理员控制台界面（通知内容由既有动作系统生成，无需管理员审核）。

## 4. 用户故事

### 4.1 接收通知

- **US-N1:** 作为创作者，我希望有人点赞我的模板时收到通知，以便知道作品被欣赏。
- **US-N2:** 作为创作者，我希望有人收藏我的模板时收到通知，以便了解哪些模板被人们认为值得保存。
- **US-N3:** 作为创作者，我希望有人 fork 我的模板时收到通知，以便知道模板被复用和改编。
- **US-N4:** 作为用户，我不希望收到自己对自己模板操作的通知，以便收件箱不被噪音淹没。
- **US-N5:** 作为用户，我不希望有人反复开关点赞时产生重复通知，以便收件箱保持干净。

### 4.2 消费通知

- **US-N6:** 作为登录用户，我希望头部有带未读计数徽标的铃铛图标，以便一眼看出是否有新内容。
- **US-N7:** 作为用户，我希望使用应用期间徽标自动刷新，以便无需重新加载页面就能得知新的参与。
- **US-N8:** 作为用户，我希望铃铛弹出的下拉显示最近的几条通知，以便不离开当前页面即可分诊。
- **US-N9:** 作为用户，我希望点击通知跳转到它指向的模板，以便立即看到上下文。

### 4.3 管理通知

- **US-N10:** 作为用户，我希望有完整的通知历史页，以便浏览所有过去的参与。
- **US-N11:** 作为用户，我希望历史页支持全部/未读筛选，以便优先处理新条目。
- **US-N12:** 作为用户，我希望能将单条通知标为已读，以便自己掌控未读状态。
- **US-N13:** 作为用户，我希望能一键全部已读，以便快速把徽标清零。
- **US-N14:** 作为用户，我希望能删除通知，以便移除不关心的条目。

### 4.4 系统

- **US-N15:** 作为系统，我将通知严格限定在其接收者范围内，以便任何用户都绝不可能读到其他用户的通知。
- **US-N16:** 作为系统，我在服务端用已知安全的数据（操作者显示名、模板标题）生成通知内容，以便绝不渲染任何用户可控的标记。
- **US-N17:** 作为系统，我自动清理过期通知，以便表不会无限增长。

## 5. 功能需求

### 5.1 事件生成（服务端）

- **FR-1:** 当用户点赞（开启）、收藏（开启）或 fork 另一个用户拥有的模板时，系统应创建一条通知。接收者 = 模板所有者；操作者 = 执行动作的用户；类型 ∈ {`like`, `favorite`, `fork`}。
- **FR-2:** 当操作者是模板所有者时（自我操作抑制），系统不应创建通知。
- **FR-3:** 若已存在相同的未读通知（相同接收者、操作者、模板、类型），系统不应再创建（防开关刷屏去重）。在早先那条已读或被删除后允许再次通知。
- **FR-4:** 每条通知应存储事件发生时操作者 `display_name` 的快照；操作者当前的 `avatar`（可为空）在读取时联表获取。不暴露操作者的其他数据（绝不暴露邮箱）。
- **FR-5:** fork 通知应在既有 `ForkTemplate` 服务流程内发出（该流程中源模板与操作者已知）；无需对 `templates` 表做任何模式变更。
- **FR-6:** 删除模板应级联删除其通知（外键 `ON DELETE CASCADE`）；删除用户应级联删除其作为接收者或操作者的通知。
- **FR-7:** 通知创建绝不应导致触发动作失败：若插入出错，点赞/收藏/fork 仍然成功，错误仅记录日志。

### 5.2 铃铛与未读徽标（头部）

- **FR-8:** 已认证用户应在头部看到铃铛图标（位于语言切换与个人菜单之间）。匿名用户不显示铃铛。
- **FR-9:** 当 unread_count > 0 时铃铛应显示未读计数徽标，上限显示"99+"。为 0 时隐藏徽标。
- **FR-10:** 未读计数应通过每 60 秒轮询 `GET /api/v1/notifications/unread-count` 刷新（标签页可见且用户已认证时）；标签页隐藏时暂停轮询，可见性变化或窗口聚焦时恢复（并立即刷新一次）；出错时间隔指数退避（60s → 120s → 300s 封顶），成功后重置；登出时停止轮询并清空状态。
- **FR-11:** 当用户在应用内任何位置将通知标为已读时，徽标应立即（乐观）更新，随后与服务端响应对账。

### 5.3 铃铛下拉

- **FR-12:** 点击铃铛应打开下拉，列出最近 10 条通知（已读与未读混合，最新在前），打开时获取。未读条目有视觉区分。
- **FR-13:** 下拉头部应显示标题"通知"和"全部已读"操作，仅在 unread_count > 0 时显示。
- **FR-14:** 点击通知条目应将其标为已读（乐观），关闭下拉，并导航到所指向的模板（`/templates/:id`）。
- **FR-15:** 下拉底部应提供"查看全部"链接，指向 `/notifications`。
- **FR-16:** 下拉应在外部点击、Escape 或路由变化时关闭（与既有个人资料下拉模式一致）。

### 5.4 历史页（`/notifications`）

- **FR-17:** 通知历史页应位于 `/notifications`（需认证；匿名 → 重定向登录）。
- **FR-18:** 页面应按最新在前列出通知，每页 20 条，存在更多结果时通过既有 page_token 模式提供"加载更多"按钮。
- **FR-19:** 筛选标签"全部"与"未读"（带实时计数）；切换筛选会重置分页。
- **FR-20:** 每行应显示：事件图标（心/星/fork）、文案（"{{actor}} 赞了你的模板\"{{title}}\""）、相对时间（`title` 中有绝对时间）、未读指示，以及操作："标为已读"（仅未读条目）与"删除"。
- **FR-21:** 页面级"全部已读"按钮应将所有未读通知标为已读（服务端批量）并刷新列表与徽标。
- **FR-22:** 空状态：全部筛选 → "还没有通知 —— 当有人点赞、收藏或 fork 你的模板时，会显示在这里。"；未读筛选 → "你已全部看完。"

### 5.5 API

- **FR-23:** `GET /api/v1/notifications?filter=all|unread&page_size=20&page_token=...` → `{notifications: [{id, type, actor: {id, display_name, avatar}, template: {id, title}, created_at, read_at}], next_page_token, unread_count}`。需认证；始终按 token 限定接收者范围。
- **FR-24:** `GET /api/v1/notifications/unread-count` → `{unread_count}`。需认证。适合 60 秒轮询的低成本索引计数。
- **FR-25:** `POST /api/v1/notifications/{id}/read` → 将单条通知标为已读（幂等；非本人所有则 404）。
- **FR-26:** `POST /api/v1/notifications/read-all` → 将调用者所有未读通知标为已读；返回 `{updated_count}`。
- **FR-27:** `DELETE /api/v1/notifications/{id}` → 删除单条通知（非本人所有则 404）。
- **FR-28:** gRPC 层面（建议，由架构师定夺）：在既有 proto 中新增 `NotificationService`，包含 `ListNotifications`、`GetUnreadNotificationCount`、`MarkNotificationRead`、`MarkAllNotificationsRead`、`DeleteNotification`；事件创建是内部行为（在点赞/收藏/fork 服务路径中调用仓储插入），不是 RPC。

### 5.6 普通用户与管理员划分

- **FR-29:** 通知是按用户的普通界面：每个已认证用户（包括管理员）为自己模板收到的参与收到通知，体验完全一致。
- **FR-30:** 本功能不包含任何管理员控制台页面（`/admin/*`）与管理员 API（`/api/v1/admin/*`）。通知内容由既有动作系统生成，v1 没有需要管理员审核的内容。

## 6. 非功能需求

- **NFR-1（性能）:** `unread-count` p95 < 100ms（接收者 + 未读的部分索引）；列表 p95 < 300ms（每用户 1 万条通知）；全部已读受索引约束。
- **NFR-2（可扩展性）:** 轮询设计目标：1 万个并发已认证标签页 → 约 170 unread-count 请求/秒，全部是缓存友好的索引计数；间隔与退避由客户端强制执行，且集中在一个常量中可配置。
- **NFR-3（兼容性）:** 无破坏性变更；一张新表、新端点、一处头部新增。既有页面不变。既有 toast 系统（`NotificationContext`）保持不动，继续负责操作结果 toast。
- **NFR-4（隐私）:** 仅接收者可访问，服务端强制（token 派生用户 id，绝不使用客户端参数）；操作者仅暴露 display_name + avatar；不暴露邮箱或 UI 尚未展示的 ID。
- **NFR-5（无障碍）:** 铃铛、下拉与历史页完全可键盘操作；徽标计数对屏幕阅读器可感知；新未读计数通过 live region 礼貌播报（见 UI/UX 文档 §10）。
- **NFR-6（国际化）:** 所有面向用户的字符串中英文同步；通知文案由客户端基于类型化数据（类型 + 操作者 + 标题）组装，因此完全可翻译；相对时间用共享工具；模板标题是用户内容，绝不翻译。
- **NFR-7（保留策略）:** 已读超过 90 天与所有超过 180 天的通知被清理（后端周期性清理；机制由架构师决定 —— 见 §10）。
- **NFR-8（韧性）:** 轮询/网络失败绝不破坏 UI：徽标保留最后已知值，下拉/页面显示错误 + 重试；事件插入失败绝不导致触发动作失败（FR-7）。
- **NFR-9（安全）:** 所有端点需认证；每个按 id 寻址的操作都做所有权校验；通知内容以纯文本渲染（React 转义），绝不作为 HTML 渲染。

## 7. 验收标准

- **AC-1:** 点赞、收藏或 fork 另一个用户的模板会为所有者创建恰好一条通知（自我操作不创建；快速开关不产生重复）。
- **AC-2:** 已认证用户看到铃铛与正确的未读徽标（上限"99+"）；匿名用户看不到铃铛。
- **AC-3:** 标签页可见时，新通知在 60 秒内反映到徽标；隐藏时暂停；标签页聚焦时立即刷新。
- **AC-4:** 下拉列出最近 10 条通知，未读条目有视觉区分；仅当未读 > 0 时显示"全部已读"。
- **AC-5:** 点击下拉条目会将其标为已读、关闭下拉并导航到对应模板。
- **AC-6:** `/notifications` 按最新在前列出全部通知，全部/未读筛选、加载更多分页、单条已读、单条删除、全部已读均可用。
- **AC-7:** 标为已读（单条或全部）会立即更新徽标，且页面刷新后保持一致。
- **AC-8:** 匿名访问 `/notifications` 或任何通知 API 重定向/返回 401；用户 A 无法读取、标记或删除用户 B 的通知（404）。
- **AC-9:** 删除模板会移除其通知；删除用户会移除其通知（接收者与操作者两侧）。
- **AC-10:** 所有新 UI 字符串在 `en` 与 `zh` 翻译文件中存在且键集一致；通知语句在两种语言下均正确渲染。
- **AC-11:** 既有页面（广场、模板详情、个人资料、API keys）行为不变；既有 toast 系统不受影响。
- **AC-12:** 通知 API 不可达时应用其余部分正常工作；徽标/下拉/页面降级为带重试的错误状态。

## 8. 范围之外（v1）

- 实时推送（WebSocket/SSE）—— 仅轮询。
- 邮件或 Web Push 摘要。
- 聚合（"Alice 和另外 3 人赞了…"）—— v1 仅单个事件。
- 评论通知 —— 产品没有评论功能。
- 关注/订阅通知 —— 产品没有关注功能。
- 通知偏好/设置页（按类型关闭）—— 待量级需要后做 v2。
- 管理员控制台通知管理（`/admin/*`）—— v1 无需审核。
- 参与事件（点赞/收藏/fork）之外的任何事件类型 —— v1 仅覆盖这三种；新增事件类型需要新一轮设计。
- 移动应用专属布局（仅响应式 Web）。

## 9. 依赖与假设

- **D-1:** `template_likes` 与 `template_favorites` 行带有 `created_at`（已在 `deployment/init.sql` 确认）；点赞/收藏服务路径（`ToggleLikeTemplate`、`ToggleFavoriteTemplate`）在开启时已知操作者、模板与所有者 —— 通知插入挂在那里。
- **D-2:** `ForkTemplate`（backend/internal/service/prompt.go）目前不在 fork 上持久化源模板；fork 通知在该流程内源模板已知处发出 —— 无需 `templates` 表模式变更。
- **D-3:** `users.display_name` 非空（快照始终可得）；`users.avatar` 可为空（UI 回退到首字母占位符，与 Header 模式一致）。
- **D-4:** 相对时间工具与 user-dashboard 功能共享（其 D-6）；若该功能尚未交付，则由本功能引入。
- **D-5:** 轮询不需要新基础设施（无 Redis pub/sub、无 WebSocket 服务器）；网关在既有路由旁新增通知路由。
- **D-6:** 头部已实现下拉打开/外部点击关闭模式（个人资料下拉）—— 铃铛下拉复用它。
- **D-7:** 既有 `NotificationContext` toast 保留其名称；新 UI 使用独立的 `notifications.*` i18n 命名空间与 `notificationsSlice` Redux slice，避免任何冲突。
- **D-8:** 徽标状态需在头部铃铛、下拉与历史页之间共享 —— 假定用一个小 Redux slice（`notificationsSlice`：`unreadCount`、`lastFetchedAt`、`error`），与既有 Redux Toolkit 用法一致。

## 10. 给架构师的开放问题

1. **服务位置:** 在既有 proto 中新增 `NotificationService`（推荐 —— 领域边界清晰）还是扩展 `PromptService`（动件更少）。两者皆可；REST 层面完全相同。
2. **保留机制:** 后端专用 cron/goroutine ticker 还是惰性清理（例如在 `read-all` 时顺带删除）。建议：先做惰性清理（无调度器依赖），需要时再加 ticker。
3. **列表响应中的 `unread_count`（FR-23）:** 包含它使下拉/历史页无需额外调用即可刷新徽标 —— 请确认可接受，还是保持计数端点为唯一来源。
