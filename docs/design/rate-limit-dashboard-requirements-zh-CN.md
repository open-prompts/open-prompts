# 限流仪表盘（Rate Limit Dashboard）— 需求分析

- **Feature ID:** rate-limit-dashboard
- **Version:** 1.0
- **Status:** Proposed（待架构评审）
- **Author:** ui-ux-agent
- **Date:** 2026-10-12
- **相关文档：** [UI/UX 设计](./rate-limit-dashboard-ui-ux-design-zh-CN.md) · [Requirements (EN)](./rate-limit-dashboard-requirements.md)

## 1. 竞品调研总结

| 平台 | 限流方案 | 关键启示 |
|---|---|---|
| **GitHub REST API** | 未认证 60 次/小时（按 IP），认证后 5,000 次/小时（按用户）；**每个**响应都带 `X-RateLimit-Limit/Remaining/Reset` 头；429 带 `Retry-After` | 每个响应（而非仅错误）都带头，让守规矩的客户端在撞墙之前自我调节 —— 被复制最多的约定 |
| **OpenAI Platform** | 按端点类别分层 RPM/TPM 限额；429 带结构化错误与重试指引；用量仪表盘展示限额消耗 | 按端点类别分层（廉价读 vs 昂贵写）既保护数据库又不惩罚浏览；"用量 vs 限额"仪表能减少工单 |
| **Stripe** | 生产与测试流量分开限额；敏感端点（如 token 创建）限得更紧；429 响应体解释限额 | 敏感端点应有独立、更紧的桶 —— 单一全局限额永远不对 |
| **Cloudflare（限流规则）** | 管理仪表盘：被拦截请求的时间图表、Top 客户端 IP、规则命中数、手动封禁/放行 | 管理界面与执行本身同样重要：事故期间第一个问题就是"现在谁被限流了" |
| **Vercel** | 每项目用量仪表，软/硬限额与重置倒计时 | 一个简单的"已用 X / Y，N 分钟后重置"仪表就能传达用户所需信息的 90% |
| **PromptBase / FlowGPT / Snack Prompt** | 无公开 API，无限流界面 | 模式必须来自开发者平台 —— 与 api-usage-history 结论一致 |

**综合分析：** Open Prompts 目前只对两条路径限流 —— 评论（按用户，Redis 固定窗口，`COMMENT_RATE_PER_MINUTE/DAY`）和管理员登录（按 IP，5 次失败/15 分钟）—— 而其余约 23 个公开 REST 路由和发邮件的 `/api/v1/verification-code` 端点**完全没有限流**。api-playground 设计已经*假设*"标准的按用户 API 限流适用"，api-usage-history 则明确排除了执行层。本功能用代码库既有模式补上这个缺口：网关层 Redis 固定窗口限流器，按身份（认证后按用户 ID，匿名按客户端 IP）分桶，按端点类别（读/写/敏感）分层，输出标准 `429 + Retry-After + X-RateLimit-*` 头。用户侧界面是 (1) 全局 429 toast 带人性化的重试倒计时（把 CommentComposer 已有的局部处理泛化），(2) `/usage` 页新增"限额"卡片展示当前窗口仪表。管理侧是 `/admin/rate-limits` 仪表盘：被限流请求摘要、Top 被限流 IP/用户，以及带理由的"清除限流"操作并写入管理员审计日志。

## 2. 问题陈述

1. **公开 API 没有保护。** `cmd/server/main.go` 中全部 25 条 REST 路由（模板、分类、标签、登录、注册、个人资料、评论、API key……）接受无上限的请求速率。一个脚本就能轰炸模板列表或 fork 端点。
2. **验证码端点是邮件炸弹。** `SendVerificationCode`（`user.go:57-91`）每次调用都发邮件，没有按邮箱或按 IP 的限制 —— 循环调用该端点可以轰炸任意收件箱并耗尽邮件服务商配额。
3. **429 处理是局部的，不是全局的。** `CommentComposer` 和 `AdminLoginPage` 各自手写 429 解析；其他所有界面（模板创建、点赞、fork、API key 管理）被限流时只会显示通用错误 —— 一旦限额存在，这会变得很常见。
4. **用户看不到自己的限额。** 限额存在后，集成者需要知道自己离上限有多近（GitHub 式响应头 + 仪表），否则会提交"API 坏了"的报告。
5. **管理员在事故期间是盲的。** 没有任何界面显示谁被限流、在哪个端点、频率如何 —— 这是任何滥用或故障排查的第一个问题。

## 3. 目标用户

- **匿名浏览者：** 只在极端情况下触发按 IP 读限额；需要清晰、平和的 429 提示。
- **注册用户（Web）：** 评论/点赞/fork 突发可能触发写限额；需要在操作位置内联看到重试倒计时。
- **API 集成者：** 通过 API key 产生最多流量；需要 `X-RateLimit-*` 响应头和用量页仪表来自我调节。
- **管理员：** 需要发现滥用（爬虫、轰炸者），区分他们与合法重度用户，并进行补救（清除被误限的执行者）且留有审计痕迹。

## 4. 用户故事

- **US-1:** 作为匿名访客，我被限流时希望看到带重试倒计时的清晰提示，这样我知道网站没坏、何时可以再来。
- **US-2:** 作为评论者，429 之后我希望发布按钮显示实时倒计时，这样我不会丢失草稿也不会盲目重试。
- **US-3:** 作为 API 集成者，我希望每个响应都带 `X-RateLimit-Limit/Remaining/Reset` 头，这样我的客户端可以在被限流之前退避。
- **US-4:** 作为 API 集成者，我希望用量页有限额卡片，这样不用发探测请求就能看到自己离读/写上限有多近。
- **US-5:** 作为 API 集成者，我希望 429 响应体是结构化的（`retry_after` 以秒计），这样错误处理可以自动化而不是解析字符串。
- **US-6:** 作为请求验证码的用户，我希望有合理的按邮箱限额，这样没人能用这个端点灌满我的收件箱。
- **US-7:** 作为用户，我希望 API key 流量计入可预测的按用户预算，这样一个集成不会饿死我的其他 key（规则也简单易懂）。
- **US-8:** 作为管理员，我希望看到过去 24 小时被限流请求的仪表盘（量、独立执行者数、Top 端点），这样能快速发现滥用浪潮。
- **US-9:** 作为管理员，我希望看到 Top 被限流 IP 和用户（请求数、最后出现时间），这样能区分爬虫和合法重度用户。
- **US-10:** 作为管理员，我希望能清除被误封执行者的限流计数器，这样一次误判不会把人锁满整个窗口。
- **US-11:** 作为管理员，我希望每次清除限流都要求理由并进入审计日志，这样补救权力是可问责的。
- **US-12:** 作为使用 API playground 的开发者，我希望响应面板显示限流响应头，这样实验时就能了解剩余预算。

## 5. 功能需求

### 5.1 执行层（网关）

- **FR-1:** 一个限流中间件包裹 `cmd/server/main.go` 中所有 `/api/v1/*` REST 处理器。身份解析：已认证（会话 JWT 或 API key）→ 用户 ID；匿名 → 客户端 IP（既有网关辅助函数，已作为 `x-client-ip` 元数据转发）。同一身份的所有请求共享一组计数器。
- **FR-2:** 三个限额层级，每层是按身份的 Redis 固定窗口计数器（复用 `checkCommentRate` 模式 —— `count:expires` 值，TTL = 窗口）：**读**（GET）默认 120 次/分钟；**写**（POST/PUT/PATCH/DELETE）默认 30 次/分钟；**敏感**（`/verification-code`、`/register`、`/login`）默认 10 次/分钟按 IP，*叠加*在其写桶之上。所有值可通过环境变量配置（`RATE_LIMIT_READ_PER_MIN`、`RATE_LIMIT_WRITE_PER_MIN`、`RATE_LIMIT_SENSITIVE_PER_MIN`）；未设置 → 文档化默认值。
- **FR-3:** 每个响应（不仅 429）都带服务该请求层级的 `X-RateLimit-Limit`、`X-RateLimit-Remaining`、`X-RateLimit-Reset`（unix 秒）。429 额外带 `Retry-After`（最严格被触发窗口的重置秒数）和 JSON 体 `{ "error": "rate_limit_exceeded", "retry_after": <秒>, "tier": "read|write|sensitive" }`。
- **FR-4:** `/api/v1/verification-code` 增加两个专用计数器：按邮箱（默认 3 次/小时）和按 IP（默认 10 次/小时），在*发送邮件之前*检查。任一触发即返回 429 且不发送。
- **FR-5:** Redis 不可用时（nil 客户端、Get/Set 错误）中间件**失效放行** —— 与评论和管理员登录限流一致。API 可用性高于保护；故障日志每分钟最多一条，而非每请求一条。
- **FR-6:** API key 认证的请求计入**key 所有者**的用户 ID 桶（而非按 key 分桶）。按 key 限额不在范围内（见 §8）。

### 5.2 用户侧界面

- **FR-7:** 全局 axios 响应拦截器捕获 `/api/v1/*` 的任何 429：显示一个 toast（"请求过于频繁 —— N 秒后重试"，N 取自 `Retry-After`，默认 60），并抑制同一窗口的重复 toast。有定制处理的界面（CommentComposer、AdminLoginPage）保留其更丰富的局部 UX 并退出全局 toast。
- **FR-8:** 刚返回 429 的提交按钮自我禁用并渲染实时倒计时（"N 秒后可重试"），归零后重新启用；用户的进行中输入（草稿、表单状态）永不清空。
- **FR-9:** 新端点 `GET /api/v1/usage/limits`（需认证）→ `{ read: {limit, remaining, reset_at}, write: {limit, remaining, reset_at} }`，从调用者的 Redis 计数器读取。`/usage` 页（api-usage-history）新增**限额卡片**：两个仪表（读/写）、剩余次数、重置倒计时；Redis 宕机时卡片降级为"限额不可用"（与失效放行一致）。
- **FR-10:** API playground 响应面板（api-playground 设计）在存在时显示 `X-RateLimit-*` 和 `Retry-After` 头，让集成者测试时能观察预算。

### 5.3 管理仪表盘

- **FR-11:** 每次 429 递增 Redis 小时计数器（24 小时保留）：`rl_throttle:h:<YYYYMMDDHH>`（总量）、`rl_throttle:ip:<ip>:h:<…>`、`rl_throttle:user:<id>:h:<…>`、`rl_throttle:ep:<endpoint>:h:<…>`。新管理页 `/admin/rate-limits`（需管理员会话）展示：摘要卡片（24 小时被限流请求数、被限流独立执行者数、被限流最多的端点）、24 小时被限流请求柱状图、两张表 —— Top 被限流 IP 和 Top 被限流用户（身份、请求数、最后出现时间、命中的端点）—— 每行在适用时链接到该执行者的既有详情界面（用户详情页）。
- **FR-12:** 管理员**清除限流**操作：通过 `DELETE /api/v1/admin/rate-limits/throttle?actor_type=ip|user&actor_id=…` 删除一个执行者（IP 或用户 ID）的所有限流计数器。要求理由（3–500 字符，与其他审计操作相同规则），写入一条 `admin_audit_logs`（action CHECK 扩展 `rate_limit_clear`，target_type 扩展 `ip`），并在 UI 中确认。其余只读：仪表盘展示环境变量配置的限额但不能运行时修改。

## 6. 非功能需求

- **NFR-1（性能）：** 中间件在请求路径上增加 < 1 ms p99（每层一次 Redis GET+SET 管道；计数器 O(1)）。热路径无额外数据库写 —— 限流分析数据只存 Redis。
- **NFR-2（可用性）：** Redis 故障时失效放行（FR-5）；API 绝不因*限流器本身*故障而返回 429。`/usage/limits` 和管理仪表盘优雅降级为"不可用"状态。
- **NFR-3（安全/隐私）：** Redis 键只存 IP、用户 ID、端点路径和计数 —— 无载荷、无超出审计日志已有内容的 PII。所有计数器 TTL ≤ 24 小时（身份窗口 ≤ 1 小时）。清除限流仅限管理员、要求理由、写入审计。
- **NFR-4（一致性）：** 所有路由共享一个限流器实现（评论限流的固定窗口模式泛化）；不允许按路由手写计数器。既有评论/管理员登录限额保持不变（更严格的领域专属限额），并在管理页文档化为"附加限额"。
- **NFR-5（可观测性）：** 429 记录一条结构化日志（身份类型、层级、端点、retry-after），warn 级别，每身份每分钟最多采样一次，避免攻击期间日志洪水。
- **NFR-6（国际化）：** 所有用户可见字符串（全局 toast、倒计时按钮、限额卡片、管理仪表盘）通过 react-i18next 提供 EN 和 ZH；429 JSON 体保持机器可读的英文（它是 API 契约，不是 UI）。

## 7. 验收标准

- **AC-1:** 默认配置下，匿名脚本一分钟内对 `/api/v1/templates` 发出 130 个 GET，第 121 个收到 429，带 `Retry-After` ≤ 60 和 `X-RateLimit-Remaining: 0`；120 个成功响应各自带递减的 `X-RateLimit-Remaining`。
- **AC-2:** 已认证用户的 GET 和 POST 来自独立桶：120 次读不阻塞随后的模板创建；一分钟内第 31 次写被限流。
- **AC-3:** 持有效 API key 的请求与同一用户的会话请求共享一个预算（相同用户 ID → 相同计数器）。
- **AC-4:** 一小时内对同一邮箱调用 `/api/v1/verification-code` 4 次：前 3 次发送（或测试模式下记录日志），第 4 次返回 429 且不发送。
- **AC-5:** 停止 Redis 后，所有路由正常服务（失效放行），`/usage/limits` 返回 503 且 UI 友好显示"限额不可用"，每分钟恰好一条 warn 日志。
- **AC-6:** 模板点赞/fork 上的 429 显示带正确倒计时的全局 toast，且没有通用"错误"toast；倒计时归零后点赞按钮重新启用。
- **AC-7:** 评论编辑器的 429 保留草稿文本、显示编辑器局部倒计时（而非全局 toast），窗口重置后发布成功。
- **AC-8:** `/usage` 页限额卡片显示的读/写仪表与探测请求的新鲜 `X-RateLimit-Remaining` 一致，并向显示的重置时间倒计时。
- **AC-9:** 后端发送时，API playground 响应面板列出 `X-RateLimit-Limit/Remaining/Reset`。
- **AC-10:** 限流爆发后 5 分钟内（小时桶粒度），`/admin/rate-limits` 显示 24 小时被限流总量、图表和 Top IP/用户表；无被限流记录时渲染空状态。
- **AC-11:** 无理由的清除限流被拒绝（强制 3–500 字符）；理由有效时执行者计数器被删除、行状态更新，且存在一条 action 为 `rate_limit_clear` 带理由的 `admin_audit_logs` 记录。
- **AC-12:** 所有限额值可通过环境变量覆盖并有文档化默认值；未设置变量绝不禁用限流器（应用默认值），管理仪表盘显示生效值。

## 8. 不做范围（v1）

- 按 API key 的限额（所有 key 共享所有者的用户预算 —— FR-6）。
- 滑动窗口或令牌桶算法（固定窗口与既有模式一致；如出现突发公平性投诉再议）。
- 配额、用量上限或计费分层（api-usage-history 已排除执行层；范围内无货币化）。
- 管理界面的运行时限额配置（v1 仅环境变量）。
- 自动 IP 封禁 / 滥用升级（block-users 覆盖用户级封禁；IP 封禁是独立功能）。
- gRPC 内部限流（只包裹公开 REST 网关）。
- 静态资源或管理控制台自身登录的限流（已有限流）。

## 9. 依赖与假设

- **D-1:** Redis 已部署并接入 `cmd/server/main.go`（已验证：`data.NewRedisClient`，第 111 行），已支撑评论和管理员登录限流；限流器复用该客户端。
- **D-2:** 网关的客户端 IP 辅助函数（`main.go:~1528-1539`，作为 `x-client-ip` 元数据转发）可信 —— 部署位于正确配置的代理之后，代理设置 `RemoteAddr`；防伪造缓解是部署侧关注点，见 §10。
- **D-3:** api-usage-history（设计）定义了限额卡片落地的 `/usage` 页；本功能提供卡片和 `/usage/limits` 端点。
- **D-4:** api-playground（设计）定义了将渲染限流头的响应面板（FR-10 是集成说明，非阻塞项）。
- **D-5:** `admin_audit_logs` 的 action/target_type CHECK 约束通过迁移扩展，采用与先前功能相同的增量模式（archive-templates 扩展过同一 CHECK）。
- **D-6:** CommentComposer 和 AdminLoginPage 既有的局部 429 处理仍是规范的定制 UX；全局拦截器（FR-7）不得在这些界面上重复 toast。

## 10. 给架构师的开放问题

1. **认证流量的按用户 vs 按 IP：** 已认证用户是否*也*应消耗 IP 桶（防御一个 IP 轮换多个账号），还是 v1 只按用户 ID 即可？
2. **IPv6：** 按整个 /64 限流（推荐，防止轻易轮换）还是精确地址？
3. **可信代理：** `RemoteAddr` 是否保证是真实客户端（入口的 proxy protocol / X-Forwarded-For 归一化），还是网关应解析转发头？
4. **窗口对齐：** 固定窗口锚定在首个请求（当前评论模式）还是对齐墙钟分钟（重置显示更简单）？限额卡片的重置倒计时在两种方案下不同。
5. **计数器写策略：** INCR+TTL（两次往返，原子）还是既有的 GET-再-SET 模式（一次逻辑读，非原子但与代码库一致）—— 我们标准化哪个？
6. **`/usage/limits` 是否也暴露敏感层**（验证码预算），还是只暴露读/写？考虑到敏感层对匿名流是按 IP 的。
7. **审计 CHECK 扩展：** 按设计扩展 `target_type` 加 `ip`，还是把 IP 清除记录为 `target_type: user, target_id: ip:<addr>` 以避免改动约束？
