# 模板评论 — 需求分析

- **功能标识:** template-comments
- **版本:** 1.0
- **状态:** 已提案（待架构评审）
- **作者:** ui-ux-agent
- **日期:** 2026-10-12

## 1. 竞品研究摘要

| 平台 | 评论方式 | 关键启示 |
|---|---|---|
| **FlowGPT** | 每个提示词下方平铺评论列表；纯文本；创作者内联回复；无嵌套 | 平铺评论足以承载提示词反馈（"在 GPT-4 上效果很好"、"补一个示例变量"）；嵌套是加分项而非必需 |
| **Snack Prompt** | 评论 + 表情回应；创作者回复视觉高亮 | 高亮创作者回复让问答一目了然；轻量回应降低参与门槛 |
| **PromptBase** | 星级评价 + 卖家回复 | 评价门槛式的星级模型不适合免费社区；独立的评分功能需另行设计（本文不含） |
| **AIPRM** | 目录中提示词的公开评论/反馈 | 评论同时充当社会证明：有评论的提示词显得活跃且被维护 |
| **PromptHero** | 提示词作品下的评论；平铺、最新在前 | 平铺 + 最新在前 + 分页是标准的浏览模式 |
| **GitHub（讨论/议题）** | 嵌套、可编辑、可删除、支持 @提及；仓库所有者审核 | 所有者侧审核（删除/隐藏）是最小可行审核模型；带历史的编辑对 v1 过重 |
| **Reddit** | 嵌套、投票、版主删除并显示"已删除"占位 | 可见的"已删除"占位能在中间评论被移除时保留上下文 |

**综合结论:** v1 的胜出模式是模板详情页上的平铺、分页评论列表：任何已登录用户可发评论（被封禁用户不可），作者可在时间窗内编辑/删除自己的评论，模板所有者可删除其模板下的任何评论（所有者审核），管理员可在管理控制台全站删除评论。嵌套、提及、回应、富文本均延后。Open Prompts 目前没有任何双向沟通：用户无法问"这个模板最适合什么模型？"，创作者也无法公告"v2 已修复边界情况" —— 提示词平台最强的社区回路缺失。

## 2. 问题陈述

1. **没有双向沟通渠道。** 模板详情页展示点赞/收藏/fork 计数，但想提问、反馈提示词输出质量差、或分享技巧的用户无处发声，唯一渠道在站外。
2. **除计数外没有社会证明。** 爱心旁的数字无法告诉潜在用户模板是否真的好用。评论是所有竞品上最主要的信任信号。
3. **创作者没有公告面。** 创作者改进模板后，页面上没有地方宣布（"v2 修复了 JSON 输出问题"）。
4. **新的 UGC 文本缺少审核路径。** 产品目前唯一的用户自由文本是模板内容（已通过管理员可见性进行审核）。评论带来一个量更大的新 UGC 面，从第一天起就需要所有者审核 + 管理员审核，并与既有审计日志集成。

## 3. 目标用户

- **潜在用户（主要阅读者）:** 评估模板、在使用/fork 前通过评论判断质量与适配性的用户。
- **评论者:** 提问或分享技巧的已登录用户；被封禁用户除外。
- **创作者（模板所有者）:** 回答问题、公告更新，并审核自己模板的评论区。
- **管理员:** 通过管理控制台全站审核评论（删除违规内容）并留审计痕迹。

## 4. 用户故事

### 4.1 阅读评论

- **US-C1:** 作为潜在用户，我希望在模板详情页阅读评论，以便在使用前判断模板是否好用。
- **US-C2:** 作为用户，我希望评论最新在前并分页，以便热门模板下也能流畅浏览。
- **US-C3:** 作为用户，我希望看到每条评论的作者（显示名、头像）和时间，以便掂量反馈的分量。
- **US-C4:** 作为用户，我希望创作者的回复有视觉区分，以便快速找到官方回答。
- **US-C5:** 作为用户，我希望看到模板的评论数（计数器），以便感知社区活跃度。

### 4.2 发表评论

- **US-C6:** 作为已登录用户，我希望在公开模板下发表评论，以便提问或分享反馈。
- **US-C7:** 作为评论者，我希望在发布后短时间内编辑自己的评论，以便修正错别字。
- **US-C8:** 作为评论者，我希望删除自己的评论，以便彻底撤回。
- **US-C9:** 作为匿名访客，尝试评论时被引导登录，以便流程可理解。
- **US-C10:** 作为被封禁用户，我不能发评论，与账号受限状态一致。

### 4.3 创作者互动与审核

- **US-C11:** 作为创作者，我希望以高亮的创作者身份回复自己模板下的评论，以便答疑并建立信任。
- **US-C12:** 作为创作者，我希望删除自己模板下的任何评论，以便保持评论区无垃圾/辱骂内容。
- **US-C13:** 作为创作者，我希望有人评论我的模板时收到通知，以便及时回应。*（依赖通知功能，见 §9）*

### 4.4 管理员审核

- **US-C14:** 作为管理员，我希望全站浏览并搜索所有评论，以便找到违规内容。
- **US-C15:** 作为管理员，我希望以必填理由删除任何评论，以便通过审计日志问责。
- **US-C16:** 作为管理员，我希望在操作前看到评论的完整上下文（模板、作者、内容），以便准确审核。

### 4.5 系统

- **US-C17:** 作为系统，我强制只有评论作者、模板所有者和管理员能删除某条评论。
- **US-C18:** 作为系统，我绝不将用户评论文本作为 HTML 渲染，以便杜绝 XSS。
- **US-C19:** 作为系统，删除模板或用户时同步删除其评论，以便不残留孤儿内容。

## 5. 功能需求

### 5.1 数据模型

- **FR-1:** 新增 `template_comments` 表：`id`（UUID）、`template_id`（外键 → templates，`ON DELETE CASCADE`）、`user_id`（外键 → users，`ON DELETE CASCADE`）、`content`（TEXT，去除首尾空白后 1–2000 字符）、`created_at`、`updated_at`（TIMESTAMPTZ）。建索引 `(template_id, created_at DESC)` 用于列表查询；`user_id` 建索引。
- **FR-2:** `templates.comment_count`（INT，默认 0）在插入/删除时事务性维护（与 `like_count`/`favorite_count` 相同模式），以便列表和详情页无需逐行 COUNT(*) 即可展示计数。
- **FR-3:** 编辑评论仅更新 `updated_at`；不改变评论在列表中的位置（仍按 `created_at` 排序）。

### 5.2 阅读（普通用户面）

- **FR-4:** `GET /api/v1/templates/{id}/comments` 返回分页列表（默认 20、最大 50，`page`/`page_size` 或游标 —— 由架构师决定），按 `created_at` 降序；每项含 `id`、`content`、`created_at`、`updated_at`、`is_edited`（布尔）及公开作者对象（`id`、`display_name`、`avatar` —— 绝不含 email）。响应包含 `total_count` 与查看者自己评论的 id（或 `is_own` 标志），以便 UI 展示编辑/删除入口而不泄露他人权限。
- **FR-5:** 公开模板的该端点公开（匿名可读），与模板本身可见性一致；私有模板的评论仅所有者可读。
- **FR-6:** 模板详情响应（`GET /api/v1/templates/{id}`）包含 `comment_count`。
- **FR-7:** v1 中删除的评论为硬删除（无占位行）；列表直接排除。*（带"已删除"占位的软删除是 v1 的明确非目标 —— 见 §8。）*

### 5.3 发表（普通用户面）

- **FR-8:** `POST /api/v1/templates/{id}/comments`（需登录）创建评论，`content` 去除首尾空白后 1–2000 字符；否则返回 400 及字段级错误。被封禁用户（`users.status = 'banned'`）返回 403。私有模板仅所有者可评论。
- **FR-9:** `PUT /api/v1/comments/{commentId}` 允许作者在 `created_at` 起 15 分钟内编辑内容（同样 1–2000 校验）；超时返回 403 及明确文案（"编辑窗口已过期 —— 请删除后重发"）。
- **FR-10:** `DELETE /api/v1/comments/{commentId}` 在调用者为评论作者、模板所有者或管理员时允许。模板所有者与管理员通过具备管理能力的端点（§5.4）操作以便审计；作者自删不审计。
- **FR-11:** 速率限制：每用户每分钟最多 5 条、每天最多 50 条评论（HTTP 429 带 `Retry-After`），以遏制垃圾信息。具体上限可在服务端配置。
- **FR-12:** 评论文本以纯文本存储与返回；API 接受并原样往返 Unicode；UI 以 React 转义渲染（绝不使用 `dangerouslySetInnerHTML`）。

### 5.4 管理员审核（管理面）

- **FR-13:** `GET /api/v1/admin/comments` 全站列出所有评论，支持筛选：全文 `q`（匹配内容）、`template_id`、`user_id`（作者），按 `created_at` 降序，分页（默认 20）。每行包含评论字段及模板标题/所有者、作者显示名/email 等审核上下文。
- **FR-14:** `DELETE /api/v1/admin/comments/{commentId}`（需管理员角色）可删除任何评论。请求体须含必填 `reason`（3–500 字符，与其他管理操作同规则）；操作写入 `admin_audit_logs`（`action='delete_comment'`、`target_type='comment'`、`target_id=commentId` 及理由）。
- **FR-15:** 管理员模板详情页（`/admin/templates/:id`）展示该模板的评论（可读 + 带理由删除），复用同一管理删除端点。
- **FR-16:** 管理 API 与既有 `/api/v1/admin/*` 端点一样要求管理员角色（管理员 JWT）；普通用户返回 403。

### 5.5 通知集成

- **FR-17:** 当有人在他人所有的模板下创建评论时，系统通过通知功能的事件机制向所有者发出 `comment` 通知（接收者 = 所有者，操作者 = 评论者，类型 = `comment`），遵循该功能的自操作抑制与去重规则。若通知功能尚未上线，本需求顺延至其上线（不做独立兜底）。

### 5.6 关联删除行为

- **FR-18:** 删除模板级联删除其评论（外键），`comment_count` 随行消失；删除用户级联删除其评论。受影响模板的计数由同一事务性维护（FR-2）修正或重算。

## 6. 非功能需求

- **NFR-1（性能）:** 单模板 1 万条评论时列表端点 p95 < 150 ms（`(template_id, created_at DESC)` 索引）；发评论 p95 < 200 ms。模板列表上的 `comment_count` 无 N+1（反范式列）。
- **NFR-2（可扩展性）:** 速率限制（FR-11）保护写路径；读无状态且缓存友好。不引入新基础设施（不做搜索索引 —— `q` 筛选在有限结果集上用 SQL ILIKE，与既有管理搜索模式一致）。
- **NFR-3（兼容性）:** 纯增量 —— 一张新表、`templates` 一个新列、新端点、模板详情页一个新区块、管理台一个新页面 + 一个详情区块。不改变既有页面行为。
- **NFR-4（隐私）:** 作者仅暴露 `display_name` + `avatar` + 用户 id（均为平台已公开信息）；email 仅在管理审核面可见，与既有管理用户页一致。
- **NFR-5（无障碍）:** 评论列表为语义列表；输入框为带标签与字数统计的 textarea；所有操作可键盘触达；删除后的焦点管理遵循既有 Modal 模式；满足 WCAG 2.1 AA（与无障碍功能设计一致）。
- **NFR-6（国际化）:** 所有面向用户的文案中英同步；评论内容为用户内容绝不翻译；时间戳用共享相对时间工具；输入框占位符、校验文案、审核文案全部本地化。
- **NFR-7（安全）:** 所有写操作需登录；每次变更服务端校验所有权/角色；纯文本渲染（React 转义）；管理操作带必填理由审计；写路径限速。
- **NFR-8（韧性）:** 评论加载失败绝不阻塞模板详情页（区块级错误 + 重试）；发表失败显示内联错误并保留草稿。

## 7. 验收标准

- **AC-1:** 已登录用户可在公开模板下发表评论；无需刷新页面即出现在列表（最新在前）且 `comment_count` 加一。
- **AC-2:** 匿名访客可阅读公开模板的评论，但看到登录提示而非输入框；私有模板的评论仅所有者可见。
- **AC-3:** 空（0 字符）与超过 2000 字符的评论被拒绝并给出字段级错误；纯空白内容被拒绝。
- **AC-4:** 作者可在 15 分钟内编辑评论（之后显示"已编辑"标记）；超窗后编辑返回 403 及说明文案。
- **AC-5:** 作者可删除自己的评论；行消失且 `comment_count` 减一。
- **AC-6:** 模板所有者可通过确认弹窗删除其模板下任何评论；管理员可在管理控制台以必填理由删除任何评论。
- **AC-7:** 第三方无法编辑或删除他人评论（403/404）；被封禁用户无法发评论（403）。
- **AC-8:** 超过每分钟 5 条返回 429 及 `Retry-After`；UI 显示友好提示并保留草稿。
- **AC-9:** `/admin/comments` 列出所有评论，q/模板/作者筛选与分页可用；删除需理由并写入 `admin_audit_logs`（`action='delete_comment'`），在审计日志页可见。
- **AC-10:** 管理员模板详情页展示该模板评论，并具备同样的带理由删除操作。
- **AC-11:** 删除模板移除其评论；删除用户移除其评论；计数保持一致。
- **AC-12:** 所有新 UI 文案在 `en` 与 `zh` 翻译文件中键集一致；区块在两种语言与两套主题下均正确渲染。
- **AC-13:** 包含 `<script>` 或 HTML 的评论文本按字面渲染（转义），绝不执行。
- **AC-14:** 评论 API 故障时模板详情页仍完整渲染，评论区显示内联错误 + 重试。

## 8. 不做范围（v1）

- 嵌套/楼中楼回复（仅平铺；"回复"只是一条新评论）。
- @提及及提及通知。
- 评论表情回应。
- 富文本 / Markdown 渲染（仅保留换行的纯文本）。
- 评论投票/按热度排序（仅最新在前）。
- 创作者置顶评论。
- 超过 15 分钟的编辑窗口或编辑历史。
- 带"已删除"占位行的软删除。
- 匿名/游客评论。
- 新评论邮件摘要。
- 自动内容审核/脏话过滤（v1 仅人工审核）。
- 对评论者自己评论串的通知（仅通知模板所有者）。
- 任何与变现相关的功能（遵循项目范围规则）。

## 9. 依赖与假设

- **D-1:** `templates` 已有由仓库层维护的反范式 `like_count`/`favorite_count`（已在 `deployment/init.sql` 与 `template_repository.go` 确认）；`comment_count` 沿用完全相同的模式。
- **D-2:** `users.status`（'active'/'banned'）与 `users.role`（'user'/'admin'）已存在（已确认）；封禁检查复用登录/API-key 流程的状态语义。
- **D-3:** 管理控制台已有列表页模式（筛选 + 分页 + 表格，见 `UsersPage`/`TemplatesPage`）、封禁/解封的理由弹窗模式及审计日志集成 —— 评论管理页三者全部复用。
- **D-4:** 通知功能（已设计、开发中）定义了事件机制；FR-17 挂接其上。若其先上线，`comment` 成为点赞/收藏/fork 之外的第四种事件类型；其需求文档将"评论通知"列为范围外是*因为当时评论功能不存在* —— 本功能补上它。
- **D-5:** 模板详情页已加载模板 + 版本 + prompts 并有点赞/收藏/fork 区块；评论区追加在既有社交统计之下，沿用相同取数风格（api service + 本地 state）。
- **D-6:** REST 网关（`:8080`，`/api/v1`）经 gRPC 路由到后端服务；新评论路由沿用既有模板子资源模式（`/templates/{id}/likes` 风格）。
- **D-7:** 限速基础设施：auth 服务已用 Redis 实现登录失败节流；评论限速假定复用同一 Redis 计数器方案（放置位置由架构师确认）。

## 10. 给架构师的开放问题

1. **分页风格:** 偏移（`page`/`page_size`）还是键集游标（`before_id`）。建议：v1 用偏移（与既有管理列表一致、total_count 更简单），热门模板快速翻动后再考虑键集。
2. **服务放置:** 扩展 `PromptService`（评论是模板子资源；推荐）还是新建 `CommentService`。两者皆可；REST 面一致。
3. **限速放置:** 网关中间件还是服务层 Redis 计数器。建议：服务层，复用 auth 节流模式。
4. **`comment` 通知类型:** 确认在通知设计的事件枚举中增加第四种类型，还是将 FR-17 顺延至通知 v2。
