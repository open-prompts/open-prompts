# 批量操作(Bulk Operations)— 需求分析

- **功能 ID:** bulk-operations
- **版本:** 1.0
- **状态:** 已提议(待架构评审)
- **作者:** ui-ux-agent
- **日期:** 2026-10-12

## 1. 竞品调研摘要

| 平台 | 批量模式 | 关键启示 |
|---|---|---|
| **GitHub** | 列表多选(issues、projects)配浮动操作栏;表头三态复选框 "全选本页";批量打标签/关闭/指派 | 显示 "已选 N 项 + 操作" 的浮动栏是经典交互;三态表头复选框(全选/部分/无)是预期配置 |
| **Gmail** | 复选框多选 + 工具栏操作;批量归档/删除/打标签并带撤销提示 | 破坏性批量操作后的撤销大幅降低支持成本;逐项失败报告必不可少 |
| **YouTube Studio** | 视频批量操作:多选 → 更改可见性、删除、加标签 | "更改可见性" 是内容所有者最常用的批量操作 —— 对应我们的私有/公开切换 |
| **Notion** | 多选页面 → 移动/删除/导出 | 带明确数量的确认("删除 12 个页面?")防止大规模误操作 |
| **Stripe** | 批量转账/发票,带逐行结果报告和部分失败摘要 | 部分失败 UX(部分成功、部分失败)必须是一等公民,而非全有或全无的错误 |
| **Stack Overflow** | 版主批量处理标记 | 管理员批量治理:一个原因应用到多个目标,每个操作单独审计 |

**综合结论:** 行业范式一致:(1) 复选框多选 + 三态 "全选本页" 表头,(2) 显示选择数量的上下文操作栏,(3) 带确切数量(和条目预览)的确认对话框,(4) 服务端批量端点返回**逐项结果**以便精确报告部分失败,(5) 破坏性批量操作需数量确认 + 可选的键入确认。Open Prompts 目前没有任何多选表面:`AdminTable` 没有选择列,用户仪表板列表没有复选框,所有变更 RPC 都是单目标。user-dashboard 设计(§8:"批量操作(多选删除)")和 admin-user-management 设计(§8:"批量封禁、批量改角色")都明确将此推迟到专门功能。

## 2. 问题陈述

1. **清理只能逐个进行。** 拥有 30 个过时模板的创作者必须逐个打开详情页删除 —— 一个概念操作需要几十次点击和页面加载。
2. **可见性切换很繁琐。** "评审前把我所有草稿设为私有" 或 "发布这 10 个模板" 需要 10 次独立编辑流程。
3. **管理员治理无法扩展。** 一波垃圾账号意味着每个用户走一遍封禁流程(各自的原因对话框);管理员需要将一个原因应用到多个目标。
4. **没有共享的选择基础设施。** 未来的每个列表(评论治理、合集管理)都要重新发明复选框;一个可复用的选择模型 + 组件能在全产品复用。

## 3. 目标用户

- **创作者:** 清理或重组模板库(删除、可见性)。
- **管理员:** 治理成批的滥用账号(带统一原因的批量封禁/解封)。
- **所有用户:** 受益于未来列表表面可复用的选择模式。

## 4. 用户故事

### 4.1 创作者 — 模板库管理

- **US-B1:** 作为创作者,我希望在仪表板 "我的模板" 列表中多选模板,以便一次操作多项。
- **US-B2:** 作为创作者,我希望批量删除所选模板,以便一次操作清理过时作品。
- **US-B3:** 作为创作者,我希望批量更改可见性(设为私有/设为公开),以便控制成组模板的曝光。
- **US-B4:** 作为创作者,我希望确认时显示将受影响的确切模板数量,以免破坏超出预期。
- **US-B5:** 作为创作者,我希望批量操作后看到哪些条目失败及原因,以便重试或修复。

### 4.2 管理员 — 账号治理

- **US-B6:** 作为管理员,我希望在管理端用户列表中多选用户,以便高效治理多个账号。
- **US-B7:** 作为管理员,我希望用一个原因批量封禁所选用户,以便一波垃圾信息只需一次操作而非 N 次。
- **US-B8:** 作为管理员,我希望批量解封所选用户,以便快速回滚误操作。
- **US-B9:** 作为管理员,我希望每个被批量封禁的用户都有带共享原因的独立审计日志条目,以便审计轨迹保持逐目标。

### 4.3 系统完整性

- **US-B10:** 作为系统,我绝不允许对操作者不拥有(用户)或无权限(管理员)的条目执行批量操作,并将其作为逐项失败报告而非中止整批。

## 5. 功能需求

### 5.1 选择模型(共享)

- **FR-1:** 可复用的选择模型应支持:切换单行、三态表头复选框("全选本页"/部分选择时半选/无)、"清除选择"、以及可见计数。选择在同一列表会话的客户端分页间保持,并在筛选变化、路由变化或批量操作后的列表刷新时清除。
- **FR-2:** 选择每批最多 50 项(与列表页大小一致)。超过 50 时显示说明上限的提示;"全选" 最多选择当前页条目。
- **FR-3:** `AdminTable` 应增加可选的选择模式(复选框列 + 表头三态 + `onSelectionChange` 回调),且不破坏现有非选择用法(所有现有管理页面渲染不变)。

### 5.2 创作者批量操作(仪表板 "我的模板")

- **FR-4:** 在 "我的模板" 中选中 ≥ 1 个模板时,应出现浮动批量操作栏(视口底部),显示 "{{count}} 已选" 及操作:**删除**、**设为私有**、**设为公开**、**清除**。
- **FR-5:** **批量删除**应打开确认弹窗,列出数量和前 5 个标题("+N 个更多"),选中 ≥ 5 个模板时要求键入 `DELETE`(少于 5 个时为普通确认按钮),然后调用批量端点。删除按现有删除语义软删除;其他实体上的 fork/like/comment 计数不受影响。
- **FR-6:** **批量更改可见性**应打开确认弹窗("将 {{count}} 个模板设为私有/公开?")并总结后果(私有模板从公开列表和嵌入中消失),然后调用批量端点。
- **FR-7:** 两个操作都应调用新的批量 RPC —— `BatchDeleteTemplates(template_ids[])` 和 `BatchUpdateTemplateVisibility(template_ids[], visibility)` —— 仅限**调用者拥有**的模板;外来 ID 返回逐项失败 `not_found`(不泄露信息)。每个 RPC 按项执行单事务(项级原子性),返回 `results[] = {template_id, success, error_code?}`,并对超过 50 项强制 `invalid_argument`。
- **FR-8:** 批量操作后,列表应刷新、选择应清除,结果提示显示 "完成:X 成功,Y 失败"。若 Y > 0,提示可展开(或链接)到逐项失败列表(标题 + 错误信息)。失败条目保留在列表中且未选中。

### 5.3 管理员批量操作(用户列表)

- **FR-9:** 管理端用户列表(`/admin/users`)应启用选择模式,浮动栏中有 **封禁** 和 **解封** 批量操作。
- **FR-10:** **批量封禁**应打开弹窗,要求填写一个原因(3–500 字符,与单个封禁相同校验)、列出数量和前 5 个邮箱,然后调用 `BatchBanUsers(user_ids[], reason)`。**批量解封**对应 `BatchUnbanUsers(user_ids[], reason)`(原因可选,默认 "bulk unban")。
- **FR-11:** 管理批量 RPC 应独立处理每个用户(项级原子性),对受保护目标(自己、其他管理员)跳过并作为逐项失败 `forbidden` 报告,并使用现有 `ban`/`unban` 操作和共享原因为**每个用户写一条审计日志** —— `admin_audit_logs` 无需 schema 变更。
- **FR-12:** 管理批量结果应与 FR-8 相同方式呈现(提示 + 可展开失败项)。用户列表刷新且选择清除。

### 5.4 安全护栏

- **FR-13:** 选择为空时浮动栏隐藏;破坏性操作(删除、封禁)始终需要确认弹窗 —— 不允许从操作栏直接执行。
- **FR-14:** 批量操作应限流(如每用户每分钟 10 次批量调用)以防意外连击;超限显示友好的重试提示。
- **FR-15:** 所有批量操作 UI 文案应以相同键存在于 `en` 和 `zh`。

## 6. 非功能需求

- **NFR-1(一致性):** 批量端点按项复用现有单项服务逻辑(相同校验、相同副作用:批量可见性不发通知、删除的级联语义)—— 批量与单条路径无行为分歧。
- **NFR-2(性能):** 50 项批量在 p95 < 2 秒内完成(此规模下逐项顺序调用可接受;无需并行)。
- **NFR-3(可审计):** 每次管理员批量封禁/解封产生与单个操作无法区分的逐用户审计行(相同操作者、原因、批内时间戳)。
- **NFR-4(无障碍):** 复选框是带标签的真实 `input[type=checkbox]`;表头复选框播报 "全选本页";浮动栏是可聚焦的 `toolbar` 区域并带 `aria-live` 计数更新;确认弹窗遵循现有弹窗无障碍模式。
- **NFR-5(无回归):** 选择模式关闭时,所有现有列表页(管理端用户/模板/评论、仪表板标签页)渲染和行为完全一致。
- **NFR-6(国际化):** 所有新文案在 `en`/zh`;逐项错误信息从错误码映射到本地化文本。

## 7. 验收标准

- **AC-1:** 在 "我的模板" 中,点击行复选框更新浮动栏("已选 N 项");表头复选框全选/取消全选本页,部分选择时显示半选状态。
- **AC-2:** 选择 3 个模板并选择 "设为私有" 显示带数量的确认;确认后 3 个全部变为私有(列表徽标验证)、选择清除、显示成功提示。
- **AC-3:** 批量删除 ≥ 5 个模板要求键入 `DELETE`;少于 5 个显示普通确认。确认后模板从列表消失并出现 "已删除 3 个" 式提示。
- **AC-4:** 包含外来模板 ID 的批量请求(构造请求)使该项失败(`not_found`)而拥有的条目成功 —— UI 显示 "X 成功,1 失败" 及失败原因。
- **AC-5:** 超过 50 个 ID 的批量请求在任何变更前被 `invalid_argument` 拒绝;UI 绝不发送超过 50 个。
- **AC-6:** 管理员以原因 "spam wave" 批量封禁 4 个用户:全部封禁、写入 4 条审计行(action=`ban`,相同原因)、显示结果提示;批量中选中管理员自己的账号时该项返回 `forbidden` 失败。
- **AC-7:** 管理员批量解封恢复用户并写入带所给原因的 `unban` 审计行。
- **AC-8:** 选择在任何批量操作后、筛选变化时、路由变化时清除;不会泄漏到其他标签页。
- **AC-9:** 选择模式关闭时,所有现有管理页面和仪表板标签页渲染像素级一致(新可选列不造成布局偏移)。
- **AC-10:** 每个新 UI 文案以相同键存在于 `en` 和 `zh`;错误码 → 信息映射已本地化。
- **AC-11:** 键盘用户可切换行(复选框聚焦 + 空格)、到达操作栏按钮、并在无鼠标情况下完成整个批量删除流程。
- **AC-12:** 一分钟内超过 10 次批量调用显示友好的限流提示;被拒绝的调用不产生部分变更。

## 8. 不在范围内(v1)

- 批量添加/移除标签(标签分类交互值得单独一轮)。
- 批量加入/移出合集。
- 批量 fork、批量导出(import-export 覆盖单项导出;批量导出可后续跟进)。
- 跨页选择("选择所有 N 个匹配项" 超出当前页)。
- 管理员批量改角色(仅封禁/解封;角色变更保持审慎且单个)。
- 批量评论治理(单个删除已有;批量可后续沿用相同模式)。
- 定时/延迟批量操作、撤销/恢复窗口(软删除恢复属于版本化范畴)。
- 拖拽范围选择。

## 9. 依赖与假设

- **D-1:** 用户仪表板的 "我的模板" 标签页(user-dashboard 设计)列出调用者的模板及 `id`、`title`、`visibility` —— 选择 UI 挂载于此。若仪表板未上线,Profile 页的模板列表是备选表面(相同数据)。
- **D-2:** `DeleteTemplate` 和 `UpdateTemplate` 服务逻辑(所有权检查、软删除、可见性转换规则)已存在,由批量 RPC 按项复用。
- **D-3:** `BanUser`/`UnbanUser` 服务逻辑(受保护账号检查、原因校验 3–500、审计行写入)已存在并由批量 RPC 按项复用;`admin_audit_logs` 的 CHECK 约束已接受 `ban`/`unban` 且 `target_type='user'` —— 无需迁移。
- **D-4:** `AdminTable` 是唯一的管理列表组件(用户/模板/评论页共用)—— 选择列只需在那里添加一次。
- **D-5:** 基于 Redis 的限流基础设施(评论功能在用)可用于 FR-14。
- **D-6:** 浮动操作栏模式对应用是新的;将放在 `frontend/src/components/bulk/` 并可被未来列表表面复用。

## 10. 给架构师的开放问题

1. **批量 RPC 形态:** 按操作一个 RPC(`BatchDeleteTemplates`、`BatchUpdateTemplateVisibility`、`BatchBanUsers`、`BatchUnbanUsers`)如提案,vs. 通用 `BatchOperation(entity, action, ids, payload)`?我推荐按操作 RPC(类型化、自文档);请确认。
2. **事务范围:** 项级原子性(按项提交、报告失败)如提案,vs. 全有或全无事务?我推荐项级(符合 Stripe/GitHub 心智模型和 FR-8 UX);请确认。
3. **可见性批量 + 嵌入:** 模板通过批量设为私有时,现有嵌入显示 "不可用"(按 embedding-widget 设计)—— 确认批量无需向所有者发送额外通知(单项变更同样不通知)。
4. **限流键:** 按用户(提案)vs. 管理端点按 IP?管理员已认证;按用户似乎足够。
