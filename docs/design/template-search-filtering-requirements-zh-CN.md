# 模板搜索与筛选 — 需求分析

- **功能标识:** template-search-filtering
- **版本:** 1.0
- **状态:** 已提案（待架构评审）
- **作者:** ui-ux-agent
- **日期:** 2025-06-25

## 1. 竞品研究摘要

调研覆盖了主流提示词市场与提示词库产品，以及用户已经习惯的通用内容平台搜索模式。

| 平台 | 搜索与筛选方式 | 关键启示 |
|---|---|---|
| **PromptBase** | 市场首页显著的关键词搜索框；分类标签；排序下拉（Top、New、Price）；搜索结果页展示结果数量 | 搜索是首要发现入口；结果页展示数量并支持排序；分类浏览是次要路径 |
| **FlowGPT** | 首页大号搜索框；标签标签；分类侧栏；排序选项（Top rated、Most popular、Newest）；无限滚动 | 大搜索框 + 标签是主流模式；排序是紧凑下拉而非独立页面 |
| **Snack Prompt** | 顶栏搜索框；筛选面板（分类、标签、语言）；排序（Trending、Newest、Most liked）；社区投票排名 | 关键词搜索与结构化筛选结合；默认"Trending"排序提升参与度 |
| **AIPRM** | 扩展库内搜索；带计数的多选标签筛选；排序（Views、Votes、Use count、Newest）；保存的搜索 | 带计数的标签多选优于单选；重度用户重视可保存/复用的筛选组合 |
| **PromptHero** | 搜索优先的落地页；模型筛选；排序（New、Top、Hot）；关键词建议 | "Hot/Trending"时间窗排序营造活跃感；建议减少空结果 |
| **通用 SaaS（Stripe/Vercel/Supabase 仪表盘）** | URL 同步筛选、防抖搜索、汇总活动筛选的筛选标签（chips）、带明确下一步动作的空状态 | URL 状态使筛选可分享/收藏；chips 让复杂筛选状态清晰可读；防抖避免请求风暴 |

**综合结论:** 所有竞品都将关键词搜索作为首要发现机制，叠加在既有分类/标签浏览之上。排序始终是 3–5 个命名选项的紧凑下拉。多选标签、筛选 chips、URL 同步状态是区分成熟产品与基础产品的分水岭。没有任何竞品要求独立的搜索结果页 —— 搜索就住在主列表页上。

## 2. 问题陈述

Open Prompts 目前支持按可见性、分类和单个标签浏览模板，排序严格按创建时间。随着模板库增长：

1. **没有关键词搜索。** 用户无法按标题、描述或内容关键词查找模板。仅有的发现路径是分类浏览和标签点击。这是相对所有竞品的最大易用性缺口。
2. **没有排序。** `ORDER BY t.created_at DESC` 是硬编码的。热门、高赞或近期更新的模板被更新的模板淹没。用户无法找到"最多点赞"或"趋势"内容。
3. **单标签筛选。** API 接受标签数组但 UI 只会发送一个标签（点击标签会替换选择）。用户无法组合标签。
4. **筛选状态不可见。** 活动筛选没有在任何地方汇总；用户必须记住自己在侧栏点了什么。筛选不反映在 URL 中，因此结果无法分享或收藏，浏览器前进/后退也无法恢复筛选状态。
5. **没有结果数量或反馈。** UI 从不告知用户有多少模板匹配，因此空结果与页面故障在阅读空状态之前无法区分。
6. **搜索后端缺口。** 仓储层不支持搜索条件；proto `ListTemplatesRequest` 没有关键词或排序字段。两者都必须扩展。

## 3. 目标用户

- **普通用户（浏览者）:** 访客与已登录用户，希望按需求描述（"写邮件"、"代码审查"、"logo 设计"）快速找到有用的提示词。
- **重度用户（创作者）:** 维护大量模板的用户，希望按关键词、标签组合和排序定位自己或他人的作品。
- **管理员:**（间接）当管理员模板审核列表（admin-user-management 功能）复用这些能力时受益。

## 4. 用户故事

### 4.1 搜索与发现

- **US-S1:** 作为访客，我希望在首页搜索框输入关键词，以便无需浏览分类就能找到匹配我需求的模板。
- **US-S2:** 作为访客，我希望搜索能匹配标题、描述和提示词内容，以便标题不含我的关键词但内容含有的模板仍可被找到。
- **US-S3:** 作为访客，我希望看到匹配结果的数量，以便知道筛选是否过窄。
- **US-S4:** 作为用户，我希望将关键词搜索与分类和标签筛选组合，以便在领域内收窄（如关键词 "email" + 分类 "marketing"）。
- **US-S5:** 作为用户，我希望选择多个标签，以便找到主题交集的模板。
- **US-S6:** 作为用户，我希望一键清除所有活动筛选，以便快速开始全新搜索。
- **US-S7:** 作为用户，我希望当前搜索/筛选反映在 URL 中，以便收藏、分享以及用浏览器前进/后退恢复结果。
- **US-S8:** 作为用户，我希望获得搜索建议（匹配输入的热门标签/分类），以便在提交完整搜索前获得指引。

### 4.2 排序

- **US-S9:** 作为用户，我希望按最新、最多点赞、最多收藏或趋势排序结果，以便找到优质或新鲜内容。
- **US-S10:** 作为用户，我希望排序与筛选一起持久化在 URL 中，以便分享的链接能精确重现视图。

### 4.3 系统故事

- **US-S11:** 作为系统，我对关键词输入防抖（300ms），以便打字不会每个按键触发一次请求。
- **US-S12:** 作为系统，我保持搜索结果与可见性规则一致，以便私有模板绝不泄漏到公开搜索结果中。
- **US-S12a:** 作为系统，我保持搜索结果与管理员审核状态一致，以便管理员功能上线后被封禁用户的公开模板被排除（依赖见 §9）。

## 5. 功能需求

### 5.1 关键词搜索

- **FR-1:** 系统应在首页（Prompt Square）提供接受自由文本关键词的搜索输入框。
- **FR-2:** 系统应（不区分大小写地）匹配模板的 `title`、`description` 以及最新版本提示词 `content` 字段。
- **FR-2a:** 系统应（不区分大小写地）匹配模板的 `tags` 与 `category` 值，以便搜索标签名能找到带该标签的模板。
- **FR-3:** 系统应将多词关键词作为单个短语处理（跨字段 AND 语义，字段内短语匹配）。
- **FR-4:** 系统应只返回请求者可见的模板：匿名用户仅公开模板；登录用户为公开 + 自己的私有模板（既有可见性规则不变）。
- **FR-5:** 系统应为当前查询/筛选显示匹配模板总数（结果数量），并在每次查询变化时更新。
- **FR-6:** v1 不做高亮（无摘要/高亮）—— 结果卡片与今天一致。
- **FR-7:** 系统应修剪并合并关键词中的空白；空/纯空白关键词等同于无关键词筛选。
- **FR-8:** 系统应将关键词长度限制为 100 字符；超长输入仅取前 100 字符参与匹配（输入框允许继续输入但仅前 100 字符生效）。

### 5.2 排序

- **FR-9:** 系统应在模板列表上支持以下排序选项：`newest`（默认，`created_at DESC`）、`most_liked`（`like_count DESC, created_at DESC`）、`most_favorited`（`favorite_count DESC, created_at DESC`）、`trending`（见 FR-10）。
- **FR-10:** `trending` 应按尾随时间窗内的互动排名（v1：最近 7 天的 like_count + favorite_count，平局时 `created_at DESC`）。时间窗是服务端常量，不对用户开放配置。
- **FR-11:** 系统应在所有列表上下文（公开、私有、混合、我的点赞、我的收藏）中一致地应用所选排序。
- **FR-12:** 系统应忽略非法排序值并回退到 `newest`（服务端校验，客户端只发送合法值）。

### 5.3 标签与分类筛选

- **FR-13:** 系统应支持选择多个标签（AND 语义：模板必须包含所有所选标签）。
- **FR-14:** 系统应在侧栏标签云中显示标签选择计数（既有行为），并通过复选框式交互支持多选。
- **FR-15:** 系统应支持在单个请求中组合关键词 + 分类 + 标签 + 可见性 + 排序。
- **FR-15a:** 系统应支持独立清除分类筛选而不影响标签和关键词。
- **FR-16:** 系统应提供"全部清除"操作，重置关键词、分类、标签和排序（可见性回到用户持久化的默认值），并让用户回到未筛选列表。

### 5.4 URL 状态与可分享性

- **FR-17:** 系统应将关键词、分类、标签、排序和可见性同步到首页路由的 URL 查询参数（`?q=`、`?category=`、`?tags=a,b`、`?sort=`、`?visibility=`）。
- **FR-18:** 系统应在页面加载时从 URL 参数恢复完整筛选状态（深链恢复），包括语言切换或刷新后。
- **FR-18a:** 系统应在筛选变化时更新 URL，但关键词输入时不为每次击键添加历史条目（关键词输入用 replace 而非 push；离散筛选变化用 push）。
- **FR-19:** 系统应支持浏览器前进/后退导航恢复之前的筛选状态。

### 5.5 搜索建议（v1 范围：轻量）

- **FR-20:** 用户输入时（≥2 字符），系统应显示最多 5 条建议：先匹配的分类，后匹配的标签，取自既有 `/api/v1/categories` 与 `/api/v1/tags` 端点（客户端匹配，无新端点）。
- **FR-21:** 选择分类建议应用分类筛选；选择标签建议应用该标签筛选（建议处为单标签应用，与侧栏 FR-13 的多选并存）。
- **FR-22:** 系统不应因建议加载而阻塞输入或搜索提交（建议是纯增量 UI）。

### 5.6 API 与后端

- **FR-23:** `ListTemplatesRequest` proto 应增加 `string keyword = 10;` 与 `string sort = 11;` 字段。
- **FR-24:** REST 网关应在 `GET /api/v1/templates` 上接受 `keyword` 与 `sort` 查询参数并映射到 proto 字段。
- **FR-25:** 仓储 `List` 应通过 SQL `ILIKE` 在 `title`/`description`/`tags`/`category` 及最新版本内容上实现关键词匹配（见 FR-2/FR-2a；内容匹配通过联接最新模板版本实现）。
- **FR-26:** 仓储 `List` 应将四种排序实现为参数化的 `ORDER BY` 子句（服务端白名单；绝不从用户输入拼接）。
- **FR-27:** 系统应为所有新筛选/排序维持既有分页语义（page_token 为偏移量、next_page_token）。
- **FR-28:** 系统应随结果返回匹配总数（`ListTemplatesResponse` 中的 `total_count`）以支撑 FR-5。*（若总数计算成本高，v1 可仅在每个查询的第一页返回 `total_count` —— 见 NFR-4。）*
- **FR-28a:** 系统应保持登录混合视图既有的混合公开/私有的分页 token 格式（`public:private`）不变。

### 5.7 前端 UI

- **FR-29:** 首页应在模板网格上方渲染搜索栏（桌面端：与页面头部区域同行；移动端：吸顶于 header 下方）。
- **FR-30:** URL 同步的筛选应在搜索栏与网格之间以可移除筛选 chips 汇总：活动关键词、分类、每个标签和排序各一个 chip（排序 chip 可移除 → 回到默认）。
- **FR-30a:** 系统应在查询进行中显示加载状态（骨架卡片或既有 spinner），查询失败时显示带重试的错误状态。
- **FR-31:** 排序控件应为紧凑下拉（自定义、Aurora 风格），含四个选项，位于搜索栏行右侧。

### 5.8 普通用户与管理员划分

- **FR-32:** 本功能的所有需求适用于普通用户界面（首页 / Prompt Square）。不涉及管理员界面变更。
- **FR-33:** 管理员模板审核列表（admin-user-management 功能）可复用此处引入的关键词/排序仓储能力；本功能不新增管理员专属搜索 UI。

## 6. 非功能需求

- **NFR-1（性能）:** 在 ≤10 万模板、ILIKE + btree 索引下，关键词搜索 p95 < 500ms。全文搜索（tsvector）不在 v1 范围（见 §8）。
- **NFR-2（性能）:** 建议由已获取的分类/标签在客户端计算；零额外请求。
- **NFR-3（兼容性）:** 不发送 `keyword`/`sort` 的既有客户端应获得与今天完全一致的行为（默认排序、无关键词筛选）。无破坏性 API 变更。
- **NFR-4（性能）:** `total_count` 应通过同一查询筛选以 `COUNT(*) OVER()` 窗口函数或并行计数查询计算；若 p95 超预算，降级为仅首页计数。
- **NFR-5（无障碍）:** 搜索输入、排序下拉、筛选 chips 和建议必须可键盘操作并被屏幕阅读器播报（见 UI/UX 文档 §11）。
- **NFR-6（国际化）:** 所有新增 UI 字符串提供 EN 与 ZH 并保持同步；关键词匹配本身与语言无关（对存储内容 ILIKE）。
- **NFR-7（安全）:** 关键词与排序值参数化；无 SQL 注入面。排序值服务端白名单。
- **NFR-8（数据）:** v1 无需 schema 变更（对既有列 ILIKE；trending 使用既有点赞/收藏计数与时间戳）。*（若 trending 需要滚动窗口，未来可增加物化每日互动汇总 —— v1 范围外。）*
- **NFR-9（可观测性）:** 服务应在 ListTemplates 调用中记录关键词长度（非内容）与排序值，实现无 PII 顾虑的可观测性。

## 7. 验收标准

- **AC-1:** 在搜索框输入 "email" 并回车（或等待防抖）后，仅返回标题/描述/内容/标签/分类匹配 "email"（不区分大小写）的模板，并显示结果数量。
- **AC-2:** 选择标签 `["marketing", "seo"]` 仅返回同时拥有两个标签的模板。
- **AC-3:** 选择"最多点赞"按 like_count DESC 重排结果；选择"趋势"按 7 天互动重排；URL 分别包含 `?sort=most_liked` / `?sort=trending`。
- **AC-4:** 筛选活动时，URL 反映关键词、分类、标签和排序；将 URL 复制到新标签页可恢复完全一致的视图。
- **AC-5:** 应用筛选后按浏览器后退按钮可回到之前的筛选状态。
- **AC-6:** 无匹配的查询显示空状态，回显活动关键词并提供"全部清除"操作。
- **AC-7:** 匿名用户搜索绝不在结果中看到私有模板。
- **AC-8:** 登录用户在混合视图搜索时，看到匹配关键词的自己私有模板与公开匹配并列，且既有混合分页正常工作。
- **AC-9:** 向 API 发送非法 `sort` 值（如 `sort=bogus`）时回退到 `newest` 且不报错。
- **AC-10:** 省略 `keyword`/`sort` 的既有测试与客户端行为与之前完全一致（无回归）。
- **AC-11:** 在搜索框打字不会在 300ms 窗口内触发超过一次请求（通过网络面板验证防抖）。
- **AC-12:** ≥2 字符后出现建议，先显示分类后显示标签，选择其一应用相应筛选。
- **AC-13:** 所有新增 UI 字符串在 `en` 与 `zh` 翻译文件中存在且键集一致。

## 8. 范围外（v1）

- 全文搜索引擎（PostgreSQL tsvector/GIN 或外部引擎如 Meilisearch/Elastic）—— v1 使用 ILIKE；为架构师记录迁移路径。
- 搜索结果高亮/摘要。
- 相关性排名（BM25 式评分）；v1 排序仅为四个显式选项。
- 每用户保存的搜索 / 搜索历史。
- 跨用户或其他实体搜索（仅模板）。
- 作者/所有者搜索（按创作者名搜索）。
- 日期范围筛选。
- 管理员专属搜索 UI（管理员列表仅复用后端能力）。
- 服务端搜索分析（超出 NFR-9 日志）。
- 语音/模糊匹配与容错。
- 中文分词匹配（ILIKE 子串匹配无需分词即可用于中文）。
- 物化 trending 汇总表（v1 从原始计数计算 trending；汇总是未来优化）。

## 9. 依赖与假设

- **D-1:** 既有 `templates` 表列（`title`、`description`、`tags`、`category`、`language`、`like_count`、`favorite_count`、`created_at`）可用于 ILIKE 匹配与排序。*（列名 `favorite_count` 以当前 schema 为准。）*
- **D-2:** 最新版本内容匹配（FR-2）需要联接 `template_versions` 取每个模板的最新版本；若联接成本高，架构师可将 v1 简化为仅标题/描述/标签/分类 —— 需求将内容匹配视为应有项而非阻塞项。
- **D-3:** v1 的 trending（FR-10）使用 `template_likes`/`template_favorites` created_at 时间戳在尾随窗口内计算的既有聚合计数；若这些表缺少时间戳，trending 降级为全时段 `like_count + favorite_count` 并以 `created_at DESC` 平局。由架构师确认。
- **D-4:** URL 状态（FR-17/18）假设首页路由使用 React Router v6 `useSearchParams`；无需路由升级。
- **D-5:** 不依赖 admin-user-management 功能；两个功能相互独立。若两者都上线，管理员审核列表可复用搜索/排序仓储能力（FR-33）。
- **D-6:** 既有混合视图分页 token 格式（`public:private`）保留（FR-28a）；新筛选同时作用于两个流。
- **D-7:** 建议（FR-20）依赖侧栏已获取的既有 `/api/v1/categories` 与 `/api/v1/tags` 端点；无新端点。
- **D-8:** `total_count` 响应字段（FR-28）对 `ListTemplatesResponse` 是增量字段；既有客户端忽略未知字段。
- **D-9:** 中文内容的 ILIKE 性能：子串匹配可用，但无索引时 ILIKE '%kw%' 无法使用 btree；pg_trgm GIN 索引是记录在案的升级路径（v1 范围外，为架构师标注）。
- **D-10:** 首页目前将可见性选择持久化在 localStorage；本功能保留该行为并在其上叠加 URL 状态（加载时 URL 优先，其次 localStorage 默认，再次认证状态默认）。
