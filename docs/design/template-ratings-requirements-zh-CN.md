# 模板评分 — 需求分析

- **功能标识:** template-ratings
- **版本:** 1.0
- **状态:** 已提案（待架构评审）
- **作者:** ui-ux-agent
- **日期:** 2026-10-12

## 1. 竞品研究摘要

| 平台 | 评分方式 | 关键启示 |
|---|---|---|
| **PromptBase** | 提示词上的星级评分；卡片与详情页展示总分 + 计数 | 总分 + 计数是标准呈现；没有计数的分数毫无意义 |
| **FlowGPT** | 点赞/点踩投票；分数 = 赞数；可按 "Top rated" 排序 | 单一赞/踩是门槛最低的信号；但它把"完美可用"和"还行"压进同一个桶 |
| **Snack Prompt** | 基于点赞的排名；社区投票驱动 "Trending" | 社区投票驱动发现排序；评分与点赞作为独立信号共存（质量 vs 欣赏） |
| **AIPRM** | 赞/踩 + 查看/使用计数；按投票排序 | 使用计数为评分提供上下文（"4 万次使用有效"）；我们已有点赞/收藏计数作为相邻信号 |
| **PromptHero** | 无评分；仅红心 | 纯欣赏信号留下质量缺口 —— 用户无法表达"这对我没用" |
| **Amazon / 电商** | 1–5 星，每用户每商品一条，可修改，总分 + 分布直方图 | 每人一条可修改的评分是经典模型；分布直方图（5★ 70% / 1★ 5%）是深度用户寻找的信任信号 |
| **Chrome 应用商店 / VS Code 插件市场** | 1–5 星，每人一条，卡片显示总分，详情显示分布 | 市场模式：详情页评分、卡片总分、列表按评分排序 |

**综合结论:** v1 的胜出模式是市场模型：1–5 星评分，每用户每模板一条（upsert —— 重新评分替换旧值），卡片与详情页展示平均分 + 计数，详情页展示分布直方图，模板所有者不能给自己的模板评分。评分是*质量*信号，与点赞（欣赏）、收藏（书签）刻意分离 —— 三者共存。搜索筛选功能的排序选项增加 `top_rated`；评论功能的详情页区块获得评分组件作为兄弟。Open Prompts 目前没有任何质量信号：一个有 500 赞但提示词已损坏的模板与正常模板看起来一模一样。

## 2. 问题陈述

1. **没有质量信号。** 点赞与收藏衡量欣赏与收藏，而非"这个模板是否真的产出好结果"。用户无法表达"这对我没用"，潜在用户在投入时间前看不到质量。
2. **发现无法按质量排序。** 搜索筛选功能支持按最新/点赞/收藏/趋势排序 —— 全是热度代理。"评分最高"是每个市场最被需要的排序，没有评分就无法实现。
3. **没有反馈梯度。** 唯一信号是二元的（点赞/收藏）。5 级量表能捕捉"不错但不算好" —— 这是最常见的真实评价。
4. **创作者得不到质量反馈。** 创作者看到点赞数，却无法区分"效果很好"与"看着漂亮但实际不行"。

## 3. 目标用户

- **潜在用户（主要阅读者）:** 在使用/fork 前需要质量信号的模板评估者；他们看平均分、计数与分布。
- **评分者:** 使用过模板并想为其真实表现打分的已登录用户；被封禁用户除外。
- **创作者:** 获得模板的质量反馈（平均分 + 分布）；不能给自己评分。
- **管理员:** v1 无管理控制台界面 —— 评分是数值数据，不是需要审核的内容。（管理员模板详情可展示总分作为只读上下文；见 FR-13。）

## 4. 用户故事

### 4.1 评分

- **US-R1:** 作为试用过模板的用户，我希望打 1–5 星，以便分享它的实际效果。
- **US-R2:** 作为用户，我希望之后修改评分，以便评分反映我当前的体验（例如版本更新后）。
- **US-R3:** 作为用户，我希望删除我的评分，以便彻底撤回。
- **US-R4:** 作为用户，我希望返回时看到自己当前评分被预选，以便状态清晰。
- **US-R5:** 作为创作者，我不能给自己的模板评分，以便总分保持诚实。
- **US-R6:** 作为匿名访客，尝试评分时被引导登录，以便流程可理解。
- **US-R7:** 作为被封禁用户，我不能评分，与账号受限状态一致。

### 4.2 消费评分

- **US-R8:** 作为潜在用户，我希望在模板卡片上看到平均分与计数，以便浏览时扫读质量。
- **US-R9:** 作为潜在用户，我希望在详情页看到平均分、计数与星级分布，以便深入判断质量。
- **US-R10:** 作为用户，我希望按"评分最高"排序模板列表，以便找到最好的模板而非只是热门的。
- **US-R11:** 作为用户，我希望评分针对模板整体（而非按版本），以便信号保持简单且样本充足。

### 4.3 系统

- **US-R12:** 作为系统，我保持每（用户, 模板）恰好一条评分，以便总分准确。
- **US-R13:** 作为系统，我在每次评分变化时事务性重算聚合值，以便计数与平均永不漂移。
- **US-R14:** 作为系统，我绝不让评分操作暴露谁给什么评了分（除评分者本人查看自己的评分），以便保护评分隐私。

## 5. 功能需求

### 5.1 数据模型

- **FR-1:** 新增 `template_ratings` 表：`user_id`（外键 → users，`ON DELETE CASCADE`）、`template_id`（外键 → templates，`ON DELETE CASCADE`）、`rating`（SMALLINT，`CHECK (rating BETWEEN 1 AND 5)`）、`created_at`、`updated_at`（TIMESTAMPTZ），`PRIMARY KEY (user_id, template_id)`。为聚合重算在 `template_id` 上建索引。
- **FR-2:** `templates.rating_sum`（INT/BIGINT，默认 0）与 `templates.rating_count`（INT，默认 0）在评分创建/更新/删除时事务性维护（与 `like_count` 相同的反范式计数模式）；平均分计算为 `rating_sum / rating_count`（绝不存储，避免漂移）。
- **FR-3:** 模板列表与详情响应包含 `rating_avg`（浮点，2 位小数，`rating_count = 0` 时为 null）、`rating_count`，以及 —— 仅详情 —— 分布 `{1: n, 2: n, 3: n, 4: n, 5: n}`。

### 5.2 评分操作（普通用户面）

- **FR-4:** `POST /api/v1/templates/{id}/rating`（需登录），请求体 `{rating: 1..5}`，对调用者的评分执行 upsert：不存在则插入，存在则替换（每用户每模板单行）。返回 `{rating_avg, rating_count, my_rating}`。自我评分（调用者 = 所有者）返回 403 及明确文案。被封禁用户返回 403。私有模板：仅所有者可评分（而自我评分被禁止，因此实际上无人可评 —— 见 FR-6 注）。
- **FR-5:** `DELETE /api/v1/templates/{id}/rating`（需登录）移除调用者的评分并重算聚合。幂等：删除不存在的评分返回 200 及当前聚合。返回 `{rating_avg, rating_count, my_rating: null}`。
- **FR-6:** `GET /api/v1/templates/{id}/rating` 并入模板详情响应（FR-3）而非独立端点；包含 `my_rating`（匿名为 null）以便 UI 预选用户的星级。不提供公开的"谁评了什么"列表。
- **FR-7:** 速率限制：每账号每分钟最多 20 次评分变更（HTTP 429 带 `Retry-After`）。服务端可配置。
- **FR-8:** v1 中评分不发出通知（评分是匿名的；"有人给你的模板评了 3★"的通知易成噪音 —— 随通知功能未来的偏好设置工作一并考虑）。

### 5.3 展示与发现（普通用户面）

- **FR-9:** 模板卡片（首页广场、搜索结果、收藏夹、创作者主页）展示紧凑星级行：平均分（1 位小数）+ 计数，如 "★ 4.6 (128)"；`rating_count = 0` 时隐藏（渲染为"还没有评分"或不渲染）。
- **FR-10:** 模板详情页展示：可交互的 5 星组件（悬停预览、点击评分、我的评分状态）、平均分（2 位小数）、计数、分布直方图（5 行：星级、条、百分比）。
- **FR-11:** 模板列表排序选项（搜索筛选功能）增加 `top_rated`：`rating_count >= 5 AND rating_avg DESC` —— 最低计数阈值防止单条 5★ 评分登顶；低于阈值的模板排在达标模板之后（以 `rating_count DESC` 为平局决胜，再 `created_at DESC`）。阈值服务端可配置。
- **FR-12:** 评分组件在视觉与功能上独立于点赞/收藏按钮（独立区块、独立语义：质量 vs 欣赏）；无 UI 耦合。

### 5.4 管理面（只读）

- **FR-13:** 管理员模板详情响应（`GET /api/v1/admin/templates/{id}`）包含 `rating_avg` 与 `rating_count` 作为只读上下文。v1 不提供管理员评分管理端点（评分是匿名数值数据；没有可审核的内容）。
- **FR-14:** 封禁用户不删除其评分（解封后可能回归）；其评分继续计入聚合。删除用户级联删除其评分并重算受影响聚合（FR-2）。

### 5.5 删除行为

- **FR-15:** 删除模板级联删除其评分（外键）；聚合列随行消失。

## 6. 非功能需求

- **NFR-1（性能）:** 评分 upsert/删除 p95 < 200 ms；聚合重算是同一事务内的两个整数列更新（无表扫描）。列表查询读取反范式列 —— 无 N+1、无运行时 AVG()。
- **NFR-2（可扩展性）:** 速率限制（FR-7）保护写路径。`top_rated` 排序是索引排序问题（架构师可加复合索引或计算列 —— 开放问题 §10.2）。
- **NFR-3（兼容性）:** 纯增量 —— 一张新表、`templates` 两个新列、新端点、卡片/详情展示增强、一个新排序值。既有排序、筛选与页面行为不变。
- **NFR-4（隐私）:** 评分天然匿名：无公开的按评分者数据；`my_rating` 仅返回给其所有者；管理员仅见聚合值。
- **NFR-5（无障碍）:** 星级组件可键盘操作（方向键选择、Enter/Space 提交），有可访问名称与值（"评分：5 星中的 4 星"），直方图是带文本值的语义表格/列表 —— 绝非仅颜色。WCAG 2.1 AA。
- **NFR-6（国际化）:** 所有面向用户的文案中英同步；星级术语、"评分最高"排序标签、"还没有评分"与计数格式本地化；数字用本地化格式。
- **NFR-7（安全）:** 所有写操作需登录；服务端校验（仅 1–5 整数、所有者检查、封禁检查）；无用户控制的标记；限速。
- **NFR-8（韧性）:** 评分失败显示 toast 并回退组件；列表/详情渲染绝不依赖评分可用性（空值安全展示）。
- **NFR-9（数据完整性）:** 并发评分下聚合保持一致（事务性 sum/count 维护）；upsert 语义使客户端重试安全。

## 7. 验收标准

- **AC-1:** 已登录用户可在详情页为公开模板打 1–5 星；平均分、计数与直方图即时更新且刷新后保持。
- **AC-2:** 重新评分替换旧值（每用户每模板一行）；聚合正确移动（如 4★ → 2★ 使平均分下降）。
- **AC-3:** 用户可删除自己的评分；聚合重算；组件回到未评状态。
- **AC-4:** 模板所有者不能给自己的模板评分（403 带文案）；匿名访客看到登录提示；被封禁用户得到 403。
- **AC-5:** 卡片在有评分时显示 "★ 4.6 (128)"，`rating_count = 0` 时显示中性的"还没有评分"状态。
- **AC-6:** 详情页直方图显示全部五行，百分比之和为 100%（± 舍入）。
- **AC-7:** 按 `top_rated` 排序时，`rating_count >= 5` 的模板按平均分降序，再按计数、再按最新；低于阈值的模板排在达标模板之后。
- **AC-8:** 无效评分（0、6、"abc"、3.5）被拒绝并返回 400 字段级错误。
- **AC-9:** 超过每分钟 20 次评分变更返回 429 及 `Retry-After`；UI 显示友好提示。
- **AC-10:** 管理员模板详情页显示平均分与计数；不存在管理员评分端点（尝试的管理评分路由返回 404）。
- **AC-11:** 删除用户移除其评分并重算受影响模板的聚合；删除模板移除其评分。
- **AC-12:** 所有新 UI 文案在 `en` 与 `zh` 翻译文件中键集一致；组件、直方图与排序标签在两种语言与主题下正确渲染。
- **AC-13:** 星级组件完全可键盘操作并向读屏器播报其值；直方图有文本值。
- **AC-14:** 评分 API 故障时详情页与列表完整渲染；组件回退并弹错误 toast。
- **AC-15:** 任何端点都不泄露哪些用户为某模板评了分（除用户自己的 `my_rating`）。

## 8. 不做范围（v1）

- 文字评价（附在评分上的文本）—— 评论功能覆盖文字反馈；星级 + 文字结合是未来的"评价"功能。
- 按版本评分（评分针对模板整体）。
- 评分加权（按评分者声誉/使用量加权）。
- "验证使用"门槛（仅在使用模板生成过 prompt 后才能评分）—— 未来的信任增强。
- 向所有者的评分通知（FR-8 的理由）。
- 匿名/游客评分。
- 管理员评分审核或删除端点。
- 评分导出/导入。
- 任何与变现相关的功能（遵循项目范围规则）。

## 9. 依赖与假设

- **D-1:** `templates` 已有由仓库层事务性维护的反范式 `like_count`/`favorite_count`；`rating_sum`/`rating_count` 沿用完全相同的模式（sum 用 BIGINT 更安全）。
- **D-2:** 搜索筛选功能（已设计）定义了排序框架（`newest`、`most_liked`、`most_favorited`、`trending`）；`top_rated` 作为带阈值规则的新值加入。若搜索筛选尚未上线，本功能的排序需求等待其上线（评分数据与展示独立具有价值）。
- **D-3:** 模板详情页已渲染点赞/收藏/fork 统计与（随评论功能）评论区；评分组件位于社交统计旁，直方图在其下。
- **D-4:** `PromptCard` 在首页广场、搜索结果、收藏夹与创作者主页渲染模板列表项；增加星级行是纯展示性变更，不得破坏卡片既有用法。
- **D-5:** users 表有 `status`（'active'/'banned'）用于封禁检查（与评论 FR-8 相同）。
- **D-6:** 限速复用 Redis 计数器方案（与评论 D-7、follow-creators D-7 假设相同）。
- **D-7:** REST 网关现有模板子资源路由（`/templates/{id}/likes` 风格）；评分端点沿用该模式。经既有 Bearer-token 拦截器认证。

## 10. 给架构师的开放问题

1. **聚合存储:** `rating_sum` + `rating_count` 列并计算平均（推荐 —— 整数运算、无漂移）还是直接存 `rating_avg`（更新时浮点漂移）。请确认计算方案。
2. **`top_rated` 索引:** 带阈值（`rating_count >= 5`）时，对 `(rating_sum/rating_count)` 建普通索引很别扭。选项：(a) 接受对筛选集排序，(b) 计算列/生成列 `rating_avg` 加索引与筛选，(c) 物化排行榜。建议：v1 用 (a) 并在 `(rating_count, rating_sum)` 上建复合索引 —— 列表延迟劣化时再评估。
3. **分布查询（FR-3）:** 详情页每次视图对 `template_ratings` 做 `GROUP BY rating`，还是在 `templates` 上反范式 5 桶计数？建议：GROUP BY（详情页流量远低于列表；桶方案要多维护 5 列）。
4. **服务放置:** 扩展 `PromptService`（评分是与点赞一样的模板子资源；推荐）还是新建 `RatingService`。
