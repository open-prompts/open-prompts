# API Playground — 需求分析

- **Feature ID:** api-playground
- **Version:** 1.0
- **Status:** Proposed（待架构评审）
- **Author:** ui-ux-agent
- **Date:** 2026-10-12

## 1. 竞品调研总结

| 平台 | 开发者控制台 / 试验场做法 | 关键启示 |
|---|---|---|
| **OpenAI Platform（API reference + Playground）** | 每个 REST 端点都有 "try it" 面板：鉴权从登录会话注入，参数为可编辑表单，响应渲染为带状态码/耗时的格式化 JSON | 会话注入鉴权消除了第一摩擦（复制密钥）；按端点的表单比裸 curl 更利于发现 |
| **Anthropic Workbench** | 浏览器内控制台：选模型、编辑请求 JSON、运行、检查响应；每个工作区有请求历史 | 一个聚焦的运行器加历史就足够 —— 不需要完整的 Postman 克隆 |
| **Stripe API Explorer** | 交互式文档：左侧端点列表，右侧参数表单 + 生成的代码片段（curl/Node/Python），可实时 "Send request" | 与表单状态同步生成的代码片段极大缩短了从"试用"到"集成"的路径 |
| **Swagger UI / OpenAPI explorers** | 从规范自动生成 try-it 表单；顶部一个 API key 输入框完成鉴权 | 事实上的基线体验；顶部密钥框 + 按端点表单 |
| **Postman** | 完整工作区：集合、环境、脚本 | 对产品内控制台而言过重；我们只需要"对我们的 API 跑一个请求" |
| **GitHub GraphQL API Explorer** | 文档与运行器同页；默认使用登录会话令牌，可切换为 PAT 测试 | 默认会话令牌、可选测试个人令牌是正确的信任模型 |
| **Kong / Konga 等网关** | 带请求构建器的管理控制台 | 网关控制台证明该模式同样适用于非 LLM API |

**综合结论：** v1 的制胜模式是 "API explorer"：在 Web 应用内新增 `/playground` 页面，登录用户选择 Open Prompts 自身的一个 REST 端点（v1：按别名解析模板），填写小型参数表单，实时运行请求。鉴权默认从当前会话注入，可选粘贴个人 API key（与 SDK 相同的 `X-API-Key` 机制），以便用户验证代码将要使用的凭证。响应面板展示状态码、耗时、响应头和格式化 JSON。生成的代码片段（curl / Python / JavaScript）与当前表单状态同步，将试验场与模板详情页现有的 SDK Integration 卡片连接起来。**LLM 执行明确不在范围内** —— 试验场只调用 Open Prompts 自身的 REST API（模板解析），不调用任何模型厂商。

## 2. 问题陈述

1. **API 是隐形的。** Open Prompts 暴露了真实的 REST API（`GET /api/v1/templates/{id}/aliases/{alias}` 按别名解析模板版本，`X-API-Key` 鉴权），但产品内无法试用。用户必须阅读 SDK 片段、离开应用、手写 curl 命令。
2. **API key 无法验证。** 用户在 API Keys 页面创建密钥，却无法在接入代码前验证密钥可用。拼错或已吊销的密钥只能在用户自己应用的错误日志里被发现。
3. **模板详情页只有静态代码教学。** SDK Integration 卡片展示 Python 片段，但用户看不到端点返回的真实 JSON —— 响应结构（版本内容、解析变量、元数据）在产品内无文档。
4. **集成调试靠猜。** 当用户的集成失败（401？404 别名？模板 id 错？）时，产品内没有可对照的参考点。

## 3. 目标用户

- **集成者（主要）：** 想从自己的代码调用 Open Prompts API 的登录用户 —— 需要理解请求/响应结构并验证 API key。
- **模板创作者：** 想确认自己的模板通过 API 路径（别名 → 版本 → 内容）解析出的结果与消费者收到的一致。
- **评估平台的高级用户：** 想在投入模板之前看到"这里有真实可用的 API"。
- **管理员：** v1 无专属管理界面 —— 试验场只调用普通用户 API。（管理 API 探索不在范围内；见 §8。）

## 4. 用户故事

- **US-P1:** 作为集成者，我希望在浏览器里对模板解析端点发起真实请求，以便不写代码就能看到确切的响应 JSON。
- **US-P2:** 作为集成者，我希望试验场默认使用我的登录会话，以便无需先创建密钥就能立即试用 API。
- **US-P3:** 作为集成者，我希望可选粘贴一个 API key 并用它重发请求，以便验证代码将要使用的凭证。
- **US-P4:** 作为集成者，我希望有与当前表单状态同步的代码片段（curl / Python / JavaScript），以便把可运行的代码复制进项目。
- **US-P5:** 作为集成者，我希望看到每个响应的状态码、耗时和格式化 JSON，以便对照已知良好的参考来调试集成。
- **US-P6:** 作为模板创作者，我希望选择我的某个模板和别名、填入变量、看到解析后的版本内容，以便确认消费者收到的内容。
- **US-P7:** 作为集成者，我希望最近的试验场请求保留在本地历史列表中，以便在会话内重跑或对比之前的请求。
- **US-P8:** 作为慢网络用户，我希望有清晰的加载与错误状态（网络失败、401、404），以便始终知道发生了什么。

## 5. 功能需求

### 5.1 数据模型

- **FR-1:** 不新增数据库表。试验场是纯前端界面，构建于现有 REST API（`GET /api/v1/templates/{template_id}/aliases/{alias_name}`）与现有资源（模板、别名、API key）之上。
- **FR-2:** 请求历史仅存于客户端（组件状态，最多保留最近 10 条，页面卸载即清空）。v1 不做服务端历史。

### 5.2 普通用户界面（`/playground` 页面）

- **FR-3:** Web 应用新增路由 `/playground`，入口位于 Header（桌面导航）和用户下拉菜单，文案 "API Playground" / "API 试验场"。
- **FR-4:** v1 仅支持一个端点：`GET /api/v1/templates/{template_id}/aliases/{alias_name}`（按别名解析模板版本）。端点以固定的只读"请求卡片"呈现（方法徽标 `GET` + 含两个路径参数的路径）。
- **FR-5:** 请求表单包含：
  - **模板选择器**（可搜索下拉，列出用户可访问的模板 —— 自己的模板加公开模板，复用现有模板列表 API 与搜索框）；
  - **别名选择器**（下拉数据来自所选模板的 `GET /api/v1/templates/{id}/aliases`，默认 `latest`，支持自由输入自定义别名）；
  - **鉴权选择器**：`会话（默认）` 或 `API key`，选择后者时显示密码类型的密钥输入框。密钥以 `X-API-Key` 头发送，与 SDK 完全一致。
- **FR-6:** 选中模板与别名后，预取别名元数据（可用变量列表），并为每个 `$$variable$$` 占位符渲染一个输入框，让用户看到并填写该端点接受的变量。
- **FR-7:** **Run** 按钮从浏览器发起请求。`会话` 模式使用用户既有的 Authorization 头（Web 应用常规的已登录 axios 实例）；`API key` 模式仅设置 `X-API-Key`（不带会话头），使测试忠实于服务端代码的调用方式。
- **FR-8:** 响应面板展示：带颜色编码的 HTTP 状态码（2xx 绿、4xx 琥珀、5xx 红）、毫秒耗时、响应头（可折叠）、以及语法高亮、可折叠的 JSON 响应体。
- **FR-9:** 代码片段面板根据当前表单状态生成可复制的片段，三个标签页：`curl`、`Python`、`JavaScript (fetch)`。Python 标签页与模板详情页现有 SDK Integration 片段风格一致（使用 `OpenPromptsClient`、`base_url` 与 `api_key`）。片段始终使用 API key 鉴权形式（绝不嵌入会话令牌）。
- **FR-10:** 历史：每次执行的请求追加一条记录（时间戳、模板、别名、鉴权模式、状态、耗时）到最多 10 条的本地列表；点击记录恢复其表单状态与响应；记录不做服务端持久化，刷新即丢失。
- **FR-11:** 错误处理：网络失败渲染友好错误状态与 Retry 按钮；HTTP 错误响应（401/403/404/429）渲染状态码、响应体中的服务端错误消息，以及通俗提示（如 401 → "请检查 API key 是否有效且处于激活状态"）。
- **FR-12:** 试验场需要登录。匿名访问者重定向到登录页并携带 return-to-`/playground` 回跳，与其他需登录页面一致。

### 5.3 管理端界面

- **FR-13:** v1 无。试验场只调用普通用户 API。管理 API 探索器是未来的候选（见 §8）。

### 5.4 限流与滥用

- **FR-14:** 试验场从用户浏览器直接向现有网关发起请求；不新增服务端端点，因此不新增攻击面。其发出的请求适用标准的按用户 API 限流。请求进行中时 Run 按钮禁用（防重复提交）。

### 5.5 删除与生命周期

- **FR-15:** 若历史记录涉及的模板或别名被删除，重跑该记录得到 404 与标准错误提示；历史记录不做服务端自动清理（它们仅存在于客户端）。

## 6. 非功能需求

- **NFR-1（易用性）：** 首次使用的集成者从 API Keys 页面 → 试验场 → 成功响应，全程不超过 2 分钟，无需阅读文档。
- **NFR-2（性能）：** 试验场页面随应用包加载；Run 往返耗时仅受现有 API 延迟约束。响应 JSON 渲染需支持最大 1 MB 的响应体而不冻结 UI（大数组虚拟化/折叠）。
- **NFR-3（安全）：** API key 输入框为 `type="password"` 并带显示/隐藏切换；密钥绝不写入 localStorage；生成的片段包含字面占位符 `YOUR_API_KEY`，绝不包含真实密钥。试验场绝不显示或记录会话令牌。
- **NFR-4（兼容性）：** 页面与应用其余部分使用相同的浏览器矩阵（React 18、现代常青浏览器），支持浅色/深色主题，并完整响应式适配至移动端（堆叠布局）。
- **NFR-5（国际化）：** 所有文案通过 i18next 提供 EN/ZH，匹配现有 translation.json 结构。
- **NFR-6（无障碍）：** 全键盘可操作（选择器、变量输入、Run、片段标签页）；状态色满足 WCAG 2.1 AA 对比度；响应到达时有屏幕阅读器播报。
- **NFR-7（可维护性）：** 端点定义（路径、参数、片段生成器）集中在一个数据驱动的配置对象中，未来新增端点无需重构页面。

## 7. 验收标准

- **AC-1:** 已登录用户可从 Header 打开 `/playground`，选择模板与别名、填写变量，收到 200 响应，展示状态码、耗时、响应头与格式化 JSON。
- **AC-2:** 切换到 `API key` 鉴权并粘贴 API Keys 页面中的有效密钥得到 200；粘贴已吊销/乱写的密钥得到 401 及通俗提示。
- **AC-3:** 三个片段标签页（curl/Python/JavaScript）反映当前模板 id、别名与变量；复制得到以 `YOUR_API_KEY` 为占位符的可运行代码。
- **AC-4:** 对不存在的别名发起请求得到 404，响应面板渲染服务端消息与提示。
- **AC-5:** 历史展示会话内最近 ≤10 条请求；点击一条恢复表单与响应；刷新后清空。
- **AC-6:** 匿名访问 `/playground` 重定向到登录页，登录后回到 `/playground`。
- **AC-7:** 所有文案 EN/ZH 已翻译；无硬编码文案。
- **AC-8:** 功能中没有任何变现相关内容。

## 8. 不做范围

- **LLM 执行 / 模型厂商调用。** 试验场只调用 Open Prompts 自身的 REST API。绝不调用任何 AI 模型厂商，没有模型参数、token 或成本概念。
- 管理 API（`/api/v1/admin/*`）探索。
- 服务端请求历史、保存的集合或共享的试验场状态。
- POST/PUT/DELETE 端点（v1 仅为只读的解析端点）。
- 任何形式的变现（支付、定价、购买、收益）—— 本产品永久不做。
- 以原始 JSON 编辑请求（v1 中表单是唯一事实来源）。
- Mock 模式 / 离线沙箱。

## 9. 依赖与假设

- **D-1:** 现有端点 `GET /api/v1/templates/{template_id}/aliases/{alias_name}`（网关 → `PromptService.GetPromptByAlias`）仍是解析 API；试验场是其消费者，不改变它。
- **D-2:** 现有 `X-API-Key` 鉴权路径（`AuthInterceptor.VerifyAPIKey`）接受 API Keys 页面创建的同一批密钥。
- **D-3:** 现有模板列表/搜索 API 可填充模板选择器（公开 + 自己的模板）。
- **D-4:** 现有 `GET /api/v1/templates/{id}/aliases` 端点填充别名选择器。
- **D-5:** 开发中的 notifications 功能不是前置条件；试验场不产生通知。
- **D-6:** 假设 follow-creators 功能的"创作者身份"工作不冲突；端点无重叠。

## 10. 给架构师的开放问题

1. **CORS：** 试验场从浏览器发送带 `X-API-Key`（和会话 Authorization）的同源请求 —— 请确认网关的 CORS 配置已允许 `X-API-Key` 头（同源本应无碍，但该头目前不在 `Access-Control-Allow-Headers` 中）。
2. **鉴权模式保真度：** 选择 `API key` 模式时，请求是否应完全省略 cookie/会话头（推荐，以忠实模拟服务端到服务端调用）？网关对头鉴权与会话鉴权请求的限流是否一致？
3. **端点目录：** 单端点 v1 是否可接受，还是数据驱动设计（NFR-7）应随附第二个端点（如 `GET /api/v1/templates/{id}`）以验证模式？
4. **片段准确性：** Python 片段引用 `OpenPromptsClient`（与模板详情 SDK 卡片一致）。是否有已发布的 SDK 可链接，还是在 SDK 发布前 Python 标签页应使用原生 `requests`？
