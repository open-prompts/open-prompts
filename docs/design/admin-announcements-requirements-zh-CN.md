# 管理员公告 — 需求分析

- **功能 ID：** admin-announcements
- **版本：** 1.0
- **状态：** Proposed（待架构评审）
- **作者：** ui-ux-agent
- **日期：** 2026-10-13
- **配套文档：** `admin-announcements-ui-ux-design-zh-CN.md`

## 1. 竞品调研

| 产品 | 公告能力 | 优势 | 不足 |
|---|---|---|---|
| GitHub | 关键通知的全局横幅；组织/仓库级讨论 | 关键事项无法错过 | 一次一条；无排期 |
| Discourse | 管理员"横幅话题"置顶所有页面直至关闭 | 高可见性、可关闭 | 单一活动横幅；无受众定向 |
| Notion | 应用内"新功能"弹窗 + 更新日志页 | 富媒体、有版本历史 | 容易错过；无紧急级别 |
| Linear | 更新日志流 + 大版本发布时的全屏弹窗 | 干净、产品主导 | 无按受众的管理员定向 |
| Vercel | 状态横幅 + 更新日志 | 运维清晰 | 界面分裂 |
| PromptBase/FlowGPT | 无（无公告系统） | — | 提示词平台无可借鉴；适用 SaaS 管理后台模式 |

**结论：** 胜出模式是**单一活动横幅**（GitHub/Discourse 模式）用于限时高可见通知，加上**公告历史列表**（Notion/Linear 模式）让用户事后补看。按角色定向受众（仅管理员 vs 全体用户）覆盖内部运维而无需独立渠道。提示词平台在此空白 —— SaaS 管理后台模式直接适用。

## 2. 问题陈述

平台无法告知用户任何事：维护窗口、新功能、政策变更或事故通知。今天唯一的渠道是带外（邮件/README）。管理员需要一种产品内、限时、可关闭的触达全体用户的方式；用户需要一个能查看当前与历史公告、又不被永久纠缠的地方。

## 3. 目标用户

- **管理员** —— 发布、排期、编辑、结束公告；查看阅读/关闭指标。
- **全体用户** —— 看到活动公告、关闭它、浏览历史。
- **作为接收者的管理员** —— 在同一系统中接收仅管理员的运维公告（如"部署窗口"）。

## 4. 用户故事

- **US-1**：作为管理员，我想发布带开始与结束时间的横幅公告，使其在定义窗口内对全体用户可见。
- **US-2**：作为管理员，我想选择受众（全体用户 / 仅管理员），使运维通知不打扰普通用户。
- **US-3**：作为管理员，我想将公告标记为紧急（不可关闭）或普通（可关闭），以尊重紧急程度。
- **US-4**：作为管理员，我想编辑或结束活动公告，以便纠正错误与变更计划。
- **US-5**：作为管理员，我想看到阅读与关闭计数，以了解触达率。
- **US-6**：作为用户，我想让活动公告以可关闭（当可关闭时）的横幅展示，不阻挡我的工作。
- **US-7**：作为用户，我想让已关闭的公告跨会话保持关闭，不被反复纠缠。
- **US-8**：作为用户，我想要公告历史页，以补看错过的内容。
- **US-9**：作为用户，我想在横幅中有可选链接，以便对通知采取行动（如更新日志、状态页）。

## 5. 功能需求

- **FR-1**：管理员可创建公告，包含：标题（必填，≤ 120 字符）、正文（必填，≤ 2000 字符，支持换行的纯文本）、可选链接 URL + 链接文字、受众（`all_users` | `admins_only`）、级别（`standard` | `critical`）、`starts_at`/`ends_at`（ISO-8601；starts_at 默认现在；ends_at 必填）。
- **FR-2**：每个受众同一时间最多**一条**活动公告；向已有活动公告的受众发布新公告需显式结束现有公告（UI 提供"结束并替换"）。
- **FR-3**：公告在 `now ∈ [starts_at, ends_at)` 时**活动**；横幅仅为匹配查看者受众的活动公告渲染（管理员同时看到 `all_users` 与 `admins_only`）。
- **FR-4**：`critical` 公告以独特样式渲染且**不可关闭**；`standard` 公告按用户可关闭。
- **FR-5**：关闭状态按用户按公告服务端持久化（`announcement_dismissals` 表）；已关闭的普通公告对该用户跨会话、跨设备不再渲染。
- **FR-6**：横幅出现在每个已认证页面顶部（header 之上），可通过 × 按钮关闭（仅普通），显示标题 + 正文摘录 + 可选链接。
- **FR-7**：横幅（及用户菜单）中的"查看全部公告"链接打开 `/announcements` —— 按查看者受众反向时间排序的公告列表，含标题、正文、级别 chip、活动窗口；分页（20/页）。
- **FR-8**：管理控制台：`/admin/announcements` 列出所有公告（任意状态），含状态（已排期/活动中/已结束）、受众、级别、窗口、阅读/关闭计数；`/admin/announcements/new` 与 `/admin/announcements/:id/edit` 提供表单。
- **FR-9**：管理员 API：`POST /api/v1/admin/announcements`（创建）、`GET /api/v1/admin/announcements`（列表，按状态过滤）、`GET /api/v1/admin/announcements/{id}`、`PATCH /api/v1/admin/announcements/{id}`（已排期或活动中可编辑）、`POST /api/v1/admin/announcements/{id}/end`（设 ends_at = now）、`DELETE /api/v1/admin/announcements/{id}`（仅已排期）。
- **FR-10**：用户 API：`GET /api/v1/announcements/active` → 查看者的活动公告（或空）、`GET /api/v1/announcements?page_size=20&page_token=...` → 查看者受众的历史、`POST /api/v1/announcements/{id}/dismiss`（仅普通；幂等）。
- **FR-11**：每个用户每条公告只计一次浏览（横幅或历史项首次渲染时）通过 fire-and-forget beacon 上报；阅读计数是近似值，仅供参考。
- **FR-12**：编辑活动公告不重置关闭或阅读计数；编辑仅限标题、正文、链接、ends_at（受众与级别发布后不可变）。
- **FR-13**：所有管理员公告操作（创建/编辑/结束/删除）写入审计日志，含操作者、目标 id、变更字段。
- **FR-14**：公告仅纯文本 —— v1 不支持 HTML、Markdown 渲染或内嵌媒体；链接字段中的 URL 必须为 http(s)。
- **FR-15**：横幅不得出现在管理员登录页或普通登录/注册页（未认证界面）。
- **FR-16**：公告结束（ends_at 过后）后，横幅在 60 秒内对所有用户消失，无需刷新页面（有横幅可见时客户端最多每 60 秒轮询活动公告；否则在页面加载时轮询）。

## 6. 非功能需求

- **NFR-1（性能）**：`GET /announcements/active` p95 < 50 ms；横幅不产生可感知布局偏移（加载后预留高度）。
- **NFR-2（规模）**：关闭与浏览追踪不得产生无界写入 —— 每用户每公告一行，最多更新一次。
- **NFR-3（国际化）**：所有 UI 字符串中英同步；公告内容为管理员撰写，原样展示（不翻译）。
- **NFR-4（无障碍）**：横幅是带标签的区域；紧急横幅首次渲染用 `role=alert`；关闭操作可键盘访问。
- **NFR-5（安全）**：链接 URL 经净化（仅 http/https）并以 `rel="noopener noreferrer"` 新标签页打开；正文以文本渲染，绝不作为 HTML（构造上防 XSS）。

## 7. 验收标准

- **AC-1**：创建 starts_at = 现在、ends_at = +7 天的公告，立即以可关闭的普通横幅对全体用户可见。
- **AC-2**：已有一条全体用户活动公告时再发布第二条，提示"结束并替换"；确认后旧公告结束、新公告原子性生效。
- **AC-3**：紧急公告以独特样式渲染且无 × 按钮；普通公告显示 ×。
- **AC-4**：关闭普通公告后，登出/登录及另一浏览器中保持关闭（服务端关闭状态）。
- **AC-5**：仅管理员的公告对普通用户不可见（横幅与历史均不可见），但对管理员可见。
- **AC-6**：`/announcements` 最新在前列出已结束公告，含级别 chip 与窗口；20/页分页正常。
- **AC-7**：编辑活动公告正文不重置其阅读/关闭计数，已关闭它的用户仍看不到它。
- **AC-8**：`POST /announcements/{id}/end` 设 ends_at = now；横幅 60 秒内对所有用户消失，无需刷新。
- **AC-9**：普通用户调用任何 `/api/v1/admin/announcements` 端点收到 403。
- **AC-10**：正文包含 `<script>alert(1)</script>` 时按字面文本渲染，绝不执行。

## 8. 不在范围内

- 公告的邮件/推送送达；通知中心集成（公告是独立界面）。
- 富文本/Markdown 正文、图片或内嵌媒体。
- 全体用户/仅管理员之外的受众定向（不按用户、语言或群组定向）。
- starts_at/ends_at 之外的排期队列（无重复、无时区感知窗口）。
- 公告翻译流程。
- 任何形式的变现 —— 本产品永久不做。

## 9. 依赖与假设

- **D-1**：复用 admin-user-management 的审计日志基础设施实现 FR-13。
- **D-2**：复用 admin-user-management 的管理控制台外壳（`/admin` 布局、导航、鉴权守卫）承载新页面。
- **D-3**：已认证应用外壳（header/布局组件）是挂载横幅的唯一位置。
- **D-4**：fire-and-forget beacon 遵循 template-watch 的浏览 beacon 模式（非阻塞、容忍丢失）。
- **D-5**：与通知系统无交互（notifications FR-30 保持分离）；公告是独立界面。

## 10. 给架构师的开放问题

- **OQ-1**：`GET /announcements/active` 应纳入初始页面加载的 bootstrap 载荷（避免无横幅闪烁），还是独立调用？（提案：独立调用并预留横幅高度。）
- **OQ-2**：用专门的 `announcement_dismissals`（user_id, announcement_id）表，还是 users 上的 JSONB 数组？（提案：专门表 —— 可索引、有界。）
- **OQ-3**：浏览追踪应复用 dismissals 表加 `read_at` 列，还是单独的 `announcement_reads` 表？（提案：同表，`read_at` 可空列。）
- **OQ-4**：60 秒活动公告轮询是否需要抖动以避免惊群，还是用户量小可忽略？
- **OQ-5**：DELETE 是否应允许用于活动公告（带审计），还是如提案仅限已排期（活动公告必须先结束）？
