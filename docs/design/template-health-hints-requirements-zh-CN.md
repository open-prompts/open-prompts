# 模板健康度提示 — 需求分析

- **功能 ID：** template-health-hints
- **版本：** 1.0
- **状态：** 已提案（待架构评审）
- **作者：** ui-ux-agent
- **日期：** 2026-10-13

## 1. 竞品调研总结

| 平台 | 质量/完整度方式 | 关键启示 |
|---|---|---|
| **LinkedIn** | 档案完整度计量（0–100%）带命名的下一步操作（"添加一项技能"） | 单一分数加一键下一步操作是史上被复制最多的参与模式；每个提示必须链接到其修复处 |
| **Etsy** | 商品质量清单：照片数、标签填写、描述长度；发布前可见 | 发布前清单在源头提升内容质量；在发布*之前*展示检查优于事后修复 |
| **Shopify** | 商品页健康分，带加权因子和内联解释 | 可解释的加权因子优于不透明分数；解释本身就是产品 |
| **Google Search Console** | 覆盖报告：每页 错误/警告/有效 状态并可下钻 | 三个严重级别（错误/警告/通过）干净地映射到内容检查 |
| **Webflow / 建站工具** | 发布前清单弹窗（SEO 标题、描述、OG 图） | 在注意力最集中的发布时刻，紧凑清单捕获问题 |
| **提示词市场（PromptBase/FlowGPT）** | 无质量工具；弱列表比比皆是 | 质量工具是未被占领的差异化点；更好的列表改善所有人的搜索/发现 |

**综合分析：** 成熟模式是**带严重级别和一键修复的透明加权清单**：LinkedIn 证明了分数+下一步循环；Etsy/Shopify 证明清单在创建时提升质量；Search Console 证明了 错误/警告/通过 三分法。对 Open Prompts，检查可从现有模板元数据和内容计算（描述存在、标签数、分类设置、变量命名质量、内容长度区间、更新新鲜度、变更说明）。本功能面向创作者且仅为建议 —— 绝不阻塞，绝不公开给用户打分。

## 2. 问题陈述

在用户遇到问题之前，Open Prompts 中没有任何东西告诉创作者他们的模板规格不足：

1. **弱列表静默发布。** 无描述、无标签、无分类的模板在没有任何提示的情况下发布。它随后不可被发现（搜索和过滤依赖这些字段），并在结果中显得被遗弃。
2. **变量质量问题在编辑后存活。** advanced-editor 在*编辑时*验证语法，但从不重新打开编辑器的创作者永远看不到旧模板有 `$$Name$$` vs `$$name$$` 近重复或早期时代的空 `$$$$`。
3. **无整体视图。** 用户仪表板列出带统计的模板（user-dashboard）但没有质量信号；有 15 个模板的创作者无法看到哪些需要关注。
4. **过时不可见。** 6 个月未更新的模板（伴随生态中变量语法漂移）在创作者自己的列表中与新鲜的无法区分。

## 3. 目标用户

- **创作者（主要）：** 发布和维护模板并希望作品可被发现、可被信任的用户。
- **新创作者：** 由清单引导形成良好的首批模板（补充 onboarding 的激活目标）。
- **浏览用户（间接）：** 从更好描述、更好标签的模板中受益于搜索结果（template-search-filtering 匹配这些字段）。
- **管理员：** v1 无管理员界面（§8）；健康度是建议性的、创作者自有的，不是审核分数。

## 4. 用户故事

### 4.1 查看健康度

- **US-H1：** 作为创作者，我在仪表板上每个模板旁看到健康指示器（分数 + 严重颜色），知道哪些需要关注。
- **US-H2：** 作为创作者，我可以打开任何模板的健康清单，显示每项检查的 通过/警告/错误 状态和通俗解释，准确理解要修复什么。
- **US-H3：** 作为创作者，每个未通过的检查直接链接到修复位置（编辑模式、标签编辑器、分类选择器），修复只需一键。
- **US-H4：** 作为创作者，在发布私有模板前或创建新模板后看到健康清单，质量问题在注意力最集中的时刻浮现。

### 4.2 理解分数

- **US-H5：** 作为创作者，我理解分数如何计算（每项检查的权重可见），分数可信而非黑盒。
- **US-H6：** 作为创作者，我的健康状态对我私有 —— 访客绝不看到我模板的健康分，提示提供建议而不羞辱。

### 4.3 系统故事

- **US-H7：** 作为系统，我只从现有模板元数据和内容计算检查，不需要新数据收集。
- **US-H8：** 作为系统，我在模板变更（创建/更新/版本/发布）时重新计算健康度，清单绝不过期。

## 5. 功能需求

### 5.1 健康检查

- **FR-1：** 系统应按模板计算以下检查（严重级别：error / warning / info；权重）：
  | 检查 | 条件 | 严重级别 | 权重 |
  |---|---|---|---|
  | `has_description` | 描述非空，≥ 20 字符 | 空为 error；< 20 为 warning | 15 |
  | `has_tags` | ≥ 1 个标签；≥ 3 个为完全通过 | 0 为 error；1–2 为 warning | 15 |
  | `has_category` | 已设置分类 | 未设置为 error | 10 |
  | `variable_quality` | 所有变量为有效名称（复用 advanced-editor FR-4 规则：无空名、无纯空白、无未闭合定界符、无大小写近重复） | 任一无效为 error；仅大小写近重复为 warning | 20 |
  | `content_length` | 内容在 50–20,000 字符之间 | 区间外为 warning | 10 |
  | `has_change_note` | 最新版本有变更说明（template-versioning 字段） | 缺失为 info | 5 |
  | `recently_updated` | 180 天内更新过 | 更早为 info | 10 |
  | `has_language` | 已设置语言字段 | 未设置为 info | 5 |
- **FR-2：** 健康分应为通过检查的权重之和（0–90，归一化为 0–100%）；存在未通过的 `error` 级检查时，无论其他通过与否，分数上限为 49%。
- **FR-3：** 检查结果应包含 `fix_action` 标识（`edit_description`、`edit_tags`、`edit_category`、`edit_content`、`add_change_note`、`edit_language`、`none`），UI 可深链到正确的编辑界面。
- **FR-4：** 检查仅为建议：任何检查都不阻塞保存、发布或列表。健康度在 v1 中绝不影响搜索排名或可见性。

### 5.2 界面

- **FR-5：** 用户仪表板的模板列表（user-dashboard 功能）应为每个模板显示紧凑健康徽章：分数 % 加严重颜色（绿 ≥ 80、黄 50–79、红 < 50），仅所有者可见。
- **FR-6：** 模板详情页应显示仅所有者可见的"模板健康"面板（可折叠，位于 owner stats 之下，若 prompt-analytics 已交付）：分数、清单行（检查名、状态图标、解释、修复链接）。
- **FR-7：** 创建模板或保存新版本后，轻量 toast 应显示未通过检查数（"有 3 项可改进 —— 查看清单"）并链接到面板；可关闭且绝不为模态。
- **FR-8：** 仪表板应为所有者的模板列表提供"需要关注"排序/过滤（健康度 < 80%）。
- **FR-9：** 健康界面仅为所有者渲染；其他查看者（包括查看其他用户模板的管理员）什么都看不到。

### 5.3 计算与新鲜度

- **FR-10：** 健康度应在读取时（仪表板列表、详情页）由服务端从当前模板状态计算；v1 不存储分数列（计算是对已获取字段的 7 项廉价检查 —— OQ-1）。
- **FR-11：** `variable_quality` 检查应在服务端复用共享的变量解析/验证工具（advanced-editor NFR-6）；两处适用相同规则。
- **FR-12：** 客户端已拥有完整模板数据时（详情页），可按相同规则在本地计算清单；服务端和客户端实现共享同一规范（§5.1）以防止漂移。

### 5.4 普通用户与管理员分离

- **FR-13：** 所有界面均为普通用户（所有者）界面。无管理员控制台页面；无 `/api/v1/admin` 端点；管理员审核（admin-user-management）在 v1 不消费健康数据。

### 5.5 API

- **FR-14：** `GET /api/v1/templates/{id}/health` → `{score, checks: [{id, state: pass|warning|error|info, explanation_key, fix_action}]}`。仅所有者（否则 403）。
- **FR-15：** 仪表板列表端点可为每个拥有的模板嵌入 `health_score` 整数（附加字段；现有客户端忽略）—— 优于 N+1 详情调用（OQ-2）。

## 6. 非功能需求

- **NFR-1（性能）：** 健康度计算在服务端每模板增加 < 5ms（纯字段检查 + 对内容的一次正则）；50 个模板的仪表板列表保持在现有延迟预算内。
- **NFR-2（隐私）：** 健康度对所有者私有（FR-9）；分数绝不出现在公开页面、匿名用户 API 或管理员界面上。
- **NFR-3（非评判语气）：** 所有文案均为建议性（"有可改进项"），绝不羞辱（"糟糕的模板"）；严重颜色遵循现有语义色板。
- **NFR-4（兼容性）：** 无 schema 变更；无现有端点行为变化（仅附加字段，FR-15）。
- **NFR-5（无障碍）：** 健康徽章通过文本+图标传达状态（不仅靠颜色）；清单可键盘导航；修复链接是标准链接（UI/UX 文档 §9）。
- **NFR-6（国际化）：** 所有检查名和解释以 EN 和 ZH 提供且键集一致；解释是客户端解析的 i18n 键（服务端返回 `explanation_key`）。
- **NFR-7（确定性）：** 相同模板状态 → 相同分数，始终；§5.1 的检查规范是服务端和客户端实现的唯一事实来源。

## 7. 验收标准

- **AC-1：** 无描述、无标签、无分类的模板在所有者仪表板上显示红色徽章（< 50%）；清单显示三个未通过检查及修复链接。
- **AC-2：** 点击 `edit_tags` 修复链接打开模板编辑模式并聚焦标签字段。
- **AC-3：** 内容含 `$$$$` 或 `$$Name$$` + `$$name$$` 的模板未通过 `variable_quality` 并有具体解释；修复内容并保存新版本后重新计算变绿。
- **AC-4：** 完全规范的模板（描述 ≥ 20 字符、3 个标签、有分类、有效变量、内容在区间、有变更说明、近期更新、有语言）得 100%。
- **AC-5：** 非所有者（登录或匿名）请求 `GET /api/v1/templates/{id}/health` 收到 403；详情页不显示健康面板。
- **AC-6：** 创建有未通过检查的模板后出现保存后 toast 并链接到清单；绝不阻塞或要求关闭才能继续。
- **AC-7：** "需要关注"过滤仅显示所有者健康度 < 80% 的模板。
- **AC-8：** 健康度计算不改变搜索排名或可见性（FR-4）：红色徽章的公开模板的列表方式与之前完全一致。
- **AC-9：** 相同模板的服务端和客户端计算清单一致（测试中抽查）。
- **AC-10：** 所有新 UI 字符串以 EN 和 ZH 存在于翻译文件中且键集一致。

## 8. 范围之外（v1）

- 模板卡片/页面上的公开健康徽章或质量分（永久私有，FR-9）。
- 健康度作为搜索排名或趋势信号（FR-4）。
- 自动修复（"全部修复" AI 重写）—— 仅链接。
- 健康度历史/时间趋势。
- 管理员审核集成（健康度不是审核输入）。
- 关于低健康度的邮件摘要。
- 任何形式的变现 —— 本产品永久超出范围。

## 9. 依赖与假设

- **D-1：** 所有被检查字段今天已存在：`description`、`tags`、`category`、`language`、内容（最新版本）、`updated_at`；变更说明随 template-versioning（其 `change_note` 字段）到来 —— 若缺失，`has_change_note` 始终报告 info-缺失，其权重从分母中排除（优雅降级）。
- **D-2：** 变量验证规则是 advanced-editor 指定的共享工具（其 NFR-6）—— 本功能在服务端消费相同规则；若该工具今天仅客户端，架构师提取/移植（OQ-3）。
- **D-3：** 用户仪表板模板列表（user-dashboard 功能）存在以承载徽章和过滤；若未交付，徽章先落在详情页面板，仪表板集成随后。
- **D-4：** 编辑模式深链（`fix_action` 目标）对应现有编辑界面（详情页编辑模式；创建弹窗字段）。
- **D-5：** 仪表板列表端点是所有者的模板列表（现有 `ListTemplates` 的 owner 作用域）—— 嵌入 `health_score` 是附加响应字段。

## 10. 给架构师的开放问题

1. **读取时计算 vs. 存储分数：** §5.1 检查很廉价，但仪表板嵌入（FR-15）逐行计算。确认读取时计算；若列表延迟回退，回退方案是模板写入时更新的 `health_score` 列。
2. **嵌入 vs. 详情调用：** FR-15 在所有者列表响应中嵌入 `health_score`；完整清单仅在面板打开时来自 FR-14。确认此拆分。
3. **共享验证工具：** advanced-editor 的验证指定为客户端（其 FR-4/NFR-6）。规范实现在哪里，使编辑器和本功能的服务端检查都使用它（Go 移植 vs. 通过规范测试共享的 JS）？
4. **权重调优：** §5.1 权重是产品提案；实现前确认或调整（规范表是数据驱动的，调优是一行变更）。
