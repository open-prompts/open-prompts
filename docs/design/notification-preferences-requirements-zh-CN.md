# 通知偏好（Notification Preferences）— 需求分析

- **功能 ID：** notification-preferences
- **版本：** 1.0
- **状态：** 已提案（待架构评审）
- **作者：** ui-ux-agent
- **日期：** 2026-10-12

## 1. 竞品调研总结

| 平台 | 偏好方式 | 关键启示 |
|---|---|---|
| **GitHub** | Watch/订阅 UI 中的按类别通知设置；细粒度的按仓库覆盖 | 按仓库的细粒度控制受喜爱但沉重；全局类别是 80% 的场景 |
| **Twitter/X** | 通知标签页 → 设置齿轮 → 按类型开关（点赞、转发、关注、提及）+ 质量过滤 | "通知界面内的设置齿轮"模式是标准入口 |
| **YouTube** | 按频道的铃铛级别（全部/个性化/无）+ 全局默认 | 按来源的细粒度（按创作者）是全局开关之后最常用的控制 |
| **Reddit** | 按类型开关 + 按社区覆盖；"聊天请求"单独 | 全局开关优先，按来源覆盖其次 —— 绝不相反 |
| **FlowGPT / Snack Prompt** | 无通知偏好（无通知系统） | 提示词平台没有可复制的；社交平台模式适用 |
| **Notion** | 单一"通知"设置页，按类型的邮件/应用内矩阵 | 矩阵（类型 × 渠道）只在多渠道时需要；我们只有一个 |

**综合分析：** 通知功能（开发中）提供顶栏铃铛、下拉和历史页面，覆盖点赞/收藏/fork 事件，并明确将偏好推迟到"数量证明合理的 v2"。社交层现在正在到来（评论增加 `comment` 事件；follow-creators 增加 `follow` 事件），这正是推迟所预期的数量触发点。制胜的 v1 模式是 Twitter/Reddit 混合：既有通知界面内的**通知偏好**区（通知页面的齿轮图标 → 设置面板），五种事件类型（点赞、收藏、fork、评论、关注）的**按类型开关**，**全部默认开启**，更改立即生效（无保存按钮 —— 每个开关自动保存），以及用于缓解过载的**主"暂停全部"开关**。v1 无按来源（按创作者）细粒度（YouTube 式按频道铃铛是 v2）。无邮件/推送渠道（仅应用内 —— 除验证码外产品没有邮件通知基础设施）。抑制在事件发射时：禁用的类型绝不创建行，因此历史页面保持干净，未读徽章绝不计入被抑制的事件。

## 2. 问题陈述

1. **用户无法控制通知数量。** 随着五种事件类型到来（点赞、收藏、fork、评论、关注），受欢迎创作者的通知流变成噪音；今天唯一的办法是忽略铃铛。
2. **偏好被明确推迟。** 通知设计将"按类型退出"列为 v2；社交层（评论、关注）正是现在构建它的数量触发点。
3. **没有过载缓解。** 没有"暂时全部静音"的控制，供想要安静期而不放弃产品的用户使用。
4. **抑制语义未定义。** 没有偏好契约，每个新事件类型（评论、关注和未来的）都会即兴决定用户能否以及如何退出 —— 构造上就不一致。

## 3. 目标用户

- **活跃创作者（主要）：** 模板吸引点赞/收藏/fork/评论、资料吸引关注的用户 —— 通知量最高的群体。
- **普通用户（次要）：** 任何想要更少打扰或更安静铃铛的人。
- **所有用户（面向未来）：** 每个新事件类型从第一天起就带偏好开关，而不是事后补救。

## 4. 用户故事

- **US-P1：** 作为创作者，我可以从通知页面打开通知偏好，以便控制位于噪音所在之处。
- **US-P2：** 作为创作者，我可以关闭特定事件类型（如点赞），以便高量低信号的事件不再到达我。
- **US-P3：** 作为用户，我可以用一个开关暂停所有通知，以便在不取消关注生活或删除历史的情况下获得缓解。
- **US-P4：** 作为用户，我的偏好更改立即生效而无需保存步骤，因此应用与否没有歧义。
- **US-P5：** 作为用户，被抑制的事件绝不出现在我的历史或徽章计数中，因此我的通知界面只反映我选择加入的内容。
- **US-P6：** 作为用户，我在每个开关下看到简短的白话描述，因此我确切知道每种类型覆盖什么。
- **US-P7：** 作为回访用户，我的偏好在会话和设备间持久（服务端），因此它们跟随我的账户。
- **US-P8：** 作为用户，我可以随时重新启用任何类型，因此退出绝不是陷阱。

## 5. 功能需求

### 5.1 数据模型

- **FR-1：** 新表 `notification_preferences`：`user_id`（FK → users，`ON DELETE CASCADE`，PK）、`like_enabled BOOLEAN NOT NULL DEFAULT true`、`favorite_enabled BOOLEAN NOT NULL DEFAULT true`、`fork_enabled BOOLEAN NOT NULL DEFAULT true`、`comment_enabled BOOLEAN NOT NULL DEFAULT true`、`follow_enabled BOOLEAN NOT NULL DEFAULT true`、`paused_all BOOLEAN NOT NULL DEFAULT false`、`updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()`。每用户一行，在首次偏好更改时惰性创建（缺失 = 全部默认）。
- **FR-2：** 无需迁移回填：缺失的行意味着全部启用/未暂停（默认值）。每次为接收者发射事件时读取该表。

### 5.2 偏好界面

- **FR-3：** 通知历史页面顶栏的齿轮图标（以及铃铛下拉的页脚链接）可进入**通知偏好**面板。面板列出五种事件类型，每种带：类型名称、白话描述和开关（默认开启）。
- **FR-4：** **暂停所有通知**主开关位于类型列表上方。开启时不创建任何类型的通知（事件仍在发射时抑制）；暂停期间铃铛不显示新项目。既有历史不受影响且保持可浏览。
- **FR-5：** 开关在更改时自动保存（每个开关 PATCH；无保存按钮）。微妙的"已保存"指示确认每次更改；失败则视觉上回滚开关并显示错误 toast。
- **FR-6：** 面板诚实显示当前状态：暂停时类型开关显示为禁用（灰色）并带说明"暂停全部已开启" —— 重新启用需要先关闭暂停。

### 5.3 抑制语义

- **FR-7：** 抑制发生在**事件发射时**：插入通知行之前，发射器检查接收者的偏好；类型被禁用或暂停全部 ⇒ 不创建行。被抑制的事件绝不出现在历史中，绝不计入未读徽章，且以后无法"找回"。
- **FR-8：** 偏好绝不影响*操作者*的体验：关闭点赞的用户仍为他人生成点赞通知（偏好管辖接收，不管辖操作）。
- **FR-9：** 自操作抑制（既有通知行为）不变；偏好叠加其上（自操作无论偏好如何都被抑制）。
- **FR-10：** 管理/系统通知（如果未来出现任何类型）在 v1 不在抑制范围内 —— 仅五种用户事件类型。

### 5.4 API

- **FR-11：** `GET /api/v1/users/me/notification-preferences`（需认证）返回有效偏好（无行时物化默认值）：`{like_enabled, favorite_enabled, fork_enabled, comment_enabled, follow_enabled, paused_all}`。
- **FR-12：** `PATCH /api/v1/users/me/notification-preferences`（需认证）接受六个布尔字段的任意子集；未知字段被忽略；校验以标准错误形态拒绝非布尔值。返回完整有效偏好对象。
- **FR-13：** 从不触碰偏好的用户，其铃铛下拉和历史页面保持不变（默认零行为差异）。

### 5.5 管理界面

- **FR-14：** 无。偏好是个人设置；v1 无管理员可见性或覆盖。

## 6. 非功能需求

- **NFR-1（性能）：** 偏好读取为事件发射增加 < 5 毫秒（单行 PK 查找，可缓存）；PATCH p95 < 200 毫秒。
- **NFR-2（默认零）：** 从不打开面板的用户体验零变化：不创建行、UI 无差异、不抑制事件。
- **NFR-3（一致性）：** 有效偏好读取（FR-11）和发射时检查（FR-7）使用相同的解析逻辑（缺失行的默认值）—— 一条代码路径。
- **NFR-4（国际化）：** 所有偏好 UI 字符串翻译（EN/ZH）；类型名称复用通知功能既有的事件类型标签以保持一致。
- **NFR-5（无障碍）：** 开关是真实的 switch 角色（`role="switch"`、`aria-checked`），可键盘操作，分组在带图例的 fieldset 中；面板按既有模式是无障碍弹窗或内联区。
- **NFR-6（兼容性）：** 仅增量 —— 一张表、两个端点、一个面板；通知功能的既有界面（铃铛、下拉、历史）渲染不变。

## 7. 验收标准

- **AC-1：** 通知页面的齿轮图标打开偏好面板，含五个类型开关（全部开启）和暂停全部（关闭）。
- **AC-2：** 关闭"点赞"无需保存按钮即持久；随后用户模板上的点赞不创建通知行、徽章计数或历史条目。
- **AC-3：** 开启暂停全部停止所有五种事件类型；铃铛不显示新内容；既有历史保持可浏览。
- **AC-4：** 暂停时类型开关禁用并带"暂停全部已开启"说明；关闭暂停后以其先前状态重新启用。
- **AC-5：** 带字段子集的 PATCH 只更新这些字段；GET 返回有效偏好（无行时为默认值）。
- **AC-6：** 失败的 PATCH 视觉上回滚开关并显示错误 toast。
- **AC-7：** 偏好在会话和设备间持久（服务端存储）。
- **AC-8：** 关闭点赞的用户仍为其他用户生成点赞通知（仅接收语义）。
- **AC-9：** 从不打开面板的用户看到零行为差异（无行、无抑制、UI 相同）。
- **AC-10：** 所有偏好 UI 字符串以 EN 和 ZH 渲染；类型标签与通知功能的标签一致。

## 8. 范围之外

- 邮件或 Web 推送渠道（仅应用内；除验证码外没有邮件通知基础设施）。
- 按来源细粒度（按创作者或按模板的铃铛 —— YouTube 式按频道级别）。
- 摘要/频率选项（每日/每周汇总）。
- 单个项目或话题的通知静音。
- 用户偏好的管理员可见性/覆盖。
- 管理/系统通知类型的偏好（v1 不存在）。
- 任何形式的变现（付费、定价、购买、收益）—— 本产品永久排除。

## 9. 依赖与假设

- **D-1：** 通知功能的事件发射层（接收者、操作者、类型）是插入偏好检查（FR-7）的单一咽喉点；其自操作抑制先运行。
- **D-2：** 五种事件类型（点赞、收藏、fork、评论、关注）是完整的 v1 集合：点赞/收藏/fork 来自通知功能；评论来自评论功能的 FR；关注来自 follow-creators FR-16。如果评论或关注未上线，其开关渲染但不抑制任何内容（尚无事件）—— 面板向前兼容。
- **D-3：** 通知历史页面存在（或将存在），页面顶栏有齿轮图标的位置；铃铛下拉存在且有页脚链接槽。
- **D-4：** 既有的个人资料/设置区模式（block-users 的"已屏蔽账号"使用）在面板改放个人资料设置时提供视觉习惯 —— 设计偏好通知界面位置（US-P1），但两者都可行。
- **D-5：** `users` 表的主键（TEXT id）支持带 CASCADE 的外键；惰性行模式避免回填迁移。

## 10. 给架构师的开放问题

1. **按类型列 vs JSONB：** 六个布尔列（我的推荐 —— 固定类型集、简单检查）vs JSONB `disabled_types` 数组（对新类型灵活但约束较弱）？如果你预期类型快速增加，JSONB 可能胜出。
2. **发射时检查形态：** 每个发射事件对 `notification_preferences` 的直接 PK 查找（推荐，可用短 TTL 进程内缓存）vs 连接到发射查询中？
3. **面板位置：** 通知历史页面的齿轮图标 + 铃铛下拉页脚链接（我的推荐 —— 控制位于噪音所在之处）vs 个人资料设置标签页？两者都设计了；请确认主要的。
4. **暂停全部语义：** 发射时抑制（推荐 —— 不创建行，徽章保持干净）vs 标记已读/静默投递（创建行但隐藏）？发射抑制意味着暂停的用户永久错过事件；确认这可接受。
5. **未来类型的开关细粒度：** 当新事件类型上线（如 team-collaboration 的团队邀请）时，其开关是否应默认开启（需要列/JSONB 条目 + UI 行）—— 确认"每个新类型带开关上线"的契约。
6. **速率限制：** PATCH 偏好每账号每分钟最多 30 次（防篡改）—— 确认或调整。
