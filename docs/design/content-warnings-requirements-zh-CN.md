# 内容警告 — 需求分析

- **功能 ID：** content-warnings
- **版本：** 1.0
- **状态：** Proposed（待架构评审）
- **作者：** ui-ux-agent
- **日期：** 2026-10-13
- **配套文档：** `content-warnings-ui-ux-design-zh-CN.md`

## 1. 竞品调研

> 说明：本次会话无法进行实时网络调研；下表基于对各平台行为的既有产品知识整理。

| 产品 | 能力 | 优势 | 不足 |
|---|---|---|---|
| YouTube | 年龄限制 + 敏感内容遮罩；创作者自我申报问卷；观众播放前看到插页 | 清晰一致的门控；不删内容也能保护观众 | 标准不透明；申诉量大 |
| X（Twitter） | 创作者将媒体标记为敏感 → 模糊显示并带标签，点击揭示；用户可设置"始终显示敏感媒体" | 一键揭示；默认由观众掌控 | 自我标记不一致；易绕过 |
| Reddit | 帖子 NSFW 标签；缩略图模糊；个人设置可显示 NSFW；版主可切换标签 | 简单二元；社区 + 自我标记 | 仅二元 —— 无原因粒度 |
| Twitch | 主播从固定分类法声明内容分类标签（赌博、毒品、成人游戏），以标签展示 | 固定分类法、预先声明、无门控摩擦 | 仅标签 —— 完全没有视觉门控 |
| Etsy | "成人内容"商品标记；成人商品从部分界面隐藏 | 市场平台对政策中间地带的先例 | 单一粗糙标记 |
| FlowGPT | 浏览中有 NSFW 过滤开关；NSFW 提示词存在于过滤之后 | 证明提示词平台确有此需求 | 粗糙；依赖创作者自觉 |
| PromptBase | 政策上一律禁止 NSFW | 零暴露风险 | 合法的成人用途（小说、安全）无处安放 |

**结论：** 获胜模式是 **Twitch 的固定分类法 + X 的模糊/揭示 + Reddit 的观众偏好**：少量固定的警告原因、发布时创作者自我申报、带一键揭示的模糊预览、观众"始终显示"偏好、以及其上的审核员执法。一律禁止（PromptBase）放弃了合法创作者；仅标签（Twitch）对不起观众；分级门控同时服务两者。

## 2. 问题陈述

Open Prompts 当前的审核是二元的：模板要么完全公开，要么下架。对敏感但合法的内容没有中间层。具体而言：

1. **创作者面临全有或全无。** 含成人主题的小说写作提示词、描述攻击技术的安全测试提示词、讨论自伤风险因素的医学提示词，要么零信号地发布，要么被彻底移除。
2. **观众被惊吓。** 浏览广场可能看到观众不想看的内容，无警告也无法回避。
3. **审核员工具太钝。** 唯一的执法手段是下架/锁定/删除 —— 对仅需打标的内容过于严厉，迫使审核员要么不作为、要么过度移除。
4. **政策无处表达。** 平台没有机制说"此内容允许，但需门控" —— 这正是 pre-publication-review 明确移交给本功能的缺口。

内容警告层为平台提供分级响应：内容保持可发现、可排序，但被视觉门控并可过滤，由创作者自我申报、审核员执法。

## 3. 目标用户

- **敏感但合法模板的创作者**（小说、安全研究、医疗/临床话题）：需要负责任地发布而不被封禁。
- **普通观众**：绝不能被意外暴露；需要模糊 + 一键揭示。
- **门控内容的常客**：需要"始终显示"偏好，门控不给工作流增加摩擦。
- **审核员**：需要执法正确打标（增删警告）并留审计轨迹，作为下架之外的轻量手段。

## 4. 用户故事

- **US-1:** 作为创作者，我可以在创建或编辑模板时从固定列表中选择一个或多个内容警告，从而负责任地让内容触达合适的受众。
- **US-2:** 作为创作者，我在模板卡片与详情页看到已应用的警告，从而知道打标已生效。
- **US-3:** 作为观众，带警告的模板在浏览与搜索结果中模糊显示并带警告标签，从而我绝不会被意外暴露。
- **US-4:** 作为观众，我可以一键揭示带警告模板的内容，门控是减速带而非墙。
- **US-5:** 作为观众，我可以在设置中开启"始终显示警告内容"，工作流零额外点击。
- **US-6:** 作为观众，我可以将警告模板从浏览/搜索结果中完全隐藏，信息流只含无警告内容。
- **US-7:** 作为匿名访客，警告模板对我同样模糊且门控，保护不需要账号。
- **US-8:** 作为审核员，我可以对任意模板增删警告并必须填写原因，打标可执法、可审计。
- **US-9:** 作为审核员，我可以按警告状态筛选管理端模板列表，从而审计全目录的打标情况。
- **US-10:** 作为创作者，审核员施加的警告在我的编辑器中显示为锁定且我无法移除，执法不会被悄悄撤销。

## 5. 功能需求

- **FR-1:** 系统应支持固定的四类内容警告分类：`mature`（成人/性主题）、`violence`（血腥暴力）、`profanity`（强烈语言）、`sensitive`（敏感/令人不安话题）。分类法应由配置驱动，无需发版即可新增类型。
- **FR-2:** 创作者应能在创建与编辑表单中设置/清除内容警告（多选复选框组）；选择存储在模板上，并在所有模板 API 响应中以 `content_warnings`（字符串数组）返回。
- **FR-3:** 在浏览、搜索及任何卡片列表中，带警告的模板应渲染为内容预览模糊并带指明原因的警告角标；标题保持可读。
- **FR-4:** 带警告模板的详情页应在内容前显示插页：警告原因与"显示内容"按钮。揭示应在浏览器会话内按模板持久。
- **FR-5:** 用户设置 `show_warned_content`（默认关闭）开启后，应同时跳过该用户的模糊与插页。
- **FR-6:** 列表与搜索接口应接受 `exclude_warned` 布尔值；UI 应将其暴露为"隐藏警告内容"筛选角标，默认关闭，按用户持久（匿名：仅 URL 参数）。
- **FR-7:** 审核员应能在管理端模板详情页对任意模板增删警告；增删必须填写原因并写入审计日志条目（`template.warning_add` / `template.warning_remove`），含操作者、目标、原因与变更后的警告集。
- **FR-8:** 审核员施加的警告应对创作者不可变：创作者编辑器将其显示为锁定，API 拒绝创作者侧的移除尝试（403）。
- **FR-9:** 管理端模板列表应支持按警告状态筛选：无警告 / 任意警告 / 特定警告类型。
- **FR-10:** 审核员在模板上增删警告时，创作者应收到含原因的应用内通知。
- **FR-11:** 警告不应影响搜索排序、趋势计算或 pre-publication-review 门控 —— 可见性门控与质量/风险轴保持独立。
- **FR-12:** 带警告模板的嵌入（template-embedding-widget 界面）应在展示内容前呈现同样的插页。
- **FR-13:** v1 中系统不应允许对模板以外的任何对象施加警告（集合、评论与主页不在范围内）。

## 6. 非功能需求

- **NFR-1（性能）：** 模糊/揭示纯客户端实现；列表接口响应中含 `content_warnings` 不增加可测延迟（p95 不变）。
- **NFR-2（可配置）：** 警告分类法存于平台设置（与 pre-publication-review 的 N/M 同机制），无需发版即可调整。
- **NFR-3（无障碍）：** 模糊绝不是唯一信号 —— 每个门控界面同时携带指明警告的文字标签；两套主题下满足 WCAG 2.1 AA 对比度。
- **NFR-4（国际化）：** 所有警告名称、插页文案、设置与管理端文案在英文与中文中存在且键集一致。
- **NFR-5（可审计）：** 每次审核员警告变更可归因且不可变（沿用 `admin_audit_logs` 语义）。
- **NFR-6（规模）：** 管理端列表按警告状态筛选与公开列表的 `exclude_warned` 在目录规模（10k+ 模板）下不降级。

## 7. 验收标准

- **AC-1:** 创作者创建时标记 `mature` → 卡片显示模糊预览与"成人内容"角标；详情页显示插页；API 返回 `content_warnings: ["mature"]`。
- **AC-2:** 观众点击"显示内容" → 内容揭示；同会话刷新保持揭示；新会话重新显示插页。
- **AC-3:** 开启 `show_warned_content` 的观众在任何地方都看不到模糊与插页。
- **AC-4:** 开启"隐藏警告内容"筛选后，警告模板从浏览与搜索结果中消失；登录用户的筛选状态在刷新后保留。
- **AC-5:** 审核员以某原因添加 `violence` → 审计日志含 `template.warning_add`（操作者/原因）；创作者收到含原因的通知；创作者编辑器中 `violence` 显示为锁定。
- **AC-6:** 创作者通过 API 移除审核员施加的警告返回 403；移除自己施加的警告成功。
- **AC-7:** 管理端模板列表按"任意警告"筛选只显示带警告模板；按 `mature` 筛选只显示带 `mature` 的模板。
- **AC-8:** 匿名访客与登录观众看到相同的模糊与插页（仅少一个偏好设置）。
- **AC-9:** 带警告模板在趋势/最新/最多点赞排序中的位置与无警告时完全一致（无排序影响）。
- **AC-10:** 带警告模板的嵌入显示插页；在嵌入内揭示不会揭示别处的模板页。

## 8. 不在范围内

- 年龄验证或年龄门控账号（观众通过偏好自选）。
- 对集合、评论、用户主页或提示词施加警告（仅模板）。
- 按警告类型的观众偏好（v1 仅单一全局"始终显示"开关）。
- 自动/AI 辅助的警告建议。
- 面向 SDK 消费者的警告门控 API 访问（API 返回数组；客户端自行决定）。
- 邮件通知（仅应用内）。
- 任何形式的变现 —— 本产品永久不做。

## 9. 依赖与假设

- **D-1:** admin-template-moderation 提供管理控制台外壳、`/admin/templates` 列表 + 详情页、原因弹窗模式与 `admin_audit_logs` —— 本功能增加一个面板与两个动作码。
- **D-2:** 通知系统投递创作者通知；新增 `template.warning_changed` 事件类型（按 mention-notifications 模式数据驱动注册）。
- **D-3:** template-embedding-widget 界面需更新以遵循插页（其设计假设嵌入内容直接渲染；本功能对其门控）。
- **D-4:** 平台设置存储（pre-publication-review NFR-5 同样需要）保存分类法；若缺失由架构师补充。
- **D-5:** templates 表新增 `content_warnings` 列（TEXT[] 或 JSONB —— 架构师选择）；迁移回填空数组。
- **D-6:** pre-publication-review 的审核队列在提交上显示警告角标，让审核员在上下文中看到自我申报的警告（附加展示，按 FR-11 无门控交互）。

## 10. 给架构师的开放问题

- **OQ-1:** `content_warnings` 用 Postgres 数组列（简单，可 GIN 索引）还是 `template_warnings` 关联表（更多元数据：谁施加、何时）？FR-8 的审核员锁定无论如何都需要来源标记 —— 并行 `locked_warnings` 数组列，还是关联表上的来源字段？
- **OQ-2:** 匿名访客的 `exclude_warned` 应默认开启（政策：最大化保护）还是关闭（政策：最大化可发现性）？设计假设关闭且模糊可见。
- **OQ-3:** 会话级揭示（设计选择）还是按用户的每模板持久"已揭示"列表 —— 存储边界选哪个？
- **OQ-4:** 审核员对 `in_review` 提交的警告变更应作为信号（非阻塞）在 pre-publication-review 队列中可见，还是完全分离？
- **OQ-5:** 通知事件携带完整的新警告集还是仅增量？创作者通知深链到模板还是警告说明帮助页？
